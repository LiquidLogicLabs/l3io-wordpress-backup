# Close-out owner decisions (Shawn, 2026-11-07)

Each is implemented after all are collected, then the item is resolved with the commit.

1. **BL-E002-098 (root restore extraction race): (c) now, (a) after release.** A restore running as root is refused (usage error, exit 2) unless the operator passes an explicit flag (e.g. `--allow-root`); with the flag it proceeds and logs a WARNING naming the race. File a post-release item: extract to a private staging dir and move entries in with `openat`/`renameat` (new ADR). Interacts with O4 (a): WP-CLI's root warning still applies once the flag is given.
2. **BL-E002-063 (credentials sent to the site's DB_HOST): (a).** A backup refuses a non-local `DB_HOST` (anything but localhost/127.0.0.1/::1/a socket) before any connection unless the operator confirms it with an explicit flag naming the host (mirroring restore's `--archive-database`). Provider-agnostic: no credential source (AWS or any other) changes this rule.
3. **BL-E002-064 (Archive written inside the Site Root): (a).** A backup whose target resolves inside the Site Root is refused (exit 2) before any effect unless the operator passes an explicit allow flag. This is a deliberate behaviour change from v0.2.21's default (running from the docroot); it is a named release-note entry (AD-22 change), and the refusal text names the flag and suggests a target outside the Site Root.
4. **BL-E002-065 + BL-E003-086 (plaintext residue after a hard kill): (a) + (b).** Each Run sweeps the current OS user's stale `l3io-wp-backup-*` workspaces under `$TMPDIR` and stray `.partial` files of its own target older than 24 h (never a live Run's: age cutoff plus the Site Lock), logging what it removed by path; SIGHUP and SIGQUIT are handled like SIGTERM (cleanup, then exit).
5. **BL-E006-010 (database library spans record raw exception text): (a).** Ask the database agent to record only the error type on its spans (no message, no stack trace), release it, then raise backup's floor and add a test that a planted secret in a database error never reaches an exported span.
6. **BL-E004-055 (database's `age` CLI backend inherits the full environment): (a).** Bundled with #5 into one database release: `age` is started with a minimal explicit environment and an absolute path; then raise backup's floor and add a test that the child's environment carries no `L3IO_WP_BACKUP_*` value.

This rejects the proposed stage-then-swap (option a), so no swap API is needed from l3io-wordpress-database. For these targets it relaxes ADR-0022's "live site intact on failure" guarantee: recovery is from the snapshot. ADR-0027 is to be revised to (b) and the remaining questions re-asked against it.
50. **ADR-0027 Q2, a failed load into the live database: (a) roll back automatically.** On any failure after the load starts, the Safety Snapshot is reloaded into the live database before exit. If the rollback itself fails, the Run is recorded as interrupted and the error names both failures, the snapshot and the recovery command. The owner confirmed: (a), with (b) as the fallback.
51. **ADR-0027 Q3, confirming the live database name: (b) no flag.** The resolved name and host are logged and shown in the Dry Run; the Safety Snapshot plus automatic rollback (decision 50) is the protection. Owner guidance (2026-11-08): the tool must stay easy to run unattended, as a Docker sidecar or a simply installed Python app. Every required confirmation or opt-in flag is a cost to justify.
52. **Owner principle (2026-11-08): a backup captures the site's current state, and a restore brings back exactly that state.** After a restore, the database has no tables the Archive did not have.
53. **ADR-0027 Q4, extra tables:** every database restore, in every Mode, removes tables that are not in the Archive, so the database matches the Archive. Covered by the Safety Snapshot and automatic rollback. Scope: (a) only tables carrying the site's table prefix; tables without it (another application, or another WordPress with another prefix) are never touched.
54. **Friction 1, `--confirm-db-host` on backup (decision 2 reversed): (a) drop the confirmation.** The host is logged and shown in the Dry Run. Only hosts that cannot be right (e.g. unresolved expression text) are refused. WordPress itself sends the same credentials to the same host on every request.
55. **Friction 3, administrator credentials for restore: (a) direct load for every site with the WordPress account.**
    - **Sequence:** take the Safety Snapshot, drop the site's prefixed tables, load the Dump, roll back automatically on failure.
    - **Administrator:** needed only when the database does not exist yet or the WordPress account lacks the rights; then the Run refuses early and names what is missing.
    - **Removed:** the staging database (`<name>_l3s_<id>`) and the `wp-config.php` cutover for `DB_NAME`.
    - **Superseded:** ADR-0027's swap proposal and ADR-0022's staging design, both to be amended. The site is down for the length of the load.
56. **Friction 2, verified TLS for non-local databases: (a) connect the way WordPress does.** There is no TLS requirement by default for backup or restore, for the WordPress account or an administrator. Stricter TLS is opt-in (`--db-tls {required,verify-ca,verify-identity}` and `--db-tls-ca FILE`), replacing the `--admin-tls*` policy. The BL-E002-114 TLS policy is amended accordingly.
57. **Friction 4, `--force` for a non-empty target: (b) only when the target does not look like a WordPress site.**
    - **Files:** a non-empty Site Root with none of `wp-config.php`, `wp-includes/` or `wp-content/` needs `--force`.
    - **Database:** a database with tables but none carrying the site's prefix needs `--force`.
    - **No flag:** an empty target, or a recognisable WordPress site, needs no flag. The Safety Snapshot covers the overwrite.
58. **Friction 5, a root restore (decision 1 reversed): (b) run as the site's owner.**
    - **The switch:** started as root, the tool reads the credentials and anything only root can read first, then drops to the uid and gid that own the Site Root for the rest of the Run.
    - **What it removes:** `--allow-root` and the root extraction race. Restored files get the site owner's ownership.
    - **Refused:** a Site Root owned by root, which has no owner to drop to, unless decided otherwise. BL-E002-122's staged extraction remains a post-v1 hardening.
59. **Friction 6, a passphrase with an unencrypted Archive (E004 D1 / ADR-0016 amendment reversed): (a) warn and proceed.** A WARNING `archive_not_encrypted` is logged and the restore proceeds. `--require-encrypted` remains the opt-in hard stop. `--allow-unencrypted` is removed, or kept as a no-op alias with a deprecation notice; the agent decides by what is least surprising pre-1.0, and records it in the CHANGELOG.
60. **Friction 7, the backup target in the Site Root (decision 3 reversed): (a), plus configuration by environment and file.**
    - **Default target:** never inside the Site Root. It is the current directory when that is outside the site, else a per-user data directory, and is logged and shown in the Dry Run.
    - **Explicit in-site target:** proceeds with a WARNING that it may be web-downloadable. `--allow-target-in-site-root` is removed.
    - **One setting, three spellings:** every setting a Run needs has a CLI flag, an `L3IO_WP_BACKUP_*` environment variable and a config-file key. Examples: Site Root (`--wp-dir` / `L3IO_WP_BACKUP_WP_DIR`), Archive directory (`--archive-dir` / `L3IO_WP_BACKUP_ARCHIVE_DIR`), mode, require-encrypted, DB TLS, passphrase. Every existing environment variable gets a CLI argument if it lacks one.
    - **Config file:** settings can all be loaded from a config file, with precedence CLI > environment > config file > defaults. A config file holding a secret must not be group- or world-readable.
    - **Sidecar image:** sets the Site Root to `/var/www/html` and the Archive directory to `/backups`, so a scheduled backup is `wpbackup2 backup` with no flags.
    - **How it is chosen:** the format and the library are chosen in an ADR that evaluates maintained libraries (rule 1: no hand-rolled config or argument layering), and a contract test derives the flag, variable and key mapping from one source of truth.
61. **Friction 8, minimum lengths: (b).** A database password shorter than the redaction floor (4 characters) is accepted, with a WARNING (`credential_below_redaction_floor`, naming the source, never the value) that it cannot be masked in logs. This amends ADR-0018. The 12-character floor for a new encryption passphrase stays; decryption has no floor.
62. **Item A, files left over after a restore: (b) keep today's split.** A normal restore leaves files the Archive does not have; `--cleanfirst` (the `-clean` Modes) clears the Site Root first. Decision 52's exact-state rule applies to the database (decision 53); files keep the operator's choice.
63. **Item B, `--drop-database`:** obsolete under decision 55 (the direct load leaves no old database). It is removed, or kept as a no-op that warns; the agent chooses, with a CHANGELOG entry.
64. **Item C, choosing the Archive: (a) `--archive latest`** (also `L3IO_WP_BACKUP_ARCHIVE=latest` and the config-file key).
    - **Which Archive:** the newest by the Manifest's `created_at` among the Archives in the Archive directory whose Manifest is for this site, so a shared volume never picks another site's.
    - **Visibility:** the choice is logged and shown in the Dry Run.
    - **No default:** `--archive` stays required, so a restore never runs on an unnamed Archive.

66. **Item E, the 256 MiB Manifest cap: (a) keep it for v1; (c) the streaming Manifest reader after the release** (BL-E008-001 / BL-E008-035, post-v1).
67. **A backup started as root: (a) switch to the Site Root owner, as a restore does (decision 58).** The backup reads its credentials, the passphrase and anything only root can read first, then drops to the Site Root owner's uid and gid for the rest of the Run. Backup and restore then share one state directory and Site Lock, and Archives are owned by the site's user. The Archive directory must be writable by that owner, otherwise the Run is refused early, naming the directory.
68. **The library run as root: (a) refuse.** `api.restore()` and `api.backup()` refuse when the process runs as root, telling the caller to drop privileges first or use the CLI. A library never changes its host process's identity.
69. **Short passphrases for decryption: (b) allow, with a WARNING.** A passphrase under the 4-character redaction floor is accepted for decrypting (verify and restore), with a WARNING (`credential_below_redaction_floor`) that it cannot be masked in logs, consistent with decision 61. New encryption still needs at least 12 characters.
70. **ADR-0028, layered configuration through pydantic-settings over argparse (TOML files): accepted.**
71. **The AWS Secrets Manager credential provider (PRD FR-14): (c) keep it as an optional extra for v1; (b) after the release, generalise it into a provider-neutral secret-command setting, with AWS as one use of it** (post-v1 backlog item).

72. **A failed URL rewrite (SEARCH_REPLACE) after a relocation: roll back automatically.** Before exiting, the database is reloaded from the Safety Snapshot and the original `wp-config.php` is put back from its saved copy, so the site is as it was before the restore. A failed rollback is reported as in decision 50.
73. **`--new-db-name` naming an existing database with tables: refuse.** A relocation's target database must be missing (created by the Run, and dropped again on failure) or empty. A database holding tables is refused before any change, naming it, so nothing is overwritten without a Safety Snapshot. `--force` does not waive this.
