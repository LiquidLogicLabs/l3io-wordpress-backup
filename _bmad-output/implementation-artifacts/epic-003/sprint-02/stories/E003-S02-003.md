# E003-S02-003: Take a safety snapshot before destroying anything


**Implements:** FR-8


As an operator,
I want the tool to capture what is there before it overwrites it,
So that a bad restore is reversible.

**Acceptance Criteria:**

**Given** a destructive restore against an existing Site
**When** the run begins
**Then** a Safety Snapshot Archive is written before the first destructive operation
**And** it is verified after writing, and encrypted when encryption is configured — to the configured `age` recipients now, or under the AD-26 passphrase once `l3io-wp-database` 0.2.0 ships (ADR-0014)
**And** its scope is derived from the Restore Mode, covering everything that mode may destroy
**And** it is written outside the Site Root and outside any web-served directory, and its path is reported
**And** if it cannot be written and verified, the destructive restore does not proceed
**And** opting out is explicit and recorded in the run's logs

*(ADR-0024, 2026-10-29: the recipients clause of the second line is superseded. The passphrase resolved by AD-26's chain is the only v1 key; the snapshot is encrypted iff it resolves, otherwise the Run proceeds with AD-26's WARNING.)*

## Business acceptance criteria

### Outcome

Before the first destructive phase of a restore against a Site with content, the Run writes a Safety Snapshot. It is a full v1 Archive of everything the Restore Mode may destroy, verified after writing (`integrity: VERIFIED`), encrypted when encryption is configured, and stored outside the Site Root and outside any web-served directory. Its path is printed on stdout and logged. It survives the Run, whether the restore succeeds or fails. If it cannot be written and verified, the restore stops with nothing destroyed. The snapshot is taken by the backup path itself **inside the restore's Run**: one Run ID, one workspace, one Site Lock, and no deadlock. An operator who opts out does so explicitly, and the log records that. A reviewer can tell it happened by running a destructive restore, then restoring the reported snapshot path and getting back the pre-restore Site.

### Non-goals

- Pruning or retaining old snapshots — Retention Policy is v1.1 (FR-17); snapshots accumulate until the operator removes them.
- Automatic rollback from the snapshot after a failed restore. The snapshot makes the restore reversible; reversing it is an operator action (a restore of the reported path), guided by story 3.5's journal.
- Implementing encryption. The snapshot is encrypted iff `request.cipher is not None`, which is iff a passphrase resolved at the restore root; E003-S02-006 passes that cipher (Epic 4's passphrase-only `PayloadCipher`, bound by E008-S01-001) to the joined backup *(Gate AG-9, 2026-10-28; ADR-0024)*.
- A second Archive writer, verifier or encryption call specific to snapshots — the snapshot *is* a backup.
- Snapshots for `backup` or `verify` Runs; only restore takes one.

## Technical acceptance criteria

### Interface contracts

Files this story changes: `adapters/restore_runner.py` (Epic 3's: `snapshot_result`, the post-publish check below) — nothing in `cli/restore.py`, and nothing in `core/restore.py`: the pure snapshot-scope and location rules and `SnapshotResult` are declared there by E003-S01-001, and this story implements the behaviour that uses them *(Gate AG-3 re-check, 2026-10-28)*. This story provides the parts; E003-S02-006 binds them into the `take_snapshot` callable that story 3.1's executor runs for the `SNAPSHOT` phase *(Gate AG-3, 2026-10-28)*. Conventions as recorded in story 3.1.

- **The snapshot JOINS the restore's Run Context; it never opens a second one (AD-16, AG-9, AG-11).** `take_snapshot` calls E002's backup entry point, the one E002-S01-004's joining test calls — `cli/backup.py::backup(...)`, whose signature E003-S02-006's step 8 cites — passing the restore's `RunContext`. `backup()` takes `ctx: RunContext` as a required keyword and never opens a Run: it does not call `join_or_open`, it reads `ctx.adapters`, `ctx.workspace` and `ctx.clock` and touches nothing of the context's lifecycle *(E003 pre-build re-check, 2026-11-03)*. So it creates nothing, binds nothing and configures nothing: no new `run_id`, no second `structlog` configuration, no second workspace, no second `finally` over the workspace. The snapshot's records therefore carry the restore's `run_id`. Nothing in this story calls `open_run`.
- **The Site Lock is re-entrant for the holder, so there is no deadlock (E002-S02-008).** The restore's `open_run(site_root=...)` holds the `LockHandle` in `RunContext.site_lock`, keyed on the canonical Site Root. The joined backup entry point targets the **same** canonical Site Root (`SiteDescriptor.site_root`, never re-resolved from a different spelling), so it acquires nothing and releases nothing. `FcntlSiteLock`'s per-process `{canonical_path: (run_id, depth)}` registry is the second line: even a stray `acquire` for the same path by the same `run_id` increments depth instead of blocking on a second `flock` fd. The lock is released once, by the restore's `finally`, after the last phase.
- **Scope from the Restore Mode (AD-12, AD-5).** `core/restore.py::snapshot_scope(mode, target)` is declared, with its per-mode mapping, by E003-S01-001; this story's `take_snapshot` receives its result as `RestorePlan.snapshot_scope` *(Gate AG-3 re-check, 2026-10-28)*.
- **Location (AD-12).** `core/restore.py::snapshot_location(site_root, config_dir, requested)` and its `UnsafeSnapshotLocationError` rule are declared by E003-S01-001 *(Gate AG-3 re-check, 2026-10-28)*. `requested` is always passed in: the root (E003-S02-006) computes the default, `platformdirs.user_state_path("l3io-wp-backup") / "snapshots" / sha256(canonical Site Root)` — the same per-user state root as E002-S02-008's `locks/`, created mode `0700` — or takes `--snapshot-dir`, and passes it as `build_restore_plan`'s `snapshot_dir`, with `config_dir` = the located config's directory (E003-S01-001); `build_restore_plan` is the one caller of `snapshot_location` *(Gate AG-6 re-check, 2026-10-28)*; `core/` never imports `platformdirs` *(Gate AG-6, 2026-10-28; BL-E003-017)*. The file name, computed in advance by the root for the journal header (ADR-0021), is `<UTC yyyymmddThhmmssZ>-<run_id>.tar.gz`, written as a `file:` Storage Target (E002 grammar) through E002's `LocalArchiveStore` (AD-20 temp name, verify, `os.replace`, mode `0600`, existing name refused).
- **What "web-served" covers, stated so nobody assumes more.** The mechanical check refuses the Site Root and the config directory. It cannot know an arbitrary web server's document roots, so a `requested` directory that a server serves from elsewhere is not detected. The default location (per-user state directory) is never a document root by convention. This limit is written in `snapshot_location`'s docstring and in the CLI help for the location option.
- **Verified after writing (AD-12, AD-6).** E002's `LocalArchiveStore.publish()` already verifies the staged file before `os.replace`. After publish, `adapters/restore_runner.py::snapshot_result(path: PurePosixPath, *, scope: BackupScope, encrypted: bool, bytes: int, performed: bool) -> SnapshotResult` takes the joined backup's **result** — E003-S02-006 passes the fields of the returned `BackupResult` (E002-S01-004), so this module imports nothing from `cli/` (ADR-0022) *(Gate AG-5, 2026-10-28)*. When `performed` is true it runs E002's `adapters/tar.py::verify_archive` on the final path and requires `passed is True` and `integrity is Integrity.VERIFIED`; a `STRUCTURAL_ONLY` snapshot is impossible for a v1 writer and is treated as failure. When `performed` is false (the Dry Run's no-op store, E002-S02-007) it reads nothing and returns a not-performed result reported as "would verify". `SnapshotResult` is declared in `core/restore.py` by E003-S01-001; this function populates it *(Gate AG-3 re-check, 2026-10-28)*.
- **Encryption (AD-12, AD-26, ADR-0014).** The snapshot is encrypted iff `request.cipher is not None`: E003-S02-006 passes `request.cipher` to the joined `backup(..., cipher=...)`, which encrypts the snapshot's one payload through it under the resolved passphrase, the only v1 key (`l3io-wp-database` v0.2.0 is pinned) *(ADR-0024)*. **No silent plaintext snapshot:** when `request.cipher is None`, the Run proceeds and says so explicitly on stderr (`safety snapshot is NOT encrypted: <path>`) and in the WARNING `safety_snapshot_unencrypted` (emitted by E003-S02-006's `take_snapshot`) *(Gate AG-9, 2026-10-28; BL-E003-002)*.
- **Refusal if not written and verified (FR-8).** Any failure in `take_snapshot` (write, publish, verify, location unsafe, disk full) propagates as `SnapshotFailedError(RefusedError)` carrying `cause`. Story 3.1's executor stops before `CLEAN`/`EXTRACT`/`LOAD_DUMP`. A failed snapshot's temporary file is discarded by `LocalArchiveStore`, and no partial snapshot is left at the final name.
- **Opt-out is explicit (FR-8, §7.1).** `build_restore_plan` takes keyword-required `snapshot: SnapshotPolicy` (`TAKE` / `SKIP`, a closed `StrEnum` in E002-S02-011's `domain/restore.py`) and `snapshot_dir: Path`, both computed by the root, with **no default** at any function that consumes them (E003-S01-001); `RestorePlan` carries the policy. `SKIP` removes `SNAPSHOT` from `plan.phases` and from the printed Dry Run actions, and logs `safety_snapshot_skipped` at WARNING with `opted_out_by` (the flag or the API argument) *(Gate AG-6, 2026-10-28)*.
- **Snapshot path survives the Run.** It is outside `RunContext.workspace`, so the workspace `finally` never touches it. The Run Journal is **not** kept beside it: it is always in the per-Site state directory, whatever `--snapshot-dir` says, and its header records the snapshot's actual path (ADR-0021, E003-S02-005) *(Gate AG-11, 2026-10-28)*.

### Error and edge case handling

- Snapshot directory not creatable or not writable: `SnapshotFailedError` → `REFUSED`, naming the path; nothing destroyed.
- Disk fills mid-snapshot: `LocalArchiveStore` discards the temp file; `SnapshotFailedError`; nothing destroyed; no partial file at the final name.
- Post-publish `verify_archive` fails or reports `STRUCTURAL_ONLY`: `SnapshotFailedError`; the bad snapshot is left in place, named in the error, not deleted (it may still hold the only copy), and the restore does not proceed.
- `requested` inside the Site Root (including through a symlink — canonicalised before the check) or inside the config directory: `UnsafeSnapshotLocationError` → `REFUSED`.
- Database part touched but the database is absent, or the Site Root part touched but empty: that part is dropped from the scope, and the snapshot covers the rest. When both are empty, there is no `SNAPSHOT` phase, and `safety_snapshot_not_needed` is logged with the reason.
- `--mode files` against a site whose database is unreachable: the snapshot scope is `FILES`, so no database is contacted (E002-S01-002 behaviour of the `files` scope).
- `request.cipher` given (a passphrase resolved, ADR-0024): the snapshot is encrypted through it; `None`: unencrypted, with the stderr line and `safety_snapshot_unencrypted` *(Gate AG-9, 2026-10-28)*.
- A second process tries to restore or back up the same Site while the snapshot is being written: refused `LOCKED` by the held, re-entrant lock (the join did not release it).
- An entry point that wrongly calls `open_run` inside the restore: `RunContextActiveError` (a `RefusedError`, E002-S01-004) → `REFUSED` immediately. A nested Run is an error, never a hang.
- Dry Run: the joined backup runs with the Run Context's dry-run adapter set, so no snapshot file is written and the planned action `safety snapshot of <scope> to <path>` is reported. The location check still runs for real (it is a plan-time rule). `snapshot_result` is given the not-performed result and reports "would verify" without failing (ADR-0022) *(Gate AG-5 and AG-9, 2026-10-28)*.
- Restore fails after the snapshot: the snapshot remains, and its path is repeated in the failure message — `drive_restore` sets `BackupError.snapshot_path` before re-raising and `run_restore` prints it (E003-S02-006) *(Gate AG-15, 2026-10-28)*.

### Observability requirements

- `safety_snapshot_written` (INFO) with `path`, `scope`, `bytes`, `encrypted`, `integrity`, `restore_mode`. The same path is printed on stdout as a line a script can grep (`safety snapshot: <path>`).
- `safety_snapshot_unencrypted` (WARNING) with `path` when `request.cipher is None` — the one name; E003-S02-006 emits it *(BL-E003-002, 2026-10-28)*.
- `safety_snapshot_skipped` (WARNING) with `opted_out_by`; `safety_snapshot_not_needed` (INFO) with the empty parts.
- The `SNAPSHOT` phase emits one `phase_completed` (E002-S01-004 `phase()`), and the joined backup's own phase records nest under it with the **same** `run_id`. There is exactly one `run_started` and one `run_finished` for the whole restore.

### Security considerations

- The snapshot contains the entire database and Site Root. It is written mode `0600` in a `0700` directory under the per-user state root, never inside the Site Root or config directory, and is encrypted when configured. When it is not encrypted, the operator is told, never left to discover it.
- The snapshot's Manifest carries no credential and no key material (E002 Manifest rules; ADR-0014).
- The location check canonicalises `requested` with `resolve()` before comparing, so a symlink into the Site Root is refused.
- E002-S01-006's `credential_sentinel` covers the snapshot path, because it runs inside the full restore that story 3.1 instruments.

### Testability approach

- **No-deadlock proof — `tests/integration/test_snapshot_joins_run.py`** (unmarked where it can use a database double, `@pytest.mark.integration` for the database scope). It runs, in a subprocess with `subprocess.run(..., timeout=120)`, `execute_restore` inside a Run opened by `open_run` with **the real `FcntlSiteLock`** (no recording double) and a `take_snapshot` that joins E002's `backup(..., ctx=ctx)` as E003-S02-006 binds it — not `cli/restore.py` *(Gate AG-3, 2026-10-28)* — with E003-S02-005's `load_staged` as the `load_database` slot (E003-S01-001's signature) for the database part *(Gate AG-3 re-check, 2026-10-28)*: a destructive `all` restore against a non-empty fixture Site, with JSON logging. Assertions:
  - the process exits `OK` before the timeout (a deadlock fails as `TimeoutExpired`, not as a hang);
  - the JSON stream has exactly one distinct `run_id`, exactly one `run_started`, one `run_finished` and one `site_lock_acquired`;
  - every `phase_completed` from the joined backup carries that `run_id`;
  - the snapshot path in `ExecutionReport.snapshot` exists, is outside the Site Root, and passes `verify_archive` with `VERIFIED`;
  - after exit, the lock is immediately acquirable.
- **The lock is held across the snapshot — same file.** A hook pauses the Run inside `SNAPSHOT`. A second process opening a Run against the same Site Root, spelled through a symlink, gets `SiteLockedError` (`LOCKED`) naming the first Run's `run_id`. The first Run is then released and completes.
- **Nesting is an error, not a hang — `tests/unit/cli/test_snapshot_join.py`.** A variant `take_snapshot` that calls `open_run` instead of joining raises `RunContextActiveError` within the test's default time. A recording `SiteLock` shows zero `acquire` calls from the joined path for the same Site Root.
- `tests/unit/core/test_snapshot_scope.py` and `tests/unit/core/test_snapshot_location.py` are E003-S01-001's, moved there with the declarations they test *(Gate AG-3 re-check, 2026-10-28)*.
- `tests/unit/adapters/test_restore_runner.py` (story 3.1's): a `take_snapshot` that raises yields an empty destructive-command log; `SKIP` yields no `SNAPSHOT` phase, no snapshot action and the WARNING record.
- **Dry Run case (ADR-0022):** `snapshot_result` given `performed=False` calls no `verify_archive`, returns `performed=False`, and the SNAPSHOT phase completes; a `performed=True` result for a missing file fails *(Gate AG-5, 2026-10-28)*.
- `tests/integration/test_snapshot_reversible.py` (`@pytest.mark.integration`): restore over a populated Site, then restore the reported snapshot with the same mode, and assert the Site Root tree and `CHECKSUM TABLE` equal the pre-restore state.

### Existing-library check

- Writing, publishing and verifying the snapshot: E002's backup path, `LocalArchiveStore` and `verify_archive`. This story writes none of them a second time (the DRY choice AD-16 names).
- Encryption: `l3io-wordpress-database` v0.2.0 `encrypt`/`decrypt` with a passphrase behind the `PayloadCipher` E003-S02-006 passes (ADR-0014, ADR-0024). No `pyrage`, no cipher here *(Gate AG-9, 2026-10-28)*.
- Per-user state directory: `platformdirs.user_state_path`, the dependency E002-S02-008 adds, called by the root (E003-S02-006), never by `core/`.
- Hashing the Site Root for the directory name: stdlib `hashlib`. Timeouts in the no-deadlock test: stdlib `subprocess.run(timeout=)`, so no `pytest-timeout` dependency is added.
