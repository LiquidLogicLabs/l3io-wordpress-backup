# E003-S02-004: Report honestly what the database restore did


**Implements:** FR-9


As an operator,
I want to know whether the database was actually restored,
So that I am not told "done" when nothing happened.

**Acceptance Criteria:**

**Given** a restore covering the database
**When** it completes
**Then** it either restored, or exited non-zero stating why
**And** encountering an existing database is never silently treated as success
**And** it reports which of the database and user it created, from `l3io-wp-database`'s `EnsureResult` (`created_database`, `created_user`, `password_set`, `granted`)
**And** existence is read from database's `survey` with administrator credentials — a failed login by the account being provisioned is evidence about the account, never about the database (AD-29)
**And** provisioning is database's `ensure`; this package issues no `CREATE DATABASE`, `GRANT` or `DROP DATABASE` itself, so AD-28's escaping is database's (ADR-0015)

## Business acceptance criteria

### Outcome

A restore whose Restore Mode includes the database ends in exactly one of two ways:

- **Exit `OK`, with a report** naming the database the site now runs on, whether this Run created that database, created the WordPress user, set its password and granted it access (from `l3io-wp-database`'s `EnsureResult`), and how many bytes the load moved.
- **Exit non-zero, with a stated reason.**

"Done" is never printed for a database that was not loaded. An existing database is never mistaken for a restored one. Whether the database and user already existed is decided by the administrator's view of the server, never by whether the WordPress account could log in. A reviewer can tell it happened by restoring onto three servers — fresh (no database, no user), user-only, and fully populated — and reading three different, accurate reports.

### Non-goals

- The staging database, the cutover, and removing the database that loses it — story 3.5. This story reports on what 3.5's sequence did.
- The FR-7 refusal over an existing database (story 3.2). This story supplies the administrator-read `DatabaseTargetState` that 3.2's guard consumes.

- Relocated database name, host or user (`--new-db-*`) — Epic 7.
- Issuing any SQL. Escaping a grant pattern (AD-28) is database's; this package proves the outcome, not the escaping.

  | `ProvisioningError` / `TransferError` | `FAILED` |

### Error and edge case handling

- **Database mode, Archive has no Dump:** `ArchiveHasNoDumpError` → `REFUSED` (story 3.1), stating that the Archive's scope was `files`. This is never a silent skip.
- **Existing live database encountered:** it is reported in the plan (`database_exists`, `table_count`), guarded by story 3.2, and loaded around by story 3.5. It is never interpreted as "already restored".
- **`ensure` refuses** (missing administrator privilege, `USER_ABSENT`-class blockers): `REFUSED`, naming database's finding codes and messages (credential-free, per database's own redaction). Nothing has been created.
- **`ensure` fails part-way:** `ProvisioningError.completed` lists the steps that ran. The report names them (for example "created database; create user failed"), the Run exits `FAILED`, and story 3.5's journal records what to undo.
- **`ensure` succeeds, but database's own post-check finds the account still cannot use the database:** database raises `ProvisioningError`, so the Run exits `FAILED`. This is never reported as granted.
- **Load raises:** the cause is `TransferError` (mid-stream damage, client exit), `RefusedError` (`DATABASE_NOT_EMPTY`, `CROSS_FAMILY_DUMP`, `INCOMPATIBLE_DUMP_SOURCE`, `IDENTITY_REQUIRED`) or `DatabaseUnreachableError`. The Run exits non-zero naming the cause, and `restored` is never set.
- **Administrator authentication fails:** `CREDENTIALS`, naming the administrator account label (never the password). The WordPress account is not tried in its place.
- **Fresh server (no database, no user):** `survey` returns `database_exists=False`, `user_exists=False`. `ensure` creates both, and the report says so. This is the AD-29 case an integration test covers.
- **Account exists, database does not:** the report says the database was created and the user was not (AD-29's reachable case, asserted).
- **Dry Run:** `survey_target`, `check_ensure` and `check_load` run for real, so a missing privilege or an absent account refuses exactly as the real Run would. `survey_target` runs in E003-S02-006's step 6; the `check_*` queries are run by E003-S02-005's `check_staged` in the executor's `PREFLIGHT` (E003-S01-001's `check_database` slot), in both Runs, and tested by E003-S02-005's `tests/unit/adapters/test_staging.py` — this story assigns them nowhere else *(E003 pre-build re-check, 2026-11-03)*. `NoopDatabase.ensure_database` returns an all-`False` `EnsureOutcome` with `performed=False`, and the printed report says "would ensure" rather than "created"; `restored` is `False` and the Dry Run still exits `OK` (ADR-0022) *(Gate AG-5, 2026-10-28)*.

### Security considerations

- Administrator credentials are resolved by an explicit call: the spec from `cli/credentials.admin_spec(...)`, the source from `cli/credentials.admin_source(...)` (E002-S01-006; only `adapters/database.py` constructs database's credential classes), bound into the database adapter and never logged, printed or placed in an exception. E002-S01-006's `credential_sentinel` fixture is extended to seed the administrator password too, across a full database restore.
- No fallback from administrator to WordPress credentials. That fallback would be both a privilege escalation (AD-9) and the reason existence becomes unanswerable (AD-29).
- AD-28 is proven by reachability, not by statement text. After a restore through this package's path, the restored WordPress user can see its own database and **cannot** see a neighbouring `wpX<suffix>`, and connecting with `database=wpX<suffix>` raises.
- This package contains no SQL DDL or DCL. A contract test scans `src/l3io/wp/backup/` for `CREATE DATABASE`, `CREATE USER`, `GRANT `, `DROP DATABASE`, `ALTER USER` and `DROP USER` (case-insensitive, in string literals) and fails on any hit.
