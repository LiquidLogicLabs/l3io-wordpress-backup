# E003-S02-005: Survive being killed mid-restore


**Implements:** NFR-1 (AD-18) — the recoverability guarantee FR-9 reports on


As an operator,
I want an interrupted restore to leave my site recoverable,
So that a power cut does not silently produce a half-restored site that still boots.

**Acceptance Criteria:**

**Given** a restore interrupted at any phase
**When** the operator looks at the site
**Then** a durable Run Journal records the phase that was interrupted and what would undo it
**And** a later run refuses to proceed until that journal is resolved, naming the interrupted phase
**And** `wp-config.php` is written to a temporary file and `os.replace`d, so a partial config is never observable
**And** the Dump loads into a staging database through `l3io-wp-database`'s `ensure` and `load(replace=)`, with the live name switched only by that atomic write after the load is checked
**And** the database that loses the cutover is removed with database's `drop_database`, never by SQL issued here
**And** an interrupted load therefore leaves the live site on its original database, untouched

*(Per the E002 gate reconciliation 2026-10-27: the load goes through E002-S02-012's `DatabaseCommand.load_dump(location, source)`, which has no `replace` parameter — E002-S02-009's adapter calls database's `load` with no confirmation token — and `ensure`/`drop_database` through `ensure_database(location)`/`drop_database(location, confirm=...)`.)*

## Business acceptance criteria

### Outcome

A restore killed at any point — SIGKILL, power loss, OOM — leaves the Site recoverable and leaves the next Run unable to pretend otherwise. Specifically:

- **A durable Run Journal names the interrupted phase.** It records the phase that was in progress and what would undo it: the Safety Snapshot path, the staging database name, the previous `DB_NAME`.
- **The next restore against that Site refuses.** It exits `REFUSED` (3), naming the interrupted Run ID and phase, until the operator resolves the journal.
- **An interruption anywhere before the cutover leaves the live site on its original database.** *(Corrected 2026-10-27: AD-17 amended again — the cutover is the set `DB_NAME` plus, with relocation, `DB_HOST`/`DB_USER`/`DB_PASSWORD`, not `DB_NAME` alone.)* The Dump loads into a staging database (or the operator's `--new-db-name`), and `wp-config.php`'s connection keys move to it only through consecutive atomic, verified writes inside one journaled step, after the load has been checked. Before that step the original database is untouched and `wp-config.php` is byte-identical; a Run killed inside it is named by the journal, key by key, and resolution completes the set.
- **`wp-config.php` is never observable half-written.**

A reviewer can tell it happened by killing a restore at every journal boundary in turn and observing, each time, a booting site on its original database (or, past the cutover, on the fully-loaded new one), plus a refusal from the next Run naming that phase.

### Non-goals

- **Making the file phases atomic.** `CLEAN` and `EXTRACT` stay individually irreversible. This story journals them and points the operator at the Safety Snapshot (story 3.3) to undo them; it does not stage the Site Root.
- **Automatic recovery or rollback** on the next Run. The next Run refuses and explains; the operator decides.
- **Relocation constants' values and the URLs** — Epic 7. *(Corrected 2026-10-27: under AD-17 as amended 2026-10-27 this story's cutover writes `DB_HOST`, `DB_USER` and `DB_PASSWORD` as well as `DB_NAME`; Epic 7 supplies their values through `RestoreRelocation` (E003-S01-001), and `WP_SITEURL`/`WP_HOME` stay in Epic 7's `REWRITE_CONFIG`.)* Without relocation this story writes only `DB_NAME`.
- **Keeping the database name stable across restores.** The site ends up on the staging database's name; renaming a database back is SQL this package does not issue (ADR-0015). The new name is reported, and a consequence of AD-18 as written.
- **Durability against a host whose storage ignores `fsync`.**

## Technical acceptance criteria

### Interface contracts

*(Adopted 2026-10-27 from the E002 gate, changes 1, 2, 3, 7 and 8.)* Files this story adds: `adapters/journal.py` and `adapters/staging.py`, both Epic 3's per the Epic List. It also changes `core/restore.py` (pure interrupted-phase and undo derivation, and `staging_name`); the step names and `is_orderly_failure` are declared there by E003-S01-001, and this story journals the steps and produces the failures the predicate recognises *(Gate AG-3 re-check, 2026-10-28)*. Nothing in `cli/restore.py`: this story provides the parts and E003-S02-006 binds them *(Gate AG-3, 2026-10-28)*. Conventions are as recorded in story 3.1. `adapters/journal.py` implements E002-S02-012's `RunJournalQuery`/`RunJournalCommand`; `adapters/staging.py` calls the restore halves of E002-S02-012's `DatabaseQuery`/`DatabaseCommand` (implemented by E002-S02-009) through `AdapterSet.restore_database_query`/`restore_database_command`. Both no-op twins (`NoopRunJournal`, `NoopDatabase`) are Epic 2's; this story defines none.

- **The load contract (E002-S02-012, AD-18.3).** The Dump goes in through `DatabaseCommand.load_dump(location: DatabaseLocation, source: IO[bytes] | Path) -> LoadResult`, which has no `replace`, credential or decryption parameter. The target database is `location.name`; the WordPress account is the source bound into `AdapterSet.restore_database_command`. E002-S02-009's adapter calls database's `load` without a confirmation token, so a target that already holds tables is refused by database (`DATABASE_NOT_EMPTY` → `DatabaseRefusedError` → `REFUSED`) rather than loaded over, and a freshly-ensured staging database, being empty, needs none. database streams into the named database with no rename and no swap, so there is no conflict with AD-18's wp-config cutover: the switch is the cutover write below. That the port cannot express "load over a non-empty database" is asserted by E002-S02-012's `tests/contracts/test_no_load_replace.py`.
- **Staging (`adapters/staging.py`, AD-18.3).**
  - **The `LOAD_DUMP` slot:** `adapters/staging.py::load_staged(inputs: RestoreInputs, journal: RunJournalCommand, *, ports: RestorePorts) -> DatabaseRestoreReport` is the real `load_database` slot of E003-S01-001's `execute_restore`. It performs, in order, the creation, load, post-load check, cutover and loser drop below and journals their steps through the `journal` it is handed (the step-name constants are E003-S01-001's); the mode it reads for the loser is `inputs.header.restore_mode`. E003-S02-006's root binds it with `functools.partial(load_staged, ports=<the Run's RestorePorts>)`, over the dry-run adapters in a Dry Run *(Gate AG-3 re-check, 2026-10-28)*.
  - **Staging name:** `core/restore.py::staging_name(live: str, run_id: str) -> str` returns `f"{live[:51]}_l3s_{run_id.replace('-', '')[:8]}"`. It is pure and applies only the length rule, ≤ 64 characters (database's `MAX_DATABASE_NAME`). `adapters/staging.py` checks the name with `l3io.wp.database.validate_database_name` before the first call that uses it, so `core/` imports nothing from the database package (AD-1) *(Gate AG-13, 2026-10-28)*.
  - **Load location:** `load_location = <base location>.with_name(<staging or load name>)` (E002-S01-001's `DatabaseLocation`; the base location and name are chosen by the staging hook below).
  - **Creation:** `DatabaseCommand.ensure_database(load_location) -> EnsureOutcome`. With the bound administrator source it creates the staging database, and the bound WordPress account's user and its escaped grant if absent (E002-S02-009 over database's `ensure`); story 3.4 reports the `EnsureOutcome`.
  - **Load:** `DatabaseCommand.load_dump(load_location, source)`, so the Dump goes in as the bound WordPress account. `source` is the Dump member streamed from the Archive (AD-21, no `bytes`); when the Manifest marks that member encrypted, `source` is the plaintext stream from the Run's `MemberCipher.decrypt` (E004-S01-003), decrypted upstream of the port.
  - **Post-load check:** takes the load's `LoadResult` (ADR-0022). When `performed` is true it runs a query, `DatabaseQuery.survey_target(load_location, table_prefix=site.table_prefix, wordpress_user=<the loading account's user name>) -> DatabaseTargetState`, which must return `is_wordpress is True` and `schema_version is not None`; otherwise the step `"check_failed"` is journaled and `StagingCheckFailedError(BackupError)` → `FAILED`. When `performed` is false (a Dry Run's `NoopDatabase`), it surveys nothing and reports "would check `<load database>`" without failing *(Gate AG-5, 2026-10-28)*. This is structural, and its docstring says so.
- **Cutover — the only place the live connection changes (AD-18.2, AD-18.3; corrected 2026-10-27 for AD-17's second amendment, and to call `adapters/config_writer` as the round-1 gap map requires).** After the post-load check passes, the keys of E003-S01-001's `CUTOVER_KEYS` (`DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, in that order) whose value changes are written — the same under `ConfigPolicy.OVERWRITE`, because its `replace_file` has already put the target's prior `DB_*` values into the replaced file (ADR-0023) *(Gate AG-16, 2026-10-28)* — **one atomic `ConfigCommand.set_constants(config_file, {key: value})` call per key**, inside one journaled step. That is E002-S02-009's `WpConfigWriter` over `l3io.wp.config.WpConfigFile.set` (v0.1.1), which for each key:
  1. writes `wp-config.php.l3io-tmp` in the same directory;
  2. reads it back and runs `verify_write` (value-span comparison, ADR-0010);
  3. raises `ReadBackError` with the original unchanged on mismatch;
  4. only then `replace`s it onto `wp-config.php`.

  This package writes no config bytes itself (AD-18.2 delegates the write and its verification). Without relocation the set is `{DB_NAME: <load database>}` — one write. With relocation, `DB_HOST` is `relocation.cutover_host` (the operator's spelling), `DB_USER` is `relocation.cutover_user`, and `DB_PASSWORD` is resolved from the relocated WordPress source (`RestorePorts.cutover_credentials`, bound by E003-S02-006) **immediately before its write**, registered with the Run's `SecretRegistry`, and dropped after the call. Before each key's write the intent is journaled, `step_completed(LOAD_DUMP, "cutover_started:<KEY>")`, and once it lands `step_completed(LOAD_DUMP, "cutover:<KEY>")` (key names only), so a kill inside a write is never mistaken for a kill before the cutover *(Gate AG-1 re-check, 2026-10-28)*. `ConfigWriteFailedError` (carrying `written`) is re-raised as `ConfigCutoverError(BackupError)` → `FAILED`; the key that failed is byte-identical. When `written` is empty the step `"cutover_readback_failed"` is journaled and the staging database dropped (an orderly failure, below); otherwise the journal stays blocking naming written and pending keys *(Gate AG-7, 2026-10-28)*. The config path is `relocation.config_file or inputs.config_path` — the located config (`LocatedConfig.path`, carried in `RestoreInputs`, E003-S01-001), never a recomputed `<site_root>/wp-config.php` *(Gate AG-10, 2026-10-28)*.
- **An existing `wp-config.php` is never extracted over.** That is E003-S01-001's `ConfigPolicy.KEEP` exclusion (moved there as extraction behaviour; ADR-0023); this story relies on it, so under `KEEP` the cutover's `set()` calls are the only writes to the target's config *(Gate AG-3 and AG-10, 2026-10-28)*. A Mode restoring the database where no `wp-config.php` will exist at the config path when the cutover runs (target has none, nothing lays one down, and `EXTRACT` is not planned or brings none) is refused at plan time with `NoConfigForCutoverError(RefusedError)` → `REFUSED`, before `SNAPSHOT` — never discovered at the cutover after the load, because `set()` never creates a file. The config path everywhere (cutover, journal header) is `relocation.config_file or inputs.config_path`.
- **The loser (AD-18.3, story 3.4's `previous_database`).**
  - **Cutover succeeds, mode names database removal** (`database-clean`, `all-clean`): the previous live database is dropped, after cutover only, as follows — the step `"loser_drop_started"` journaled first *(BL-E003-020, 2026-10-28)*:
    1. `DatabaseCommand.revoke_grants(live_location, user=wp_user, confirm=wp_user)`, where `live_location` is `site.database_location()` (E002-S02-009 passes database's `revoke` its `user_host`). This leaves no stale database-level grant row to be inherited by a later database of the same name.
    2. `DatabaseCommand.drop_database(live_location, confirm=live)`, then the step `"loser_dropped"` is journaled (ADR-0020) *(Gate AG-1, 2026-10-28)*.

    database's `LIVE_WORDPRESS_SITE` finding is a warning, so it is logged, not a blocker.
  - **Cutover succeeds, mode does not name database removal** (`database`, `all`): the previous database is **retained** and reported (FR-6: a mode not naming database removal drops nothing).
  - **Failure before the cutover:** the loser is the staging database. It is created by this Run, so dropping it destroys nothing that existed. It is removed with `DatabaseCommand.drop_database(load_location, confirm=staging)` in the error path, and the journal records that removal as the step `"staging_dropped"`.

  No SQL is issued here (story 3.4's `test_no_sql_ddl.py`).
- **Run Journal (`adapters/journal.py`, AD-18.1).** It implements E002-S02-012's `ports/journal.py` over E002-S02-012's `domain/journal.py` types, and declares none of them: `RunJournalQuery.incomplete(site_root) -> JournalRecord | None`, where `JournalRecord` is `(header: JournalHeader, entries: tuple[JournalEntry, ...])`, and `RunJournalCommand.begin_run(header)`, `phase_started(phase, target)`, `step_completed(phase, step)`, `phase_completed(phase)`, `finish_run()`, `resolve(run_id, resolved_by)` *(Gate AG-1 and AG-8, 2026-10-28)*. This story owns the file layout and the durable write sequence. The record on disk is the `JournalRecord`: `begin_run` writes the header with no entries, and each `phase_started`, `step_completed` and `phase_completed` call appends one `JournalEntry`.

  Each write behaves as follows:
  1. It serialises the whole record with `json.dumps`.
  2. It writes `current.json.tmp` with `O_CREAT|O_TRUNC`, mode `0600`, then `os.fsync` on the file.
  3. It runs `os.replace` onto `current.json`, then `os.fsync` on the directory fd.

  The record is therefore either the previous or the new version, durable before the phase it announces begins. `finish_run` renames `current.json` to `completed/<run_id>.json` (the audit trail) when every `phase_started` entry has its `phase_completed`, and to `failed/<run_id>.json` otherwise, and fsyncs the directory. Only `current.json` blocks.

  **Lifecycle (ADR-0021)** *(Gate AG-7, 2026-10-28)*. E003-S02-006 builds the `JournalHeader` before `SNAPSHOT`; E003-S01-001's executor writes `begin_run` immediately before `SNAPSHOT` (or the first destructive phase when the snapshot is skipped) and calls `finish_run` only on success, or when `core/restore.py::is_orderly_failure(entries)` holds — the predicate and its rule are declared by E003-S01-001; this story's slot journals the steps that make a failure orderly *(Gate AG-3 re-check, 2026-10-28)*. Every other failure leaves `current.json` blocking; there is no `finally: finish_run()`.

  **Undo text is derived when the journal is read, never stored (ADR-0020)** *(Gate AG-1, 2026-10-28; BL-E003-001)*. The one derivation is `core/restore.py::undo_for(interrupted: RestorePhase | None, last_step: str | None, header: JournalHeader) -> str`, pure, a `match` over every `RestorePhase` ending in `assert_never`. `interrupted` is `interrupted_phase(entries)`; `last_step` is the `step` of the last `step_completed` entry inside that phase, or `None`. The named steps are the step-name constants E003-S01-001 declares in `core/restore.py` *(Gate AG-3 re-check, 2026-10-28)*. From the first `"cutover_started:*"` step on, the text never names `header.load_database` as something to drop, except after `"cutover_readback_failed"`, which proves no key landed (its row below) *(Gate AG-1 re-check, 2026-10-28; restated after the second re-check)*.

- **Journal location (AD-18.1 as amended; ADR-0021).** Always the per-Site state directory `platformdirs.user_state_path("l3io-wp-backup") / "snapshots" / sha256(canonical Site Root)`; it never follows `--snapshot-dir`, so a later Run without the flag finds it, and it exists when the snapshot is skipped *(Gate AG-11, 2026-10-28)*. E003-S02-006 computes the directory and constructs `adapters/journal.py`'s pair with that path; `core/` receives only paths. It is story 3.3's default snapshot directory, under the same per-user state root as E002-S02-008's `locks/`, and it is never inside the Site Root. It is created mode `0700`.
- **Refusal on an incomplete journal.** The restore composition root calls `RunJournalQuery.incomplete` after acquiring the Site Lock and before `PREFLIGHT`, as a query, so a Dry Run refuses too. A record raises `IncompleteRunError(RefusedError)` → `ExitCode.REFUSED` (E002-S01-005's docstring: "AD-18 refusals → `REFUSED`"; no new code). The error has fields `run_id` and `started_at` (from `record.header`), `interrupted_phase`, `undo` and `journal_path`. `interrupted_phase` is derived purely by `core/restore.py::interrupted_phase(entries: tuple[JournalEntry, ...]) -> RestorePhase | None` — the last `phase_started` entry without a matching `phase_completed`; when every started phase completed, the last completed phase (the Run died between phases or before `finish_run`); `None` only when no phase started — and `undo` is `undo_for(interrupted, last_step, record.header)` *(Gate AG-1, 2026-10-28)*.

It is performed by an acknowledgement that must carry the interrupted Run's ID, so a blanket flag in a cron line cannot resolve a journal nobody read.

**Added 2026-10-27 (gap pass 2; decision 2 — the staging hook Epic 7 fills; decision 1 — journaling the four-key cutover).**

- **The staging hook (`adapters/staging.py`).** The load target and its location come from E003-S01-001's `RestoreRelocation`, never from Epic 7 code and never from `wp-config.php`:
  - **Name:** `load_name = relocation.load_database or staging_name(live, run_id)`. With `--new-db-name` the Dump therefore loads **straight into the operator's database**, so `DB_NAME` ends as that name, not `<name>_l3s_<id>`. Everything else is unchanged: `ensure_database` creates it if absent, `load_dump` refuses it if it already holds tables (`DATABASE_NOT_EMPTY` → `REFUSED`, nothing loaded over), the post-load `survey_target` checks it, and only then the cutover.
  - **Location:** `relocation.load_location or site.database_location()`, then `.with_name(load_name)` (E002-S01-001's `DatabaseLocation`; nothing re-parses a host string). `ensure_database`, `load_dump` and the post-load `survey_target` address it, through `AdapterSet.restore_database_*` (E002-S02-012), which `real_adapters` binds to the relocated WordPress account when E003-S02-006 passes one as `restore_wordpress_source`. The FR-7 guard does **not** address the staging name: it checks the live database and, when `load_database` is set, that database (E003-S01-002) *(Gate AG-12, 2026-10-28)*.
  - **Failure before the cutover, operator-named target:** the database is dropped in the error path only if `EnsureOutcome.created_database` says this Run created it; an operator-named database that already existed (empty) is **left in place** and the journal stays blocking with the undo "`<name>` existed and was empty before this Run; empty or drop it". A staging name is always this Run's creation and is dropped as before.
  - **The loser across hosts:** when `load_location` is on a different host or port than the live database, the previous database is **retained and reported in every Mode** — `*-clean`'s database removal applies to the database being replaced at the same location, and the bound administrator source is not assumed valid on the old server. The report says so (`previous_database_retained`, `reason: "different server"`).
- **Journaling the cutover (AD-18.1).** This story defines the values of E002-S02-012's `JournalHeader` fields, which E003-S02-006 computes before `SNAPSHOT` (ADR-0021) *(Gate AG-7, 2026-10-28)*: `load_database`, `cutover_keys` (the subset of `CUTOVER_KEYS` this Run will write, in order), `cutover_targets` (non-secret target values for `DB_NAME`/`DB_HOST`/`DB_USER` only), `prior_constants` (the same three keys read through `ConfigQuery.read_constants` before any config write), `phase_undo` and `saved_config` (ADR-0020, ADR-0023); `JournalHeader.__post_init__` refuses `DB_PASSWORD` in `cutover_targets` and `prior_constants`, so it cannot be journaled. `RunJournalCommand.step_completed(phase, step)` is written with the same temp-fsync-replace-fsync sequence; it records the config lay-down (`"config"`, E003-S01-001) and each cutover key (`"cutover:<KEY>"`). `IncompleteRunError` gains `written_keys`/`pending_keys` when the interrupted step is the cutover, derived in `core/restore.py` from `header.cutover_keys` and the `step_completed` entries. The cutover's undo text is the undo table's.

### Error and edge case handling

- **Killed after `begin_run`, before any phase:** the next Run refuses with `interrupted_phase=None`, and the Site is unchanged.
- **Killed during `CLEAN` or `EXTRACT`:** the files are partially changed and the database is untouched. The next Run refuses naming the phase, with the snapshot path as the undo.
- **Killed during `ensure` or `load` into staging:** the live database and `wp-config.php` are byte-identical, so the site boots on its original data. The next Run refuses with the undo "drop staging database `<name>`". A leftover staging database is never adopted by a later Run, because the next Run's staging name differs (its own `run_id`) and `load_dump` cannot load over a non-empty target.
- **Killed between the post-load check and the first cutover write:** the original `wp-config.php` is intact. At most a `wp-config.php.l3io-tmp` remains beside it; the journal names it, and it is never read by WordPress.
- **Killed between two cutover writes** (relocation; added 2026-10-27): `wp-config.php` is valid but half-switched (e.g. new `DB_HOST`, old `DB_NAME`). The next Run refuses naming the interrupted step and the written/pending keys. `--resolve-interrupted-run <run_id>` **completes** the set (the load was already checked, so forward is the safe direction): it re-reads the four keys through `ConfigQuery.read_constants` to learn what actually landed (after a `"cutover_started:<KEY>"` entry, `<KEY>` may or may not have landed), writes the pending ones from the header's non-secret targets and, for `DB_PASSWORD`, from the relocated source the resolving Run is given again (`--new-db-password` or its successor); with no such source it raises `CredentialsError` naming `DB_PASSWORD` and the journal stays blocking. Reverting instead is the operator's manual alternative, named in the undo text (the Safety Snapshot holds the prior file).
- **Killed after the cutover, before the loser is dropped:** the site runs on the fully-loaded, checked staging database. The journal says the cutover completed and the drop did not. The undo names the old database as retained, and never names the now-live database as something to drop (ADR-0020) *(Gate AG-1, 2026-10-28)*.
- **The post-load check fails** (not WordPress, no schema version): the staging database is dropped, `wp-config.php` is not touched, and the Run exits `FAILED`. The journal records `"check_failed"` and `"staging_dropped"` and is finished as failed — it is moved to `failed/<run_id>.json`, not left blocking, because `is_orderly_failure` holds (ADR-0021). This is an orderly failure with nothing to recover, because the live site was never changed.
- **The cutover's read-back verification fails:** `ConfigCutoverError`, the original is byte-identical, the staging database is dropped, and the Run exits `FAILED`. With no key written, the journal records `"cutover_readback_failed"` and `"staging_dropped"` and is finished as failed (an orderly failure, ADR-0021); with a key written it stays blocking.
- **Dropping the staging database in the error path itself fails:** the journal stays `current.json` (blocking), with the undo "drop staging database `<name>`". The original error is preserved, and the secondary one is logged.
- **Journal write fails** (disk full, permissions): the phase does not begin, nothing more is destroyed, and the Run exits `FAILED`. A phase is never run unjournaled.
- **Journal unreadable or corrupt on the next Run:** refuse, naming `journal_path` and saying the interrupted phase could not be determined. It is never treated as absent (NFR-1).
- **Incomplete journal for a different Site:** irrelevant. The journal directory is keyed by the canonical Site Root hash.
- **Staging name collides with an existing database:** `ensure_database` treats an existing database as present. `load_dump` then refuses `DATABASE_NOT_EMPTY` if it holds tables, so the Run exits `REFUSED` without loading over anything. An empty colliding database is loaded into — it held nothing to lose.
- **Dry Run:** the incomplete-journal query and every database `check_*` run for real. `NoopRunJournal` (E002-S02-012) writes nothing, `NoopDatabase` creates and drops nothing, and no config write occurs. The plan reports the staging name and the cutover as actions. The post-load check is given the not-performed `LoadResult` and reports "would check" instead of surveying a database that was never created (ADR-0022) *(Gate AG-5, 2026-10-28)*.

- `journal_written` (DEBUG) per record, with `phase`, `event: started|completed`, `journal_path`.

- `database_cutover` (INFO) with `from`, `to`, `wp_config_path`.
- `previous_database_dropped` / `previous_database_retained` (INFO) with the name.
- `staging_database_dropped` (WARNING, error path).
- `incomplete_run_found` (ERROR), carrying the `IncompleteRunError` fields, which are also printed on stderr.
- The cutover is its own `phase_completed`-shaped record (`phase: "LOAD_DUMP"`, `step: "cutover"`), so its duration is visible separately from the load.
- All records carry `run_id` (E002-S01-004).

### Security considerations

- The journal holds no credential: only names, paths, the Run ID, the mode and undo text. It is mode `0600` in a `0700` directory, written with `json.dumps` (never string formatting). The `credential_sentinel` fixture (E002-S01-006) scans journal files after a full restore.
- `wp-config.php` keeps its mode and owner across every cutover write (asserted; guaranteed by the pinned `l3io-wordpress-config` v0.1.1 — corrected 2026-10-27, formerly an OPEN). No copy of `wp-config.php` is written outside its own directory, and the `.l3io-tmp` sibling is removed by `l3io-wordpress-config` on failure. `DB_PASSWORD` is never journaled, logged or held past its one write.
- The old database's grant is revoked before it is dropped, so a database later created with that name does not silently inherit the WordPress user's access (AD-28's concern, by revocation rather than escaping).
- Staging and loser removal go through `DatabaseCommand.drop_database(location, confirm=<exact name>)` (database's `drop_database`, E002-S02-009). A confirmation mismatch is a blocker, so a wrong-name drop is refused by database.

### Testability approach

- **`tests/integration/test_kill_mid_restore.py`** (`@pytest.mark.integration`, CI MySQL and MariaDB).
  - **Harness:**
    1. The restore runs as `execute_restore` (E003-S01-001), with wrapped adapters and `load_staged` bound over them as the `load_database` slot *(Gate AG-3 re-check, 2026-10-28)*, in a `multiprocessing` spawn child — not the library entry point (Epic 6) and not `drive_restore` (E003-S02-006) *(Gate AG-3, 2026-10-28; BL-E003-006)*.
    2. The child's adapter set wraps the real `RunJournalCommand` in a test adapter that, after each durable write, sends the record's ordinal to the parent over a pipe and blocks.
    3. The parent SIGKILLs the child at ordinal *k*.
  - **Scope:** *k* is parametrised over every journal write a full `all-clean` restore emits. The scope is derived from a first uninterrupted recording run, asserted non-empty and to include the cutover and the loser-drop writes, so a phase added later is covered automatically. The wrapped `SiteFilesCommand`, `ConfigCommand` and `restore_database_command` signal an ordinal too, **after** each effect lands and before it returns, so *k* also falls between an effect and the journal entry that records it — the window a journal-only harness cannot reach *(Gate AG-1 re-check, 2026-10-28)*.
  - **Assertions per *k*:**
    - `wp-config.php`'s `DB_NAME` is the original name, or (only for *k* after the cutover write) the staging name. It is never anything else, and the file always parses through `l3io.wp.config`.
    - The original database's `CHECKSUM TABLE` is unchanged for every *k* before the cutover.
    - The next Run's incomplete-journal query (a new process) raises `IncompleteRunError` naming the interrupted phase and Run ID.
    - The reported `undo` text equals the undo table's row for that *k*: before the first cutover write it names the staging database; after it, it never names the now-live database as something to drop *(Gate AG-1, 2026-10-28)*; at a *k* inside a cutover write it is the `"cutover_started:<KEY>"` row, and `--resolve-interrupted-run` then leaves all four keys at their new values.
    - After resolution, a further restore succeeds.
- **`tests/unit/adapters/test_run_journal.py`** (real filesystem in `tmp_path`):
  - *(Adopted 2026-10-27 from the E002 gate, changes 1 and 3.)* `incomplete()` finds `current.json` and returns a `JournalRecord` whose `entries` equal each prefix of a write sequence;
  - a crash simulated between temp-write and `replace` leaves the previous record readable;
  - a corrupt `current.json` refuses;
  - `finish_run` (to `completed/` or `failed/`) and `resolve` move the file;
  - modes are `0600`/`0700`.
- **`tests/unit/core/test_restore_journal.py`** (pure): `undo_for` is total over `list(RestorePhase)` and returns each undo-table row for each prefix of a recorded `all-clean` entry sequence; `interrupted_phase` is correct for each prefix, and `None` for none; `is_orderly_failure`'s own tests are E003-S01-001's `test_orderly_failure.py` *(Gate AG-3 re-check, 2026-10-28)*; `staging_name` stays ≤ 64 characters for a 64-character live name and is distinct per `run_id` *(Gate AG-1 and AG-7, 2026-10-28)*.
- No load-confirmation test here: E002-S02-012's `tests/contracts/test_no_load_replace.py` asserts that `load_dump` declares no `replace` and that `adapters/database.py` never passes database's `load` a confirmation token.
- **`tests/integration/test_cutover_mode.py`:** a `0640` `wp-config.php` keeps mode `0640` across a restore, with and without relocation (four writes). *(Corrected 2026-10-27: no `xfail` — the pinned v0.1.1 fixes it.)*
- Placement and naming follow E002's `tests/unit/<layer>/`, `tests/contracts/` and `tests/integration/` pattern.
