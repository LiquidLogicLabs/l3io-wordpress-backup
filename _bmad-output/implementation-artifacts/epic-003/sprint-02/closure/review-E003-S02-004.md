## R-001 — HIGH — kind: claim — `src/l3io/wp/backup/adapters/staging.py:429-445`, `src/l3io/wp/backup/cli/restore.py:186`

**Defect.** `previous_database` is decided only from the Mode and the server identity (`_loser`). Nothing tells it whether the live database existed. `load_staged` has no access to the survey's `database_exists`. So:
- In a non-removing Mode it reports `"retained"`, printed as `previous database 'X': retained, not removed`, for a database that never existed.
- In `DATABASE_CLEAN`/`ALL_CLEAN` it returns `"dropped"` even when `drop_database` returned `changed=False` (library `provision.py:721`: "An absent database is `changed=False`"). The `dropped` result is logged and then ignored.

**Failure scenario.** Integration case (b) (account exists, database absent, Mode `DATABASE`) yields `created_database=True, created_user=False, previous_database="retained"`. Case (c) (populated server) yields exactly the same flags and `"retained"`. In the staging design `created_database` is True on every server, because the staging name is always new. So the two reports differ only in a database name. The (b) report states something false: that an existing database was kept. This contradicts the story's Outcome ("three servers … three different, accurate reports") and "An existing database is never mistaken for a restored one" in reverse: an absent one is reported as existing. Test (b) (`tests/integration/test_database_restore_report.py:219`) does not assert `previous_database`, so the error passes.

**Suggested fix.** Carry the administrator survey's `database_exists` for the live database into `RestoreInputs` (or `_Target`). Have `_loser` return a distinct value such as `"none"` (printed as "none (did not exist)") when the live database was absent. In removing Modes, return `"dropped"` only when `drop_database` reports it removed something. Assert `previous_database` in integration tests (a) and (b), and add a unit case to `test_database_report.py`.

## R-002 — MEDIUM — kind: claim (observability) — `src/l3io/wp/backup/adapters/staging.py:503-506`, `:524`

**Defect.** The outer `except BaseException` logs one `database_restore_report` at ERROR with `restored: false` for every failure, including:
- failures **after** the cutover completed: `_loser`'s `revoke_grants`/`drop_database` raising;
- a part-way `ConfigCutoverError`, whose `written`/`pending` keys are not put in the record.

In the first case all three facts of `database_restored` held: the site already runs on the loaded database. The record does not say the cutover happened, or which keys landed.

**Failure scenario.** In a `DATABASE_CLEAN` restore, the drop of the losing database raises `ProvisioningFailedError` (a privilege was revoked mid-run). wp-config.php now points at the new database, but the only report says `restored: false`, `error_type: ProvisioningFailedError` and "nothing created" (see R-005). An operator who reads it as "the restore did not happen" re-runs it, or rolls back a site that was in fact restored. The story requires the failure record to carry "what is known".

**Suggested fix.** Record progress in the failure fields: `cutover_written` (the keys landed so far, from `ConfigCutoverError.written`/`.pending`, or the full tuple once `_cutover` returned) and `live_database_after` once the cutover completed. Consider whether a loser failure after a full cutover should still be `restored: true` with the loser error reported separately. Add a unit case: the fake `drop_database` raises in a clean Mode, and the record names the completed cutover.

## R-003 — MEDIUM — kind: test-quality (guard scope) — `tests/contracts/test_no_sql_ddl.py:31-37`

**Defect.** The DDL regex requires `CREATE\s+(DATABASE|…|USER|ROLE…)` immediately after `CREATE`. So it misses MariaDB's `CREATE OR REPLACE USER|DATABASE|ROLE` and `CREATE TEMPORARY TABLE`. Verified: `DDL.search("CREATE OR REPLACE USER x")`, `("CREATE OR REPLACE DATABASE x")` and `("create temporary table t")` are all `False`. The docstring's **Not seen** list names only literals split by concatenation, `join` or `%`, or read from a file. It claims coverage of "CREATE … of a database, schema, table, user, role", so the prose overstates the guard (global rule 3). CI has a MariaDB leg, where `CREATE OR REPLACE` is idiomatic.

**Failure scenario.** A later change adds `cur.execute("CREATE OR REPLACE USER %s@%s IDENTIFIED BY %s", …)` to an adapter. `test_no_string_literal_in_the_package_is_ddl` stays green, and ADR-0015 is silently broken.

**Suggested fix.** Allow optional modifiers: `(?:CREATE(?:\s+OR\s+REPLACE)?(?:\s+TEMPORARY)?|DROP|ALTER|TRUNCATE|RENAME)\s+(?:DATABASE|…)`. Add those three spellings to `test_planted_ddl_the_widened_scan_sees`.

## R-004 — MEDIUM — kind: test-quality / claim — `tests/integration/test_database_restore_report.py:234`, `tests/integration/live_restore.py:419`

**Defect.** The story's case (c) claims "the FR-7 guard surveyed the **live** database and `--force` waived it (E003-S01-002)". The harness builds every plan with `OverrideSet(waived=frozenset(Override))`, which waives every override for every case. Test (c) asserts only that the administrator's survey saw the database (`before.database_exists`, `table_count > 0`). It never asserts that the guard fired, or that the waiver is what let the plan through. Because (a) and (b) also run fully waived, a guard that wrongly refuses a fresh or account-only server would also go unseen.

**Failure scenario.** A regression makes `check_target` stop consulting `database_exists`, so the guard no longer refuses populated targets. All five integration cases still pass.

**Suggested fix.** In (c), first build the plan with no overrides and assert the FR-7 refusal, naming the live database and its `table_count`. Then build it with only the `--force` override and run it. In (a)/(b), build with no overrides and assert no refusal. `RestoreSpec` needs an `overrides` field that `live_restore.restore` honours.

## R-005 — LOW — kind: claim (message accuracy) — `src/l3io/wp/backup/domain/errors.py:279`

**Defect.** The new message says `(nothing created)` whenever `completed` is empty. But `ProvisioningFailedError` is the `failed` class for every admin-side call through `WpDatabase._mapped`: `survey_target`, `check_ensure`, `check_revoke`, `check_drop_database`, `revoke_grants`, `drop_database`, and `OSError`. It is also raised by `ensure`'s own post-check ("ensure ran but … still not usable"), and in that case `completed` can be empty even though the earlier state was already partly provisioned.

**Failure scenario.** `_loser`'s `drop_database` fails with a `DatabaseError`. The operator reads `provisioning failed: DatabaseError (nothing created)` after a completed cutover. The text is about creation, and it is irrelevant to a drop.

**Suggested fix.** Print the progress clause only for `ensure` failures, for example with a `steps_known: bool` argument or a subclass that `ensure_database` raises. Otherwise leave it out.

## R-006 — LOW — kind: test-quality (guard scope) — `tests/contracts/test_existence_by_admin.py:41`

**Defect.** A block is "authentication-shaped" only by `AuthenticationFailed` in the class name or by the constant `1045`. `wpdb.AccessDeniedError` (MySQL `1044`) is caught next to it in the adapter (`adapters/database.py:515`, `:558`, `:828`), and it is the same kind of ambiguity. An authenticated account connecting to a database it has no privilege on gets `1044` whether or not that database exists. The module docstring's "does not see" list does not mention this shape.

**Failure scenario.** `except wpdb.AccessDeniedError: database_exists = False` in an adapter is exactly the inference AD-29 forbids, and the guard reports clean.

**Suggested fix.** Add `AccessDenied` and `1044` to the trigger set, with a planted case. If that is excluded on purpose, name it in the docstring's "does not see" list.
