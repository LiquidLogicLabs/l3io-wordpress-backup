## Findings

### M-1: ADV-9 overrides ADR-0021's "only when" predicate without an amendment

- **Severity:** MEDIUM
- **Kind:** spec
- **Location:** `src/l3io/wp/backup/core/restore.py:728-732`
- **Problem:** ADR-0021, Decision, Lifecycle:

  > "`finish_run()` is called **only** on success, or on an orderly failure … It returns
  > true only when no `CLEAN`, `EXTRACT` or `REWRITE_CONFIG` phase started, no cutover key
  > landed …, and the failure is either a failed post-load check whose staging drop
  > succeeded, or a cutover read-back failure with the original config intact."

  Its Consequences accept the cost explicitly:

  > "a Run that fails in a way the predicate does not recognise blocks the next Run even
  > when nothing was changed. That is the safe direction (NFR-1)."

  The new early `return True` adds a third orderly case that the ADR excludes. The
  behaviour is sound today, as shown under "Checked, no finding". However, its safety
  rests on an invariant that nothing enforces: every effect after SNAPSHOT is preceded
  by a non-SNAPSHOT `phase_started`. A future phase that records its start after its
  first effect, or an effect added to SNAPSHOT itself, would close the journal over a
  changed Site. The test `test_a_failure_before_any_destroying_phase_is_orderly` checks
  the predicate, not that invariant.
- **Fix:**
  1. Have Shawn amend ADR-0021's predicate clause, citing ADV-9.
  2. Add a phase-sequence test over the recording adapters for every `RestoreMode`. It
     must assert that no command-port call happens before the first `phase_started` whose
     phase is not `SNAPSHOT`. This makes the invariant the predicate relies on a checked
     one.
  3. If the amendment is refused, revert `:728-732` and the two parametrised tests, and
     restore "That Run's journal stays open" in `docs/restore.md`.

### M-2: The RT-002 trust decision was taken by the developer, and two ADR consequence statements are now false

- **Severity:** MEDIUM
- **Kind:** decision
- **Location:** `src/l3io/wp/backup/cli/restore.py:1143-1148`; the BL-E003-036 row in the
  completion notes; `docs/restore.md` "Trust"
- **Problem:** BL-E003-036 asked for a STRUCTURAL_ONLY policy. The developer chose
  "waive, with a warning", and the completion notes say the owner may want a refusal
  flag. The new `docs/restore.md` correctly states the trust model: "whoever can write
  the Archive can rewrite both". That contradicts two accepted ADR consequences:
  - ADR-0016 amendment: "a tampered config member can only produce an abort".
  - ADR-0022, Consequences: "a tampered header can only make the Run abort at `VERIFY`".

  For an unencrypted Archive, and for every STRUCTURAL_ONLY (v0) one, a consistent
  forgery passes `VERIFY` and is restored. The `--archive-database` check mitigates
  only the database redirect. It does not stop a forged file tree from being laid into
  the Site.
- **Fix:**
  - Record the owner's decision, as an ADR-0022 amendment or a backlog item, choosing
    between "proceed, warning" and "refuse STRUCTURAL_ONLY or unauthenticated unless
    acknowledged by a new flag".
  - Correct the two ADR sentences to "… unless the Archive is unencrypted, in which case
    a consistent forgery is restored; see docs/restore.md Trust".

### M-3: A library caller can turn administrator TLS off by passing `admin_tls=None`

- **Severity:** MEDIUM
- **Kind:** security
- **Location:** `src/l3io/wp/backup/cli/restore.py:697`, `:1082`, `:1108`;
  `src/l3io/wp/backup/adapters/database.py:200-203`, `:1018-1022`
- **Problem:** `RestoreRequest.admin_tls` is typed `AdminTls`, but nothing enforces it at
  runtime. `__post_init__` checks only `opted_out_by`.
  - `check_admin_tls(None, host)` returns silently.
  - `real_adapters(admin_tls=None)` is the backup root's plaintext default.

  So `drive_restore(RestoreRequest(..., admin_tls=None, ...))`, the Epic 6 `api.restore`
  path, restores to a remote host over plaintext with the administrator's credentials.
  It raises no error and no warning. The CLI cannot lower the policy, but the library
  can. In effect the security half's guarantee is "restore always uses the policy unless
  the caller passes `None`".
- **Fix:** in `RestoreRequest.__post_init__`, raise `TypeError`/`UsageError` when
  `admin_tls` is not an `AdminTls`. Alternatively, have `drive_restore` coerce `None` to
  `AdminTls(mode=None, ca_file=None)` before `check_admin_tls`. Add a unit test that
  `admin_tls=None` either refuses or builds `VERIFY_IDENTITY` for a remote host.

### M-4: The snapshot directory is created by an `if not run.dry_run` effect in the root, not by adapter selection

- **Severity:** MEDIUM
- **Kind:** architecture
- **Location:** `src/l3io/wp/backup/cli/restore.py:1227-1230`
- **Problem:** The code is
  `if not run.dry_run and (...): snapshot_dir.mkdir(mode=0o700, parents=True, exist_ok=True)`.
  This is the defect class AD-4 exists to prevent: "an effect site … that forgets to
  check the flag". Here the root performs a filesystem effect directly and suppresses it
  with a conditional. The grep gate allows the name in a root, but the rule's mechanism
  ("Dry Run is adapter selection, never a conditional") is bypassed. There are two
  consequences:
  1. If the directory cannot be created, the real Run raises a bare `OSError`. That is
     an AD-14 violation: "An exception from … the stdlib is caught at the boundary and
     re-raised as a package-owned type". The Dry Run of the same command exits `OK`,
     although AD-4 says "a Dry Run that reports 'would restore' where the real run would
     refuse is a defect".
  2. The directory is created before `PREFLIGHT`/`VERIFY`, which is an effect before
     the checks. It is not a Site effect.
- **Fix:** create the directory inside the command that writes into it. The Safety
  Snapshot's store `publish` and the `saved_config` write are both command ports with
  no-op twins. That removes the conditional. If it must stay in the root for now, wrap
  the `OSError` as `ArchiveWriteError`/`SnapshotFailedError` and add a Dry Run vs real
  Run test over an uncreatable `--snapshot-dir`.

### M-5: `test_admin_tls.py` switches TLS off server-wide on the shared CI server, contradicting the completion notes

- **Severity:** MEDIUM
- **Kind:** test (and claim)
- **Location:** `tests/integration/test_admin_tls.py:91-127`
- **Problem:** The completion notes say:

  > "a server with TLS disabled → `UNREACHABLE`; it **skips on a server whose `have_ssl`
  > is `YES`** … so it needs a CI leg with TLS off to exercise".

  The code does not skip. The `tls_disabled` fixture runs `SET GLOBAL ssl_cert/ssl_key/ssl_ca`
  to a missing file and `ALTER INSTANCE RELOAD TLS` on the CI database. That changes
  global server state, which no other test owns.
  - Any test running concurrently on the same server (pytest-xdist, or another job
    sharing the service) sees TLS disappear. This includes `test_an_unverifiable_certificate_is_refused`,
    which then gets a handshake error instead of a verification error.
  - A teardown failure leaves the server without TLS. The fixture reports it with
    `pytest.fail`, but cannot undo it.

  The rule for these tests is "throwaway objects, drop nothing else", and this mutates
  the server itself.
- **Fix:** do one of the following, and correct the completion note to match:
  - mark the test `xdist_group`/serial and make CI run it in its own step;
  - run it only against a dedicated TLS-off service (the CI leg the note describes),
    selected by an env var, and skip otherwise.

## Deviation verdicts (asked by the orchestrator)

### 1. `--archive` is required on every restore, checked in `main` before any Run (completion deviation 11)

**Keep.** Governing clause, AD-22:

> "Flags may gain behaviour and new flags may be added; **no existing flag is renamed or
> removed.**"

Requiring a value for `--archive` neither renames nor removes it. The check is in
`cli/__init__.py:112`, after argument validation and before `configure_logging` and any
Run. A real restore cannot proceed without an Archive. The one cost is resolution
(ADR-0021: "keyed by the canonical Site Root only"), where the value is often never read.
See L-2. I could not check whether v0.2.21's restore treated `--archive` as optional with
a default, because the CLI surface record was outside my read scope. If it did, this is a
behaviour change that belongs in the release notes.

### 2. A failure before any destructive phase now closes the journal (ADV-9)

**Keep the behaviour, conditional on an ADR-0021 amendment. Revert if the owner does not
amend.** Governing clause, ADR-0021, Lifecycle:

> "It returns true **only when** no `CLEAN`, `EXTRACT` or `REWRITE_CONFIG` phase started,
> no cutover key landed …, **and** the failure is either a failed post-load check whose
> staging drop succeeded, or a cutover read-back failure with the original config intact."

ADR-0021's Consequences also accept that a Run "blocks the next Run even when nothing was
changed. That is the safe direction (NFR-1)." The new case contradicts that text.

On safety, "pre-destructive" is decided structurally: no `phase_started` for any phase
other than SNAPSHOT. I checked `restore_runner.py` for every phase:
- `begin_run` is written only at the first non-check phase (`:330-332`).
- Each later phase records `phase_started` before its first command (`:709`,
  `:721`/`:739`, `:809`, `:834`, `:845`).
- The re-survey before the first destroying phase is query-only (`:379-388`).

So today the journal is never closed after an effect on the Site. The invariant is not
guarded, so M-1 asks for the phase-sequence test that makes it one.

### 3. The `--archive-database` identity check also applies to files-only Modes when the target has no `wp-config.php` (completion deviation 7)

**Keep.** It is the AC's own wording rather than a deviation. Story, Security
considerations:

> "On the no-target-config path (ADR-0016 amendment) the restore **refuses** unless the
> operator states the expected identity with the new flag `--archive-database …`"

Error handling:

> "No target `wp-config.php` and `--archive-database` absent, or not equal … →
> `REFUSED` … before any database connection."

Neither clause is limited to database Modes. The check is also needed in a files Mode:
- `PREFLIGHT`'s `DumpReadinessPreflight` is bound to `site.database_location()` from the
  Archive's config (`cli/restore.py:907-912`).
- With no target config, the files Mode lays the Archive's `wp-config.php` into the
