## Findings

### R1 — MEDIUM — kind: claim — `src/l3io/wp/backup/core/restore.py:739-748` (`_load_undo`), `:783` (`undo_for`)

**Claim:** "a durable Run Journal records the phase that was interrupted and **what
would undo it**".

**What is wrong:** `undo_for(interrupted, last_step, header)` derives the
`LOAD_DUMP` rows from the last step alone. In a Mode that restores files
(`all`, `all-clean`), `CLEAN`/`EXTRACT` have already completed when `LOAD_DUMP`
runs. A Run killed during ensure/load, or one whose post-load check failed (which
stays blocking because `is_orderly_failure` rejects file phases), then reports:

- `"live site untouched; drop staging database <name>"`, or
- `"live site untouched; the staging database was already dropped"`.

The Site Root was cleaned and re-extracted, so "live site untouched" is false, and
the Safety Snapshot undo the operator needs for the files is never mentioned. The
undo table in the story has the same gap. The code follows the table, but the
result contradicts the AC's outcome.

**Fix:**
1. Let the derivation see whether a file phase completed. Either pass `entries`, or
   pass a `files_changed: bool` computed in `incomplete_run_error` from
   `phase_completed` entries in `{CLEAN, EXTRACT, REWRITE_CONFIG}`.
2. In that case, replace "live site untouched" with
   "the database and wp-config.php are untouched; files were replaced:
   <_snapshot_undo(header)>", and keep the staging-drop clause.
3. Route the table amendment to the story or ADR-0020 owner.
4. Add an `all-clean` failure-path prefix to `test_restore_journal.py`.

### R2 — MEDIUM — kind: testability / claim — `tests/integration/test_kill_mid_restore.py:225-236` (undo assertions in `_check_kill`)

**Claim (Testability):** "The reported `undo` text **equals the undo table's row**
for that *k*".

**What is wrong:** the harness checks only substrings, and only for `LOAD_DUMP`:

- `load in error.undo` before the cutover;
- "drop staging database" is absent once the cutover began;
- "the cutover was writing" appears inside a write;
- "to complete the set" appears for a non-last key.

Nothing is asserted for:

- the `None`/`PREFLIGHT`/`VERIFY` rows;
- the `CLEAN` and `EXTRACT` rows, including the `config_started`/`config` lay-down
  rows (the lay-down scenario exists precisely to reach them);
- `cutover:<last key>`;
- `loser_drop_started`;
- `loser_dropped`.

A wrong row for any of these, produced from the *real* runner's entry sequence,
which can differ from the fake-recorded one, passes green. The pure unit test does
check row text, but only over fake recordings.

**Fix:** in `_check_kill`:
1. Compute the expected row from `done`: interrupted phase and last journal step.
2. Assert `error.undo == undo_for(phase, step, record.header)`.
3. Assert the row's distinguishing text, reusing `_row` from
   `tests/unit/core/test_restore_journal.py` by moving it into `tests/staging_fakes.py`.
4. Assert exactly one table row matches for every *k*, not only for `LOAD_DUMP`.

### R3 — MEDIUM — kind: security-testability — `tests/integration/test_cutover_mode.py:68,108-110`; `tests/integration/test_kill_mid_restore.py:124`; `tests/unit/adapters/test_staging.py:55`

**What is wrong:** the relocated `DB_PASSWORD` is the only credential this story
newly handles: resolved from `cutover_credentials`, held for one write, written by
the cutover and by `complete_cutover`. It is a bespoke literal
(`f"sentinel-pw2-{uuid}"`, `"cutover-sentinel-5b1f0c"`), not part of
`credential_sentinel.secrets`. So `credential_sentinel.assert_clean()` scans every
log, error and repr surface for the *live* password only.

The relocated password is checked only against the journal text, by substring
(`test_cutover_mode.py:108`). No test asserts it is absent from:

- the structlog records (`cutover_key_written`, `database_cutover`,
  `cutover_completed`, `phase_completed`);
- `ConfigCutoverError`/`CredentialsError` messages;
- reprs.

This breaks the security AC "No record carries a DB_PASSWORD value" and the
project rule that test secrets come from `credential_sentinel`/`live_account`.

**Fix:**
1. Give `CredentialSentinel` a way to plant an additional secret, e.g. a
   `relocated_password` field included in `secrets`, set by a small fixture in
   `tests/conftest.py`.
2. Use it as the relocated account's password in `test_cutover_mode.py` and the
   kill harness.
3. Call `assert_clean()` after the relocated restore and after `complete_cutover`.
4. In `test_staging.py`, run the relocated-cutover and read-back-failure cases under
   `credential_sentinel` with that planted secret.

### R4 — LOW — kind: edge — `src/l3io/wp/backup/adapters/staging.py:460` (no journal step for `EnsureOutcome`), `core/restore.py:743-746`

**What is wrong:** whether this Run created the load database is known only in
memory (`ensure.created_database`) and is never journaled. The `LOAD_DUMP`
`None`-step row therefore guesses from `header.staging_database`, and gets two
cases wrong:

- **Operator-named database this Run created, killed during the load:** the undo
  says "`<name>` existed and was empty before this Run". That is false.
- **Staging name colliding with a pre-existing database:** the undo says "drop
  staging database `<name>`" for a database this Run did not create. If the
  collision held tables (refused `DATABASE_NOT_EMPTY` at load, which
  `check_load` normally catches at `PREFLIGHT`, so this needs a race), the operator
  is told to drop a populated database.

**Fix:**
1. Journal a step right after `ensure_database`, e.g. `"load_database_created"`
   when `created_database` is true. Declare the constant in `core/restore.py`
   beside the others.
2. Make the `None`/`check_failed`/`cutover_readback_failed` rows say "drop" only
   when that step is present. Otherwise say "`<name>` was not created by this Run;
   nothing was loaded into it" (or "…was loaded into it; empty it").
3. Amend the undo table accordingly.

### R5 — LOW — kind: testability — `tests/unit/core/test_restore_journal.py:137,196`; `tests/unit/adapters/test_staging.py`

**What is wrong:** row text is asserted only over prefixes of *successful*
recordings. The following rows are never checked:

- `LOAD_DUMP` after `"check_failed"`, `"cutover_readback_failed"` and
  `"staging_dropped"`;
- the operator-named variant (`staging_database is None`);
- `REWRITE_CONFIG` with a `config_*` step;
- `REWRITE_CONFIG`/`SEARCH_REPLACE` with `phase_undo` set and unset;
- the "unrecognised step" fallback.

`test_undo_for_is_total…` asserts only that the result is non-empty. The
failure-path tests in `test_staging.py` assert the steps but not the undo the next
Run would show.

**Fix:**
1. Add recordings for the failure paths to the `recorded` fixture: check failed,
   read-back failure with no key, read-back failure after a key, and an
   operator-named load. `StagedHarness` already supports all of them.
2. Run the same prefix/row test over them.
3. Add `_row` cases for `REWRITE_CONFIG`/`SEARCH_REPLACE` with a `phase_undo`
   header.

### R6 — LOW — kind: edge — `src/l3io/wp/backup/adapters/staging.py:368-369`

**What is wrong:** `"cutover_started:DB_PASSWORD"` is journaled *before*
`_cutover_value` calls `ports.cutover_credentials()`. If resolution raises (secret
store unreachable, `CredentialsError`) and no key has landed, the result is:

- the error escapes the `ConfigWriteFailedError` branch;
- the staging database is not dropped;
- the journal stays blocking with "the cutover was writing DB_PASSWORD and it may
  have landed; do not drop `<load>`", although nothing was written.

This happens with a relocation that sets only the password, where the keys are
`(DB_PASSWORD, DB_NAME)`.

**Fix:** resolve the value first, then journal `cutover_started:<KEY>`, then call
`set_constants`. This is still "immediately before its write". Alternatively,
treat any exception raised before `set_constants` was entered, with `landed`
empty, like the read-back path: journal `cutover_readback_failed` (or a new
`cutover_aborted`) and drop staging.

### R7 — LOW — kind: observability — `src/l3io/wp/backup/adapters/staging.py:278-303` (`_drop_staging`)

**What is wrong:** one `try` wraps both `drop_database` and
`journal.step_completed(STEP_STAGING_DROPPED)`. If the drop succeeds and the
journal write fails, the code logs `staging_database_drop_failed`, while the
database is in fact gone. The AC's `staging_database_dropped` (WARNING) is never
emitted.

**Fix:**
1. Log `staging_database_dropped` immediately after `drop_database` returns.
2. Wrap the journal write separately, and log `journal_write_failed` with
   `step="staging_dropped"` when it fails.

### R8 — LOW — kind: guard-scope — `tests/integration/live_restore.py:543` (`SIGNALLED`)

**What is wrong:** the kill points between an effect and its journal entry are a
hand-kept set of method names per port. Today it matches the restore-side members
of `SiteFilesCommand`, `ConfigCommand` and `DatabaseCommand`. A command method
added later, for example a grant or rename, would silently not be a kill point,
while the docstring claims "a phase or effect added later is covered".

**Fix:** derive the set from the Protocols. For example, take the public callables
of `ports.site_files.SiteFilesCommand`, `ports.config.ConfigCommand` and
`ports.database.DatabaseCommand`, minus an explicit, asserted exclusion
(`{"dump_to"}`). Also add a test that fails if a Protocol gains a member that is
neither signalled nor excluded.

### R9 — LOW — kind: test-secrets rule — `tests/integration/live_restore.py:526`; `tests/integration/test_restore_inroot_config.py:75`; `tests/unit/core/test_restore_journal.py:70`

**What is wrong:** these are literal secrets outside
`credential_sentinel`/`live_account`:

- `wpdb.Explicit("unused", "unused")`, where the password is the common word
  "unused";
- `password="source-pw-77"` in an Archive's `wp-config.php`;
- `password="unit-password-3e9a"`.

A leak of these values is invisible to the sentinel scan.

**Fix:**
- Use `credential_sentinel.password` (or the planted secret from R3) for the
  archive config and the unit cutover password.
- For `survey_named`, which surveys as the administrator, pass `live_account`
  with the sentinel password instead of a dummy account.

### R10 — LOW — kind: edge / error-handling — `src/l3io/wp/backup/adapters/journal.py:394-401` (`resolve`), `CorruptJournalError`

**What is wrong:**
- `resolve()` reads through `incomplete()`, so a corrupt `current.json` makes
  `--resolve-interrupted-run` raise `CorruptJournalError`. No Run can clear it.
- The message says only "inspect the Site and that file before restoring again".
  It does not say that the operator must move the file aside by hand, or where.
- `incomplete(site_root)` discards its argument (`del site_root`, line 301).
  `resolve` passes the journal *directory* as a "site root", so the port's
  parameter carries no meaning. A FileRunJournal bound to the wrong directory
  would answer for the wrong Site silently.

**Fix:**
1. State the manual recovery in `CorruptJournalError`'s message, e.g. "after
   inspecting it, move `<journal_path>` into `<dir>/resolved/`".
2. In `incomplete`, compare `record.header.site_root` with the `site_root`
   argument, and raise `CorruptJournalError("journal names another Site")` on a
   mismatch.
3. Have `resolve` pass the header's own `site_root`.

## Not findings (checked)

- **`interrupted_phase`** matches the AC rule and the unit oracle.
- **`finish_run`** chooses `completed/` or `failed/` by set inclusion. The
  orderly-failure path finishes into `failed/` as ADR-0021 requires.
- **`check_staged`:**
  - makes every query before judging any result;
  - filters `ENSURE_RESOLVES` before mapping;
  - maps through `blocked_dump_error` and then falls back to `DatabaseRefusedError`;
  - skips the loser checks on another server.
  - Dry Run parity is tested over every database Mode × every blocked check.
- **The cutover:**
  - order follows `CUTOVER_KEYS`, one `set_constants` per key;
  - `cutover_started:` comes before each write and `cutover:` after;
  - with no key landed it journals `cutover_readback_failed` and then
    `staging_dropped`, an orderly failure;
  - with a key landed it stays blocking with the written and pending keys.
- **`complete_cutover`:**
  - refuses before reading or writing when `DB_PASSWORD` is pending without a
    source;
  - re-reads the keys;
  - skips non-secret keys already at their target.
- **Kill harness:**
  - spawn child, after-effect signalling, SIGKILL at a derived *k*;
  - `drive` asserts the child exited with `-SIGKILL`;
  - pre-cutover assertions cover all four keys, the password by hash, plus
    `CHECKSUM TABLE`;
  - the next query and the resolution run in a separate process from the one
    killed.
