## Findings

### M-1 (medium) — Deferred AC obligations are not recorded where E003-S02-006 will pick them up; the unreadable-root exit code cannot be fixed by class at the root

- **Location:** `_bmad-output/implementation-artifacts/epic-003/sprint-02/stories/E003-S02-006.md`
  (missing content). Related code: `src/l3io/wp/backup/adapters/site_files.py:38-46` and
  `src/l3io/wp/backup/domain/errors.py:136`.
- **Issue:** The developer moved three of this story's ACs to E003-S02-006's `cli/restore.py`.
  The S02-006 story only covers one of them, and only partly:
  - **`target_checked` (INFO).** It must carry `site_root_empty`, `database_exists`,
    `table_count` and the applied overrides. It appears nowhere in the repo outside this story.
  - **`restore_refused` (ERROR).** S02-006 line 72 names only its `authorizing` field. The
    `reason: "non_empty_target"`, `parts`, `found`, `detail` and `restore_mode` fields are not
    recorded.
  - **"Site Root unreadable → `REFUSED`, `detail` naming the error."** This is not recorded in
    S02-006. It also cannot be done cleanly at the root:
    - `InvalidSiteDescriptorError` maps to `ExitCode.FAILED`, through `BackupError`.
    - The same class is raised for a missing Site Root (`resolve(strict=True)`) and for a
      missing config, both of which this story's AC wants as `InvalidSiteDescriptorError`.
    - So the root could only tell "unreadable" apart by matching the message text.
  - **Result:** today an unreadable Site Root exits `FAILED`, not `REFUSED` as the AC says. When
    S02-006 is built from its own story, nothing tells it to emit `target_checked` or the full
    `restore_refused`. Per global rule 3, these obligations currently exist only in the
    developer's hand-off.
- **Suggested fix:**
  1. Add to E003-S02-006's Observability section:
     - `target_checked` (INFO), with its four fields;
     - `restore_refused` (ERROR), with the full field list, built from
       `NonEmptyTargetError.parts`, `.found`, `.detail`, `.mode` and the CLI-rendered
       `.authorizing`.
     Make the test plan of S02-006 (`test_restore_cli.py`) assert both events.
  2. Choose where the unreadable-root case becomes `REFUSED`. Either:
     - give the listing failure its own `RefusedError` subclass, or a `reason` discriminator on
       `InvalidSiteDescriptorError`, in E002's adapter; or
     - amend this story's AC to `FAILED` (`InvalidSiteDescriptorError`) with a recorded reason.
     Record the choice in both stories.
  3. Add a dev note to E003-S01-002 recording deviations 1 and 2.

### L-1 (low) — The specificity test lists its modes by hand

- **Location:** `tests/unit/core/test_target_guard.py:118` —
  `@pytest.mark.parametrize("mode", [RestoreMode.ALL, RestoreMode.ALL_CLEAN])`.
- **Issue:** The AC says "for each mode touching both parts". The test lists two modes instead
  of deriving them, so a new two-part Mode would not be covered (global rule 4).
- **Suggested fix:**
  `[m for m in RestoreMode if restores_files(m) and restores_database(m)]`, plus an assertion
  that the list is non-empty.

### L-2 (low) — The credential check is vacuous and does not use the fixture the story names

- **Location:** `tests/unit/core/test_target_guard.py:197-201`
  (`test_the_refusal_is_refused_and_names_no_credential`).
- **Issue:**
  - The test asserts `"wp-config:" not in str(err)`. But `check_target` never receives `SITE`
    or its `credential_source`, only a `TargetState`, so this assertion cannot fail.
  - The Security AC says the refusal path is "covered by E002-S01-006's `credential_sentinel`",
    and that fixture exists in `tests/conftest.py:201`.
  - The integration test does check the real `DB_PASSWORD`, but only in CI.
  - Structurally the risk is nil, because `TargetState` carries no credential. The test's name
    still overstates what it proves.
- **Suggested fix:** Either:
  - rename the test to the `REFUSED` mapping only, and note that `TargetState` carries no
    credential field; or
  - add a `credential_sentinel` case that builds a real `TargetState` from the sentinel site
    (`LocalSiteFiles`, with the database left `None`) and asserts the sentinel is absent from
    `str(err)`, `err.found` and `err.detail`.

### L-3 (low) — `mypy --strict` errors in the new unit suite

- **Location:** `tests/unit/core/test_target_guard.py:193-194`.
- **Issue:** The parameter is annotated `database: object`, but it is passed to
  `dataclasses.replace(..., database=..., load_target=...)`, which expects
  `DatabaseTargetState | None`. This gives two `arg-type` errors. CI only type-checks `src`,
  so nothing flags them.
- **Suggested fix:** Annotate `database: DatabaseTargetState | None`.

### L-4 (low) — The refusal text separates each "found" from its count

- **Location:** `src/l3io/wp/backup/core/restore.py`, `NonEmptyTargetError.__init__` and the end
  of `check_target`.
- **Issue:**
  - When both parts refuse, the message reads
    `found '/srv/www'; db.internal:3307/wp (3 entries; 12 tables)`. The pairing of each target
    with its count is only positional.
  - The same parallel `"; "`-joined strings become the `found`/`detail` log fields for
    E003-S02-006, so any consumer has to re-split and zip them.
  - A path containing `"; "` makes the split ambiguous.
- **Suggested fix:** Render the message per target:
  `found '/srv/www' (3 entries); db.internal:3307/wp (12 tables)`. Optionally also expose a
  `findings: tuple[tuple[str, str], ...]` field for the root's structured log, keeping
  `found`/`detail` as the joined strings the AC names.

### L-5 (low) — Thin coverage of the load-database path

- **Location:** `tests/unit/core/test_target_guard.py` (the `TARGETS` matrix and the two
  `load_target` cases), and `tests/restore_harness.py:439-449`.
- **Issue:**
  - The table-wide matrix never sets `load_target`.
  - No test checks that:
    - `--force` waives a non-empty load database;
    - a non-empty live database and a non-empty load database are both named in one refusal
      (`check_target` lists both);
    - a `load_target` with `load_location=None` falls back to "the load database".
  - `Harness.target()` sets `load_location` from the relocation but always sets
    `load_target=None`, so the fixture is internally inconsistent and never reaches this branch.
- **Suggested fix:**
  - Add a `"load"` entry to `TARGETS`: `EMPTY` with `load_target=FULL_DB`,
    `load_location=LOAD`. Have `_non_empty` count it as `"database"`.
  - Add one case where both databases are non-empty, asserting both locations appear in
    `found`.
