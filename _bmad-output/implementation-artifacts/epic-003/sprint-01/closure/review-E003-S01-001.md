## F-1 — VERIFY emits two `phase_completed` records; the test filters one out

- **Severity:** MEDIUM
- **Kind:** claim / test-quality
- **Location:** `src/l3io/wp/backup/adapters/restore_runner.py:360` (with `adapters/tar.py:856`);
  `tests/unit/adapters/test_restore_runner.py:107`
- **Claim contradicted:** "One `phase_completed` record per executed phase through E002-S01-004's
  `phase()` helper, `phase` equal to the `RestorePhase` value" (Observability).
- **Problem:** the executor opens `phase("verify")` (`RestorePhase.VERIFY.value`). Inside it,
  `verify_archive_view` calls `join_phase(BackupStep.VERIFY.value)`, which is `"VERIFY"`. The names
  differ, so `join_phase` does not join the open phase. It opens a nested one instead.
- **Observed:** every restore emits `[('VERIFY', 'ok'), ('verify', 'ok')]`. A failed verification
  emits two failure records.
- **Test hides it:** `test_each_mode_touches_exactly_its_parts` drops the extra record with
  `if p != "VERIFY"`, so it cannot catch the duplicate.
- **Fix:** let `verify_archive_view` take the phase name to join (default
  `BackupStep.VERIFY.value`), and have the executor pass `RestorePhase.VERIFY.value`. Then remove
  the filter from the test and assert exactly one record per planned phase.

## F-2 — a lay-down of an in-root config lays down nothing and then excludes the tree's copy

- **Severity:** MEDIUM
- **Kind:** correctness / test-quality
- **Location:** `src/l3io/wp/backup/adapters/restore_runner.py:415` and `:421`;
  `tests/unit/adapters/test_restore_runner.py` (`test_a_lay_down_extracts_the_config_first`)
- **Problem:** when `relocation.lay_down_config` is set, the first extract uses
  `roles=frozenset({MemberRole.CONFIG})`. A v1 Archive whose config sits in the Site Root has no
  `config`-role member: `write_v1` and the builders use `site-root/wp-config.php`, role
  `site-root`. That extract therefore writes nothing. `laid_in_root` is still `True`, so the
  `site-root` extraction then excludes `wp-config.php`.
- **Observed:** with `real_files=True`, the `url-only` relocation plus `lay_down_config=True`, mode
  `all`, and the target config removed, the Run reports success and the Site Root has no
  `wp-config.php` afterwards.
- **Consequence in a real Run:** `REWRITE_CONFIG` or the cutover then fails, because
  `l3io-wordpress-config`'s `set()` never creates a file. That happens after `EXTRACT`, so the
  journal is left blocking.
- **Why the test passes:** it uses the recording fake, which returns `members=1` whatever it
  extracts.
- **Note:** the code follows the story text literally (`roles=frozenset({MemberRole.CONFIG})`). It
  is latent until Epic 7 sets `lay_down_config`.
- **Fix:**
  - Compute `laid_in_root` from what the lay-down actually wrote (`laid.members > 0`), not from the
    destination path.
  - Or refuse at plan time with `ValueError` when `lay_down_config` is set and the view has no
    `config`-role member.
  - Add a `real_files=True` case asserting the config exists after the Run.

## F-3 — the executor re-derives `config_exists` instead of using the plan's fact

- **Severity:** MEDIUM
- **Kind:** correctness
- **Location:** `src/l3io/wp/backup/adapters/restore_runner.py:290`, `:202`, `:468`
- **Problem:** the plan decides whether `REWRITE_CONFIG` exists from `TargetState.config_exists`
  (`core/restore.py:573`). The executor ignores that fact and queries
  `site_files_query.file_exists(inputs.config_path)` again in `PREFLIGHT`. It then decides whether
  to overwrite from that second answer (`overwrites_config`).
- **Failure case:** if the two answers disagree, the planned "overwrite … keeping its DB_* values"
  action is silently skipped and the Run reports success. Disagreement can come from a race between
  the root's probe and `PREFLIGHT`, or from a root that built `TargetState` differently. A Dry Run
  would have printed the action; the real Run quietly does nothing.
- **Fix:** carry the fact once. Either add `config_exists` to `RestoreInputs`, or make the overwrite
  arm conditional only on `REWRITE_CONFIG in plan.phases and config_policy is OVERWRITE`. If the
  re-query is kept as a safety check, raise when it contradicts the plan rather than skipping.

## F-4 — the Restore Mode travels in two copies that are never cross-checked

- **Severity:** MEDIUM
- **Kind:** claim / correctness
- **Location:** `src/l3io/wp/backup/adapters/restore_runner.py:235` (`execute_restore`);
  `tests/restore_harness.py:491`
- **Claim:** "the declared mode governs the whole run and is never re-defaulted by a sub-step";
  "Restore Mode is carried, never re-derived".
- **Problem:** the two copies can split one Run:
  - The executor's arms use `plan.mode` (`restores_files(run.plan.mode)` in `_extract` and
    `_check_space`).
  - The `LOAD_DUMP` slot gets the mode from `inputs.header.restore_mode`. The fake reads it to
    decide the loser drop, as the real `load_staged` will.
  - Nothing checks that the two agree. A root that built the header with a different Mode would
    extract per one Mode and drop or retain per another.
- **Fix:** at the top of `execute_restore`, raise `ValueError` when
  `inputs.header.restore_mode is not plan.mode` (a programming error, raised before `PREFLIGHT`).
  Add a test with a mismatched header.

## F-5 — `planned_skipped_links` is untested, and its agreement with extraction is unproven

- **Severity:** MEDIUM
- **Kind:** test-coverage / reuse
- **Location:** `src/l3io/wp/backup/core/restore.py:514`
- **Problem:** the story requires the Dry Run warning lines to be "computed from the view (a
  query), so the two agree" with what extraction skips.
  - **Untested:** nothing under `tests/` references `planned_skipped_links`.
  - **Two rules:** it re-states the symlink rule lexically with `posixpath.normpath`. Extraction
    decides with `tarfile.data_filter`, which uses `realpath`. These can diverge, for example when
    a Site Root component on the target is already a symlink.
- **Fix:** add a parametrised test over a crafted v1 Archive with these symlinks:
  - absolute;
  - `../`-escaping, including from a nested directory;
  - in-root;
  - `..` exactly.

  Assert that `planned_skipped_links(view)` equals `extract_archive(...).skipped_links` as
  `(path, link_target, reason)` sets. Record in the docstring that the rule is lexical, and the one
  case where it can differ from the realpath check.

## F-8 — a v0 Archive is first read in PREFLIGHT, not VERIFY

- **Severity:** LOW
- **Kind:** claim
- **Location:** `src/l3io/wp/backup/adapters/restore_runner.py:331`
- **Claim:** "Archive path missing or unreadable: E002's `ArchiveNotFoundError` → `FAILED`, raised
  during `VERIFY`."
- **Problem:** for an unindexed (v0) view, `PREFLIGHT` already reads the Archive through
  `member_digests` and then `Path(...).stat()`. So a missing Archive fails in the `preflight` phase
  record, not `verify`. And `stat()` bypasses the probe port: if the file vanishes between the two
  calls, it raises a raw `FileNotFoundError`, which is not a `BackupError`. The exit code is the
  same.
- **Fix:** take the compressed size from the probe, or catch `OSError` and raise
  `ArchiveNotFoundError`. Amend the story line to say a v0 Archive is first read in `PREFLIGHT`.

## Recorded risk (not a defect in this diff) — the snapshot location rule versus a home-directory config

- **Severity:** LOW
- **Kind:** design (cross-story)
- **Location:** `src/l3io/wp/backup/core/restore.py:392`
- **Problem:** `snapshot_location` correctly refuses anything inside `config_dir` when that differs
  from the Site Root. Take the common shared-hosting layout: Site Root `~/public_html`, config at
  `~/wp-config.php` (FR-29's one-level-up). There `config_dir` is the operator's home, so a
  per-user default under `~/.local/state/…` is refused on every restore.
- **Owner:** E003-S02-003, which owns the default.
- **Fix:** E003-S02-003 should either choose a default outside `$HOME` for that layout, or confine
  the `config_dir` rule to the config file's directory when it is web-served. Add a test for the
  `~/public_html` plus `~/wp-config.php` layout.
