# E003-S01-001: Restore files and database from an archive


**Implements:** FR-6, FR-19 (restore path)


As an operator,
I want to put an archive back onto a site,
So that I can recover from a bad change.

**Acceptance Criteria:**

**Given** a declared Restore Mode
**When** the restore runs
**Then** the declared mode governs the whole run and is never re-defaulted by a sub-step
**And** each documented mode is reachable and does exactly what its name says
**And** a mode that does not name file removal removes no files; one that does not name database removal drops nothing
**And** phases execute as a subsequence of the ordered `RestorePhase` enum, so reordering is unrepresentable (AD-17)
**And** a test exists per mode asserting both what it touches and what it does not
**And** Verification (story 2.3) runs automatically before the first destructive step, and a failure stops the run with nothing changed *(moved from story 2.3, AG-29)*
**And** a restore run as a Dry Run reports its actions in order and leaves the Site and every Storage Target unchanged, by binding no-op command adapters (AD-4) *(moved from story 2.7, AG-29)*

## Business acceptance criteria

### Outcome

`wpbackup2 restore --wp-dir <Site Root> --archive <target> --mode <files|db|all> [--cleanfirst] [--force]` (and the same call through the library) puts the Archive back onto the Site in exactly the declared Restore Mode, and nothing else. A reviewer can tell it happened by restoring each of the six FR-6 modes onto a fixture Site and seeing, per mode, that the parts the mode names were restored and the parts it does not name are byte-identical (files) or `CHECKSUM TABLE`-identical (database). Before anything on the Site or database changes, the Archive is verified; a corrupt Archive ends the Run with exit `VERIFICATION_FAILED` (8) and the Site untouched. The same command with `--whatIf` prints the ordered actions the real Run would take — including the refusals it would hit — and leaves the Site, the database, every Storage Target, the snapshot directory and the journal directory unchanged. A database-including mode against an Archive that carries no Dump exits non-zero saying so, rather than reporting a database restore that did not happen (FR-2's restore-side consequence, assigned here by E002-S01-002).

### Non-goals

- The FR-7 non-empty-target refusal and its flag authorization — story 3.2. This story's modes run against targets 3.2 has already cleared.
- The Safety Snapshot (story 3.3), the database provisioning report (story 3.4), the Run Journal and staging-database cutover (story 3.5). This story builds the plan that schedules their phases and the executor that runs them; it does not implement them.
- Relocation: `REWRITE_CONFIG` constants other than what 3.5's cutover writes, and `SEARCH_REPLACE` — Epic 7.
- v0 Archive fixtures — Epic 4 commits them; this story restores whatever `ArchiveView` the E002 classifier returns, including `STRUCTURAL_ONLY`.
- Defining `RestoreMode`, `OverrideSet` or `RestorePhase`: they live in E002-S02-011's `domain/restore.py`. Likewise the Run Journal ports, `domain/journal.py` types and `NoopRunJournal` (E002-S02-012); Epic 3 implements only `adapters/journal.py` (E003-S02-005).
- Remote Storage Targets (`file:` only, per E002's grammar).

## Technical acceptance criteria

### Interface contracts

Files this story adds under `src/l3io/wp/backup/` (all Epic 3's except where marked): `core/restore.py`; `adapters/restore_runner.py` (the executor — outside the Epic List's named set, recorded on the same precedent E002-S01-001 used for `adapters/workspace.py`; no other epic claims it). Sibling conventions, read from `domain/flag_map.py` and `cli/parser.py` and recorded in E002-S01-001: every module opens with `from __future__ import annotations`, has a module docstring naming the AD it implements, declares `__all__`; no `__init__.py` is added above `l3io/wp/backup/`; `core/` stays inside `tools/check_purity.py` and the three `[tool.importlinter]` contracts with no exemption; ports are split `<Capability>Query` / `<Capability>Command` (E002-S02-007); new error classes subclass `BackupError` in `domain/errors.py`, which E002-S01-001 provides for ("later stories add subclasses here").

- **`core/restore.py` — the pure plan (AD-1, AD-17).** `build_restore_plan(site: SiteDescriptor, mode: RestoreMode, overrides: OverrideSet, view: ArchiveView, target: TargetState, *, relocation: RestoreRelocation, snapshot: SnapshotPolicy, snapshot_dir: Path, config_dir: Path, config_policy: ConfigPolicy, extra_tools: tuple[ToolRequirement, ...] = ()) -> RestorePlan` — the one statement of this signature; other stories cite it *(Gate AG-6, AG-14 and AG-16, 2026-10-28)*. When `snapshot` is not `SKIP`, it calls E003-S02-003's `snapshot_location(site.site_root, config_dir, snapshot_dir)` and so refuses an unsafe location at plan time, before any effect; `config_dir` is the directory of the located `wp-config.php` (`LocatedConfig.path.parent`, the Site Root itself when the target has no config) *(Gate AG-6 re-check, 2026-10-28)*. `mode`, `overrides`, `relocation`, `snapshot`, `snapshot_dir`, `config_dir` and `config_policy` are required with **no default** — and so is every `RestoreMode`-, `SnapshotPolicy`- or `ConfigPolicy`-annotated parameter anywhere in this story's code, enforced by the existing `tools/check_mode_defaults.py` (AD-5). The root (E003-S02-006) computes `snapshot_dir` (the per-Site default or `--snapshot-dir`); `core/` never computes a default path. Frozen `RestorePlan(mode: RestoreMode, phases: tuple[RestorePhase, ...], snapshot: SnapshotPolicy, snapshot_scope: BackupScope | None, required_tools: tuple[ToolRequirement, ...], actions: tuple[PlannedAction, ...])`. `phases` is built by **filtering** `tuple(RestorePhase)` with a per-mode predicate — never by listing phases in an order — so a plan is a subsequence of the enum by construction, and `__post_init__` re-asserts `phases == tuple(p for p in RestorePhase if p in set(phases))`, raising on violation (reordering is unrepresentable, AD-17). The per-mode predicate is a `match mode:` over every `RestoreMode` member ending in `case _: assert_never(mode)`, so a member added without a row fails `mypy --strict`.
- **Mode semantics, from FR-6's table and nothing else.** `files`: `EXTRACT` (Site Root roles) only. `files-clean`: `CLEAN` (files) + `EXTRACT`. `database`: `LOAD_DUMP` only. `database-clean`: `LOAD_DUMP` with the loser removed (3.5). `all`: `EXTRACT` + `LOAD_DUMP`. `all-clean`: `CLEAN` + `EXTRACT` + `LOAD_DUMP` with the loser removed. `PREFLIGHT` and `VERIFY` are in every plan, and the executor runs them (ADR-0022); `SNAPSHOT` is in every plan whose target is non-empty for the scope the mode touches (3.3) and whose `snapshot` is `TAKE` — `SKIP` removes `SNAPSHOT` from `plan.phases` and from the printed Dry Run actions *(Gate AG-4 and AG-6, 2026-10-28)*. A mode whose row does not name file removal produces no `CLEAN`; a mode whose row does not name database removal produces no database removal step — asserted per mode (Testability).
- **`TargetState`** (frozen, in `core/restore.py`): `site_root_empty: bool`, `database: DatabaseTargetState | None` — built by the restore root (E003-S02-006) from **query** ports only, before the plan exists (3.2 and 3.4 fill the fields) *(Gate AG-4, 2026-10-28; ADR-0022)*. The core never reads the filesystem or the server.
- **`adapters/restore_runner.py` — the executor.** *(Adopted 2026-10-27 from the E002 gate, changes 3, 7 and 8.)* `execute_restore(plan: RestorePlan, inputs: RestoreInputs, ports: RestorePorts, take_snapshot: Callable[[BackupScope], SnapshotResult], journal: RunJournalCommand) -> ExecutionReport` (`RunJournalCommand` is E002-S02-012's) *(Gate AG-14, 2026-10-28)*. It walks `plan.phases` in order — **every** phase, `PREFLIGHT` over `plan.required_tools` through `ports.preflight` and `VERIFY` included; the root runs neither (ADR-0022) — and, for each, runs E002-S01-004's `adapters/phase.py::phase(p.value)` context so every phase emits `phase_completed`. It writes `journal.begin_run(inputs.header)` immediately before `SNAPSHOT`, or before the first destructive phase when the plan has no `SNAPSHOT`; `PREFLIGHT` and `VERIFY` leave no journal. It calls `journal.finish_run()` only after the last phase succeeds, or when a phase raised and E003-S02-005's `is_orderly_failure(entries)` holds for the entries the executor itself has journaled in this Run (kept in memory as it writes them, so a Dry Run, whose no-op journal persists nothing, evaluates the same entries as the real Run) *(Gate AG-7 re-check, 2026-10-28)*; it has no `finally: finish_run()` (ADR-0021) *(Gate AG-4 and AG-7, 2026-10-28)*.
- **`core/restore.py::RestoreInputs`** — frozen, the Run's facts the arms use, passed beside the plan: `site: SiteDescriptor`, `view: ArchiveView`, `archive: StorageTarget` (the Archive source), `run_id: str`, `relocation: RestoreRelocation`, `header: JournalHeader`, `config_policy: ConfigPolicy`, `config_path: Path` (the located config, `LocatedConfig.path`, E002-S01-001; `<site_root>/wp-config.php` when the target has none), and `archive_config_digest: str | None` (the digest of the config bytes the root read under the ADR-0016 amendment, `None` otherwise). Built once by E003-S02-006 *(Gate AG-14 and AG-10, 2026-10-28)*. It contains no `if dry_run`/`what_if` (E002's CI grep gate covers `adapters/`); Dry Run is the composition root binding no-op command halves (AD-4). `take_snapshot` is a callable supplied by the composition root so the executor never needs the `RunContext` type (`cli/` sits above `adapters/` in the layers contract).
- **Verification before the first destructive step (moved from story 2.3, AG-29).** The `VERIFY` phase calls E002-S01-003's `adapters/tar.py::verify_archive` on the Archive and gets a `VerificationResult`. `passed is False` → raise `VerificationFailedError(result)` (E002's) → `ExitCode.VERIFICATION_FAILED`, before `SNAPSHOT` and before any command adapter call. `passed is True` with `integrity == Integrity.STRUCTURAL_ONLY` (a v0 Archive, FR-10) proceeds and is reported, never silently treated as `VERIFIED` (AG-17). When `inputs.archive_config_digest` is set, `VERIFY` also requires the config member's stored digest to equal it, else `VerificationFailedError` (ADR-0016 amendment; this check moved here from the root with ADR-0022) *(Gate AG-4, 2026-10-28)*. The restore uses the `ArchiveView` returned by the classifier for member roles; it never branches on `format_version` itself (E002-S01-003's contract test covers `adapters/`).
- **Extraction** is only through E002-S01-003's `adapters/tar.py::extract_archive(source, destination, view, *, roles=...)` (AD-11, `filter="data"`); this story adds no second extraction path. `tests/contracts/test_extraction.py`'s tripwire is satisfied by that function, not by code here. **Unsupported symlinks** *(Shawn, 2026-10-28; gate AG-2; ADR-0017 amendment)*: a symlink whose target is absolute or outside the Site Root is not supported. `extract_archive` skips it and returns it in `ExtractResult.skipped_links`; the restore does **not** fail on it. `ExecutionReport` carries the skipped links and the Run exits `OK` with the WARNING. The operator documentation, `docs/restore.md` (new, this story), states that absolute and out-of-root symlinks are not supported and are skipped with a warning on restore.
- **Dry Run of a restore (moved from story 2.7, AG-29).** The restore composition root builds the adapter set with E002-S02-007's `dry_run_adapters(...)`: same query instances, no-op command halves (the restore twins, `NoopRunJournal` among them, are E002-S02-012's). Every query — `verify_archive`, Site Root emptiness, database `survey`/`check_load`/`check_ensure`/`check_drop_database`, the Run Journal's "is there an incomplete journal" query — runs for real, so a Dry Run refuses wherever the real Run would refuse, with the same `ExitCode`. `execute_restore` runs every phase under that set exactly as in a real Run. A check that follows an effect takes that effect's result, and a no-op result is marked `performed=False`, so the check reports "would verify" or "would check" instead of failing (ADR-0022; the three checks are E003-S02-003's, E003-S02-004's and E003-S02-005's) *(Gate AG-5, 2026-10-28)*. The Dry Run also lists, as a WARNING line after the actions, each symlink in the Archive view whose `ViewMember.link_target` (E002-S01-003) is absolute or resolves outside the Site Root — the links the real Run would skip — computed from the view (a query), so the two agree; for a v0 Archive, whose view carries no `link_target`, it says such links are reported at extraction. The plan's `actions` are printed in order on stdout (`1. preflight …`, `2. verify <archive> …`, `3. safety snapshot of <scope> to <dir>`, `4. clean <Site Root>` …) and each logged as `planned_action`.
- **No Dump in the Archive** (`view.dump_present is False`) with a mode that names the database: `build_restore_plan` raises `ArchiveHasNoDumpError(RefusedError)` → `ExitCode.REFUSED`, naming the Archive's `backup_scope`; nothing changes.
- **Restore Mode is carried, never re-derived.** The composition root obtains `(RestoreMode, OverrideSet)` once from E002-S02-011's `resolve_flags` over the `domain/flag_map.py` table (AD-25) and passes `mode` explicitly into `build_restore_plan`, into `snapshot_scope`, into the journal header (3.5) and into the `run_started`-adjacent `restore_mode_resolved` log record. (2) When `target.config_exists` — or the lay-down places a config at `<site_root>/wp-config.php` — the `site-root` extraction passes `exclude=frozenset({PurePosixPath("wp-config.php")})` (E002-S01-003's `extract_archive` behind E002-S02-012's `SiteFilesCommand.extract`), whether the located config is `SITE_ROOT` or `PARENT`, so no second config is laid down beside a `PARENT` one; and `CLEAN`'s `keep` contains `wp-config.php` when the located config is in the Site Root. - **`--overwrite-wp-config` — `ConfigPolicy.OVERWRITE` (ADR-0023)** *(Gate AG-16, 2026-10-28)*. ### Error and edge case handling

- Verification fails (truncated, checksum mismatch, unsafe member path, unrecognised format, unsupported version): `ExitCode.VERIFICATION_FAILED`; the recording command log is empty; no snapshot, no journal entry.
- v0 Archive: proceeds with `integrity: STRUCTURAL_ONLY` in the human output and the `verify` phase record; never presented as `VERIFIED`.
- Archive path missing or unreadable: E002's `ArchiveNotFoundError` → `FAILED`, raised during `VERIFY`, nothing changed.
- `view.dump_present is False` with `database`, `database-clean`, `all` or `all-clean`: `ArchiveHasNoDumpError` → `REFUSED` before any phase after `VERIFY`.
- `config_policy` `OVERWRITE` and `view.config_path is None`: `ArchiveHasNoConfigError` → `REFUSED` at plan time, nothing changed (ADR-0023) *(Gate AG-16, 2026-10-28)*.
- `OVERWRITE` and the target config's owner cannot be kept: `ConfigWriteFailedError` → `FAILED`, the original byte-identical; the journal names `"config_saved"` and the saved copy.
- A `files`-scope Archive restored with `files`/`files-clean`: proceeds; no database is contacted and no admin credentials are required.
- A failure inside a phase after the first destructive phase began: the exception propagates (no catch-and-continue in the executor), the phase record carries `outcome: failed` and the mapped `exit_code`, and the Run Journal is left blocking unless `is_orderly_failure` holds (ADR-0021, E003-S02-005) *(Gate AG-7, 2026-10-28)* — the executor never reports success after a failed phase.
- Dry Run whose real Run would refuse (bad Archive, locked Site, unresolved journal, non-empty target without authorization, missing admin credentials): same `ExitCode` as the real Run, after printing the actions planned up to that point.
- A plan built with phases out of order (only reachable by a bug in the predicate): `RestorePlan.__post_init__` raises before execution.
