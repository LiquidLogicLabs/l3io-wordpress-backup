# E003-S01-001: Restore files and database from an archive


**Implements:** FR-6, FR-19 (restore path)


As an operator,
I want to put an archive back onto a site,
So that I can recover from a bad change.

**Acceptance Criteria:**

**Given** a declared Restore Mode
**When** the restore runs
**Then** the declared mode governs the whole run and is never re-defaulted by a sub-step
**And** each documented mode is reachable and does exactly what its name says
**And** a mode that does not name file removal removes no files; one that does not name database removal drops nothing
**And** phases execute as a subsequence of the ordered `RestorePhase` enum, so reordering is unrepresentable (AD-17)
**And** a test exists per mode asserting both what it touches and what it does not
**And** Verification (story 2.3) runs automatically before the first destructive step, and a failure stops the run with nothing changed *(moved from story 2.3, AG-29)*
**And** a restore run as a Dry Run reports its actions in order and leaves the Site and every Storage Target unchanged, by binding no-op command adapters (AD-4) *(moved from story 2.7, AG-29)*

## Business acceptance criteria

### Outcome

`wpbackup2 restore --wp-dir <Site Root> --archive <target> --mode <files|db|all> [--cleanfirst] [--force]` (and the same call through the library) puts the Archive back onto the Site in exactly the declared Restore Mode, and nothing else. A reviewer can tell it happened by restoring each of the six FR-6 modes onto a fixture Site and seeing, per mode, that the parts the mode names were restored and the parts it does not name are byte-identical (files) or `CHECKSUM TABLE`-identical (database). Before anything on the Site or database changes, the Archive is verified; a corrupt Archive ends the Run with exit `VERIFICATION_FAILED` (8) and the Site untouched. The same command with `--whatIf` prints the ordered actions the real Run would take — including the refusals it would hit — and leaves the Site, the database, every Storage Target, the snapshot directory and the journal directory unchanged. A database-including mode against an Archive that carries no Dump exits non-zero saying so, rather than reporting a database restore that did not happen (FR-2's restore-side consequence, assigned here by E002-S01-002).

### Non-goals

- The FR-7 non-empty-target refusal and its flag authorization — story 3.2. This story's modes run against targets 3.2 has already cleared.
- The Safety Snapshot (story 3.3), the database provisioning report (story 3.4), the Run Journal and staging-database cutover (story 3.5). This story builds the plan that schedules their phases and the executor that runs them; it does not implement them. It does declare, in `core/restore.py`, the pure values and predicates its own plan and executor need from them — `snapshot_scope`, `snapshot_location`, `SnapshotResult`, `DatabaseRestoreReport`, the journal step names and `is_orderly_failure` — and runs `SNAPSHOT` and `LOAD_DUMP` through injected slots, so it builds and tests green with no sprint-02 code *(Gate AG-3 re-check, 2026-10-28)*.
- Relocation: `REWRITE_CONFIG` constants other than what 3.5's cutover writes, and `SEARCH_REPLACE` — Epic 7.
- v0 Archive fixtures — Epic 4 commits them; this story restores whatever `ArchiveView` the E002 classifier returns, including `STRUCTURAL_ONLY`.
- Defining `RestoreMode`, `OverrideSet` or `RestorePhase`: they live in E002-S02-011's `domain/restore.py`. Likewise the Run Journal ports, `domain/journal.py` types and `NoopRunJournal` (E002-S02-012); Epic 3 implements only `adapters/journal.py` (E003-S02-005).
- Remote Storage Targets (`file:` only, per E002's grammar).

### Error and edge case handling

- Verification fails (truncated, checksum mismatch, unsafe member path, unrecognised format, unsupported version): `ExitCode.VERIFICATION_FAILED`; the recording command log is empty; no snapshot, no journal entry.
- v0 Archive: proceeds with `integrity: STRUCTURAL_ONLY` in the human output and the `verify` phase record; never presented as `VERIFIED`.
- Encrypted Archive with the wrong passphrase, or a payload damaged after its checksum was taken: `VERIFY`'s decrypt raises `PassphraseRejectedError` or `PayloadDamagedError` (E002's, `domain/errors.py`), both → `VERIFICATION_FAILED` (8) (Shawn, 2026-11-03); the recording command log is empty; no snapshot, no journal entry *(ADR-0024; E003 pre-build re-check, 2026-11-03)*.
- The Archive changed between the probe and `VERIFY` (the verified view differs from `inputs.view`): `ArchiveChangedError` → `VERIFICATION_FAILED`, nothing changed *(E003 pre-build re-check, 2026-11-03)*.
- Python without the tarfile CVE fix (no `os.path.ALLOW_MISSING`): `require_patched_tarfile` raises E002's `ExtractionRefusedError` → `REFUSED` in `PREFLIGHT`, before `CLEAN`; the recording command log is empty *(E003 pre-build re-check, 2026-11-03)*.
- Expanded size over the free-space limit, or expansion ratio over `MAX_EXPANSION_RATIO`: `InsufficientSpaceError` / `ExpansionRatioError` → `REFUSED` in `PREFLIGHT`, before `CLEAN`; a member whose tar header exceeds its indexed size: `ExtractionRefusedError` during `EXTRACT` (BL-E002-116, Security considerations) *(E003 pre-build re-check, 2026-11-03)*.
- Archive path missing or unreadable: E002's `ArchiveNotFoundError` → `FAILED`, raised during `VERIFY`, nothing changed.
- `view.dump_present is False` with `database`, `database-clean`, `all` or `all-clean`: `ArchiveHasNoDumpError` → `REFUSED` before any phase after `VERIFY`.
- `config_policy` `OVERWRITE` and `view.config_path is None`: `ArchiveHasNoConfigError` → `REFUSED` at plan time, nothing changed (ADR-0023) *(Gate AG-16, 2026-10-28)*.
- `OVERWRITE` and the target config's owner cannot be kept: `ConfigWriteFailedError` → `FAILED`, the original byte-identical; the journal names `"config_saved"` and the saved copy.
- A `files`-scope Archive restored with `files`/`files-clean`: proceeds; no database is contacted and no admin credentials are required.
- A failure inside a phase after the first destructive phase began: the exception propagates (no catch-and-continue in the executor), the phase record carries `outcome: failed` and the mapped `exit_code`, and the Run Journal is left blocking unless `is_orderly_failure` (Interface contracts, above) holds (ADR-0021) *(Gate AG-7, 2026-10-28; Gate AG-3 re-check, 2026-10-28)* — the executor never reports success after a failed phase.
- Dry Run whose real Run would refuse (bad Archive, locked Site, unresolved journal, non-empty target without authorization, missing admin credentials): same `ExitCode` as the real Run, after printing the actions planned up to that point.
- A plan built with phases out of order (only reachable by a bug in the predicate): `RestorePlan.__post_init__` raises before execution.

### Security considerations

- **Close-out gate BL-E002-116 (red team RT-3, E002 epic closure; Shawn 2026-11-03: must be closed before the project closes).** *(E003 pre-build re-check, 2026-11-03: rewritten against the built code.)*
  - **The E002 domain edit (granted here).** `domain/archive_format.py::ViewMember` gains `size: int | None` — the Manifest member's `size` for v1, `None` for v0, which has no Manifest — and `ArchiveView` gains `backup_scope: str | None` (the Manifest's `backup_scope`, `None` for v0). `classify` passes both through from the Manifest (`_classify_v1`) and sets `None` (`_classify_v0`); every `ViewMember` constructor in `src/` and `tests/` is updated in the same change.
  - **The limits, constants in `core/restore.py`, each changeable only by a later recorded decision:** `FREE_SPACE_MARGIN: Final = 0.05` and `MAX_EXPANSION_RATIO: Final = 200`. The pure rule `check_expansion(*, target_need: int, workspace_need: int, expanded: int, compressed: int, target_free: int, workspace_free: int) -> None` raises `InsufficientSpaceError(RefusedError)` (defined in `core/restore.py`, naming the filesystem that is short, the bytes needed and the bytes free) when `target_need > target_free * (1 - FREE_SPACE_MARGIN)` — free space on the target minus 5% — or when `workspace_need > workspace_free * (1 - FREE_SPACE_MARGIN)`. The need is computed **per destination** *(E003 pre-build re-check 2, 2026-11-03)*: `target_need` is the summed size of the members the plan extracts onto the target (the `site-root` and, when laid down, `config` roles — never the Dump, which never lands there); `workspace_need` is what the Run's workspace holds — the decrypted payload (the payload size when `view.encrypted`, else 0), plus the Dump's size when the plan loads one, plus the config copy; and `ExpansionRatioError(RefusedError)` (defined there too) when `expanded / compressed > MAX_EXPANSION_RATIO`. `docs/restore.md` states both limits.
  - **The preflight (step 4 of the `PREFLIGHT` arm, before `CLEAN`, queries only).** When every member of `inputs.view` has a `size`, `expanded` is their sum (the ratio's numerator) and the per-role sums give `target_need` and `workspace_need` above; `compressed` is `view.payload.size`. *(E003 pre-build re-check 2, 2026-11-03)* When any `size is None` (v0), `expanded` is the sum of the tar headers' `size` from `ports.adapters.archive_probe.member_digests(inputs.archive)` (a read) and `compressed` is the Archive file's size.
