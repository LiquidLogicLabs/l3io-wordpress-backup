# E003-S01-001: Restore files and database from an archive


**Implements:** FR-6, FR-19 (restore path)


As an operator,
I want to put an archive back onto a site,
So that I can recover from a bad change.

**Acceptance Criteria:**

**Given** a declared Restore Mode
**When** the restore runs
**Then** the declared mode governs the whole run and is never re-defaulted by a sub-step
**And** each documented mode is reachable and does exactly what its name says
**And** a mode that does not name file removal removes no files; one that does not name database removal drops nothing
**And** phases execute as a subsequence of the ordered `RestorePhase` enum, so reordering is unrepresentable (AD-17)
**And** a test exists per mode asserting both what it touches and what it does not
**And** Verification (story 2.3) runs automatically before the first destructive step, and a failure stops the run with nothing changed *(moved from story 2.3, AG-29)*
**And** a restore run as a Dry Run reports its actions in order and leaves the Site and every Storage Target unchanged, by binding no-op command adapters (AD-4) *(moved from story 2.7, AG-29)*

## Business acceptance criteria

### Outcome

`wpbackup2 restore --wp-dir <Site Root> --archive <target> --mode <files|db|all> [--cleanfirst] [--force]` (and the same call through the library) puts the Archive back onto the Site in exactly the declared Restore Mode, and nothing else. A reviewer can tell it happened by restoring each of the six FR-6 modes onto a fixture Site and seeing, per mode, that the parts the mode names were restored and the parts it does not name are byte-identical (files) or `CHECKSUM TABLE`-identical (database). Before anything on the Site or database changes, the Archive is verified; a corrupt Archive ends the Run with exit `VERIFICATION_FAILED` (8) and the Site untouched. The same command with `--whatIf` prints the ordered actions the real Run would take — including the refusals it would hit — and leaves the Site, the database, every Storage Target, the snapshot directory and the journal directory unchanged. A database-including mode against an Archive that carries no Dump exits non-zero saying so, rather than reporting a database restore that did not happen (FR-2's restore-side consequence, assigned here by E002-S01-002).

## Technical acceptance criteria

### Interface contracts

Files this story adds under `src/l3io/wp/backup/` (all Epic 3's except where marked): `core/restore.py`; `adapters/restore_runner.py` (the executor — outside the Epic List's named set, recorded on the same precedent E002-S01-001 used for `adapters/workspace.py`; no other epic claims it). Sibling conventions, read from `domain/flag_map.py` and `cli/parser.py` and recorded in E002-S01-001: every module opens with `from __future__ import annotations`, has a module docstring naming the AD it implements, declares `__all__`; no `__init__.py` is added above `l3io/wp/backup/`; `core/` stays inside `tools/check_purity.py` and the three `[tool.importlinter]` contracts with no exemption; ports are split `<Capability>Query` / `<Capability>Command` (E002-S02-007); new error classes subclass `BackupError` in `domain/errors.py`, which E002-S01-001 provides for ("later stories add subclasses here").

- **`core/restore.py` — the pure plan (AD-1, AD-17).** `build_restore_plan(site: SiteDescriptor, mode: RestoreMode, overrides: OverrideSet, view: ArchiveView, target: TargetState) -> RestorePlan`. `mode` and `overrides` are required parameters with **no default** — and so is every `RestoreMode`-annotated parameter anywhere in this story's code, enforced by the existing `tools/check_mode_defaults.py` (AD-5). Frozen `RestorePlan(mode: RestoreMode, phases: tuple[RestorePhase, ...], snapshot_scope: BackupScope | None, required_tools: tuple[ToolRequirement, ...], actions: tuple[PlannedAction, ...])`. `phases` is built by **filtering** `tuple(RestorePhase)` with a per-mode predicate — never by listing phases in an order — so a plan is a subsequence of the enum by construction, and `__post_init__` re-asserts `phases == tuple(p for p in RestorePhase if p in set(phases))`, raising on violation (reordering is unrepresentable, AD-17). The per-mode predicate is a `match mode:` over every `RestoreMode` member ending in `case _: assert_never(mode)`, so a member added without a row fails `mypy --strict`.
- **Mode semantics, from FR-6's table and nothing else.** `files`: `EXTRACT` (Site Root roles) only. `files-clean`: `CLEAN` (files) + `EXTRACT`. `database`: `LOAD_DUMP` only. `database-clean`: `LOAD_DUMP` with the loser removed (3.5). `all`: `EXTRACT` + `LOAD_DUMP`. `all-clean`: `CLEAN` + `EXTRACT` + `LOAD_DUMP` with the loser removed. `PREFLIGHT` and `VERIFY` are in every plan; `SNAPSHOT` in every plan whose target is non-empty for the scope the mode touches (3.3). A mode whose row does not name file removal produces no `CLEAN`; a mode whose row does not name database removal produces no database removal step — asserted per mode (Testability).
- **`TargetState`** (frozen, in `core/restore.py`): `site_root_empty: bool`, `database: DatabaseTargetState | None` — built by the executor from **query** ports only (3.2 and 3.4 fill the fields). The core never reads the filesystem or the server.
- **`adapters/restore_runner.py` — the executor.** `execute_restore(plan: RestorePlan, ports: RestorePorts, take_snapshot: Callable[[BackupScope], SnapshotResult], journal: RunJournalCommand) -> RestoreOutcome`. It walks `plan.phases` in order and, for each, runs E002-S01-004's `adapters/phase.py::phase(p.value)` context so every phase emits `phase_completed`. It contains no `if dry_run`/`what_if` (E002's CI grep gate covers `adapters/`); Dry Run is the composition root binding no-op command halves (AD-4). `take_snapshot` is a callable supplied by the composition root so the executor never needs the `RunContext` type (`cli/` sits above `adapters/` in the layers contract).
- **Verification before the first destructive step (moved from story 2.3, AG-29).** The `VERIFY` phase calls E002-S01-003's `adapters/tar.py::verify_archive` on the Archive and gets a `VerificationResult`. `passed is False` → raise `VerificationFailedError(result)` (E002's) → `ExitCode.VERIFICATION_FAILED`, before `SNAPSHOT` and before any command adapter call. `passed is True` with `integrity == Integrity.STRUCTURAL_ONLY` (a v0 Archive, FR-10) proceeds and is reported, never silently treated as `VERIFIED` (AG-17). The restore uses the `ArchiveView` returned by the classifier for member roles; it never branches on `format_version` itself (E002-S01-003's contract test covers `adapters/`).
- **Extraction** is only through E002-S01-003's `adapters/tar.py::extract_archive(source, destination, view, *, roles=...)` (AD-11, `filter="data"`); this story adds no second extraction path. `tests/contracts/test_extraction.py`'s tripwire is satisfied by that function, not by code here.
- **Dry Run of a restore (moved from story 2.7, AG-29).** The restore composition root builds the adapter set with E002-S02-007's `dry_run_adapters(...)`: same query instances, no-op command halves. Every query — `verify_archive`, Site Root emptiness, database `survey`/`check_load`/`check_ensure`/`check_drop_database`, the Run Journal's "is there an incomplete journal" query — runs for real, so a Dry Run refuses wherever the real Run would refuse, with the same `ExitCode`. The plan's `actions` are printed in order on stdout (`1. preflight …`, `2. verify <archive> …`, `3. safety snapshot of <scope> to <dir>`, `4. clean <Site Root>` …) and each logged as `planned_action`.
- **No Dump in the Archive** (`view.dump_present is False`) with a mode that names the database: `build_restore_plan` raises `ArchiveHasNoDumpError(RefusedError)` → `ExitCode.REFUSED`, naming the Archive's `backup_scope`; nothing changes.
- **Restore Mode is carried, never re-derived.** The composition root obtains `(RestoreMode, OverrideSet)` once from E002's `domain/flag_map.py` table (AD-25) and passes `mode` explicitly into `build_restore_plan`, into `snapshot_scope`, into the journal header (3.5) and into the `run_started`-adjacent `restore_mode_resolved` log record. ### Error and edge case handling

- Verification fails (truncated, checksum mismatch, unsafe member path, unrecognised format, unsupported version): `ExitCode.VERIFICATION_FAILED`; the recording command log is empty; no snapshot, no journal entry.
- v0 Archive: proceeds with `integrity: STRUCTURAL_ONLY` in the human output and the `verify` phase record; never presented as `VERIFIED`.
- Archive path missing or unreadable: E002's `ArchiveNotFoundError` → `FAILED`, raised during `VERIFY`, nothing changed.
- `view.dump_present is False` with `database`, `database-clean`, `all` or `all-clean`: `ArchiveHasNoDumpError` → `REFUSED` before any phase after `VERIFY`.
- A `files`-scope Archive restored with `files`/`files-clean`: proceeds; no database is contacted and no admin credentials are required.
- A failure inside a phase after the first destructive phase began: the exception propagates (no catch-and-continue in the executor), the phase record carries `outcome: failed` and the mapped `exit_code`, and the Run Journal is left unresolved (3.5) — the executor never reports success after a failed phase.
- Dry Run whose real Run would refuse (bad Archive, locked Site, unresolved journal, non-empty target without authorization, missing admin credentials): same `ExitCode` as the real Run, after printing the actions planned up to that point.
- A plan built with phases out of order (only reachable by a bug in the predicate): `RestorePlan.__post_init__` raises before execution.

### Security considerations

- The Archive is untrusted: verification completes before the first destructive step, and extraction goes only through `extract_archive` with `filter="data"` and containment re-checked (AD-11).

- `tests/unit/core/test_restore_plan.py` (pure, no I/O): parametrised over `list(RestoreMode)` — scope from the enum — asserts for each mode the exact phase tuple, that it is a subsequence of `tuple(RestorePhase)`, and the FR-6 row: files touched / not touched, database touched / not touched, file removal present only for `*-clean` with files, database removal present only for `*-clean` with database.
