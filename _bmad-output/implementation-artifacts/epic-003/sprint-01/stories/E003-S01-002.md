# E003-S01-002: Refuse to overwrite a non-empty target


**Implements:** FR-7


As an operator,
I want the tool to stop rather than guess when the target already has content,
So that a mistyped path does not delete a live site.

**Acceptance Criteria:**

**Given** a Site Root that is not empty, or an existing database
**When** a restore is attempted without explicit authorization for that specific destruction
**Then** the run exits non-zero, changes nothing, and names the flag that would authorize it
**And** authorization is specific — a flag permitting file replacement does not thereby permit dropping the database
**And** the flag combination maps through one total function with no default branch (AD-25)
**And** `--cleanfirst` without `--force` against a non-empty target refuses

## Business acceptance criteria

### Outcome

A restore whose target already has content — a non-empty Site Root, or an existing database holding tables — and that lacks the authorization for that specific destruction exits `REFUSED` (3) before anything changes. The message names the target it found (path, or `host:port/db_name` and table count) and the exact flag that would authorize it. Authorizing file replacement never authorizes database replacement, and the reverse. `--cleanfirst` without `--force` against a non-empty target refuses: the destruction is authorized but the target guard is not. A reviewer can tell it happened by running each reachable flag combination against an empty target and a non-empty one, and seeing either the documented refusal or the documented mode — never a guess.

### Non-goals

- Writing the flag→`(RestoreMode, OverrideSet)` table. It lives in `domain/flag_map.py`, Epic 2's; E002-S02-011 registers the restore flags and lands their entries in the same change. This story *consumes* the table and adds the behavioural tests that prove what each entry does to a real target.
- Any new CLI flag. AD-22 permits new flags, but none is needed: the registered `--mode`, `--cleanfirst`, `--drop-database` and `--force` — the four dimensions of `domain/flag_map.py::COVERED_FLAGS` — carry the authorizations *(E003 pre-build re-check, 2026-11-03)*.
- An interactive "are you sure?" prompt — refusing is the outcome (§7.1); automation must not hang.
- The Safety Snapshot that follows an authorized destruction (story 3.3).
- Deciding what "empty" means for a database by logging in as the WordPress user — existence comes from the administrator (AD-29, story 3.4).

## Technical acceptance criteria

### Interface contracts

Files this story changes: `core/restore.py` (Epic 3's; adds the guard) — nothing in `cli/restore.py`. This story provides the guard and the `TargetState` fields below; E003-S02-006 binds them (its root surveys the target and calls `build_restore_plan`) *(Gate AG-3, 2026-10-28)*. Conventions as recorded in story 3.1 — module docstring naming the AD, `from __future__ import annotations`, `__all__`, `core/` pure under `tools/check_purity.py` and the import-linter contracts.

- **The table is consumed, not reimplemented (AD-25).** *(Adopted 2026-10-27 from the E002 gate, changes 2, 7 and 8.)* The composition root calls E002-S02-011's `resolve_flags` over `domain/flag_map.py` once, keyed on the parser's `(dest, value)` pairs (`FlagCombination`), obtaining `(RestoreMode, OverrideSet)`. `OverrideSet` is a distinct type from `RestoreMode` (E002), so `--force` can only add an override, never select a Mode. This story adds no mapping code, no `if args.force`, and no second lookup anywhere. **`tests/contracts/test_no_flag_reads.py`** enforces it *(E003 pre-build re-check, 2026-11-03: rewritten so it is true against the built code)*:
  - **Rule:** no module reads a restore-flag value off the parsed namespace except the two permitted readers — `cli/__init__.py`, whose pre-Run `check_restore_arguments(...)` call (E002-S02-011) reads `args.cleanfirst`, `args.drop_database` and `args.force` today, and `cli/restore.py`, the restore root (E003-S02-006). A read is an `ast.Attribute` in load context whose `attr` is one of the flag `dest`s, and which is not the `func` of an `ast.Call` (so `DatabaseCommand.drop_database(...)` calls are not reads).
  - **Scope, derived, not listed:** the flag `dest`s are `domain/flag_map.py::COVERED_FLAGS` minus `mode` — `cleanfirst`, `drop_database` and `force` — so a dimension added to the table is covered without editing the test; `mode` is left out because `backup` legitimately reads `args.mode` for its Backup Scope, which this rule must not forbid. The modules are every `*.py` under `src/l3io/wp/backup/`, found by walking the tree (not `pkgutil`), asserted non-empty.
  - **Not covered, stated in the test's docstring:** `getattr(args, "force")`, `vars(args)["force"]` and a namespace passed whole to a helper that reads it.
  - **Planted violations**, each in a temp copy of the tree: `args.drop_database` in an `adapters/` module, `ns.force` (a namespace not called `args`) in a `core/` module, and `args.cleanfirst` in `cli/backup.py` — each fails the rule; `cmd.drop_database(location, confirm="x")` in an `adapters/` module does not.
- **The guard is pure and lives in `core/restore.py`.** `check_target(mode: RestoreMode, overrides: OverrideSet, target: TargetState) -> None`, called by `build_restore_plan` (story 3.1) before any phase is planned; `mode` has no default (AD-5, `tools/check_mode_defaults.py`). It raises `NonEmptyTargetError(RefusedError)` (defined in `core/restore.py`) with structured fields `parts: tuple[RestorePart, ...]` (E002's `Literal["files", "database"]`; one or both, so one refusal names every unauthorized part — the edge case below) *(E003 pre-build re-check 2, 2026-11-03)*, `found: str` (the canonical Site Root, or `host:port/db_name`), `detail: str` (entry count or table count), `authorizing: FlagCombination` *(E003 pre-build re-check, 2026-11-03)*. `authorizing` is E002's `domain/flag_map.py::authorizing_combination(mode, part)` — the table's own inverse lookup, never typed into the message. `core/` renders it in the **domain** spelling only (`mode=database cleanfirst force`); `cli/restore.py` translates it to the CLI spelling (`--mode db --cleanfirst --force`) through `cli/scope.py::CLI_MODE_TO_SCOPE`, the one place `db` and `database` meet (E003-S02-006), because `core/` cannot import `cli/` and the parser rejects `--mode database` *(E003 pre-build re-check, 2026-11-03)*.
- **Specificity.** The waiver for `files` and the waiver for `database` are separate `OverrideSet` members; `check_target` checks each part the mode touches against its own member. A mode touching both parts with only one waiver refuses for the other part, naming it.
- **`TargetState` inputs, from query ports only.** `site_root_empty`: the Site Root contains no entry other than those the Archive's own `wp-config.php` placement rule excludes — exactly "no directory entries" unless E002's descriptor says otherwise; computed by `SiteFilesQuery.is_empty(site_root)`. `database`: E002-S02-012's `DatabaseTargetState` for the **live** database, from `DatabaseQuery.survey_target(site.database_location(), table_prefix=..., wordpress_user=...)` with the bound administrator source (E003-S02-004) (`database_exists`, `table_count`) — never the staging name, which does not exist yet. `load_target: DatabaseTargetState | None`: when `relocation.load_database` (`--new-db-name`, E003-S01-001) is set, the same survey of that database at its load location, else `None`; the guard refuses for `database` when either is non-empty *(Gate AG-12, 2026-10-28)*. A database that exists with `table_count == 0` is empty for this guard; one that does not exist is empty. **The facts the refusal names** come from the same query results, as `TargetState` fields this story adds *(E003 pre-build re-check, 2026-11-03)*: `site_root: PurePosixPath` (the canonical Site Root, `SiteDescriptor.site_root`), `site_root_entries: int` (`SiteFilesQuery.entry_count(site_root)`, E002's built query), `database_location: DatabaseLocation | None` and `load_location: DatabaseLocation | None` (the locations the two surveys addressed), so `check_target` builds `found` and `detail` from its own argument with no further read.
- **Mapping to exit codes.** `NonEmptyTargetError` is a `RefusedError`, so E002-S01-005's `cli/exit.py::exit_code_for` maps it to `ExitCode.REFUSED` with no new arm — E002-S01-005's docstring already records "FR-7 … refusals → `REFUSED`". This story adds no `ExitCode` member.

### Error and edge case handling

- `--cleanfirst` without `--force`, non-empty Site Root: `REFUSED`, naming `--force` (AD-25's worked case); the recording command log is empty.
- Non-empty Site Root, no flags, mode `all`: `REFUSED` for `files`, naming the authorizing flag; the database is not contacted beyond the `survey_target` query *(E003 pre-build re-check, 2026-11-03)*.
- Both parts non-empty, only one authorized: `REFUSED` naming the unauthorized part. When both are unauthorized, both are named in one refusal (one exit, one message, two `part` entries), so the operator does not discover them one Run at a time.
- Empty Site Root and absent database: no refusal, no override needed.
- Site Root does not exist: E002's `resolve(strict=True)` fails first → `InvalidSiteDescriptorError`; never treated as "empty".
- Site Root is a symlink to a non-empty directory: canonicalised by E002 before the check, so the target's real content is checked.
- Site Root unreadable (permission denied while listing): refuse (`REFUSED`, `detail` naming the error) — an unknown state is never "empty" (NFR-1).
- Database survey cannot run (no admin credentials, unreachable): the error from story 3.4 (`CREDENTIALS` / `UNREACHABLE`), never "empty".
- Dry Run: the guard runs for real (it consumes only query results), so `--whatIf` refuses with the same code and message.
- A flag combination with no table entry is unreachable at runtime because E002's `tests/contracts/test_flag_map.py` derives its scope from the parser; this story adds no fallback for it.

### Observability requirements

- Refusal logged once as ERROR `restore_refused` with `reason: "non_empty_target"`, `parts` (list), `found`, `detail`, `authorizing` (the CLI spelling `cli/restore.py` renders, E003-S02-006), `restore_mode`; the same facts in the stderr message *(E003 pre-build re-check, 2026-11-03)*.

### Security considerations

- The refusal names paths and the database `host:port/name` only — never a username or password; covered by E002-S01-006's `credential_sentinel` applied to the refusal path.
- The guard runs before the Safety Snapshot and before any command adapter, so a mistyped `--wp-dir` pointing at a live site is refused without that site being read beyond a directory listing and an administrator `survey`.
- Site Root listing does not follow symlinks out of the Site Root and does not read file contents.

## Dev notes (2026-11-03)

Deviations from the technical ACs, each following the built code:

- **Observability is E003-S02-006's.** `core/` is pure (`tools/check_purity.py` forbids `structlog`), and `restore_refused.authorizing` is the CLI spelling, so neither `restore_refused` nor `target_checked` is emitted here. Both are now recorded in E003-S02-006's Observability section, with their full field lists. `NonEmptyTargetError` carries `.findings` (a `(where, what)` pair per non-empty target) beside the joined `.found`/`.detail`, so that log needs no re-splitting.
- **Unreadable Site Root.** E002's `LocalSiteFiles` raises `InvalidSiteDescriptorError` (`FAILED`) on a listing `OSError`, so the state is never treated as empty (NFR-1 holds), but the exit is not `REFUSED`. Changing E002's adapter is outside this story; the decision is BL-E003-034.
- **`TargetState` fields are required, not defaulted**, so the root (E003-S02-006) cannot omit the facts a refusal names. Every existing constructor was updated. The plan-shape suites build over a populated target with every refusal waived (`tests/restore_builders.py::WAIVED`, `Harness.overrides`).
- **`authorizing` is one combination.** It is `authorizing_combination(mode, parts[0])`; `test_one_combination_authorizes_every_part_a_mode_restores` pins that, for every Mode, one table row waives every part that Mode restores.
- **Domain spelling.** `core/restore.py::render_flags` renders `mode=files cleanfirst force`; E003-S02-006 plans a CLI-spelling function with the same name in `cli/restore.py`.
- The integration suite `tests/integration/test_restore_refusal.py` skips here (no MySQL); it covers every non-`--force` row of `FLAG_MAP`.
