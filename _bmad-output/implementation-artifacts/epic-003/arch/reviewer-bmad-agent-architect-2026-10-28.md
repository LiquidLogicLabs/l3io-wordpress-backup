# Architect review — E003 "Restore a site without destroying it" (arch gate, step 04)

- **Reviewer:** `bmad-agent-architect` (Winston), headless; lens: design coherence, story quality, artifact completeness
- **Date:** 2026-10-28
- **Scope:** 6 stories — `epic-003/sprint-01/stories/E003-S01-{001,002,006}.md`, `epic-003/sprint-02/stories/E003-S02-{003,004,005}.md`
- **Independence:** no other reviewer file in `epic-003/arch/` was opened.
- **Counts:** 2 BLOCKER, 13 MAJOR, 15 MINOR

The overall shape is sound. The plan is a pure filter of `RestorePhase`. Dry Run is adapter selection. The Snapshot joins the Run. The staging cutover is the last journaled step of `LOAD_DUMP`. Epic 7 reaches restore through named seams and a single granted import line. Most defects sit between stories: one story assumes a value or a call that another story never provides. Two of them reach the safety guarantee itself.

## Findings

BLOCKER: Sprint 01 cannot meet its own acceptance criteria without sprint 02 modules. E003-S01-001 §Interface contracts L95 makes the runner's `LOAD_DUMP` "E003-S02-005's staging", and L59 makes `database-clean`/`all-clean` loser removal "(3.5)". Its own §Non-goals L46 says it does not implement them, yet its §Testability L153 (`test_restore_modes.py`, every mode against a CI database) needs a working `LOAD_DUMP`. In E003-S01-006, step 2 (L60) constructs `adapters/journal.py`'s pair (created by E003-S02-005), and step 7 (L65) builds `take_snapshot` from the snapshot scope and location rules (created by E003-S02-003). Its §Testability L142 requires one integration case per FR-6 row plus the unencrypted-Snapshot warning. Sprint 01 would also ship `EXTRACT` without E003-S02-005 L78's `wp-config.php` exclusion, so the live config would be overwritten non-atomically, which AD-18.2 forbids. Options: move E003-S01-006 into sprint 02 after 003–005; or restrict sprint 01's integration criteria to file modes and plan-only database modes, with database modes refusing `UnboundAdapterError` until sprint 02; or move E003-S02-005's staging and journal into sprint 01. As written, a sprint-01 dev loop cannot go green.

BLOCKER: For a Run killed during or after the cutover, the journal's undo text tells the operator to drop the database the site now runs on. This violates AD-18.1 ("naming … what would undo it"); spine#ad-18. In E003-S02-005 L107, `IncompleteRunError.undo` "is that entry's `undo`": the last `phase_started` entry without a `phase_completed`. E002-S02-012's `JournalEntry.undo` exists only on `phase_started`, and `step_completed(phase, step)` carries no undo. The cutover and loser removal are steps inside `LOAD_DUMP`, so a kill after `cutover:DB_NAME` reports `LOAD_DUMP`'s undo from the L103 table: "live site untouched; drop staging database `<staging>`". The staging database is now live. E003-S02-005 L130 and L145 state the intended step-aware undo, but the data model and the L107 derivation cannot produce it. The L100–105 table also lists "cutover" and "loser removal" as rows of a `match` over every `RestorePhase`, and neither is a `RestorePhase` member. Fix: derive the undo at read time in `core/restore.py` from `(interrupted phase, last step_completed, header)` instead of storing it on `phase_started`. Make that the one `undo_for`, then reconcile its signature with E003-S01-001 L89 `undo_for(phase, header, relocation)`. The kill harness (L199–204) should assert the reported undo text for each *k*, not only the refusal.

MAJOR: `PREFLIGHT` and `VERIFY` are run twice, and the plan's own tools are never preflighted, which conflicts with spine#ad-13 ("preflight for every tool the *plan* requires"). E003-S01-006 L62–L64 runs `PREFLIGHT` (step 4) and `VERIFY` (step 5) before `build_restore_plan` (step 6), because the plan needs `view`. E003-S01-001 L59 then puts `PREFLIGHT` and `VERIFY` "in every plan", and L62 has the runner's `VERIFY` call `verify_archive` again. The result is a second full Archive read, duplicate `phase_completed` records, and no answer to which one emits them. `plan.required_tools` (relocation tools plus `extra_tools`, E003-S01-001 L88) exists only after step 6, after `PREFLIGHT` has run. So the passphrase backend that E003-S01-006 L70 calls "the only route" to preflight is never checked before the first effect. Decide one of two: either the root's steps 4–5 are the only `PREFLIGHT`/`VERIFY` and the runner skips them, or the plan is built from a pre-plan probe and the runner owns both. In either case, `plan.required_tools` must be checked before `SNAPSHOT`.

MAJOR: `SnapshotPolicy.SKIP` cannot reach the plan. E003-S02-003 L64 says "`SKIP` removes `SNAPSHOT` from the plan", but `build_restore_plan(site, mode, overrides, view, target, *, relocation, extra_tools)` (E003-S01-001 L58, L88) takes no `SnapshotPolicy`, and `RestorePlan.snapshot_scope` comes only from `snapshot_scope(mode, target)`. `undo_for`'s "opted out by `<flag>`" (E003-S02-005 L102) needs the same fact. Add a required `snapshot: SnapshotPolicy` parameter with no default (AD-5 style) to `build_restore_plan`, plus a field on `RestorePlan`.

MAJOR: The plan-to-executor contract is incomplete. `RestorePlan(mode, phases, snapshot_scope, required_tools, actions)` (E003-S01-001 L58) and `execute_restore(plan, ports, take_snapshot, journal)` (L61) do not carry what the runner's arms use: `relocation` (`lay_down_config`, `rewrite_values`, `search_replace`, `load_database`, `load_location`, `config_file`; L92–95, E003-S02-005 L125–129), the `SiteDescriptor` (site root, `database_location()`, `table_prefix`), the `ArchiveView` and source for `extract`/the Dump stream, the `run_id` for `staging_name`, and the `JournalHeader`. Separately, E003-S01-001 L89 says a missing undo text raises "at plan time", but undo text needs the header (snapshot path, staging name), which the plan never receives. Name the carrier explicitly, either on `RestorePlan` or as a frozen `RestoreInputs` beside it, before two sprints each invent one.

MAJOR: The Run Journal lifecycle has no owner, and its "orderly failure" rule can unblock a half-restored site. No story says who calls `begin_run`/`finish_run` or when the frozen `JournalHeader` is built. The header includes `snapshot_path` (needed for the CLEAN/EXTRACT undo) and `prior_constants`, yet E003-S01-001 L107 says no journal entry exists before `VERIFY` passes, and the snapshot path exists only once `SNAPSHOT` runs. E003-S02-005 L96 files `finish_run` to `failed/` (non-blocking) whenever any `phase_started` lacks its `phase_completed`. That contradicts E003-S01-001 L112 ("Run Journal is left unresolved" after any failure past the first destructive phase) and E003-S02-005 L77 and L148 ("journal stays blocking"). An executor or root `finally` that calls `finish_run` after a failed `CLEAN`/`EXTRACT`/cutover would release the block on exactly the state AD-18 exists to catch. Specify: header built by the root before `SNAPSHOT`, with a precomputed snapshot path; `begin_run` before `SNAPSHOT`; `finish_run` called only on success or on the named orderly failures (failed post-load check, cutover read-back failure with original intact); and every other failure leaves `current.json`.

MAJOR: Journal resolution has no port, escapes Dry Run, and the cutover-completing variant runs before the adapters exist. E002-S02-012's `RunJournalCommand` has `begin_run/phase_started/step_completed/phase_completed/finish_run`, and no resolve. E003-S01-006 step 2 (L60) and E003-S02-005 L108 move `current.json` to `resolved/` through the concrete `adapters/journal.py` pair, built before step 3's `dry_run_adapters` wrap. So `--whatIf --resolve-interrupted-run <id>` really resolves, which breaks AD-4 and E003-S01-001 L154's "journal directory unchanged". E003-S01-006 L88 and E003-S02-005 L144 make cutover resolution re-read the config and write the pending `DB_*` keys, including `DB_PASSWORD` from the relocated source. That needs `ConfigQuery`/`ConfigCommand`, the descriptor and Epic 7's `wordpress_spec`, none of which are bound at step 2 (bind is step 3; ADR-0016). This is a spec-gap against E002-S02-012: add `resolve(run_id, resolved_by)` to `RunJournalCommand`, with a no-op twin, and move the resolution branch after the bind.

MAJOR: After a later phase fails, the Safety Snapshot path has no carrier. E003-S01-006 L126 ("printed on stdout … even on failure of a later phase") and E003-S02-003 L93 ("its path is repeated in the failure message") need the path when `drive_restore` raises. MAJOR: A Dry Run fails at `SNAPSHOT` where the real Run would not (spine#ad-4). E003-S02-003 L61 runs `verify_archive` on the published snapshot path and requires `VERIFIED`. ## Carried items

**1. Run Journal location under `--snapshot-dir` (E003-S02-005 L113 OPEN vs E003-S02-003 L65). The decision is Shawn's.**
The conflict is real: E003-S02-003 L65 follows spine AD-18.1's literal "written to the Safety Snapshot's directory", while E003-S02-005 L106 always uses the per-Site default directory. Two facts weigh on the choice. First, the journal must be found by the *next* Run, which may not pass the same `--snapshot-dir`. Second, under `--no-safety-snapshot` there is no snapshot directory at all, so AD-18.1's wording has no referent for opted-out Runs. Options:
- (A) The journal always lives in the per-Site state directory (`user_state_path/…/sha256(site_root)`), with the actual snapshot path recorded in `JournalHeader.snapshot_path`. Amend AD-18.1's wording and delete E003-S02-003 L65's sentence. This is the simplest option, works for `SKIP`, and is discoverable without flags.
- (B) The journal follows `--snapshot-dir`, and the per-Site directory holds a small pointer file naming it. Discovery works, but there are two durable writes per phase and a pointer that can dangle if the operator removes the directory.
- (C) The journal is written to both directories. This gives redundancy at double the fsync cost and leaves two records to reconcile on resolution.
- (D) `--snapshot-dir` is honoured for the Snapshot only, and the journal location is not configurable. This is option A plus a help-text statement.

Assessment: only A or D satisfy discovery and `SKIP` without new mechanism. Each needs a one-line spine amendment so the text stops disagreeing with the code.

**2. ADR-0017 Concern: absolute and outward symlinks under AD-11's `filter="data"`. The decision is Epic 3's and AD-11's, and was not made by any E003 story.**
Currently such an Archive verifies, then aborts mid-`EXTRACT`. In clean Modes that happens after `CLEAN`, so the Site is left wiped and partly extracted; the journal blocks and the Snapshot is the only way back. A site carrying such a link also produces a Safety Snapshot that verifies but cannot be restored. Options:
- (A) Refuse at plan time. `build_restore_plan` scans the `ArchiveView` members (`kind == SYMLINK`, `link_target` absolute or resolving outside its role root) for the roles being extracted and raises a `RefusedError` naming the links, before `SNAPSHOT`. v0 Archives get the same check from the tar headers `verify_archive` already reads. This is safe and simple, but makes such sites unrestorable by this tool.
- (B) A restore-side filter that wraps `tarfile.data_filter`. It skips only `AbsoluteLinkError`/`LinkOutsideDestinationError` members, reports them in `ExecutionReport` and as a WARNING, and extracts the rest. This must stay inside E002's single `extract_archive` (an Epic 2 change requested by Epic 3), and it must not widen containment for any other member type. The site restores without the links, which the operator recreates.
- (C) Refuse at backup time (an Epic 2 / ADR-0017 change). Such sites could then not be backed up, and every destructive restore against them would fail at `SNAPSHOT` unless `--no-safety-snapshot`.
- (D) Combine A and B: refuse by default, and skip-and-report behind an explicit restore option (AD-22 permits a new flag). The safe default is kept and there is an escape hatch.

Assessment: whichever is chosen, the check belongs before `SNAPSHOT`, and the Safety Snapshot path needs the same treatment. Otherwise FR-8's reversibility claim is false for exactly these sites. Leaving it undecided is the MAJOR finding above.
