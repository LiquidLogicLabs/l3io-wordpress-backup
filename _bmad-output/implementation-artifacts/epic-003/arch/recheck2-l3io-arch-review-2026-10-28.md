## New findings

MAJOR: Stale contract (§ design-by-contract / single source of truth). The **Decision** section of `docs/adr/0020-restore-undo-derived-at-read.md` was not amended. L42–46 still says the cutover keys are journaled only as `"cutover:<KEY>"` and the loser only as `"loser_dropped"`. L50–55 still says "Before the first `"cutover:*"` step, the undo names the staging database to drop" — the exact AG-1 defect. Only the Consequences bullet (L69–74) mentions the intent steps, so the normative text of the ADR contradicts E003-S02-005's undo table (L112, L115) and its L101 rule. Remediation: rewrite L42–55 to name `"cutover_started:<KEY>"` and `"loser_drop_started"`, and change the boundary to "before the first `"cutover_started:*"` step". Add the `loser_drop_started` outcome ("may be partly or fully dropped") beside "retained"/"dropped".
MINOR: The orderly-failure predicate is ambiguous now that intent steps exist. ADR-0021 L55 says "no cutover step completed", and `"cutover_started:<KEY>"` is also a completed step. E003-S01-001 L164 builds its read-back orderly sequence as `"cutover_readback_failed"` + `"staging_dropped"`, without the `"cutover_started:<KEY>"` entry the real slot always writes before that failure. A predicate that matches every `"cutover*"` step would therefore pass sprint 01 and fail only in E003-S02-005's `test_staging.py`. Remediation: ADR-0021 should say `"cutover:*"`, not "cutover step". The `test_orderly_failure.py` read-back sequence should include `"cutover_started:<KEY>"` and assert it stays orderly.
MINOR: E003-S02-005 L101 contradicts its own table. L101 says "After the first `"cutover_started:*"` step the text never names `header.load_database` as something to drop". But the read-back failure path journals `"cutover_started:<KEY>"` and then `"cutover_readback_failed"`, and the table row for `"cutover_readback_failed"` (L110) correctly says "drop staging database `<load_database>`". L159 relies on this when the staging drop itself fails. Remediation: scope the sentence to "after a `cutover_started:*` step not followed by `cutover_readback_failed`", or phrase it as the harness does (L215: "never names the now-live database").
MINOR: The coverage claim is overstated (CLAUDE.md §3). ADR-0020 L71–74 says "Every effect whose interruption changes the undo is therefore preceded by an intent step". The `EXTRACT` config lay-down (E003-S01-001 L102) is not: `SiteFilesCommand.extract` runs before `step_completed(EXTRACT, "config")`, and `undo_for` does not receive the `phase_started` target `"config:<path>"`. A kill in that window reports "restore files from Safety Snapshot" instead of "remove `<path>`". The harness also wraps only `ConfigCommand` and `restore_database_command`, not `SiteFilesCommand`, and its `all-clean` recording does not lay down a config. Remediation: either add a `"config_started"` intent step (and wrap `SiteFilesCommand`), or narrow the ADR sentence to the `LOAD_DUMP` effects and state the lay-down window as uncovered.
MINOR: A shared type has no declaration. `load_staged(..., *, ports: RestorePorts)` (E003-S02-005 L66) now makes `RestorePorts` a cross-sprint contract, but no story states its module or fields. E003-S01-001 L106 only says it "names" `restore_database_*` "for every load-side call", which is stale now that the executor makes no load-side calls itself. `RestorePorts.cutover_credentials` (E003-S02-005 L78; E003-S02-006 L87, L154) has no declaring story. It must not live in `core/`, because it holds `ports/` Protocols. Remediation: declare `RestorePorts` in E003-S01-001 (in `adapters/restore_runner.py`) with its full field list, `cutover_credentials` included, and drop the "every load-side call" wording. Also noted, already present before this commit and now visible in one story: `build_restore_plan` passes `snapshot_dir: Path`/`config_dir: Path` to `snapshot_location(...: PurePosixPath)`, and `Path` is not a `PurePosixPath` under `mypy --strict`. Align the annotations when fixing this.
