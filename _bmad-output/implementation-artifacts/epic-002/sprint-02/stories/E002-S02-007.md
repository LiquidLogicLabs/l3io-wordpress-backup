# E002-S02-007: Rehearse any destructive operation


**Implements:** FR-19


As an operator,
I want to see what a backup would do before it does it,
So that I can check the plan against a production site safely.

**Acceptance Criteria:**

**Given** a backup run as a Dry Run
**When** it runs
**Then** credential resolution, preflight and planning all execute for real
**And** the actions it would take are reported in order
**And** the Site and the Storage Target are unchanged afterwards — the `ArchiveStore` command adapter is a no-op
**And** the plan is equal across the real and the no-op adapter sets
**And** no `if dry_run:` conditional exists anywhere outside a composition root — a Dry Run binds real queries and no-op commands (AD-4)

*(The restore half of FR-19 — "what a restore would do" — is Epic 3's, AG-29.)*

## Business acceptance criteria

### Outcome

`wpbackup2 --whatIf backup --wp-dir <Site Root>` (and the library equivalent, `BackupRequest(dry_run=True)`) resolves credentials, runs preflight and database dump readiness, runs every query the plan depends on for real, and reports, in order, the actions a real backup would take — then exits with the code the real backup would have had at that point, leaving the Site, the database and the Storage Target byte-identical. It does not dump the database, read or hash Site Root file contents, encrypt, write, stage, verify or publish an Archive (ADR-0019). A Dry Run that would be refused by a query reports the refusal exactly as the real Run would. This works because a Dry Run binds the real query adapters and no-op command adapters; no `dry_run` conditional exists outside a composition root. A reviewer can tell it happened by diffing the Storage Target directory and the database checksum before and after, and comparing the reported plan with a real Run's plan against the same site.

### Non-goals

- The restore half of FR-19 — Epic 3 story 3.1 (AG-29). The restore halves of the ports, `SiteFiles*`, `Config*`, `SearchReplace`, the Run Journal ports and their no-op twins — E002-S02-012. Their real implementations — E002-S02-009.
- Verifying an Archive in a backup Dry Run: there is none and none is produced. FR-19's "a Dry Run performs Verification" applies to the restore path (ADR-0019). Failures that appear only while writing (disk full, a file unreadable mid-stream) are not detected; the report says it is a plan, not a rehearsal of the write.
- WP-CLI availability checks and relocation planning — restore-only (Epic 7); backup invokes no WP-CLI.
- The generic preflight adapter for external binaries — Epic 5 story 5.2 (`adapters/preflight`). This story defines the port and binds the check that exists today.
- Dry Run spans — Epic 6 (triage E-8).
- Renaming `--whatIf`: its spelling is frozen (triage E-7); a `--what-if` alias is added here.

## Technical acceptance criteria

### Interface contracts

- **Every port splits into a query half and a command half (AD-4, AG-12).** Convention for `ports/`: each capability is two `typing.Protocol` classes named `<Capability>Query` and `<Capability>Command`. A query never changes the Site, the database or a Storage Target; a command may. Protocols that are neither carry a one-line justification on the **single-role allowance** in `ports/__init__.py`'s docstring: `ArchiveProbe`, `Clock` (queries), `Preflight` (query), `MemberCipher` (transform), `ExclusionPolicy` (pure query), `Tracer` and `RunSpan` (observation). E002-S02-008 adds `SiteLock`. This story makes the convention a test (below).
- **The archive-writer command port (ADR-0019).** `ports/archive.py::ArchiveWriterCommand(Protocol)`: `write(out: IO[bytes], *, site_root: Path | None, dump: Path | None, config: Path, exclusion: ExclusionPolicy, cipher: MemberCipher | None, manifest_builder: Callable[[tuple[ManifestMember, ...], tuple[ExcludedEntry, ...]], Manifest]) -> Manifest` (`site_root=None` for a `database` scope, `dump=None` for `files`). Collection, encryption and the write happen behind it. `adapters/tar.py::TarArchiveWriter` is the real implementation and calls E002-S01-010's `collect_site_root` and `write_archive` unchanged, emitting the `COLLECT_SITE_ROOT`, `ENCRYPT` (encrypted path) and `WRITE_ARCHIVE` phase records. E002-S01-010's `execute_backup_plan` gains `writer: ArchiveWriterCommand` and **stops calling `collect_site_root` and `write_archive` directly**, so a Dry Run has no unguarded effect to reach.
- **What each backup step is bound to.** `DUMP` → `DatabaseCommand.dump_to`; collection, `ENCRYPT` and `WRITE_ARCHIVE` → `ArchiveWriterCommand.write`; `VERIFY` and `PUBLISH` → inside `ArchiveStoreCommand`'s `StagedArchive.publish()` (E002-S01-010). The existing-final-name check is `ArchiveStoreQuery.exists`, a query, so it runs for real.
- **No-op command adapters, `adapters/noop.py`.** One per `*Command` Protocol, named per the Consistency Conventions. Each satisfies its Protocol (mypy, and `isinstance` against `@runtime_checkable` Protocols), performs no effect, records the call into an `ActionLog`, emits `phase_completed` with `outcome="skipped_dry_run"` and `bytes=0`, and returns a value of the declared type that lets the plan continue: `NoopDatabase.dump_to` → `DumpResult(bytes=0, duration_ms=0.0)`, writing nothing; `NoopArchiveWriter.write` → the `Manifest` built from an empty index, reading no Site Root file and writing nothing to `out`; `NoopArchiveStore.stage` → a `StagedArchive` whose stream is an `os.devnull` writer and whose `publish()`/`discard()` do nothing — no verifier is called (AD-21 holds; nothing accumulates in memory).
- **`AdapterSet` (E002-S01-004) gains `archive_writer: ArchiveWriterCommand`**; `real_adapters(...)` binds `TarArchiveWriter()`. **`cli/adapter_sets.py::dry_run_adapters(real: AdapterSet) -> AdapterSet`** — the only other constructor — returns a set that reuses the **same** query instances and the same `tracer` as `real` and substitutes only the command halves (`archive_store_command`, `database_command`, `archive_writer`) with their no-ops. E002-S02-012 extends it for the fields it adds.
- **Selection, only at the composition root.** `BackupRequest` (E002-S01-004) gains `dry_run: bool = False`; `drive_backup`, when it opened the Run, binds `dry_run_adapters(real_adapters(...))` when `request.dry_run` and `real_adapters(...)` otherwise. `open_run` gains `dry_run: bool = False`, bound as a context variable and passed to `tracer.run_span(dry_run=...)`. A joined Run inherits the outer root's selection (ADR-0016). `dry_run` / `what_if` appear only in `cli/` and `api/` — the existing CI step "AD-4 no dry-run conditionals" greps for this and stays as is.
- **Preflight (AD-13, AG-20).** `domain/preflight.py` (pure): frozen `ToolRequirement(name: str, minimum_version: tuple[int, ...] | None, needed_for: str, install_hint: str | None = None)` — `install_hint` is the last field and its only default — and frozen `ToolStatus(name: str, present: bool, version: tuple[int, ...] | None, path: str | None, error: str | None = None)`, `error` set when the tool was found but probing it failed (e.g. `"exit 127"`). They are in `domain/` because `core/backup.py` names `ToolRequirement` and the import-linter contract forbids `core/` → `ports/`. `ports/preflight.py::Preflight(Protocol)`: `check(requirements: Sequence[ToolRequirement]) -> Sequence[ToolStatus]`, a query. `BackupPlan` (E002-S01-010) gains `required_tools: tuple[ToolRequirement, ...]`, derived from its steps. The composition root runs preflight for every requirement **before the first command adapter is called**, in both a real Run and a Dry Run; a missing, too-old or unusable tool raises E002-S01-001's `PreflightFailedError` with `found` = `"absent"`, the version found, or `"unusable (<error>)"`, and `install_hint` passed through — never folded into `needed_for`. For E002 the `DUMP` requirement is satisfied by `DatabaseQuery.check_dump` (database's `check_dump` at v0.2.0, so the client-tool check stays database's): a `Readiness` blocker `UNREACHABLE` raises `DatabaseUnreachableError`, any other blocker raises `PreflightFailedError` naming the finding codes. Until Epic 5 supplies `adapters/preflight`, the root binds a `Preflight` that consults only `check_dump` for the dump step.
- **The plan is data, and is what a Dry Run reports.** `cli/backup.py` renders the `BackupPlan` in order on stdout — e.g. `1. resolve credentials from wp-config:<path>`, `2. check dump readiness (DatabaseQuery.check_dump)`, `3. dump <db_name> from <host>:<port>`, `4. collect files under <Site Root> (exclusions: <source>, <k> patterns)`, `5. write Archive`, `6. verify`, `7. publish to file:<path>` — and logs each as `planned_action` (with `exclusion_source` and `exclusion_patterns` on the collection line). No line names a MySQL client binary (ADR-0015). A real Run executes the same `BackupPlan` value.
- **CLI.** `--whatIf` (dest `what_if`, top-level, as v0.2.21) is wired to `BackupRequest.dry_run`; `--what-if` is added as an alias of the same action (triage E-7). Restore's use of it is Epic 3's.

### Error and edge case handling

- A Dry Run against a site whose credentials fail, whose database is unreachable, or whose `check_dump` verdict blocks: exits with the same `ExitCode` the real Run would, after reporting the actions planned up to that point; it does **not** report "would back up".
- A Dry Run whose Storage Target final name already exists: `ArchiveExistsError`, exactly as the real Run (the check is a query).
- A Dry Run with an unsupported Storage Target scheme: refused at parsing, identical to the real Run.
- `--mode files` Dry Run: no credential resolution and no database preflight, matching the real `files` plan (E002-S01-002).
- Workspace: a Dry Run still creates and removes the Run workspace (Run machinery, not a Site or Storage Target write); no-op commands write nothing into it.
- A command port added later without a no-op twin: `dry_run_adapters` cannot fill the field — caught by mypy and by `test_port_split.py`.
- A preflight tool found but unusable: `found: unusable (<error>)`, distinct from `found: absent` and `found: <version>`; the `install:` line is last.

### Observability requirements

- `run_started` carries `dry_run: true|false`, bound once at the root as a context variable so every record in the Run carries it.
- Each planned action is logged as `planned_action` with `step`, `ordinal` and the step's parameters (redacted per E002-S01-006).
- No-op command adapters emit `phase_completed` with `outcome="skipped_dry_run"` and `bytes=0`, never `outcome="ok"` — a Dry Run log never claims an effect occurred (triage E-8).

### Security considerations

- A Dry Run resolves real credentials (FR-19 requires it); they are registered with the Run's `SecretRegistry` and redacted as in a real Run. E002-S01-006's `credential_sentinel` is run once in Dry Run mode, covering the `planned_action` rendering.
- A Dry Run against production must be provably non-destructive: no command adapter can be reached except through the `AdapterSet`, and the executor calls no writer, dump or store function directly; the tests below assert it.

### Testability approach

- `tests/contracts/test_port_split.py`: walks every module under `ports/` (scope-asserted non-empty), collects every `Protocol`, and asserts each is named `*Query` or `*Command` or is on the single-role allowance (the allowance checked to name only Protocols that exist). Then asserts every `*Command` Protocol has exactly one implementation in `adapters/noop.py`, implementing every method, and every `AdapterSet` field whose type is a `*Command` is filled with a no-op by `dry_run_adapters` — scope from the Protocols and the dataclass fields, not a list.
- `tests/unit/core/test_plan_equality.py` — **the AD-4 plan-equality test**: for each `BackupScope` (parametrised from the enum), build the plan through the root's planning path with the real query set (database faked) and with the dry-run set, and assert the two `BackupPlan` values and the rendered action lists are equal.
- `tests/unit/cli/test_backup_dry_run_effects.py` (ADR-0019): a Dry Run against a temp Site Root and a recording database double leaves both unchanged, writes nothing at the Storage Target, reads no Site Root file's contents (an `open` spy scoped to the Site Root), and never calls `write_archive`, `collect_site_root` or the verifier (spies); an AST check over `cli/backup.py` finds no direct call to `write_archive` or `collect_site_root`.
- `tests/unit/cli/test_adapter_sets.py`: `dry_run_adapters(real)` shares every query instance and the tracer with `real` (`is`) and replaces every command half; a joined driver binds nothing and inherits the outer selection.
- `tests/unit/cli/test_preflight_order.py`: a recording `Preflight` and recording command adapters prove preflight completes before the first command call, in both modes; a failing preflight leaves the command log empty.
- `tests/unit/cli/test_preflight_failed.py`: `install_hint` renders as the last line; `error` renders `found: unusable (<error>)`; neither ever renders inside `needed_for`. The import-linter run proves `core/backup.py` imports `ToolRequirement` from `domain/preflight.py` with no exemption.
- `tests/integration/test_dry_run_backup.py` (`@pytest.mark.integration`): snapshot the Storage Target listing (names, sizes, mtimes), the Site Root tree and a `CHECKSUM TABLE` of every table; run `--whatIf backup`; assert all three unchanged, exit 0, ordered actions on stdout; then a Dry Run with wrong credentials exits `CREDENTIALS` like the real Run.
- E002-S01-005's `tests/integration/test_exit_codes_end_to_end.py` gains a second `NOT_READY` case: a preflight failure in a real Run and in a Dry Run.
- `tests/contracts/test_dry_run_gate.py`: runs the CI step's `grep` over a temp tree containing `core/x.py` with `if dry_run:` and asserts it fails, so the gate is proven to fire.

### Existing-library check

`typing.Protocol` / `runtime_checkable` express the port split; `os.devnull` is the discard sink. Dump readiness is `l3io-wp-database`'s `check_dump` (v0.2.0), not a reimplementation. Binary presence (Epic 5's generic preflight) will use stdlib `shutil.which`. No dry-run framework exists or is warranted; the mechanism is adapter selection.
