# E002-S02-009: Give restore the database, file and config operations it needs


**Implements:** FR-7, FR-9 (the operations), AD-18 items 2–4, AD-28, AD-29; ADR-0015.


As an operator,
I want restore's destructive operations performed only through the family packages that already do them safely,
So that a restore can never drop, clear or rewrite more than the plan says.

**Acceptance Criteria:**

**Given** the restore halves of `DatabaseQuery`/`DatabaseCommand`, `SiteFilesQuery`/`SiteFilesCommand` and `ConfigQuery`/`ConfigCommand` (E002-S02-007)
**When** a composition root binds the real adapters
**Then** every database operation goes through `l3io-wordpress-database` v0.1.0 and this package issues no SQL
**And** existence is answered only by the administrator (AD-29)
**And** `wp-config.php` is written only through `adapters/config_writer`, which delegates the write and its verification to `l3io-wordpress-config` and keeps the file's mode (AD-18.4)

*(Corrected 2026-10-27: the ports named above are declared by E002-S02-012 after the split, and the pinned database release is v0.2.0 (rev `48a7da9`, extra `>=0.2.0,<0.3`); the criteria hold against both.)*

## Business acceptance criteria

### Outcome

Epic 3 can restore without editing an Epic 2 module: `adapters/database.py` implements every restore-half method E002-S02-012 declares, `adapters/site_files.py` implements emptiness, clearing and extraction, and `adapters/config_writer.py` is the one caller of `l3io.wp.config.WpConfigFile` in the package. `real_adapters(...)` binds these in place of E002-S02-012's placeholders. A reviewer can tell it happened by running the adapter contract tests against the CI MySQL/MariaDB service and a temp Site Root, and by grepping `src/` for `l3io.wp.config` (imported only in `adapters/config_writer.py`; `adapters/database.py`'s read-only use of database's `WpConfigFile` is a different class) and for SQL DDL (none).

### Non-goals

- Deciding *when* any of these runs, the staging name, the journal and the cutover order — Epic 3 (stories 3.1–3.5) through `core/restore` and `adapters/{staging,journal}`.
- The ports, domain values and no-op twins — E002-S02-012.
- Relocation's key set (`WP_HOME`, `WP_SITEURL`, a new host) — Epic 7 calls this writer.
- Changing `l3io-wordpress-config`'s behaviour; this story pins the release that already keeps mode and fsyncs.

## Technical acceptance criteria

### Interface contracts

- **`adapters/database.py` — the restore halves (ADR-0015).** `WpDatabase`'s restore methods (stubs raising `UnboundAdapterError` since E002-S02-012) are implemented against `l3io-wordpress-database` v0.2.0, with the administrator source and the WordPress source bound at construction: `survey_target` → `survey(connection, admin, *, wordpress_user=..., user_host="%", table_prefix=...)`, its `Survey` copied into `DatabaseTargetState` field by field; `check_ensure` / `ensure_database` → `check_ensure` / `ensure(connection, admin, wordpress, *, user_host="%")`, `EnsureResult` copied into `EnsureOutcome` with the verdict's warning **codes**; `check_load` / `load_dump` → `check_load` / `load(connection, wordpress, source, *, replace=None)` — `replace` is never passed a value, and no decryption argument is passed, because the Dump is plain inside the payload (E002-S02-012's reconciled contract; ADR-0024); `check_revoke` / `revoke_grants` → `check_revoke` / `revoke(connection, admin, user, *, user_host="%", confirm=...)`; `check_drop_database` / `drop_database` → `check_drop_database` / `drop_database(connection, admin, *, confirm=location.name)`, returning `OperationResult.changed`. `Connection` is built from `DatabaseLocation` once, in E002-S01-001's private helper. The administrator source is built by E002-S01-006's `cli/credentials.admin_source(...)` from the `--admin-*` flags or the library's spec — never by the composition root itself (ADR-0015 amendment) — and its password is registered with the Run's `SecretRegistry` before the first call. `l3io.wp.database` stays a function-scope import (AD-8).
- **Error mapping (AD-14), to E002-S01-001's classes:** database `RefusedError` → `DatabaseRefusedError` (finding codes only); `ProvisioningError` → `ProvisioningFailedError`; `TransferError`, `CorruptDumpError` → `LoadFailedError(BackupError)` (added to `domain/errors.py` here); `AuthenticationFailedError` / `AccessDeniedError` → `CredentialsError`; `DatabaseUnreachableError` → `DatabaseUnreachableError`. Always `raise ... from`.
- **`adapters/site_files.py` — `LocalSiteFiles`** (beside `adapters/workspace.py`; no other epic claims it). `is_empty` / `entry_count` via `os.scandir`; `file_exists(path)` with `os.path.exists` semantics (follows symlinks, as PHP's `file_exists` does); `clean(site_root, *, keep)` removes each top-level entry not in `keep` with `shutil.rmtree` / `os.unlink`, never following a symlink (a symlinked directory is unlinked, not descended) and never removing `site_root` itself; it refuses with `UnsafeCleanTargetError(RefusedError)` (added to `domain/errors.py` here) when `site_root` is `/`, the user's home, or contains neither `wp-config.php` nor `wp-includes/` — a guard against a mistyped `--wp-dir`, stated as a heuristic in the docstring; `extract(..., exclude=)` delegates to E002-S01-003's `extract_archive` unchanged.
- **`adapters/config_writer.py` — the one writer of `wp-config.php` (AD-18.2, AD-18.4).** `WpConfigWriter` implements `ConfigQuery` / `ConfigCommand` over `l3io.wp.config.WpConfigFile` (`l3io-wordpress-config` **v0.1.3** from TestPyPI, the same code as v0.1.2 (`e975ca6`), carried by the `database` extra as `>=0.1.3,<0.2` (mode, owner and fsync since v0.1.1)): `set_constants` calls `WpConfigFile(path).set(key, value)` once per key, in the order given, each an atomic, read-back-verified write owned by that package (ADR-0010) that keeps the file's permission bits and owner and fsyncs file and directory before returning. `set_constants` writes no config bytes itself, implements no verification and does no `chmod` of its own. `save_copy` and `replace_file` (E002-S02-012, for `--overwrite-wp-config`) are the module's only own file writes: a `0600` fsynced copy, and a temp file in the config's directory — holding the source text with `keep` applied in memory through `l3io.wp.config.WpConfigString.set` (public in v0.1.1; adding a key to CRLF content works from v0.1.2), never the unmodified source; both the source and the temp file are read and written with `newline=""`, so the file's line endings (WordPress ships CRLF) are kept byte for byte — fsynced and `os.replace`d onto the path, keeping mode and owner and raising `ConfigWriteFailedError` rather than change the owner, as v0.1.1 does. Every real method returns `performed=True` *(Gate AG-16 and AG-5, 2026-10-28; ADR-0023, ADR-0022)*. `ReadBackError` / `ConfigWriteError` / `ConfigValueError` are re-raised as `ConfigWriteFailedError(path, key, reason, written)` — `written` the keys whose atomic write had already landed, in order — with the original file byte-identical for the failed key. A multi-key call is a sequence of atomic writes, not one transaction; the docstring says so and returns `changed` so the caller can journal per key (E003-S02-005's four-key cutover). Two behaviours of v0.1.1 are surfaced, not hidden: when the original's owner cannot be kept (the writer is neither root nor the owner), `set()` raises `ConfigWriteError` and leaves the file untouched — mapped to `ConfigWriteFailedError` naming the ownership cause, never retried by copying; and `set()` **never creates** a `wp-config.php` — writing to a target that has none is the caller's ordering problem (E003: lay down the Archive's `config` member in `EXTRACT`, then rewrite), refused with `ConfigWriteFailedError`. `read_constants` reads the restore target's config for E003-S02-005's `prior_constants`. Every `DB_PASSWORD` value passed in is registered with the `SecretRegistry` before the write.
- **Wiring.** `cli/adapter_sets.py::real_adapters(...)` binds `LocalSiteFiles()` for `site_files_*` and `WpConfigWriter(secrets)` for `config_*`, replacing E002-S02-012's placeholders; `restore_database_*` are `WpDatabase` instances as E002-S02-012 states. The `search_replace` and `journal` placeholders stay until Epic 7 and Epic 3 supply theirs.

### Error and edge case handling

- A restore-half call with no administrator source bound: `AdminCredentialsRequiredError`, before any connection (E002-S02-012).
- `load_dump` into a non-empty database: refused by database (`DATABASE_NOT_EMPTY`) → `DatabaseRefusedError`, exit `REFUSED`; nothing loaded over.
- `drop_database` of a database that does not exist: `False`, not an error; database's `LIVE_WORDPRESS_SITE` warning is logged, not swallowed.
- `clean` interrupted part-way (an `OSError` on one entry): stops, raises naming the entry, leaves the remaining entries — never continues past a failure.
- `set_constants` with an unrenderable value: `ConfigWriteFailedError(reason="unrenderable")`, file unchanged; with a key already at the value: `changed` omits it and the file is not rewritten.
- A four-key call whose third write fails read-back: `ConfigWriteFailedError(key=<third>, written=(<first>, <second>))`; the file holds exactly the first two changes.
- `wp-config.php` read-only, its directory unwritable, its owner not keepable, or absent: `ConfigWriteFailedError` naming the cause; original intact, no temporary file left behind.

### Security considerations

- The administrator password and any `DB_PASSWORD` value passed to `set_constants` are registered with the `SecretRegistry` before use; E002-S01-006's `credential_sentinel` is applied to each adapter's contract test.
- No SQL, `GRANT` or identifier quoting in this package (AD-28 is satisfied by database's escaping); `tests/contracts/test_no_sql_ddl.py` (Epic 3's name, created here because these are the call sites) scans `src/` for DDL keywords in string literals.
- A widened `wp-config.php` mode exposes `DB_PASSWORD` (NFR-3): the mode test below is the release gate for restore.

### Testability approach

- `tests/adapters/test_database_restore.py` (`@pytest.mark.integration`, CI MySQL 8.4 / MariaDB 11.4): survey of absent, empty and WordPress databases; ensure creates, then reports nothing to do; load into an empty database; load into a non-empty one is refused by database; revoke then drop; drop of an absent database is `False`.
- `tests/adapters/test_site_files.py`: `keep` honoured; a symlink to a directory outside the Site Root is unlinked and its target untouched; `/` and `$HOME` refused; an `OSError` mid-clean stops; `file_exists` true for a regular file and for a symlink to one, false for a dangling symlink; `extract(exclude={wp-config.php})` leaves an existing `wp-config.php` byte-identical.
- `tests/adapters/test_config_writer.py` — ordinary assertions against the pinned v0.1.3, no `xfail` marker: a `0640` `wp-config.php` is still `0640` after `set_constants`; an fsync spy sees the file and its directory synced before `set_constants` returns; a read-back failure (a `verify_write` double forced to fail) leaves the original byte-identical; one key per atomic write; the four-key partial-failure case above; values never appear in records; `replace_file` keeps a CRLF source CRLF and an LF source LF (byte comparison of everything outside the four `DB_*` values), writes the `keep` values (the replaced file's `DB_*` read back equal them, and no write anywhere carries the source's `DB_*` values — a write spy over the temp file), keeps a `0640` file's mode and owner, leaves the original byte-identical when the replace fails, and refuses when the owner cannot be kept; `save_copy` writes mode `0600` *(Gate AG-16, 2026-10-28)*.
- `tests/contracts/test_single_config_writer.py`: AST scan — `l3io.wp.config` is imported only in `adapters/config_writer.py`.
- `tests/unit/cli/test_adapter_sets.py` gains: `real_adapters` binds `LocalSiteFiles` and `WpConfigWriter`, and no restore-half database method raises `UnboundAdapterError`.
