## Findings

### F1: medium, correctness: a WordPress-account credential failure during `ensure_database` is reported as the administrator's
- **Location:** `src/l3io/wp/backup/adapters/database.py:691` (`ensure_database`), also `:802-805` (`_mapped` → `_refusal`). The `check_ensure` readiness path at `:632` carries the same ambiguous code.
- **What is wrong:** database's `ensure` resolves the WordPress source through `_resolve_or_finding`. A `CredentialsUnobtainableError`, `CredentialsAbsentError` or `ConfigurationError` from that source becomes a `credentials_unobtainable` blocker inside a `RefusedError`. `_mapped` was entered with `admin.source` as the label, so `_refusal` → `blocked_dump_error` raises `CredentialsError(<administrator label>)`. Reproduced: with a WordPress source raising `wpdb.CredentialsAbsentError("DB_PASSWORD not defined")` and an explicit admin, `ensure_database` raised `CredentialsError: credentials from 'explicit' unusable (credentials_unobtainable)`, with `source == 'explicit'`, which is the administrator's label. The operator is told to fix `--admin-*` when it is the site's `DB_PASSWORD` that is missing.
- **Fix:** in `ensure_database`, resolve `self._credentials` (it is already a registering source) in a `try` before calling `wpdb.ensure`, and map its failure to `CredentialsError(self._credentials.source)`. If a second resolve is unacceptable, pass a label that names both sources (`f"{admin.source} or {self._credentials.source}"`) when the blocker is `credentials_unobtainable`. Add a doubles test that pins which label is raised.

### F2: medium, error-mapping (AD-14): library errors re-raised without `raise ... from`
- **Location:** `src/l3io/wp/backup/adapters/config_writer.py:211` (`set_constants` loop) and `:322` (`replace_file` keep loop).
- **What is wrong:** `ConfigValueError`, `ConfigKeyError`, `ReadBackError` and `ConfigWriteError` are caught. The `ConfigWriteFailedError` is then raised after the handler has exited, so both `__cause__` and `__context__` are `None`. The story's error-mapping rule says "Always `raise ... from`", and the module's own docstring and AD-14 say the same. The comment at `:210` ("the cause is named by `failure`") does not justify this on secrecy grounds: every one of these library errors is value-free. `ConfigValueError` carries the type name only, `ReadBackError` carries "by key, without quoting any value", and `ConfigWriteError` carries the OS error text. The errno and the original traceback are lost to no purpose.
- **Fix:** raise inside each `except` with `from exc`, or capture `exc` and use `raise ConfigWriteFailedError(...) from caught`. Add assertions that `caught.value.__cause__` is the library error in `test_a_read_back_failure_leaves_the_original_byte_identical`, `test_an_unrenderable_value_fails_...` and `test_an_unkeepable_owner_is_refused_...`.

### F3: low, claim: `file_exists` does not have `os.path.exists` semantics
- **Location:** `src/l3io/wp/backup/adapters/site_files.py:52-54`.
- **Claim:** story Interface contracts: "`file_exists(path)` with `os.path.exists` semantics (follows symlinks, as PHP's `file_exists` does)".
- **What is wrong:** on the pinned Python 3.11, `Path.exists()` swallows only ENOENT, ENOTDIR, EBADF and ELOOP. It raises `PermissionError` on EACCES, where `os.path.exists` and PHP's `file_exists` both return `False`. Reproduced with a file under a `chmod 000` directory: `os.path.exists → False`, `Path.exists → PermissionError`. A raw `PermissionError` then crosses the port. A root CI run cannot see this.
- **Fix:** `return os.path.exists(path)`. Add a non-root-only test (skip as root) that uses a `0o000` parent.

### F4: low, guard scope: `test_single_config_writer` misses relative imports
- **Location:** `tests/contracts/test_single_config_writer.py:35` (`node.level == 0`).
- **What is wrong:** `l3io.wp` is a namespace package shared with `l3io.wp.config`. Inside `src/l3io/wp/backup/adapters/x.py`, the import `from ...config import WpConfigFile` resolves to `l3io.wp.config`. Reproduced: `WpConfigFile.__module__ == 'l3io.wp.config.adapters.config_file'`. The guard drops every `ImportFrom` whose `level` is not 0, so this spelling of the AD-18.4 import is invisible. `importlib.import_module("l3io.wp.config")` is also unseen, and the docstring does not say so.
- **Fix:** resolve relative imports against the module's package, which can be derived from `path.relative_to(PROJECT_ROOT / "src")`, then apply the same prefix test. Add a planted `from ...config import WpConfigFile` case in a nested module of `tmp_path`, laid out under a fake `l3io/wp/backup` tree. Either flag string-literal `import_module` calls naming `l3io.wp.config`, or state in the docstring that they are not covered.

### F5: low, contract: a nested `keep` path silently keeps its whole top-level ancestor
- **Location:** `src/l3io/wp/backup/adapters/site_files.py:76`, with the test codifying it at `tests/adapters/test_site_files.py` (`test_clean_honours_keep_and_never_removes_the_root`, where `keep` holds `wp-content/uploads`).
- **What is wrong:** the port (`ports/site_files.py`) says "Remove every entry but `keep`" with Site-Root-relative paths, and does not say they must be top-level. `keep={"wp-content/uploads"}` keeps all of `wp-content`, including the target's old `plugins/` and `themes/`. Epic 3 will then extract the Archive over those, leaving stale code mixed with the restored site. Nothing signals that the keep was widened, and the no-op twin cannot show it either.
- **Fix:** refuse a multi-part `keep` path with `ValueError` (a programming error, the same as `require_site_relative`), and state in the port docstring that `keep` holds top-level entries. Alternatively, honour nested paths by descending only along kept ancestors. Change the test to match.

### F6: low, guard scope: the DDL scan has spellings it does not see
- **Location:** `tests/contracts/test_no_sql_ddl.py:25-31` and `:53`.
- **What is wrong:**
  - `bytes` literals are skipped (`isinstance(node.value, str)`).
  - A statement split across f-string parts is missed: `f"DROP {kind} wp_x"` yields the constants `"DROP "` and `" wp_x"`.
  - `GRANT … ON` and `REVOKE … FROM` across a newline are missed, because `.*` is used without DOTALL.
  - Privilege and account DDL outside the listed verbs is missed: `SET PASSWORD`, `FLUSH PRIVILEGES`, `DROP`/`CREATE ROLE`.

  The docstring claims "a DDL or privilege statement's opening" without stating these limits. That runs against global rule 3: prose must not overstate its coverage.
- **Fix:** scan `bytes` constants as well, and scan the rendered `JoinedStr` with each `FormattedValue` replaced by a placeholder token. Compile with `re.DOTALL`. Add `ROLE` to the object list, and add `SET\s+PASSWORD` and `FLUSH\s+PRIVILEGES`. Plant one case of each. Whatever stays out of scope should be listed in the docstring.

### F7: low, guard scope: the `WpConfigFile` exemption is module-wide, not binding-aware
- **Location:** `tests/contracts/test_credential_sources_built_once.py:62-90` (`_config_bindings`, `_is_config_class`).
- **What is wrong:** one `from l3io.wp.config import WpConfigFile` anywhere in a module, even at function scope, exempts every bare `WpConfigFile(...)` call in that module. Before this change, the bare call was always flagged. Now, in exactly the module that holds the legitimate import (`adapters/config_writer.py`), a rebinding such as `WpConfigFile = wpdb.WpConfigFile` followed by `WpConfigFile(...)` passes. The docstring's runtime-binding caveat predates the exemption and covered only `getattr`. The exemption widens what passes unflagged without saying so.
- **Fix:** treat any `Assign`, `AnnAssign`, `arg` or other `ImportFrom` that rebinds an exempt name in the module as voiding the exemption for that name. Plant the rebinding case in `test_config_wp_config_file_is_exempt_only_by_resolved_origin`.

### F8: low, claim: `adapters/database.py` still says it alone reads `wp-config.php`
- **Location:** `src/l3io/wp/backup/adapters/database.py:8-9`.
- **Claim:** "Nothing else in the package opens ``wp-config.php`` for reading (AD-3)".
- **What is wrong:** after this change, `adapters/config_writer.py` opens it. `read_defined` is called on database's behalf, and `read_constants` reads the restore target directly, as `ports/config.py` intends. The docstring now contradicts the code and the port. AD-3's real rule is that the Site Descriptor is built only here.
- **Fix:** reword to "Nothing else in the package builds a Site Descriptor from ``wp-config.php`` (AD-3); ``WP_SITEURL``/``WP_HOME`` and the restore target's constants are read through ``adapters/config_writer``."

### F9: low, claim / reuse: "no … atomic-write code is written here"
- **Location:** `src/l3io/wp/backup/adapters/config_writer.py:335-381` (`_write_over`, `_keep_owner`, `_fsync_directory`) and `:224-263` (`save_copy`).
- **Claim:** story Existing-library check: "No SQL, PHP parsing or atomic-write code is written here."
- **What is wrong:** `_write_over` is a near line-for-line copy of `l3io.wp.config.adapters.config_file.WpConfigFile._replace_verified`, `_take_ownership` and `_fsync_directory`: mkstemp beside the file, take the owner and then the mode, write, fsync, read back, `os.replace`, sync the directory. ADR-0023 and the story's own `replace_file` contract prescribe this write, so it is not graded as a hand-rolled-library defect. It is still about 60 lines that duplicate, privately, code the family library owns and tests. The Existing-library check overstates the case.
- **Fix:** correct the story's Existing-library check so it names `save_copy`/`replace_file` as the module's own atomic writes under ADR-0023. Record an upstream request for a public whole-content replace on `l3io-wordpress-config` (for example `WpConfigFile.replace_content(text, *, verify=...)`), so `_write_over` can be deleted when that lands.

### F10: low, deletion (confidence: medium): the direct `administrator_bound` assertions were removed and not re-established
- **Location:** `tests/unit/cli/test_adapter_sets.py:376` (`test_no_wp_database_restore_method_is_unbound_and_each_checks_the_admin`).
- **What is wrong:** the replaced test asserted `not bare.administrator_bound` and `admin.administrator_bound`. The only remaining test of the property, `test_dry_run_reads_the_admin_binding_wp_database_exposes`, exercises the `True` case only. `cli/adapter_sets._administrator_bound` reads this property to decide whether the Dry Run raises `AdminCredentialsRequiredError`. A regression that made it always `True` would make a Dry Run with no administrator report success, and no test would fail.
- **Fix:** restore the two assertions, either in the new test or in a dedicated one.

### F11: low, test hazard: `clean(Path("/"))` is run for real in a root CI container
- **Location:** `tests/adapters/test_site_files.py:114` (`test_root_and_home_are_refused`, `which="root"`).
- **What is wrong:** the test calls the real destructive `clean` on `/` with an empty `keep`. CI runs it as root. A regression in `_refuse_unsafe` would wipe the CI container's filesystem rather than fail an assertion. Today both the root check and the marker check stand in the way, but the test should not depend on the guard under test to protect the runner.
- **Fix:** in that test, monkeypatch `site_files_module.shutil.rmtree` and `Path.unlink` with doubles that record the call and raise `AssertionError`, so a broken guard fails the test without touching anything.

### F12: low, error-mapping: raw `OSError` crosses the `SiteFiles` port
- **Location:** `src/l3io/wp/backup/adapters/site_files.py:42-50` (`is_empty`, `entry_count`) and `:79` (the listing in `clean`).
- **What is wrong:** a mistyped or missing `--wp-dir` raises a bare `FileNotFoundError`, and an unreadable one a bare `PermissionError`, from `os.scandir`. Every other adapter in this diff maps OS failures to a package error. `clean` does map them per entry, but not for the listing itself. Epic 3's core would surface an untyped error and an internal-error exit where a refusal or usage error belongs.
- **Fix:** wrap the three `os.scandir` calls and map `FileNotFoundError`/`NotADirectoryError` to a `UsageError` (or a `RefusedError` subclass) naming the Site Root, and any other `OSError` to `CleanFailedError` or a site-files read error, `from exc`. Add one test per mapping.
