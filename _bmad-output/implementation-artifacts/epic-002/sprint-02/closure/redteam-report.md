## Scope widening (what and why)

- `adapters/tar.py::extract_archive`, `collect_site_root` (unchanged this sprint). `LocalSiteFiles.extract` delegates to the first, and the new `TarArchiveWriter` calls the second. A restore adapter's safety is the safety of the function it delegates to.
- `adapters/store.py` (stage/publish) and `domain/storage_target.py::default_archive_name`. The new `execute_backup_plan` decides when the staged file exists relative to collection, and `drive_backup` picks the default target.
- `adapters/workspace.py::run_workspace`. The new SIGTERM handling exists to reach its `finally`.
- The installed `l3io-wordpress-config` (`.venv/.../l3io/wp/config/adapters/config_file.py`), to see how `set_constants` writes through a symlink.
- `docs/adr/0021`, `0023`; `state/issues.yaml`; `epic-002/sprint-01/closure/redteam-report.md`. Used to separate owner decisions from defects and avoid re-raising known items.

## Method notes

- Dynamic checks ran only in throwaway `/tmp` directories, which were removed afterwards. Two were run: RT-1 (backup with `--wp-dir .` from inside a fake Site Root, `--mode files`, no database), and RT-8 (`WpConfigWriter.set_constants` against a symlinked `wp-config.php`). Both reproduced. Nothing else was executed. Source was not modified.
- No live web research was run. The platform claim in RT-2 (tarfile's data filter checks a path and then opens it, and is not safe against concurrent modification) comes from the CPython `tarfile` extraction-filter documentation. It is not re-fetched here.

## Conflicts with owner decisions (reported, not reopened)

- **ADR (extraction refuses on a Python without the tarfile CVE fix):** the code is consistent (`tar.py:1076-1077`, capability check). RT-2 is a different gap: race safety, not filter presence.
- **ADR (keyless verify = consistency; `verify --authenticate` = authenticity):** the code is consistent. RT-12 notes only the operational consequence while encryption is unbound.
- **No ADR backs two security-relevant story decisions:** `user_host="%"` (RT-3) and the per-user lock namespace (RT-4). Neither is in `docs/adr/`, so they are reported as findings.

## Known open items (note only)

- **BL-E002-086:** `python -m wpbackup2` does not reach the new parser. No finding raised.
- **BL-E004-042:** E004 must build on `adapters/crypto.PassphraseCipher`. No finding raised. It is the precondition for closing RT-12.

## Checked and not raised

- **Lock file handling:** `O_NOFOLLOW`, 0600/0700, hashed name, `json.dumps` record, re-check after `mkdir` against a symlinked directory. Sound for a single user.
- **`clean()` top-level removal:** symlinks are unlinked, not followed. `shutil.rmtree` is fd-based on Linux, and a dir/symlink swap raises rather than following. `/`, `$HOME` and non-WordPress directories are refused.
- **`save_copy`:** `mkstemp` and `fchmod 0600` before the copy, atomic replace into the journal directory (ADR-0023). It stays outside the docroot.
- **`replace_file`:** owner and mode are kept by `fchown`/`fchmod` (it refuses rather than re-owns), there is a read-back check, and the temp file is unlinked on failure.
- **`JournalHeader`:** `DB_PASSWORD` cannot be journaled. The mappings are read-only after validation.
- **Dry Run:** the composition root takes the real lock, and joining a real Run as a Dry Run is refused.

## EXECUTIVE SUMMARY

This review covered E002 sprint 02 of `l3io-wordpress-backup` (Python 3.11): the backup composition root and Dry Run selection, the `flock` Site Lock, the restore vocabulary and ports, and the first real restore adapters, which create, grant and drop databases, clean and extract into the Site Root, and rewrite `wp-config.php`. Overall risk is **HIGH**, with no CRITICAL. The new code is careful at the unit level (atomic writes, `O_NOFOLLOW`, secret registration, a journal that refuses `DB_PASSWORD`), and the weaknesses are in how the parts compose with a real host.

The most dangerous finding is **RT-1**, because it is reproduced and is reached by the default invocation. A backup run from the docroot archives its own staged file and every previous Archive. Archive size roughly doubles each run until the disk fills, and each Archive puts the plaintext dump and `wp-config.php` in the web root under a guessable name.

**RT-2** is the most severe once Epic 3 wires restore. A root-run extraction into a site-writable tree turns a WordPress foothold into root, through a symlink race that the `data` filter does not close.

The most important recommendation is to treat the Site Root as untrusted, site-user-writable territory:
- refuse backup targets inside it (RT-1);
- never extract or clean as root into it, by dropping privileges or extracting to a private directory and renaming in (RT-2);
- key the Site Lock on the Site rather than the invoking user (RT-4).
