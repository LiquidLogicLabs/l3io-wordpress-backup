# Code review: E002-S02-008, the Site Lock (AD-19)

## Verdict

The six declared deviations match their justifications. The core contract holds:
- **Ordering.** `drive_backup` canonicalises with `resolve(strict=True)` before `join_or_open`. `open_run` acquires the lock after the root span and `run_started`, and before `run_workspace`, `locate_wp_config`, credentials and `bind_adapters`. The inner `ExitStack` unwinds in LIFO order, so the workspace is removed first and the lock released second, both before `set_outcome`. A refusal reaches `exit_code_for` and becomes `LOCKED` on the root span.
- **Joining.** The same canonical Site acquires nothing. A different Site, or a Run that holds no lock, acquires under the Run's ID and releases it itself.
- **Release.** The holder record is unlinked before `LOCK_UN`, and the lock file is never unlinked, so there is no inode race. There is no fd leak on the `_lock` or `_reclaim_and_record` error paths.
- **Files and errors.** The directory is `0700` (and tightened if lax), the files are `0600`, the record is read and written with `O_NOFOLLOW` plus atomic `mkstemp`/`replace`, and refusal of a lock dir inside the Site Root is checked both before `mkdir` and after `resolve(strict=True)`.
- **Libraries.** The story's chosen libraries are used: stdlib `fcntl.flock`, `platformdirs`, `json` and `hashlib`. Nothing beyond the stated scope is hand-rolled.
- **Tests.** The adapter, joining and order suites, and the signal subprocess tests, attack the stated scope. This includes a lock dir reached through a symlink, a Site reached through an alias, and a misconfigured `XDG_STATE_HOME`.

Deletion check: the old `SiteLockedError` text ("holder unknown", "run R, pid P, since S") has no remaining reader in `src/` or `tests/`. `PENDING_CASES` becoming empty keeps the disjointness assertion meaningful. `main()`'s `try`/`except Exception` is preserved around the new `with`. No dropped contract qualifies, so there are no `kind: deletion` findings.

Claims check: no functional or technical AC is contradicted by the code. F1 is an interpretation of the observability AC that conflicts with the project's correlation convention. It does not contradict the AC's text.

## Findings

### F1 — MEDIUM — observability — `src/l3io/wp/backup/adapters/lock.py:333`

**Problem.** `stale_lock_reclaimed` passes the dead holder's id as the event key `run_id=` (and its pid as `pid=`). `open_run` has already bound the current Run's `run_id` through `structlog.contextvars`, and `merge_contextvars` (first in `cli/logging.py`'s chain) uses `setdefault`, so the explicit kwarg wins. As a result, the one WARNING that matters for this Run is emitted under the **dead** Run's `run_id`:
- a log query or trace correlation by the current Run's ID misses it;
- a query by the dead Run's ID shows a warning written by a different process days later.

The refusal event `site_locked` already uses the non-colliding `holder_run_id`/`holder_pid`/`holder_started_at` keys. The test (`test_a_stale_record_is_reclaimed_with_a_warning`, `test_sigkill_leaves_a_lock_the_next_run_reclaims`) uses `capture_logs()`, which runs no `merge_contextvars`, so it cannot see the collision.

**Fix.**
- Log the previous holder as `previous_run_id`, `previous_pid`, `previous_started_at` (or reuse `**_holder_fields(previous)`, matching `site_locked`), so `run_id` stays the current Run's.
- Update both tests to assert the new keys.
- Add one test through the real processor chain (`configure_logging` with JSON output, inside `open_run`) asserting that the warning's `run_id` equals `ctx.run_id`.

### F2 — LOW — error/edge — `src/l3io/wp/backup/cli/__init__.py:46-60`

**Problem.** The SIGTERM handler stays armed for the whole `finally` chain. A second SIGTERM raises `RunTerminated` from inside cleanup, which can happen in these cases:
- `systemctl stop` followed by a supervisor's retry;
- `timeout -s TERM` combined with a cgroup-wide TERM;
- an operator pressing stop twice.

If the second SIGTERM lands while `run_workspace` is removing the workspace, removal is aborted part-way. `ExitStack` still calls `lock.release`, and the kernel frees the `flock` on exit anyway, so the lock itself is safe. A partially removed workspace, possibly holding a dump of Site data, is left in `TMPDIR`. The AC's edge case "workspace removed" then holds only for a single signal.

**Fix.** Make the handler one-shot:
- in `_terminate`, first set `signal.signal(signal.SIGTERM, signal.SIG_IGN)`, then raise;
- `_sigterm_raises`' `finally` restores the previous handler as it does now.

Add a unit test that calls `_terminate` once and asserts `signal.getsignal(SIGTERM) is SIG_IGN` inside the block.

### F3 — LOW — error/edge (race) — `src/l3io/wp/backup/adapters/lock.py:310`

**Problem.** There is a window between a new holder's `flock` succeeding (`_lock`) and its record being replaced (`_reclaim_and_record`, which includes an `fsync`). In that window, the record on disk is still a **SIGKILLed** earlier holder's. A concurrent refused Run reads it and reports `site ... is locked (held by run <dead run>, pid <dead pid> ...)`, which names a process that no longer exists. The refusal itself is correct, because the kernel decides. Only the diagnostic names the wrong holder, and that misleads an operator into killing or investigating the wrong Run.

**Fix.** In `_lock`'s refusal path, when the record's hostname is this host and `_pid_alive(holder.pid)` is `False`, treat the holder as unidentified (or append "(that process has exited; the lock is being taken over)"). This keeps PID liveness to wording only, as the AC requires. Add an adapter test that plants a dead-pid record while `held_elsewhere` holds the lock.

### F4 — LOW — security/edge (spec-level) — `src/l3io/wp/backup/adapters/lock.py:267`

**Problem.** The key is `sha256(str(resolve(strict=True)))`, which is exactly what the AC prescribes. `resolve()` does not merge every spelling of one directory:
- On **macOS** (APFS is case-insensitive by default; macOS is a stated platform via the `~/Library/Application Support` location), `/Users/x/Sites/Foo` and `/Users/x/sites/foo` resolve to different strings and so to two locks.
- On **Linux**, a bind mount gives the same Site two canonical paths.

In both cases two Runs proceed concurrently against one Site. This defeats the business AC "spelled differently ... the second refuses" for spellings outside symlink, `..` and trailing slash. The story does not claim these spellings, so this is a spec gap and not a code defect.

**Fix.** One of two:
- Key on `(st_dev, st_ino)` of the canonical Site Root: hash `f"{st.st_dev}:{st.st_ino}"`, keep the clear path in the holder record, and keep `site_root` as the join comparison key.
- Or record the limitation in the story's Non-goals and in the `adapters/lock.py` docstring.

Either way, raise it with the architect, because AD-19 fixes the key.

### F5 — LOW — testability — `src/l3io/wp/backup/cli/__init__.py:52`

**Problem.** The AC states "The previous handler is restored afterwards", and the module docstring states that no handler is installed off the main thread. No test asserts either. `tests/integration/test_exit_codes_end_to_end.py` calls `main()` in-process many times. A regression that leaves `_terminate` installed would make every later SIGTERM to the pytest process raise `RunTerminated` at a random point, and nothing would report the cause.

**Fix.** Add a unit test in `tests/unit/cli/` that:
- records `signal.getsignal(SIGTERM)`;
- runs `main([...])` with a dispatch whose body asserts `signal.getsignal(SIGTERM) is cli._terminate`;
- asserts the original handler afterwards, for both a successful and a raising dispatch;
- includes a case run from a `threading.Thread` that asserts the handler is untouched.

### F6 — LOW — testability (false-green risk) — `tests/adapters/test_site_lock.py:352`

**Problem.** `test_the_resolved_default_is_outside_the_site_root` runs under the autouse `_isolated_state_dir` fixture, which points `XDG_STATE_HOME` at a `tmp_path_factory` sibling. The test only shows that two unrelated temp directories do not nest. It is tautological and would still pass if `default_lock_dir()` ignored `platformdirs` entirely. The real guarantee is carried by the refusal tests: `test_a_misconfigured_xdg_state_home_inside_the_site_is_refused` and the symlink tests.

**Fix.** Either delete it, or make it attack scope:
- `monkeypatch.delenv("XDG_STATE_HOME")`;
- point `HOME` at `tmp_path / "home"`;
- create the Site at `tmp_path / "home" / "www"`, a Site *under* the user's home, which is the realistic layout;
- assert that `default_lock_dir().resolve()` is not inside it and that `FcntlSiteLock().acquire(site, ...)` succeeds.
