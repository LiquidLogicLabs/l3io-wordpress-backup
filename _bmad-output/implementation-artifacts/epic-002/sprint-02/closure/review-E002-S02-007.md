## Findings

### R1 — MEDIUM — defect (guard scope) — `.github/workflows/ci.yml:101-103`, `tests/contracts/test_dry_run_gate.py:39-58`

**Problem.** The AD-4 gate uses `--exclude-dir=cli --exclude-dir=api`. GNU grep
matches those against the directory *basename* at any depth, so any directory named
`cli` or `api` anywhere under the package is exempt. I reproduced it: a tree with
`src/l3io/wp/backup/core/cli/x.py` containing `if dry_run:` makes the step exit 0
(`GATE_PASSED`). `test_dry_run_gate.py` plants violations only at paths whose
ancestors are not named `cli`/`api` (`core/x.py`, `ports/deep/p.py`, …). It never
attacks the exclusion itself, so it proves the rule but not its reach (global rule 4).

**Fix.** Anchor the exemption to the two composition roots. For example:
`grep -rnE '\b(dry_run|what_if)\b' src/l3io/wp/backup --include='*.py' | grep -vE '^src/l3io/wp/backup/(cli|api)/'`
(keep the `if …; then exit 1` shape). Add a parametrised case to
`test_dry_run_gate.py` that plants `core/cli/x.py` and `adapters/api/x.py` and asserts
the step fails. The story says the step "stays as is", so record this change as a
deviation.

### R2 — MEDIUM — defect (guard scope) — `src/l3io/wp/backup/cli/backup.py:332-441`, `tests/unit/cli/test_backup_dry_run_effects.py:846,985-986`

**Problem.** The executor (`execute_backup_plan`) and the Safety Snapshot entry point
(`backup()`) both live in `cli/`, so the AD-4 grep never examines them. A
`dry_run` parameter or branch added there would pass CI. The non-destructiveness
guard meant to cover them is
`_direct_calls(cli/backup.py, EFFECTS=("write_archive", "collect_site_root"))`. Its
scope is hand-listed and covers one file and two names. It does not cover the
security AC's other two classes ("the executor calls no writer, **dump or store**
function directly"), for example `wpdb.dump`, `LocalArchiveStore(...)`,
`verify_or_raise` or `os.replace`. It does not cover other `cli/` modules either. The
code is clean today; the guard is what is incomplete.

**Fix.** Derive the forbidden set from the source of truth instead of a list:
- Assert `cli/backup.py` imports nothing from `adapters.tar` or `adapters.store`.
- Assert that every name it imports from `adapters.database` is on an explicit
  query/locate allowance, checked against that module's `__all__`.
- Add an AST check that `execute_backup_plan` and `backup` have no parameter or `Name`
  called `dry_run`/`what_if`. They are executor code, not selection code.

Plant one of each violation to show the check fires.

### R3 — MEDIUM — defect (guard scope, false-green) — `tests/contracts/test_port_split.py:2195-2201`, `tests/unit/cli/test_adapter_sets.py:2733-2739`, `tests/unit/cli/test_preflight_order.py:3374-3376`

**Problem.** All three guards decide "is this `AdapterSet` field a command?" by the
annotation's trailing text:
- `getattr(hint, "__name__", "").endswith("Command")`
- `f.type.endswith("Command")`
- `str(f.type).endswith("Command")`

A command field annotated `ArchiveWriterCommand | None`, or wrapped in any generic,
has no `__name__` (UnionType), and its string ends in `None`. All three would silently
treat it as a query. `unfilled()` would then *require* `dry_run_adapters` to copy the
real instance, so the guard would actively enforce the unsafe outcome: a real command
bound in a Dry Run. E002-S02-012 adds more fields, so this is a live risk.

**Fix.** Classify by the resolved type's constituents. Use `typing.get_type_hints`,
then `typing.get_args` for unions/`Optional`, and treat the field as a command if any
member is one of the `*Command` Protocols that `protocols(SRC, PORTS)` discovered.
That ties the field scope to the Protocol scope. Share one helper across the three
tests. Plant a `widget_command: WidgetCommand | None` field in
`test_a_constructor_that_forgets_a_command_is_seen`.

### R4 — MEDIUM — defect (fail-open) — `src/l3io/wp/backup/domain/preflight.py:1519-1524`, `src/l3io/wp/backup/cli/preflight.py:1275-1282`

**Problem.** `preflight_failure` passes a requirement that has a `minimum_version`
whenever `status.version is None` ("a version that was not probed passes a
minimum"). `DumpReadinessPreflight` never probes versions: every non-dump tool comes
back with `version=None`. So every `extra_tools` minimum is unenforced, including the
`age` minimum E008-S01-001 will add. A too-old tool passes preflight and fails later
mid-write, which is the failure AD-13 exists to prevent. The rule lives in `domain/`,
so Epic 5's real adapter inherits it: a version probe that fails to parse and returns
`version=None` without `error` is also waived silently. The technical AC says a
"too-old … tool raises".

**Fix.** Make an unknown version against a stated minimum *not* pass. Either:
- `preflight_failure` returns `found="unusable (version unknown)"` (or a distinct
  `"version unknown"`) when `minimum_version is not None and status.version is None
  and status.error is None`, or
- `DumpReadinessPreflight` sets `error="version not probed"` for requirements with a
  minimum.

If waiving is truly intended until Epic 5, log a `preflight_version_unchecked`
warning and record that in the story. Update
`test_a_tool_new_enough_or_unprobed_passes` accordingly.

### R5 — MEDIUM — claim — `src/l3io/wp/backup/cli/backup.py:431-438` (`integrity=Integrity.VERIFIED`)

**Claim contradicted.** The story's non-goal says: "Verifying an Archive in a backup
Dry Run: there is none and none is produced". Triage E-8 says "a Dry Run log never
claims an effect occurred".

**Problem.** The executor sets `integrity=Integrity.VERIFIED` without conditions. In a
Dry Run, `NoopStagedArchive.publish()` calls no verifier, yet `BackupResult.integrity`
says VERIFIED. The justifying comment ("the publish gate raises unless verification
passed") is false for the no-op store. An API caller (Epic 6) reading
`result.integrity` is told an unverified, non-existent Archive was verified.

**Fix.** Make `integrity` `Integrity | None` (or add `Integrity.NOT_PERFORMED`), and
set it from `performed`. The cleanest place is the staged archive: return it alongside
`publish()`'s result. A `performed`-keyed value inside the executor is not a dry-run
conditional, since the adapter reported the fact. Add an assertion to
`test_adapter_sets.py::test_a_driver_that_opens_a_dry_run_binds_the_noop_set`.

### R6 — MEDIUM — claim — `src/l3io/wp/backup/cli/backup.py:1053-1054,1101-1104`

**Claim contradicted.** The error-handling AC says a refused Dry Run "exits with the
same `ExitCode` the real Run would, **after reporting the actions planned up to that
point**". The functional AC says it "reports, in order, the actions a real backup
would take".

**Problem.** On any refusal (`ArchiveExistsError`, preflight, credentials,
unreachable), `run_backup` raises before `emit_result`, so stdout carries nothing.
The plan appears only as `planned_action` log records, and only if the log level is
INFO or lower. With `--log-level WARNING`, a refused Dry Run reports no plan at all.
The records also hold the *whole* plan, logged before any check runs, not "the actions
planned up to that point". Two more gaps:
- A failure in `wordpress_source(...)` or `site_descriptor_from_wp_config`, both
  before `plan_actions`, reports nothing.
- `backup()` called directly (the Safety Snapshot path) returns `actions=()`.

Deviation 6 records the logging choice but not the stdout gap or the log-level
dependency.

**Fix.** Either:
- render the plan to stdout in `run_backup` for a Dry Run before calling into the
  driver, or emit it from a `finally` in `run_backup` on the failure path when
  `args.what_if` is set (`cli/` may name it), and test a refused `--whatIf` run's
  stdout; or
- amend the AC and deviation 6 to say "reported in the log at INFO", and make
  `planned_action` independent of `--log-level`.

### R7 — MEDIUM — defect (safety, silent override) — `src/l3io/wp/backup/cli/backup.py:1059-1072`, `tests/unit/cli/test_adapter_sets.py:2800-2808`

**Problem.** When `drive_backup` joins a Run (`ctx` given), it silently ignores
`request.dry_run`. `test_a_joined_real_run_stays_real_for_a_dry_run_request` pins
this: a `BackupRequest(dry_run=True)` publishes a real Archive at the Storage Target.
ADR-0016's "a joined Run inherits the outer root's selection" explains *which* set is
used. It does not require dropping a contradictory request without a word. A caller
that asked for a rehearsal gets a write. The CLI cannot reach this path today; Epic
6's `api/` and the Safety Snapshot can.

**Fix.** Make the root's selection observable on the `RunContext`
(`ctx.dry_run: bool`, set by `open_run`; this is in `cli/`, so AD-4 holds). In the
joined branch, raise `UsageError` when `request.dry_run and not ctx.dry_run`. The
inverse (real request inside a Dry Run root) stays safe and can keep inheriting.
Change the pinned test to expect the refusal.

### R8 — LOW — defect — `src/l3io/wp/backup/cli/backup.py:356-385`

**Problem.** The executor builds the Manifest's exclusions from
`plan.exclusion_source`/`plan.exclusion_patterns`, but hands the writer the separate
`exclusion` policy. Unlike the cipher/ENCRYPT and database/DUMP bindings, it never
checks that the two agree. `execute_backup_plan` is public, and the streaming test
calls it directly. A caller passing a plan built with one set and a different policy
would get a Manifest recording patterns that were not applied.

**Fix.** Add a guard next to the other binding checks:
`if (plan.exclusion_source, plan.exclusion_patterns) != (exclusion.source, tuple(exclusion.patterns)): raise UsageError(...)`.

### R9 — LOW — defect — `src/l3io/wp/backup/cli/parser.py:1189-1199`, `src/l3io/wp/backup/cli/__init__.py:40-52`

**Problem.** `--whatIf` is a top-level flag, but only `backup` reads it.
`wpbackup2 --whatIf verify …` runs normally and says nothing; verify is read-only, so
this is harmless today. Once Epic 3 wires `restore` into `main()`, `--whatIf restore`
will perform a real restore unless that story remembers to read the flag.

**Fix.** In `main()`, refuse `args.what_if` for any action that does not honour it
(`parser.error("--whatIf is not supported for 'verify'")`), with a test. Epic 3 then
removes `restore` from the refusal set as part of its own work.

### R10 — LOW — defect (test gap) — `tests/unit/cli/test_backup_dry_run_effects.py:934`

**Problem.** The workspace AC says "no-op commands write nothing into it".
`assert list(workdir.iterdir()) == []` only shows the workspace was removed
afterwards, which a real Run would also pass. Nothing observes the workspace's
contents while the Run is active.

**Fix.** Spy on `run_workspace` (or wrap `NoopArchiveStore.stage` /
`NoopArchiveWriter.write`) to snapshot `ctx.workspace` just before `publish()`, and
assert it is empty. Also check the dump destination
(`workspace / DUMP_RELATIVE`) does not exist.

### R11 — LOW — defect (test gap) — `src/l3io/wp/backup/cli/parser.py:1191`

**Problem.** The `--what-if` alias (triage E-7, part of the frozen CLI contract AD-22)
has no test. Every test uses `--whatIf`. Only the README drift check pins the help
text.

**Fix.** Parametrise one existing CLI Dry Run test (for example
`test_a_dry_run_changes_nothing_and_reads_no_site_content`) over
`["--whatIf", "--what-if"]`.

### R12 — LOW — deletion (confidence: low) — `src/l3io/wp/backup/cli/backup.py:916-950` (removed executor `COLLECT_SITE_ROOT` branch), `src/l3io/wp/backup/adapters/tar.py:460-464`

**Problem.** Site Root collection used to run at its own plan position, *before*
`store.stage(plan.target)`. It now runs inside `ArchiveWriterCommand.write`, *after*
staging. So a collection failure (an unreadable file, a vanished directory) now
creates a staged file beside the final name and then discards it, where before
nothing was staged. Phase order and member order (dump, config, Site Root) are
preserved, and the discard path is tested
(`test_a_write_failure_discards_the_staged_archive`). The behavioural change is not
mentioned in the Completion notes.

**Fix.** Either note it as an accepted consequence of ADR-0019 in the Completion
notes, or add a test that a collection failure leaves no staged file at the Storage
Target.
