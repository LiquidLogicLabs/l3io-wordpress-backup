## Findings

### M1: the AD-25 classification guard does not see boolean actions other than `store_true`

- **Severity:** medium
- **Kind:** guard scope
- **Location:** `tests/contracts/test_flag_map.py` `_is_classified_kind` (used by `_mode_selecting_dimensions` and `_unclassified`)
- **Description:** Both halves of the guard examine only `store_true` actions and actions with `choices`. A mode-selecting switch spelled any other way is skipped silently:
  - in the `restore mode` group, a `store_false` or `argparse.BooleanOptionalAction` is left out of the derivation, so it never reaches the totality or `COVERED_FLAGS` comparison;
  - outside both groups, a `store_const`, `store_false`, `count` or `BooleanOptionalAction` is not reported as unclassified.

  Checked by planting `--keep-db` (`store_false`) and `--wipe` (`BooleanOptionalAction`) in the planted twin's `restore mode` group, plus a `store_const` outside both groups. The derived set stayed `['cleanfirst', 'drop_database', 'force', 'mode']` and `_unclassified` returned `[]`.

  This is the failure AD-25 exists to prevent: a flag that changes what a restore does falls into an implicit default (`check_restore_arguments` passes only the four known values), and CI stays green. The story's prose names `store_true`/`choices`, but the rule it encodes is "every mode-selecting flag is in the table". The guard's reach is narrower than that rule, and nothing documents the gap.
- **Suggested fix:**
  - In `_mode_selecting_dimensions`, fail on any action in `restore mode` that is neither `store_true` nor `choices`, instead of `continue`. The table cannot key anything else.
  - In `_unclassified`, treat every optional action except `--help` as classifiable: anything with `option_strings` that is not a `_HelpAction`. If that is too broad, use every action with `nargs == 0` or `choices`.
  - Add planted cases for `store_false` and `BooleanOptionalAction` next to the existing `store_true`/`choices` ones.

### M2: deleting the legacy parser after a snapshot exists silently drops the frozen-spelling check

- **Severity:** medium
- **Kind:** guard scope
- **Location:** `tests/contracts/test_cli_surface.py` `test_each_frozen_spelling_lives_on_its_subcommand`, the `@pytest.mark.parametrize` argument `... if LEGACY.is_file() else []`
- **Description:** The per-spelling assertion is parametrized only from `wpbackup2/__main__.py`. The module docstring and the AC say a committed snapshot (`legacy_cli_surface.json`) may replace that file.
  - Once that happens, the parameter set is empty. The repo's pytest config has no `empty_parameter_set_mark`, so pytest's default marks the test **skipped**.
  - `test_the_legacy_surface_is_the_nineteen_frozen_spellings` still passes from the snapshot.
  - The result is that no test checks the parser against the nineteen spellings, and the suite reports green. This is the false-green mode the snapshot fallback was meant to rule out.
  - `test_a_missing_legacy_parser_without_a_snapshot_fails` attacks only the "no file and no snapshot" case, not the "snapshot present" case.
- **Suggested fix:**
  - Parametrize from a collection-time helper that reads LEGACY or else SNAPSHOT, the same order as `_legacy_surface()`. Alternatively, assert all pairs in one test that iterates over `_legacy_surface()`.
  - Set `empty_parameter_set_mark = "fail_at_collect"` under `[tool.pytest.ini_options]` so that an empty derived scope fails anywhere in the suite.
  - Add a planted case: LEGACY monkeypatched away, a tmp snapshot written, and an assertion that the per-spelling check runs (non-empty) and fails on a spelling the parser lacks.

### L1: `ADMIN_PASSWORD_VARIABLE` is a second literal of a name Epic 5 owns, and nothing reads it yet

- **Severity:** low
- **Location:** `src/l3io/wp/backup/cli/parser.py:66` (`ADMIN_PASSWORD_VARIABLE = "L3IO_WP_BACKUP_ADMIN_PASSWORD"`)
- **Description:**
  - E005-S01-001 defines `ADMIN_PASSWORD_VAR = "L3IO_WP_BACKUP_ADMIN_PASSWORD"` as the variable's owner.
  - E008-S01-001 requires the variable names to be read "from Epic 5's constants (no second literal)".
  - This story adds a parser-local copy, and `test_no_secret_valued_flags.py` asserts a third literal.
  - Today no code reads the variable, so `--admin-password --help` advertises an alternative that does not work yet. The impact is limited because `restore` exits `USAGE` regardless.
  - The risk is drift: Epic 5 renames or spells the variable differently, and the help text and the test keep passing over the stale name.
- **Suggested fix:** Record a hand-off in the issues backlog to E005-S01-001: when it defines `ADMIN_PASSWORD_VAR`, `parser.py` imports it and `ADMIN_PASSWORD_VARIABLE` is deleted. Alternatively, have the test import the constant from the module E005 will own, once it exists. Leave a `# E005-S01-001 replaces this literal` marker at the constant so the harvest picks it up.

### L2: "no restore option is silently accepted" passes on any usage error, not on the NYI refusal

- **Severity:** low
- **Kind:** test strength
- **Location:** `tests/contracts/test_not_yet_implemented.py` `test_no_restore_option_is_silently_accepted`
- **Description:** The case asserts only `code == USAGE` and `"error:" in err`.
  - For several restore options the error that fires is a different check. For example, `--admin-username x` alone hits `admin_spec`'s "required with its partner".
  - The test therefore does not show that the option reaches the `NOT_YET_IMPLEMENTED` path. It shows only that some usage error occurs.
  - The test is not vacuous today, because the `restore` subcommand entry refuses everything. The weakness is that a later edit could leave an option ignored while an unrelated error keeps this case green.
- **Suggested fix:** Supply the partner for paired flags (`--admin-username` with `--admin-password`; the aws `-region`/`-secret-id` pairs are already handled in `_argv`). Then assert that the message contains either `NOT_YET_IMPLEMENTED[f"restore {flag}"]` or `NOT_YET_IMPLEMENTED["restore"]`.
