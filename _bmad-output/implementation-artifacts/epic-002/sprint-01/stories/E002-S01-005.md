# E002-S01-005: Branch automation on what happened


**Implements:** FR-21


As an operator,
I want the exit code to tell me which kind of failure occurred,
So that my scheduler can retry a transient fault and alert on a real one.

**Acceptance Criteria:**

**Given** any run
**When** it ends
**Then** success exits 0 and every failure path exits non-zero
**And** the codes are the family table (database's `cli.Exit`: 0 OK, 1 FAILED, 2 USAGE, 3 REFUSED, 4 CREDENTIALS, 5 UNREACHABLE, 7 NOT_READY; 6 reserved) plus backup-only codes for verification failure and lock conflict, each documented
**And** the test covering every code derives its scope from the enum, never a hand-kept list
**And** invoking with no subcommand is an error, not a silent success
**And** no failure path returns a value the process then discards
**And** the code table lives in `domain/` as the source of truth, not scattered across the CLI

## Business acceptance criteria

### Outcome

A scheduler running `wpbackup2` can branch on the exit code alone: 0 means the Run succeeded; every failure exits non-zero with a code that names its kind, drawn from one documented table — the family codes shared with `l3io-wp-database` (0 OK, 1 FAILED, 2 USAGE, 3 REFUSED, 4 CREDENTIALS, 5 UNREACHABLE, 7 NOT_READY; 6 reserved for the family) plus two backup-only codes, 8 VERIFICATION_FAILED and 9 LOCKED. Running `wpbackup2` with no subcommand exits 2. The table is printed in `--help` epilog text and in the README, both generated from the enum and checked in CI, so documentation cannot drift from behaviour. The error printed on stderr names the code's meaning and passes through the Run's redaction.

## Technical acceptance criteria

### Interface contracts

- **`domain/exit_codes.py` — the source of truth (decision 3 of 2026-10-20; AG-26).** `@unique class ExitCode(IntEnum)`: `OK = 0`, `FAILED = 1`, `USAGE = 2`, `REFUSED = 3`, `CREDENTIALS = 4`, `UNREACHABLE = 5`, `NOT_READY = 7`, `VERIFICATION_FAILED = 8`, `LOCKED = 9`. **6 is reserved for the family and is not a member**; `RESERVED: Final[frozenset[int]] = frozenset({6})`. `DESCRIPTIONS: Final[Mapping[ExitCode, str]]` gives every member a one-line description. The docstring states the table is append-only under §10 (never renumbered or reused), and records how later epics map: FR-7 and AD-18 refusals → `REFUSED`; FR-13 / FR-27 missing tools → `NOT_READY`; a decryption failure (Epic 4) → `CREDENTIALS` for a missing or wrong key, `VERIFICATION_FAILED` for corrupt ciphertext. Decided 2026-10-20 (Shawn): 8 and 9 are the next free values after the family's 7, skipping the reserved 6; if the family later reserves a block above 7, these move before first release, never after.
- **Family conformance without an import.** `domain/` cannot import `l3io.wp.database`. A contract test, run when the `database` extra is installed (it is in the dev group), asserts `ExitCode[member.name] == member.value` for every member of `l3io.wp.database.cli.Exit` (v0.2.0) — scope from database's enum, so a code database adds later that this package lacks fails here.
- **One mechanism: a class attribute (decided 2026-10-20).** `BackupError.exit_code: ClassVar[ExitCode] = ExitCode.FAILED`, overridden in `domain/errors.py` on exactly these classes, which every subclass inherits: `RefusedError` → `REFUSED` (so `UnsupportedStorageSchemeError`, `ArchiveExistsError`, `RunContextActiveError`, `DatabaseRefusedError` and `ArchiveHasNoDumpError` exit `REFUSED`); `UsageError` → `USAGE` (`PassphraseUnavailableError` included); `CredentialsError` → `CREDENTIALS` (`AdminCredentialsRequiredError` included); `DatabaseUnreachableError` → `UNREACHABLE`; `VerificationFailedError`, `UnrecognisedArchiveError`, `UnsupportedFormatVersionError` → `VERIFICATION_FAILED`; `SiteLockedError` → `LOCKED`; `MissingExtraError`, `PreflightFailedError` → `NOT_READY`. Every class named here is defined in sprint 1 (E002-S01-001, E002-S01-003, E002-S01-004, E002-S01-006). A later class inherits its code from the E002 base it subclasses, or declares `exit_code` itself with an **existing** member (so Epic 4's `EncryptedMemberCorruptError` declares `VERIFICATION_FAILED` and its `EncryptionConfigError` subclasses `UsageError`); none needs an edit in `cli/`. Adding an `ExitCode` member stays E002's alone.
- **`cli/exit.py`.** `exit_code_for(exc: BaseException) -> ExitCode` returns `type(exc).exit_code` for a `BackupError`, `USAGE` for an argparse usage error, and `FAILED` otherwise (a non-`BackupError` reaching `main` is a defect and is logged with `exc_info`) — no `match` over classes. `render_failure(exc: BackupError, *, redact: Callable[[str], str]) -> str` builds the stderr text (the cause and `DESCRIPTIONS[code]`, plus the traceback at DEBUG) and passes it through the Run's `redact` before it is written (ADR-0018); the root renders while it still holds the Run's `SecretRegistry`.
- **`cli/__init__.py::main(argv) -> int`** returns `int(ExitCode.X)` on every path; `run_from_cli` passes it to `SystemExit`. No subcommand → help on stderr, `ExitCode.USAGE` (today's literal `2` becomes the enum). Every `run_*` returns `ExitCode.OK` or raises; none is called for side effect with its return discarded. `phase()` (E002-S01-010) and `run_finished` (E002-S01-004) take their `exit_code` from `exit_code_for`.
- **Documentation generated, not hand-kept (AG-25).** `tools/gen_cli_docs.py` writes the exit-code table and the CLI usage (from `build_parser().format_help()` and `DESCRIPTIONS`) between marker comments in `README.md`; CI runs it with `--check` and fails on drift. The parser's epilog lists the table from the same source. This replaces the README section that documents three flags that do not exist.

### Error and edge case handling

- No subcommand: exit 2, help on stderr.
- Unknown subcommand or flag, bad `--mode` value: argparse exits 2 itself; asserted to equal `ExitCode.USAGE`, not assumed.
- An exception raised while logging or rendering the failure (e.g. broken stderr): the original code is still returned.
- `KeyboardInterrupt`: exit 130 (shell convention) is **not** in the enum and not claimed; Python's default handling applies after the Run's `finally` blocks run. Stated so nobody adds a silent catch.
- A failure path that returns a value instead of raising: forbidden; a test drives each documented failure and asserts a non-zero exit.

### Security considerations

The stderr message and any traceback are passed through the Run's `redact` before they are written (ADR-0018); the logged exception passes through `redact_event`. An exit path never prints a raw dependency exception's text. Exit codes themselves carry no data.

### Testability approach

- `tests/unit/domain/test_exit_codes.py`: every `ExitCode` member has a `DESCRIPTIONS` entry; no value is in `RESERVED`; values unique. Parametrised from `list(ExitCode)` — **scope from the enum, never a hand list** (the epic AC).
- `tests/contracts/test_exit_codes_family.py`: the database-`Exit` conformance check, with a scope assertion that database's enum is non-empty.
- `tests/unit/cli/test_exit_mapping.py`: every concrete `BackupError` subclass (found by walking `BackupError.__subclasses__()` recursively after importing every package module) has an `exit_code` that is an `ExitCode` member other than `OK`; `RefusedError` subclasses map to `REFUSED` (so `UnsupportedStorageSchemeError`, `ArchiveExistsError` and `RunContextActiveError` are asserted by walk, not by name); no module outside `domain/exit_codes.py` constructs an `ExitCode` from an integer literal, and no module under `cli/` contains a `match` or `isinstance` chain over error classes.
- `tests/integration/test_exit_codes_end_to_end.py`: a case table keyed by `ExitCode`, each case driving a real failure through `main` with doubles — `FAILED` (dump failure), `USAGE` (no subcommand; a bad `--mode`), `REFUSED` (existing final Archive), `CREDENTIALS` (wrong password), `UNREACHABLE` (unreachable host), `NOT_READY` (the `database` extra absent), `VERIFICATION_FAILED` (`verify` of a corrupted Archive). Parametrised from the enum: every member except `OK` must have a case **or** an entry in `PENDING_CASES: Final = {ExitCode.LOCKED: "E002-S02-008"}`, which is skipped with that reason; a member that is in `PENDING_CASES` **and** has a case fails, so the entry cannot outlive the story that delivers it. E002-S02-008 adds the `LOCKED` case and removes the entry; E002-S02-007 adds a second `NOT_READY` case for a failed preflight. After sprint 2, `PENDING_CASES` is empty.
- `tests/unit/cli/test_render_failure.py`: a `BackupError` whose message contains a registered secret renders with `***`; the rendered text names `DESCRIPTIONS[code]`.
- `tests/contracts/test_cli_docs.py`: runs `tools/gen_cli_docs.py --check`; CI also runs it as a step in the `contracts` job.

## Completion notes

- `adapters/phase.py` cannot import `cli/` (AD-1 layers), so `phase()` takes its code from `domain.errors.exit_code_of`; `cli.exit.exit_code_for` delegates to it and adds argparse's `ArgumentError` → `USAGE`. The two agree on every exception a phase can see.
- `cli.main` now owns the Run's `SecretRegistry` and passes it to `run_backup(args, *, secrets)` / `run_verify(args, *, secrets)`, which return `ExitCode.OK` or raise. `report_failure` re-opens the registry for the logging pipeline while it logs, which closes BL-E002-054.
- `render_failure` takes any `BaseException` (a non-`BackupError` is named by class only), plus an optional `with_traceback`. At DEBUG its traceback withholds every non-`BackupError` message in the chain (review F-02).
- A failed `verify` raises `VerificationFailedError` (exit 8). Its `VERIFY` phase is marked failed through `PhaseRecord.fail` (review F-01). The old `verify_failed` event is now `command_failed`, like every other failure; `docs/logging.md` is updated.
- The README restore examples, which documented flags this build lacks, were replaced by the generated `cli-usage` and `exit-codes` blocks (`tools/gen_cli_docs.py`, CI step "AG-25 generated CLI docs are current").
- The orchestrator's brief also listed doctor, the NOT_YET_IMPLEMENTED flags and the frozen 19-flag surface. This story's Non-goals assign those to E002-S02-011, so they were not built here. No existing flag was renamed or removed.
