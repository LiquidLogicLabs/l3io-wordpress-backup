## Findings

### F-01 — HIGH — kind: correctness (test tier) — the live hygiene tier cannot pass in CI

- **Location:** `tests/contracts/test_credential_hygiene.py:329` (`[{"password": os.environ.get("DB_PASSWORD")}]`) together with `tests/conftest.py:109` (`("os.environ after", repr(environ))`)
- **Problem:** CI sets `DB_PASSWORD: root` (`.github/workflows/ci.yml:188`). The integration tier plants that value as the sentinel. `surfaces()` then adds `repr(os.environ)` as a surface, and it removes only `L3IO_WP_BACKUP_PASSPHRASE`. `DB_PASSWORD=root` is in that environment, so `assert_clean()` reports a leak on every live run, whatever the code under test does.
  - `"root"` is also not a unique sentinel. It is a common substring, for example in `site_root` and `/root`, so even without the environ surface the tier would report false leaks.
  - All 16 local skips include this tier, because `DB_HOST` is unset locally, so it has never executed. It is the only tier that drives real `subprocess.Popen` argv and env through the spy. The unit tier replaces `wpdb.dump` with the double, so it spawns nothing.
- **Consequence:** CI goes red as soon as this lands. The likeliest "fix" under pressure is to weaken the fixture, and that removes the only real-subprocess evidence for AD-7 items 1–4.
- **Suggested fix:** make the live sentinel unique and absent from the environment:
  - have the test or CI provision a dedicated MySQL account with a `uuid4` password, using the root connection only to create it;
  - or plant a generated password and grant it in a setup step.
  - If CI's own variable must stay, exclude it from the environ surface by name, the way `PASSPHRASE_ENV` is excluded, and assert separately that the Run did not change it.
  - Add a fixture self-test asserting that a planted sentinel never already occurs in `os.environ` or the fixture's static inputs.

### F-02 — MEDIUM — kind: correctness (redaction backstop) — escaped forms of a secret pass `redact_event` untouched

- **Location:** `src/l3io/wp/backup/adapters/redaction.py:116-119` (the `BaseException` branch), and by the same mechanism `format_exc_info` text and stdlib `%r` messages
- **Problem:** `redact` matches the raw secret only. Text produced by `repr` before the processor runs carries the escaped form: a `'` or `\` is backslash-escaped, and non-ASCII may be `\x`/`\u`-escaped. Three paths do this:
  - `str(exc)` of a multi-argument exception is `str(exc.args)`;
  - the traceback text `format_exc_info` builds contains that same `str(exc)`;
  - stdlib `logger.debug("... %r", value)` produces `record.getMessage()`.

  For an exception field, the branch finds no raw match and returns the **original exception object**. The renderer then calls `repr` on it and emits the escaped secret (see the probe above). WordPress and generated database passwords commonly contain `'`, `"`, `\` and `$`. The fixture's sentinel is `uuid4().hex`, so no test can see this.
- **Suggested fix:**
  - In `register`, also register the escaped variants, such as `repr(value)[1:-1]` and the `json.dumps(value)[1:-1]` body, when they differ from the raw value.
  - In `_walk`, always replace an exception value with its redacted `f"{type}: {exc}"` text, rather than passing the object through when nothing matched.
  - Make the fixture's generated sentinel include a `'` and a `\`, for example `f"sentinel-pw-{uuid}'\\x"`.
  - Add a unit case with a multi-argument exception.

### F-03 — MEDIUM — kind: claim — a dependency exception's text is interpolated into a package error

- **Location:** `src/l3io/wp/backup/adapters/database.py:466`. `except wpdb.TransferError as exc: raise DumpFailedError(str(exc)) from exc`
- **Claim contradicted (story, Interface contracts):** "Messages are built from structured fields (source label, host, database name) and never interpolate a credential or a dependency exception's text — that is the primary control, and redaction is the backstop."
- **Problem:** this line predates the story (E002-S01-001), but the story's AC binds it, and the dev edited this module without bringing it into line.
  - `TransferError` text comes from `l3io-wp-database` and the client tool's failure, so it is untrusted text.
  - Through the CLI it is redacted only by the stderr backstop.
  - For a library caller, through `str(exc)` and through `traceback.format_exception`, which the hygiene fixture treats as "the primary control" surface, nothing redacts it.
  - No hygiene case injects a `TransferError` that carries the sentinel, so the surface is untested.
- **Suggested fix:** build the message from structured fields only: `DumpFailedError(type(exc).__name__)`, or a reason code that `TransferError` exposes as an attribute. Then add a hygiene case where the double raises `wpdb.TransferError(f"... {password} ...")` and the driver's exception is captured with `add_exception`. Keep the chained `from exc` only if `TransferError`'s text is contractually credential-free; otherwise use the same no-chain treatment as `_RegisteringSource`.

### F-04 — MEDIUM — kind: scope — the root's built objects are a hand-kept list

- **Location:** `tests/contracts/test_credential_hygiene.py:73` (`_watch_root`: `SecretRegistry`, `wordpress_source`, `WpDatabase`, `execute_backup_plan`)
- **Claim (Testability (4)):** "`repr()` of every object the composition root builds".
- **Problem:** the list is enumerated by hand, against global rule 4.
  - It already misses `site_descriptor_from_wp_config`, which builds and returns the `WpConfigFile` credential source and is the first holder of the wp-config password.
  - It also misses `wordpress_spec`, `locate_wp_config`, `build_backup_plan`, `storage_target_from_cli`, `LocalArchiveStore` and `run_workspace`.
  - A new constructor added to `backup_from_args`, such as E002-S01-004's `BackupRequest` or `open_run`, will not be watched, and the tier will stay green.
- **Suggested fix:** derive the watch set from the source of truth. Wrap every callable in `vars(backup_cli)` whose `__module__` starts with `l3io.wp.` (classes and functions alike), or AST-walk `backup_from_args` for called names and spy each one. Assert that the derived set contains `site_descriptor_from_wp_config` and `wordpress_source`, so a shrinking scope fails. Do the same for `verify_cli`.

### F-05 — MEDIUM — kind: false-green — the request-type guard can skip forever, and its planted case bypasses the walk

- **Location:** `tests/contracts/test_credential_sources_built_once.py:113` (`and dataclasses.is_dataclass(value)`) and `:141` (`pytest.skip(...)`)
- **Problem:**
  - `_request_types()` only counts **dataclasses** named `*Request`. If E002-S01-004 defines `BackupRequest` as something else — an attrs class, a `NamedTuple`, a pydantic model, or a plain class with annotations — the set stays empty. The test then skips with "E002-S01-004 adds BackupRequest", the AC's second check is never run, and nothing fails.
  - The planted case (`test_the_hint_check_sees_a_nested_database_type`) calls `_offending_hints` directly. It never proves that `_request_types()` would *find* a planted request, so it attacks the rule and not the scope.
- **Suggested fix:**
  - Drop the dataclass filter: any class whose name ends in `Request` and that is defined in the package.
  - Skip only while no such name exists anywhere in the source, checked with an AST grep for `class \w+Request`, and fail if the AST finds one that the import walk did not return.
  - Add a planted-module test that writes a temporary package holding `class XRequest` with a database annotation, and runs the walk over it.

### F-06 — LOW — kind: correctness — overlapping (not nested) secrets leave a tail unredacted

- **Location:** `src/l3io/wp/backup/adapters/redaction.py:83` (longest-first alternation)
- **Problem:** regex alternation consumes leftmost-first. With secrets `abcd` and `cdefgh`, `"abcdefgh"` becomes `"***efgh"`, so four characters of the second secret leak (see the probe above). The AC covers the substring case, which works, but two Run secrets such as the database password and the passphrase can overlap.
- **Suggested fix:** collect every match span with `finditer` for each secret, or with an overlapping lookahead, merge the overlapping spans, and replace each merged span once. Add the overlap case to `test_redaction.py`.

### F-07 — LOW — kind: correctness — `from None` still keeps the untrusted exception on `__context__`

- **Location:** `src/l3io/wp/backup/adapters/database.py:330`
- **Problem:** `raise ... from None` sets `__suppress_context__`, but `__context__` still references the source's exception, whose text is untrusted and may hold the secret. Anything that walks `__context__` without honouring the suppress flag can surface it: a custom error reporter, `exc.__context__` in a library caller, or a debugger. The unit test asserts only `__cause__ is None` and `__suppress_context__`.
- **Suggested fix:** capture `name = type(exc).__name__` inside the `except`, leave the block, and raise `CredentialsError(label, reason=name)` outside it. Then `__context__` is `None`. Assert `caught.value.__context__ is None`.

### F-08 — LOW — kind: correctness — an existing wrapper is kept even when it is bound to a different registry

- **Location:** `src/l3io/wp/backup/adapters/database.py:335` (`_registering`)
- **Problem:** if `source` is already a `_RegisteringSource`, it is returned as is, even when the `secrets` passed in is a different registry. For example, `WpDatabase(src, secrets=B)` where `src` was built with registry `A` registers into `A` only, and a Run redacting through `B` misses the password. Today's single root passes the same registry to both, but E002-S01-004's joined Runs and Epic 6's `api/` roots are exactly where two registries can meet.
- **Suggested fix:** return the wrapper only when `source._secrets is secrets`. Otherwise wrap again, or raise `ValueError("a source bound to another Run's registry")`.

### F-09 — LOW — kind: scope — the Popen spy sees `env` only as a keyword, and the `MYSQL_PWD` check only in a `dict`

- **Location:** `tests/conftest.py:198` (`kwargs.get("env")`) and `:131` (`isinstance(env, dict)`)
- **Problem:** `env` passed positionally (it is `Popen`'s tenth parameter) is recorded as `None`. An `os._Environ` or another `Mapping` passed as `env` is skipped by the `MYSQL_PWD` assertion. The surface scan still covers the sentinel in `repr(env)`, but the named `MYSQL_PWD` check is narrower than its message implies.
- **Suggested fix:** bind the arguments with `inspect.signature(real_popen).bind(args, *rest, **kwargs)` and read `env` from the bound arguments. Test `isinstance(env, Mapping)`.

### F-10 — LOW — kind: fragility/scope — the `__repr__` ownership test relies on `co_filename`, and its planted cases bypass the walk

- **Location:** `tests/contracts/test_repr_clean.py:89` and `:123`
- **Problem:**
  - `code.co_filename == inspect.getfile(cls)` assumes a generated dataclass `__repr__` never reports the module's file. That holds today, because the code comes from `dataclasses.py`, `reprlib.py` or `<string>` depending on the version. It is an implementation detail, though. CPython has discussed giving generated methods real source locations for tracebacks, and if that happens the check passes every dataclass silently.
  - A hand-written `__repr__` wrapped by a decorator defined elsewhere, such as `reprlib.recursive_repr`, is misjudged the other way. That direction is loud.
  - The planted classes are passed to `_offenders` directly, so the walk's reach (`_classes()`) is defended only by the hand-kept `KNOWN_HOLDERS`. Nested classes, `Outer.Inner`, are not reached and have no test.
- **Suggested fix:** decide "own `__repr__`" from the module's AST: a `FunctionDef __repr__` inside the `ClassDef` that has the class's qualname. Add a planted temporary module with a nested secret-holding class, and run `_classes()`-style discovery over it.

### F-11 — LOW — kind: claim — `ExplicitCredentialSpec.__repr__` differs from the AC text

- **Location:** `src/l3io/wp/backup/domain/credentials.py:63`

### F-12 — LOW — kind: claim/scope — the constructor guard misses static import aliases, and its docstring understates this

- **Location:** `tests/contracts/test_credential_sources_built_once.py:45` (`_called_name`), and the module docstring "A call through an alias assigned at runtime is not seen"
- **Problem:** `from l3io.wp.database import Explicit as Literal_` followed by `Literal_(u, p)` is a **static** alias, and the guard does not see it. The docstring implies that only runtime aliases escape, so it overstates the guard's coverage (global rule 3).

Alternatively, flag any import of the five constructor names from `l3io.wp.database` outside the builders. Add a planted alias case. Either way, correct the docstring.

## Checks with no finding

- **Thread safety of `SecretRegistry`.** `register` mutates `_secrets` and `_pattern` under the lock, replacing each with a new object. `redact` and `__len__` read one reference, which is atomic. - **Deletion check.** The rework of `run_backup` into `backup_from_args` plus `run_backup` keeps every step and error mapping: `InvalidSiteDescriptorError ... from exc`, the dump-only credential check (FR-2), and the workspace and `ArchiveExistsError`. ### New findings

#### N-01 — LOW — kind: test realism — the transfer hygiene case plants the secret where nothing reads it, not where database puts it

- **Location:** `tests/contracts/test_credential_hygiene.py:78` (`DatabaseDouble`, `TransferError("dump failed", ..., 2, self.transfer)`) and `:273`. The path is `src/l3io/wp/backup/adapters/database.py:479` (`raise DumpFailedError(reason) from exc`).
- **Problem:** the real `TransferError` message includes the first line of the client tool's stderr: `msg = f"dump failed: {tool} exited {code}: {first}"` (database `transfer.py:245-246`). Because the error is chained `from exc`, that message appears in the `DumpFailedError` traceback, which the fixture treats as a primary-control surface. The double puts the sentinel only in `.stderr`, which no backup code reads, so the case passes whatever is in the message. It does not test the path that matters: the message reaching the traceback through `__cause__`.
  - That path is protected only by database's `text.replace(password, "***")` (`transfer.py:79`). It matches the raw password only, so it misses an escaped spelling, a password split by the stderr cap, and the backup passphrase.
- **Suggested fix:** have the double build its message the way database does (`f"dump failed: double exited 2: {first_line}"`) from a stderr that holds the sentinel, then assert the traceback is clean. If that case fails, drop the chain for `TransferError`, as `_RegisteringSource` does, or record in the module docstring that the chained cause relies on database's raw-match redaction.
