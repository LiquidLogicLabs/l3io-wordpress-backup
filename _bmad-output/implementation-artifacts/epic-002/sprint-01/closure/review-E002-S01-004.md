## Findings

### F-01 — MEDIUM — kind: bug — after the first tracer failure, `GuardedTracer` never exits spans that are already open

- **Location:** `src/l3io/wp/backup/adapters/noop.py:103` (`if self._disabled: return _FAILED`), together with `:135` and `:138` (both `manager.__exit__` calls go through `self.call`)
- **Problem:** `call()` returns `_FAILED` without running `fn` once `_disabled` is set. The `__exit__` of every span that was entered before the failure also goes through `call()`. So once any tracer call raises — `phase_span`, `set_attributes`, a phase's `set_outcome` — the root span, and any open phase span, is never exited. The probe confirms it: the inner `run_span` was entered and its exit never ran.
  - With an OpenTelemetry tracer (Epic 6), `start_as_current_span` attaches a context token on enter and detaches it on exit. Skipping the exit leaves the dead Run span as the host's current span. Later host spans become its children. The span is never ended or exported. Its generator is finalised by GC in an arbitrary context ("Failed to detach context").
  - That is the opposite of AD-24's "tracing never changes an outcome", applied to the host. It is invisible in Epic 2, where the tracer is the no-op.
- **Test gap:** `test_a_raising_tracer_changes_no_outcome` uses `Recording([], fail=...)` and never inspects the journal, so the missing `run_span_exit` is not seen. No case raises from a span's `__exit__`, and none raises from a *phase* span's `set_outcome`, because `_PhaseSpan` never fails.
- **Fix:**
  - Disable only *new* calls, such as `run_span`/`phase_span` openers, `set_attributes` and `set_outcome`. Always attempt `manager.__exit__` for a span whose `__enter__` succeeded, still catching `Exception` and logging nothing further once `tracer_failed` has been logged. For example, give `_span` its own `try/except Exception` around the exit calls and bypass the `_disabled` short-circuit.
  - Extend the parametrised test: assert `("run_span_exit",)` is in the journal for every `failing` value, and add `fail` cases for a span `__exit__` and for `_PhaseSpan.set_outcome`.

### F-02 — MEDIUM — kind: claim — a failed `verify` reports `run_finished exit_code=0` while the process exits 1

- **Location:** `src/l3io/wp/backup/cli/context.py:183` (`exit_code = 0 if error is None else 1`), together with `src/l3io/wp/backup/cli/verify.py:88-97`
- **Problem:** `drive_verify` returns a `VerificationResult` with `passed=False` instead of raising. `open_run` sees no exception, so it logs `run_finished` at INFO with `exit_code=0, error=null` and calls `run_span.set_outcome(exit_code=0, error_type=None)`. `run_verify` then prints "verify failed" and returns 1.
- **Consequence:** `jq 'select(.event=="run_finished" and .exit_code!=0)'` misses every failed verification. The tracer records a success. This contradicts the AC "`run_finished` ... with the failure's `exit_code`" and the docs' "run_finished carries exit_code".
- **Fix:** the Run must know the outcome before its `finally`. Pick one:
  - (i) give `RunContext` a write-once `set_exit_code(code)` (or `set_outcome`) that `drive_verify` calls with `1` when `not result.passed`, and that `open_run`'s `finally` prefers over the exception-derived value. This is the hook E002-S01-005 will need for `VERIFICATION_FAILED` anyway.
  - (ii) have `drive_verify` raise a `VerificationFailedError(BackupError)` that carries the result, and have `run_verify` render it.
- **Test to add:** `run_verify` on a corrupt Archive asserts `run_finished.exit_code == 1` and a recording tracer's `run_outcome` is `(1, ...)`.

### F-03 — MEDIUM — kind: claim — a failed Run's stderr is not "jq-sufficient": the plain-text error line is interleaved with the JSON stream

- **Location:** `src/l3io/wp/backup/cli/backup.py:451`, `src/l3io/wp/backup/cli/verify.py:85` and `:93-96`
- **Problem:** `--log-format json` writes one JSON object per line to stderr. On any failure the roots also `print(...)` `wpbackup2: error: ...` or `wpbackup2: verify failed: ...` as plain text to the same stderr. The docs' own recipe (`2> backup.log`, then `jq -c 'select(.run_id == ...)'`) stops with a parse error at the first failed Run in a week of appended logs.
  - This contradicts the AC "so `jq` over a log file is sufficient" and the integration test's premise that "every line parses as JSON".
  - That test covers only the success path, so it cannot see this.
- **Fix:** pick one:
  - (a) When the resolved format is JSON, route the operator message through the logger: `_log.error("command_failed", message=secrets.redact(str(exc)))` inside or after the Run. The pipeline already redacts it.
  - (b) Document that a failed Run adds one non-JSON line, and change the recipe to `jq -R 'fromjson? | select(...)'`.
  - (a) is what the AC describes. Whichever is chosen, add a failure-path case to `test_log_schema.py` or the integration test: every stderr line parses as JSON for a backup with a missing `wp-config.php`.

### F-04 — MEDIUM — kind: deletion — removing `backup_failed`/`verify_failed` leaves pre-Run failures with no log record at all (confidence: high)

- **Location:** `src/l3io/wp/backup/cli/backup.py:450` (the removed `_log.error("backup_failed", error=...)`) and `src/l3io/wp/backup/cli/verify.py:84`
- **Problem:** the removed records were emitted for **every** `BackupError` a root caught. Their replacement is `run_finished` (error class at ERROR), which exists only once a Run is open. These failures happen before `open_run` and now leave nothing in the structured stream, only the plain-text stderr line (see F-03):
  - `InvalidSiteDescriptorError` for a missing `--wp-dir` (`drive_backup` canonicalises before `join_or_open`, as the AC requires);
  - `UsageError` from `storage_target_from_cli` (bad `--archive`) or `wordpress_spec` (in both roots, during request building).
- **Consequence:** an operator filtering the JSON log for `level=="error"` does not see these failed invocations at all. The removed contract was "every failed command leaves an error record naming the error class". Nothing in the story says it is dropped. The docs' "What is and is not covered" names pre-Run *records* carrying no `run_id`, not pre-Run *failures* leaving none.
- **Fix:** in `run_backup`/`run_verify`, keep one `_log.error("command_failed", error=type(exc).__name__)` in the `except BackupError` branch. Emit it only when the failure happened before a Run opened, or always, and say in `docs/logging.md` that a failure inside a Run also has `run_finished`. Add a test asserting that `main(["backup", "--wp-dir", missing])` emits exactly one error-level record.

### F-05 — LOW — kind: claim — the workspace path is logged at WARNING, contradicting "logged only at DEBUG"

- **Location:** `src/l3io/wp/backup/adapters/workspace.py:44` (`_log.warning("workspace_not_removed", path=str(created))`); the claim is at `docs/logging.md` ("the workspace path is logged only at `DEBUG`") and in the story's security ACs
- **Problem:** the code predates this story (E002-S01-010), but this story moves workspace ownership into `open_run` and newly asserts the claim in the user-facing docs. A workspace that cannot be removed puts its path in a WARNING record, which the default `--log-level INFO` emits.
- **Fix:** log `workspace_not_removed` at WARNING without `path` and emit the path in a separate DEBUG record, or reword the docs ("only at DEBUG, except when the workspace could not be removed"). Add a test that runs `capture_logs` over a failed `rmtree` and asserts no non-DEBUG record carries the path.

### F-06 — LOW — kind: bug — `run_from_cli` reports exit 1 for a successful Run whose stdout reader has gone away

- **Location:** `src/l3io/wp/backup/cli/__init__.py:48-54`
- **Problem:** `code = 1` is the default. `BrokenPipeError` from `print(result.path)` in `run_backup`, or from the OK line in `run_verify`, is raised *inside* `main()` after the Run has finished with `run_finished exit_code=0`. `main` never returns, so the process exits 1 for a backup that published its Archive. The AC says a broken pipe does not mask the Run's exit code.
- **Fix:** have each root catch `BrokenPipeError` around its own result `print` and still return its code, with the `dup2` to `/dev/null` done there or re-done in `run_from_cli`. Alternatively, return the code from `main` before rendering. Add a test that runs `main` with `sys.stdout` replaced by a writer that raises `BrokenPipeError` and asserts `run_from_cli` exits 0 after a successful backup.

### F-07 — LOW — kind: test — the logging-configured-once guard is bypassed by an aliased import

- **Location:** `tests/contracts/test_logging_configured_once.py:27` (`FORBIDDEN_CALLS` matched by dotted name as written) and `:4-14` (the coverage statement)
- **Problem:** `import logging as log; log.basicConfig()` and `import structlog as sl; sl.configure(...)` are not seen. The docstring lists only runtime binding (`getattr`) as uncovered, so it overstates what the check covers (global rule 3). The planted-violation test attacks depth in the tree but not this spelling.
- **Fix:** per module, build an alias map from `ast.Import`/`ast.ImportFrom` (`asname` → module) and normalise the call's head name before matching. Plant `import logging as lg\nlg.basicConfig()` and `import structlog as s\ns.configure()` in `test_the_guard_fires_on_every_form_deep_in_the_tree`.

### F-08 — LOW — kind: test — "no function below `run_*` receives `args`" checks a name, in a hand-derived module set

- **Location:** `tests/unit/cli/test_drivers.py:75-82`
- **Problem:** the scope is "modules under `cli/` that define a `run_*`", and the rule is "a parameter literally named `args`". It misses two cases:
  - a helper in another module (for example `cli/scope.py` or `cli/credentials.py`) that takes the namespace;
  - any parameter named differently but annotated `argparse.Namespace`.
- **Fix:** scan every module under `cli/` (the whole package, if possible) for any function other than a `run_*` that has a parameter annotated `argparse.Namespace` (or named `args`). Plant one in a module that defines no `run_*`.

### F-09 — LOW — kind: test — the phase-schema check subtracts the verify extras from every phase, so "exactly those phase fields" is weakened

- **Location:** `tests/unit/cli/test_log_schema.py:74` (`set(line) - record - VERIFY_EXTRAS == phase`)
- **Problem:** `VERIFY_EXTRAS` is subtracted for all five phases. A `DUMP` or `COLLECT_SITE_ROOT` record that started carrying `passed` or `reason` would still pass. Separately, the hand-kept `VERIFY_EXTRAS` set can drift from what `verify_archive` actually records.
- **Fix:** subtract the extras only where `line["phase"] == "VERIFY"`, and assert `set(line) - record == phase` for the others. If possible, derive the extras from the verifier's record (for example, a constant exported next to the code that sets them) rather than a list in the test.

### F-10 — LOW — kind: test — nothing asserts a Run's registry and tracer are released when it ends

- **Location:** `src/l3io/wp/backup/adapters/redaction.py:179-190` (`open_registry`/`_OPEN`) and `src/l3io/wp/backup/cli/context.py` (the `ACTIVE_TRACER` reset)
- **Problem:** the tests check that the context variables and `active_run()` are cleared after success and after failure. They do not check that `_OPEN` is empty or that `ACTIVE_TRACER.get() is None` after a Run.
  - `test_outside_a_run_a_phase_uses_the_noop_tracer` checks `ACTIVE_TRACER` only in a test where no Run was opened.
  - A regression in either cleanup would go unnoticed: registries piling up in a long-lived API host, or a dead Run's tracer leaking into later phases.
- **Fix:** in `test_a_failure_still_finishes_the_run_and_removes_the_workspace` (both parameters) and the success case, assert `redaction._OPEN == []` (or expose a read-only `open_registries()`) and `ACTIVE_TRACER.get() is None`.

### F-11 — LOW — kind: library — every DEBUG event runs the whole chain (redaction included) even at INFO

- **Location:** `src/l3io/wp/backup/cli/logging.py:120-125` (`structlog.configure(... wrapper_class=structlog.stdlib.BoundLogger ...)`)
- **Problem:** with `stdlib.BoundLogger` and no level filter, structlog runs `merge_contextvars` … `redact_open_runs` for every `debug()` call. The stdlib logger discards the record only afterwards. Redaction walks nested event dicts per live registry, so this cost is paid on every suppressed DEBUG record during the dump and collect phases.
  - structlog already provides the filter, so this is a missing library feature, not a hand-roll.
- **Fix:** put `structlog.stdlib.filter_by_level` at the head of the structlog-side processors only, not `foreign_pre_chain` (stdlib filters foreign records itself). Do not count it in `processor_chain`, so `merge_contextvars` stays `chain[0]` and redaction stays at `len(chain) - 2`. Alternatively, use `structlog.make_filtering_bound_logger(numeric)` if the stdlib-specific methods are not needed.

## Resolution (fix iteration 1, dev)

All eleven findings were fixed in one pass; none deferred.

- F-01: `GuardedTracer.call(..., closing=True)` always attempts a span's `__exit__` after a failure, logging `tracer_failed` once. `test_a_raising_tracer_changes_no_outcome` now covers span-exit and phase-outcome failures and asserts every entered span is exited (mutation-checked: 5 cases fail without the fix).
- F-02: `RunContext.report_failure(exit_code=, error_type=)`; `drive_verify` reports a failed verification when it opened the Run, so `run_finished` and the root span carry `1`/`VerificationFailedError`.
- F-03/F-04: new `cli/output.py` — `emit_failure` always logs one `command_failed`/`verify_failed` ERROR record (class and redacted message) and prints the plain line only when the stream is not JSON; `tests/unit/cli/test_output.py`.
- F-05: `workspace_not_removed` WARNING carries no path; a DEBUG record names it.
- F-06: `emit_result` swallows `BrokenPipeError` on the result line; `run_from_cli` exits with the Run's code (test included).
- F-07: alias-resolving logging guard, planted aliases. F-08: whole-package scan for `args`/`argparse.Namespace` parameters. F-09: verify extras subtracted for VERIFY only. F-10: registry and tracer release asserted. F-11: `structlog.stdlib.filter_by_level` heads the structlog-side chain only.
