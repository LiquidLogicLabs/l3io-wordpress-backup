# Code review: E002-S01-002

## Summary

The change does what the Business ACs ask. `BackupScope` holds the Glossary values. `cli/scope.py` is the
single `MappingProxyType` table, with no fallback. The backup `--mode` flag matches v0.2.21 exactly:
`wpbackup2/__main__.py:57-60` has the same choices, the same default and the same help text. The plan is a
`match` with `assert_never`. A `files` run binds no database and resolves no credential. A `db` run
publishes a full Archive with no `site-root` member. The Manifest carries the domain value, and
`dump_present` comes from the plan.

I found nothing critical or high. The findings below are a coverage gap in one guard, two places where a test
or the code differs from the AC wording, and one regression the tests do not guard.

All six technical-AC dimensions were checked:

- Interface contracts: met. `scope` has no default. `BackupScope` is already in
  `tools/check_mode_defaults.py` `GUARDED_TYPES`, and a test plants a violation in a tmp tree to prove it.
- Errors and edge cases: met. argparse rejects any other `--mode` value with exit 2. The mapping raises
  `KeyError` and has no fallback.
- Observability: met. `backup_started` is logged once with the domain value. The tests show that only the
  planned steps produce `phase_completed`.
- Security: met. No value is printed. Credentials are resolved only when the plan has a `DUMP` step.
- Testability: met, apart from F-1 and F-4.
- Existing-library check: met. The change uses stdlib `StrEnum`, `MappingProxyType`, argparse `choices` and
  `assert_never`, and adds no hand-rolled code.

## Findings

### F-1 — medium — `kind: claim` — "exactly one place in `cli/`" is not enforced; the guard excludes all of `cli/`

- **Location:** `tests/contracts/test_no_db_spelling.py:23-27` (`_modules` drops every path whose first part
  is `cli`). The claims it was meant to back are at `src/l3io/wp/backup/domain/backup_scope.py:3-6` and
  `src/l3io/wp/backup/cli/scope.py:3-6`.
- **Description:** The story AC says "the CLI value `db` maps to the domain value `database` in exactly one
  place in `cli/`", and the Interface contract adds "No other module translates `db`". Both docstrings repeat
  this as fact ("that translation lives in exactly one place, `l3io.wp.backup.cli.scope`"; "This table is the
  only place `db` becomes `database`"). The contract test skips the whole of `cli/`. A second translation
  would pass every gate, for example `if args.mode == "db": scope = BackupScope.DATABASE` in `cli/backup.py`
  or any new `cli/` module. The Testability bullet only asks for a grep "outside `cli/`", so the test follows
  the letter of its own bullet. It still leaves the stronger AC and the docstrings without a check, which
  global rule 3 forbids.
- **Suggested fix:** Inside `cli/`, allow the `"db"` literal only in `cli/parser.py` (the `choices`) and
  `cli/scope.py` (the table). Derive the walked set from the package tree as now, and make the allow-list
  those two files instead of the `cli/` directory. Add a planted case to
  `test_a_planted_literal_in_a_new_subpackage_is_found` with a `"db"` in a tmp `cli/other.py`, and assert
  that it is reported. If you prefer to keep the narrower check, reword the two docstrings so they no longer
  claim it is enforced.

### F-2 — low — undocumented coverage limits in the `"db"` spelling guard

- **Location:** `tests/contracts/test_no_db_spelling.py:1-8` (module docstring).
- **Description:** The docstring says what the guard catches but not what it misses. It cannot see a
  computed spelling such as `"d" + "b"` or `f"{'d'}b"`, and it ignores identifiers. A domain member written
  as `DB = "database"`, or `BackupScope.DB`, would spell the scope `db` and pass. The story asks only for the
  string literal, so this is not an AC breach. The sibling `tools/check_mode_defaults.py` has a "What this
  check does NOT cover" section, and global rule 3 asks for one.
- **Suggested fix:** Add a short "does not cover" paragraph to the docstring that names these cases.
  Optionally, also check that no `BackupScope` member name is `DB`, deriving the names from `BackupScope`.

### F-3 — low — `kind: claim` — the `files` integration case does not stop the database

- **Location:** `tests/integration/test_backup_scope.py:1-7` and `:618` (`UNREACHABLE_HOST = "db.invalid"`).
- **Description:** The AC says it is "asserted by an integration test with the database stopped". The
  Testability bullet says "for `files`, run with the database service stopped". The test instead points
  `DB_HOST` at an unresolvable host. The module docstring records the substitution and its reason, which is
  that a test cannot stop the CI service container. This still proves the run makes no connection. The
  credentials in that `wp-config.php` are a valid pair, so this case cannot show that credentials are never
  resolved. That is covered separately by the double in `tests/adapters/test_backup_executor.py:416-461`.
- **Suggested fix:** No code change is needed. Record the substitution in the story's dev notes or
  completion record, so the AC is not read as met literally.

### F-4 — low — `kind: deletion` (confidence: high that the behaviour remains; high that nothing tests it) — `db`/`all` no longer have a test for the early credential check

- **Location:** `src/l3io/wp/backup/cli/backup.py:273-276`. Before this change, the call was an unconditional
  `require_wp_config_credentials(credentials)` straight after `site_descriptor_from_wp_config`.
- **Description:** The early check now runs only when `BackupStep.DUMP in plan.steps`. For `db` and `all` it
  still runs, but no test asserts that. If the call were deleted, or its condition narrowed, a half-defined
  credential pair would surface only during `DUMP`, inside the workspace, and no test would fail. The `files`
  test catches the opposite mistake: calling the check when it should not run. As a side effect, the check
  now runs after `_target()` and `build_backup_plan()`. A bad `--archive` therefore wins over bad
  credentials, which is harmless. In short, the behaviour was moved and not dropped, and it is now unguarded.
- **Suggested fix:** In `tests/adapters/test_backup_executor.py`, add a test that uses `cli_site` with
  `--mode db` and `--mode all` (parametrised from the `DUMP`-bearing scopes). Swap in a credential double
  whose `resolve()` records the call, and assert that it was called before `WpDatabase` was constructed or
  any file was written.

### F-5 — low — `kind: claim` — the "unreachable database" edge case is tested with a different error

- **Location:** `tests/adapters/test_backup_executor.py:310-322`
  (`test_a_failed_db_backup_leaves_no_archive_and_no_loose_dump`).
- **Description:** The AC says "`--mode db` against a Site whose database is unreachable: fails as
  E002-S01-001 defines (`DatabaseUnreachableError`)". The test drives `FakeDatabase(fail=True)`, which raises
  `DumpFailedError`, and it does not check the exit code or the error class. Both errors are `BackupError`s on
  the same cleanup path, so the outcome does not change. The specific error the AC names is still never
  exercised for `db` mode.
- **Suggested fix:** Give the test (or the fake) a way to raise `DatabaseUnreachableError`. Assert
  `main(argv) == 1` and the `backup_failed` event's `error` field, keeping the existing checks that leave
  nothing behind.

## Checked and not raised

- Frozen CLI: the choices, default and help text match v0.2.21 verbatim. `--mode` is on the backup subparser
  only, so `test_flag_map.py` does not pick it up as a restore dimension.
- `tests/integration/__init__.py`: with `tests/__init__.py` present, the module resolves as
  `tests.integration.test_backup_scope`, and the unit file keeps its own basename. Collection does not
  collide, and no other integration module depends on its import path.
- `cast("DatabaseCommand", database)` in `execute_backup_plan`: it is sound, because the `DUMP`/binding check
  runs first and is tested for every scope (`test_the_database_binding_must_match_the_plans_dump_step`).
- Hand-keyed `CAPTURE` and `CASES` dicts in the tests: they are parametrised from `list(BackupScope)`, so a
  new member fails with `KeyError`. Their scope comes from the enum, not from a hand list.
- `"db"` in user-facing log fields: none. `backup_scope` always carries the domain value.
