## Findings

### F-01 — MEDIUM — kind: claim — a failed `wpbackup2 verify` logs its VERIFY phase as `outcome: ok, exit_code: 0`, but `run_finished` says 8

- **Location:** `src/l3io/wp/backup/adapters/tar.py:788-805` (`verify_archive` returns a failed result from inside its own `join_phase`); `src/l3io/wp/backup/cli/verify.py:76-82` and `:94-95` (the failure is reported to the Run, then raised only after the Run has closed).
- **Problem:** The observability AC says the failing phase's `phase_completed` carries the same `exit_code` as `run_finished`. In standalone verify there is no enclosing store phase, so `join_phase` opens its own `VERIFY` phase. `verify_archive` returns normally from it, and `phase()` therefore records `outcome="ok", exit_code=0`, with only a `passed=False` field. `run_finished` then carries `exit_code=8, exit_reason=VERIFICATION_FAILED`, because of `ctx.report_failure`. A consumer that keys on `phase_completed.outcome`/`exit_code` (docs/logging.md defines `outcome` as `ok` or `failed`) sees a passing phase inside a failed Run. The backup path is consistent: `verify_or_raise` raises inside the store's `phase("VERIFY")`.
- **Test gap:** `tests/unit/cli/test_output.py::test_a_failed_verify_is_json_too` and `tests/unit/cli/test_tracing_hooks.py::test_a_failed_verify_finishes_its_run_non_zero` check `run_finished` and `command_failed`, but never the `phase_completed` record.
- **Fix:** Give `PhaseRecord` a way to record a failure without raising, for example `record.fail(exit_code)`, which `phase()` honours in its `finally`. Have `verify_archive` call it with `VerificationFailedError.exit_code` when `not result.passed`. The joined store phase raises anyway, so it is unaffected. Add an assertion to the failed-verify JSON test: the `phase_completed` record with `phase == "VERIFY"` has `(outcome, exit_code) == ("failed", 8)`.

### F-02 — MEDIUM — kind: claim (security) — at DEBUG, the stderr text includes a raw dependency exception's message

- **Location:** `src/l3io/wp/backup/cli/exit.py:135-137` (`traceback.format_exception(exc)` appended in `render_failure`); the module docstring at `cli/exit.py` lines 5-8.
- **Problem:** The story's security section says "An exit path never prints a raw dependency exception's text". The module docstring says a non-`BackupError`'s "own text is never printed — a dependency's message is untrusted". The non-DEBUG branch keeps that promise, because the cause is named by class only. At DEBUG, though, `render_failure` appends the full traceback. That traceback ends with `RuntimeError: <the dependency's message>`. For a `BackupError` raised `from` a driver error, it also prints the chained `__cause__` text, such as a MySQL driver's message with user, host or SQL. That text is then printed to stderr by `emit_failure` in console mode and written to the record's `message`. `redact` removes only *registered* secrets, so anything else in a dependency message gets through. `test_bl_e002_054_a_defect_exits_failed_and_leaks_nothing` checks only that the registered sentinel is absent; the string "a dependency echoed" is still printed. The story does ask for "the traceback at DEBUG", so the AC conflicts with itself. The docstring's unconditional claim is what the code contradicts.
- **Fix:** Choose one and make the code and prose agree:
  - (a) At DEBUG, render only the frames: `traceback.format_exception(exc)` minus the final `type: message` line for each non-`BackupError` link in the chain. The logged `exc_info` keeps the full text.
  - (b) Leave the traceback out of `render_failure` entirely. The `command_failed` record already carries it through `exc_info` for a defect. For a `BackupError` at DEBUG, add `exc_info=exc` to that record instead.
  
  Either way, correct the docstring to say what is and is not printed. Add an assertion that the non-secret part of the dependency message ("a dependency echoed") is absent from the stderr text at DEBUG.

### F-03 — LOW — kind: deletion (confidence: medium) — the verify failure message no longer names the Archive

- **Location:** `src/l3io/wp/backup/cli/verify.py:94-95`; removed lines from the old `run_verify` (`f"wpbackup2: verify failed: {path}: {first.reason.value}{member}"`).
- **Problem:** The old `verify_failed` line named the Archive path. The replacement, `VerificationFailedError.__str__`, is `archive verification failed: CHECKSUM_MISMATCH ('payload')` and has no path. The diff dropped the event name on purpose: docs/logging.md was updated to `command_failed`. Nothing says the path was meant to go, and no test re-establishes it. `test_a_corrupted_copy_fails_naming_the_payload` checks only the reason. A scheduler that verifies several Archives in one job can no longer tell from stderr or from the record which Archive failed. The `command_failed` record is emitted after the Run closed, so it has no `run_id` to correlate with the VERIFY phase's fields either.
- **Fix:** Put the path back into the operator text. For example, `run_verify` could raise `VerificationFailedError(result, path=target.path)`, and the class could include the path in its message when one is given. Alternatively, pass `path=str(target.path)` as a field on the `command_failed` record. Then assert the path appears in stderr in `test_a_corrupted_copy_fails_naming_the_payload`.

### F-04 — LOW — kind: claim — on `KeyboardInterrupt`, `run_finished` says `exit_code: 1, exit_reason: FAILED`, but the process exits 130

- **Location:** `src/l3io/wp/backup/cli/context.py:200-206` (`except BaseException` → `exit_code_for(error)`); `src/l3io/wp/backup/adapters/phase.py:87-88` (the same for the phase record).
- **Problem:** The story says exit 130 "is not in the enum and **not claimed**". `exit_code_of` maps every non-`BackupError` to `FAILED`, including `KeyboardInterrupt`, and `test_a_non_package_error_is_failed_and_argparse_is_usage` pins that. So an interrupted Run's last record claims `exit_code=1, exit_reason="FAILED"` while the shell sees 130. The integer `1` predates this change. The new `exit_reason` field makes the false claim explicit, and the README now tells operators that `run_finished` carries the process's code.
- **Fix:** In `open_run` and `phase()`, map only `Exception` through `exit_code_for`. For any other `BaseException`, record `exit_code=None` and `exit_reason=None` (or omit both), keeping `error=type(exc).__name__`. Document that in docs/logging.md, and add a case that raises `KeyboardInterrupt` inside `open_run` and asserts `run_finished` makes no exit-code claim.

### F-05 — LOW — kind: test-coverage — the literal-exit-code guard does not see the shapes the old code actually used

- **Location:** `tests/unit/cli/test_exit_mapping.py:134-151` (`literal_exit_codes`).
- **Problem:** The guard flags only `ExitCode(<int>)` calls and `exit_code=<int>` keyword arguments. Several shapes pass it:
  - the exact pre-change line in `adapters/phase.py`, `outcome, exit_code = "failed", 1`;
  - the pre-change `return 1` / `return 2` in `run_backup`, `run_verify` and `main`;
  - `raise SystemExit(3)`;
  - `sys.exit(8)`.
  
  The AC's literal wording ("constructs an `ExitCode` from an integer literal") is met. But the epic AC it serves is "the code table lives in `domain/` … not scattered across the CLI" and "`main` returns `int(ExitCode.X)` on every path", and a re-introduced literal `return 1` in `main` would pass. Per rule 4, the planted violations attack directory scope but not the rule's shape scope. I found no such literal in the current tree, so this is a gap in the guard, not a defect in the product code.
- **Fix:** Extend `literal_exit_codes` to also flag:
  - `SystemExit(<int>)` and `sys.exit(<int>)` calls;
  - `return <int>` inside a function whose return annotation is `int` or `ExitCode`, under `cli/`;
  - assignments, including tuple targets, to a name `exit_code` from an int literal.
  
  Plant the old `phase.py` tuple assignment and a `def main() -> int: return 1` in the scope test.

### F-06 — LOW — kind: claim — an argparse usage error's stderr does not name the code's meaning

- **Location:** `src/l3io/wp/backup/cli/parser.py:build_parser` (stock `ArgumentParser.error`); `tests/integration/test_exit_codes_end_to_end.py:139-140` (`if code is not ExitCode.USAGE:` skips the meaning assertion).
- **Problem:** The business AC says "The error printed on stderr names the code's meaning", and the observability AC says the same for "the stderr failure message". A bad `--mode`, an unknown flag, a missing `--wp-dir`, or `restore` ("not implemented in this build") prints only argparse's `usage: … error: …` line, with no `USAGE` or `DESCRIPTIONS[USAGE]`. The end-to-end test exempts USAGE from the check, so the gap is visible in the test but recorded nowhere as a decision. (The no-subcommand case prints the full help, including the epilog table, so it is covered.)
- **Fix:** Either (a) override `error` in a one-method `ArgumentParser` subclass that `build_parser` uses for the root and for subparsers (`parser_class=` on `add_subparsers`): print usage, then `self.exit(int(ExitCode.USAGE), f"{prog}: error: {message} [exit 2 USAGE: {DESCRIPTIONS[ExitCode.USAGE]}]\n")`, and drop the exemption in the end-to-end test. Or (b) record in the story that argparse-originated usage errors are exempt and why.

### F-07 — LOW — kind: observability — the `command_failed` record's `message` carries the stderr decoration and, at DEBUG, a whole traceback

- **Location:** `src/l3io/wp/backup/cli/exit.py:149-157`; `src/l3io/wp/backup/cli/output.py:549-554` (one `text` used for both the record and the plain stderr line).
- **Problem:** The record's `message` is now the full rendered stderr text: `wpbackup2: error: <cause> [exit N NAME: <description>]`, plus, at DEBUG, a multi-line traceback. The code is duplicated, because `exit_code` and `exit_reason` are already separate fields. For a defect at DEBUG the traceback appears twice, once in `message` and once in the `exception` field produced from `exc_info`. docs/logging.md describes `message` as "the operator message". A JSON consumer that groups or alerts on `message` now gets an unbounded multi-line field that changes with stack depth.
- **Fix:** Have `report_failure` pass the redacted cause line (without traceback) as the record's `message`, and print the full `render_failure` text only on the console stderr line. For example, give `emit_failure` an optional `stderr_text`. Leave the traceback to `exc_info` in the record. Add an assertion that the DEBUG JSON record's `message` has no newline.
