## Developer decisions: soundness

1. **Sound.** The gzip probe uses `GzipFile`, and the end-of-archive / `RECORDSIZE` check is right. I confirmed that tarfile's `_Stream` never checks the gzip CRC. One gap: the check examines only the bytes *after* the block where iteration stopped, not that block itself. See F-03.
2. **Sound.** Every `VerificationReason` is reachable through `verify_probe`. The rules "a gzip-compressed v1 outer tar is UNRECOGNISED_FORMAT" and "a payload name disagreeing with `encrypted` is UNREADABLE" are reasonable. Two problems sit in this path: the `"v0"` label on an unclassified result (F-04), and the exceptions `classify` lets through (F-02).
3. **Sound, given the fixed `classify(MemberIndex)` signature.** v0 directories and symlinks show as `file` in the view. `read_member` and extraction re-check the tar header, so nothing unsafe follows from it.
4. **Sound.** `ArchiveReadError`, `ExtractionRefusedError(RefusedError)` and `MemberReadRefusedError(RefusedError)`.
5. **Sound.** `join_phase` is backed by a ContextVar, and the store's VERIFY record is annotated, not duplicated.
6. **Sound.** The exemption is keyed by Protocol, method and return. It checks for staleness and for the cap, and it is tested against a planted scope attack.
7. **Sound as documented.** Partial writes before a refusal are Epic 3's concern. `destination` is a file path.

## Findings

### F-01 — HIGH — kind: claim (security)
- **Location:** `src/l3io/wp/backup/adapters/tar.py:863-890` (`_ExtractFilter.__call__`).
- **Trigger:** `exclude` is matched against the member's lexical role-relative name only. The kept `wp-config.php` can still be written through an in-destination symlink, in two ways (both reproduced in `/tmp/r003/bypass*.py`):
  - A symlink to a directory (`site-root/l -> .`, which `data_filter` allows because it stays inside), followed by `site-root/l/wp-config.php`.
  - A symlink at any name pointing at `wp-config.php`, followed by a regular file with the same name. This works because the filter checks only that the *name* is in the index, never the indexed kind or duplicate occurrences. Verification never opens the inner tar (ADR-0024), so a keyless crafted Archive passes `verify` and reaches this point.
- **Claim contradicted:** "`exclude` holds role-relative paths … that are skipped … so their bytes are never written" (Interface contracts, `extract_archive`). The test plan's "`exclude={wp-config.php}` leaves a pre-existing `destination/wp-config.php` byte-identical" fails as a property.
- **Why it matters:** This is the same outcome the 2026-11-03 hard-link amendment was raised to stop: a crafted Archive overwrites the target's kept config, together with its DB credentials and salts, during a restore that did not ask for `--overwrite-wp-config`. Closing the hard-link path leaves these two open.
- **Suggested fix:** In the filter, apply three checks:
  - Refuse a member whose tar type disagrees with its index `kind`.
  - Refuse a member name seen twice.
  - Compare excluded paths by resolved location: skip, or refuse, when `os.path.realpath(destination/relative)` equals `os.path.realpath(destination/entry)` for any `exclude` entry. Refusing any member whose parent chain passes through a symlink extracted from this Archive is the stricter alternative.

  Add both reproductions to `tests/contracts/test_extraction.py` as cases of the exclude test.

### F-02 — HIGH — kind: claim
- **Location:** `src/l3io/wp/backup/core/verify.py:190-198` (`verify_probe`), reached from `domain/archive_format.py` `_classify_v1` / `manifest_from_json`.
- **Trigger:** A Manifest of deeply nested JSON, which is valid JSON under the 16 MiB cap, raises `RecursionError`. A Manifest with an integer of more than 4300 digits raises `ValueError` (Python's int-string limit), which is not a `JSONDecodeError`. Neither is caught. `verify_archive`, `verify_or_raise` and `wpbackup2 verify` all crash with a traceback (`run_verify` catches only `BackupError`).
- **Claim contradicted:** "`manifest.json` not valid JSON … or larger than the cap: `UNREADABLE`" and "Security: a crafted Archive cannot exhaust …" (Security considerations). `verify()`'s docstring also says "Never raises for an Archive".
- **Why it matters:** Epic 3 runs this verifier before every destructive step. A crafted Archive turns that gate into an unhandled crash instead of a named failure, and an unhandled exception at a public boundary also breaks AD-14.
- **Suggested fix:** In `_classify_v1` (and in `manifest_from_json`), convert `RecursionError` and `ValueError` from `json.loads` / `int` into `MalformedManifestError`, which then becomes `UNREADABLE`. Add both inputs to the crafted-Manifest table in `test_tar_probe.py`.

### F-03 — MEDIUM — kind: claim
- **Location:** `src/l3io/wp/backup/adapters/tar.py:665-674` (`_walk` completeness check).
- **Trigger:** tarfile ends iteration silently on an invalid header at any offset after the first. The block it stopped on has already been consumed and is never checked for zeros. A corrupted header after the payload (a hidden zero-size member) passes verification as `VERIFIED`, and so does a byte flip in the first end-of-archive block. Both are reproduced in `/tmp/r003/hidden.py`.
- **Claim contradicted:** "a truncated or corrupted Archive fails" (AC), and the `MemberIndex.readable_to_end` docstring.
- **Why it matters:** The data effect is nil today, because tarfile stops reading at the same point. But the verifier reports a corrupted file as VERIFIED, and an outer member that an external tar tool would see goes unreported as `UNDECLARED_MEMBER`.
- **Suggested fix:** Require that every byte from `tar.offset` to the end is zero, including the block at `tar.offset`. For example, have `_Counter` keep the last `BLOCKSIZE` bytes read before the drain loop, and require them to be zero along with the drained remainder. Add both corruptions to `test_tar_probe.py`.

### F-04 — MEDIUM — kind: claim (observability)
- **Location:** `src/l3io/wp/backup/adapters/tar.py:773-778` (`verify_archive`), together with `format_label`.
- **Trigger:** An unclassified result (`TRUNCATED` before classification, `UNRECOGNISED_FORMAT`, `UNSUPPORTED_VERSION`, `UNREADABLE` Manifest) has `format_version=None`. The VERIFY record then logs `format_version="v0"` and `integrity="STRUCTURAL_ONLY"`. A truncated v1 Archive, a zip, or a v2 Archive is all logged as having been read as v0.
- **Claim contradicted:** Observability, which cites AD-23: "the Run's logs report which format was read".
- **Why it matters:** An operator reading the logs after a failed restore is told the Archive was v0 when no format was recognised.
- **Suggested fix:** When `view is None`, log `format_version=None` (or `"unknown"`) and omit `integrity`, or log it as `null`. Assert this on the `failed` record in `test_verification_emits_one_verify_record`, which currently checks only `passed`, `reason` and `member`.

### F-05 — LOW — kind: deletion (confidence: medium)
- **Location:** `src/l3io/wp/backup/cli/backup.py:284` (`LocalArchiveStore(verify=verify_or_raise)`).
- **Trigger:** The deleted `structural_check` accepted only a v1 Archive, so the publish gate's contract was "the staged file is v1 with a matching checksum". `verify_or_raise` passes any Archive whose verification passes, including a v0-shaped `STRUCTURAL_ONLY` one.
- **Why it matters:** A writer regression that produced a v0-shaped tar would now publish without failing. The AC defines `verify_or_raise` as "raises when `passed` is false", so the AC does not require this check, but the gate's old guarantee is not re-established.
- **Suggested fix:** For the publish gate only, also require `result.integrity is Integrity.VERIFIED`, either in a dedicated `publish_gate` wrapper or as a `require_verified=True` parameter. Add a test that a v0 tar staged for publishing is refused.

### F-06 — LOW — kind: correctness (error mapping)
- **Location:** `src/l3io/wp/backup/adapters/tar.py:944-945` (`extract_archive`) and `:986-991` (`decrypt_payload`).
- **Trigger:**
  - In `extract_archive`, every `OSError` becomes `ArchiveWriteError(destination)`. That includes a missing or unreadable `payload=` file (from `tarfile.open(payload, "r:gz")`) and read I/O errors on the Archive, which are read-side failures misattributed to the destination.
  - In `decrypt_payload`, an `OSError` while reading the Archive or writing `destination` (ENOSPC, EIO) passes through the `BaseException` branch as a raw `OSError`. The same branch also turns a cipher's own `EOFError` into `ArchiveReadError`, which contradicts its docstring ("the cipher's own errors propagate unchanged").
- **Why it matters:** AD-14 requires that errors cross a public boundary only as package-owned types. Wrong attribution misleads the operator about which file failed.
- **Suggested fix:**
  - Open `payload` through a helper that maps `OSError` to `ArchiveNotFoundError(payload)`.
  - In `decrypt_payload`, wrap the writer's `OSError` as `ArchiveWriteError(destination)` and the reader's as `ArchiveReadError(archive)`.
  - Catch only tar and gzip errors raised by `_payload_body`, not errors raised by the cipher.

### F-07 — LOW — kind: security (consistency)
- **Location:** `src/l3io/wp/backup/adapters/tar.py:738-749` (`read_member`) compared with `extract_archive`.
- **Trigger:** `read_member` returns the *first* inner member with the requested name. `extractall` writes every occurrence, so the last one wins. Nothing checks the inner tar for duplicates, because verification does not open it. A crafted payload can therefore show `REWRITE_CONFIG` or the restore root one config while extraction writes another.
- **Why it matters:** This is low impact on its own, but it is the same class of gap as F-01: the inner tar is trusted to match the index.
- **Suggested fix:** Covered by F-01's duplicate-name refusal. In `read_member`, also continue to the end of the stream and refuse when the name occurs again.

### F-08 — LOW — kind: test-coverage (guard reach)
- **Location:** `tests/contracts/test_extraction.py:58-119` (`FILESYSTEM_EXTRACT_CALLS`).
- **Trigger:** The one-extractor guard detects only `.extract` and `.extractall` attribute calls. `shutil.unpack_archive(archive, dest)` in an adapter extracts a tar and does not fire the guard. The docstring's "Not covered" line names `importlib`/`getattr`, but not `shutil`.
- **Why it matters:** Rule 4, scope: the guard reports success over a set that misses the stdlib's other extraction entry point.
- **Suggested fix:** Add `unpack_archive` to the detected calls, matching both `shutil.unpack_archive` and an imported name, plus a planted scope-attack case. Alternatively, list it under "Not covered" in the docstring.
