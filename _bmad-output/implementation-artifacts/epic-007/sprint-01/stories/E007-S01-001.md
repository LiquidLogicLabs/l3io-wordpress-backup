# E007-S01-001: Point a restored site at a new host and database


**Implements:** FR-11


As an operator,
I want to restore to a different database or URL,
So that I can stand up staging from a production archive.

**Acceptance Criteria:**

**Given** new values for database host, name, credentials, site URL or home URL
**When** a relocating restore runs
**Then** each supplied value reaches the restored `wp-config.php`, and each omitted one leaves its constant unchanged
**And** every relocation option exposed on the CLI has an observable effect — none is accepted and discarded
**And** the rewritten file remains valid PHP and preserves constants this tool does not manage
**And** the write is verified by reading back the rendered value span, not a canonically re-rendered statement, and not values round-tripped through `get()` (ADR-0010)
**And** a mismatch fails the restore before the atomic replace, leaving the original byte-identical

## Business acceptance criteria

### Outcome

`wpbackup2 restore --wp-dir <Site Root> --archive <Archive>` with any subset of `--new-db-host`, `--new-db-name`, `--new-db-user`/`--new-db-password`, `--new-site-url` and `--new-site-home-url` gives a restored Site whose `wp-config.php` carries every value supplied:

- `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `WP_SITEURL` and `WP_HOME` are written by `REWRITE_CONFIG`.
- `DB_NAME` is set to the supplied name by `LOAD_DUMP`'s final, journaled cutover (AD-17 as amended; E003-S02-005). `REWRITE_CONFIG` never writes it.
- The Dump is loaded into that database on the new host, after database's `ensure` has provisioned it (ADR-0015).

A key that was not supplied keeps its value. The one exception is `DB_NAME`, which Epic 3's cutover always sets to the database it loaded. When `--new-db-name` is absent that is the staging name, and the report says so. Constants this tool does not manage, and every byte outside the rewritten value spans, are unchanged.

A reviewer can tell it happened in three ways:

- Diff `wp-config.php` before and after. Only the value spans of supplied keys, plus `DB_NAME`, differ.
- Query the new host. The named database holds the Archive's tables.
- No `--new-*` flag exits `USAGE` as "not yet implemented" any longer.

### Non-goals

- Rewriting URLs inside database content: story 7.3. WP-CLI preflight: story 7.4. A `wp-config.php` outside the Site Root: story 7.2.
- Provisioning SQL. Creating the database, the user and the grant is `l3io-wordpress-database`'s `ensure` (ADR-0015). Escaping a grant pattern (AD-28) and answering existence through the administrator (AD-29) are database's too. This story passes the relocated location and credentials, and Epic 3's database report (E003-S02-004) reports the `EnsureOutcome`.
- A `--new-db-port` flag. The port travels inside `--new-db-host host:port`, which is how `DB_HOST` spells it and how FR-11's port consequence is met. A new flag would be new AD-22 surface that nothing needs.
- A source for the new WordPress password other than `--new-db-password`. That flag is frozen (AD-22) and therefore visible in the process table. A Credential Provider for the *new* WordPress account is not in FR-14's scope or in this story.
- Changing `$table_prefix`, multisite domain mapping, and the library's relocation parameter. The library parameter is Epic 6's `api/`, which passes the same `Relocation` value to `drive_restore`.
- Renaming a database or keeping the previous `DB_NAME` stable (E003-S02-005).

## Technical acceptance criteria

### Interface contracts

**Files.**

- Added: `core/relocation.py`, Epic 7's "relocation logic in `core/`".
- Changed: `domain/errors.py`, by adding subclasses only. E002-S01-001 provides for this ("later stories add subclasses here"), and E003 used the same precedent.

**Conventions,** read from `domain/flag_map.py` and recorded by E002-S01-001 and E003-S01-001:

- The module starts with `from __future__ import annotations`, has a module docstring naming AD-17/AD-18/FR-11, and declares `__all__`.
- Values are `@dataclass(frozen=True, slots=True)`.
- `core/` stays inside `tools/check_purity.py` and the three `[tool.importlinter]` contracts with no exemption. That is why nothing below imports `os` or `urllib`.
- Each error subclasses a `BackupError` branch and declares `exit_code: ClassVar[ExitCode]`. No new `ExitCode` member is added.

**`core/relocation.py`:**

- **`Relocation`** (frozen):
  - `site_url: str | None` and `home_url: str | None`;
  - `db_host: str | None`, the operator's `DB_HOST` spelling verbatim (`host`, `host:port` or `host:/socket`);
  - `db_name: str | None`;
  - `db_user: str | None`;
  - `db_password_supplied: bool`.

  `Relocation.none()` and `is_empty` are also provided.

  The password **never enters `core/`**. It travels as the composition root's `l3io.wp.database.Explicit(db_user, password)` credential source. The root registers it with the Run's `SecretRegistry` (E002-S02-004) before building anything else.
- **`validate_relocation(relocation: Relocation, *, restores_database: bool) -> None`.** It raises the errors in "Error and edge case handling" below. URL checks are string rules with no `urllib`, because `core/` may not import it:
  - an `http://` or `https://` prefix;
  - no whitespace, control character, quote or backslash;
  - no trailing `/`.
- **`config_rewrite_keys(relocation: Relocation) -> tuple[str, ...]`.** The keys `REWRITE_CONFIG` writes, as the supplied subset of the fixed order `DB_HOST, DB_USER, DB_PASSWORD, WP_SITEURL, WP_HOME`. `"DB_NAME"` is never among them (AD-17 as amended).
- **`load_target_name(relocation: Relocation) -> str | None`.** Returns `relocation.db_name`. Epic 3's staging uses it as the load target *in place of* `staging_name(live, run_id)` when it is set, so that `DB_NAME` ends as the operator's name and not as `<name>_l3s_<id>`. With no `--new-db-name`, E003-S02-005's staging name stands.
- **`relocate(site: SiteDescriptor, relocation: Relocation, *, host: str, port: int) -> SiteDescriptor`.** Built with `dataclasses.replace` and no setters (AD-3). It derives the descriptor for the *load* side: `ensure`, `load`, the post-load `survey`, and the FR-7 database emptiness check all address the relocated location.
  - `host` and `port` come from `l3io.wp.database.Connection.from_db_host(relocation.db_host, name)`, called once in the composition root. That is the one `host:port` splitter (AD-3, E002-S01-001). This package splits nothing.
  - The *unrelocated* descriptor is kept for the Safety Snapshot, which captures the target as it stands.
- **`rewrite_undo(keys: tuple[str, ...], config_file: PurePosixPath, snapshot: PurePosixPath | None) -> str`.** The journal's undo text for `REWRITE_CONFIG`. It names the keys in write order and the config path, and says where the prior values are: the Safety Snapshot, or the Archive's config member when this Run laid the file down (7.2). It never contains a value.

**Plan and executor integration.** These are dependencies on Epic 3, listed under the OPEN item below.

- `build_restore_plan` keeps `REWRITE_CONFIG` iff `config_rewrite_keys(...)` is non-empty, by the same filtering predicate, so the plan stays a subsequence of the enum.
- `RestorePlan.actions` gains `rewrite wp-config.php: <keys>` (keys only) and `load into <db_name> on <host>:<port>`.
- At `REWRITE_CONFIG` the executor calls `ConfigCommand.set_constants(config_file, values)`. That is E002-S02-009's `WpConfigWriter`, which delegates each key to `l3io.wp.config.WpConfigFile.set` (v0.1.1, ADR-0010 value-span read-back, atomic `os.replace`, mode and owner kept). `DB_PASSWORD`'s value is resolved from the bound credential source at that call and nowhere earlier.
- The `DB_NAME` cutover stays E003-S02-005's, through the same writer.

### Error and edge case handling

Each refusal below happens before `PREFLIGHT` and changes nothing:

- **A malformed URL** gives `InvalidRelocationValueError(UsageError)` → `USAGE`, naming the flag and the rule broken. This catches a missing scheme, a trailing `/` (WordPress stores `siteurl`/`home` without one), whitespace, a quote, or a value starting with `-`. **A malformed `--new-db-name`** gets the same error after database's `validate_database_name`, which the composition root calls (AD-8 function-scope import). **An unparseable `--new-db-host`** also gets it, after `Connection.from_db_host` raises.
- **`--new-db-user` without `--new-db-password`, or the reverse,** gives `IncompleteRelocationCredentialsError(UsageError)` → `USAGE`. `ensure` needs the pair, and keeping one half from the Archive would silently mix two accounts.
- **`--new-db-name`, `--new-site-url` or `--new-site-home-url` with a Restore Mode that restores no database** (`files`, `files-clean`) gives `RelocationNeedsDatabaseRestoreError(UsageError)` → `USAGE`:
  - `DB_NAME` is written only by `LOAD_DUMP`'s cutover, so in such a mode it would be accepted and discarded (FR-11);
  - a URL change would rewrite content in a database this Run did not restore.

  `--new-db-host` and the credentials alone are allowed in a files mode: they are written by `REWRITE_CONFIG` as a config-only relocation, and the plan says so.
- **The relocated load target already holds tables,** as answered by the administrator's `survey` at the relocated location (AD-29). This gives `RelocationTargetNotEmptyError(RefusedError)` → `REFUSED`, naming the database and host, before any destructive phase. `--force` does not waive it: database's `load` never loads over a non-empty database unless `replace=` is passed, and this package never passes `replace=` (E003-S02-005). An absent or empty target is provisioned by `ensure`.
- **A config write fails mid-sequence.** The writes are a sequence of atomic writes, not one transaction (E002-S02-009):
  - a read-back mismatch, or an unwritable file or directory, on the *first* key leaves `wp-config.php` byte-identical;
  - on the *k*-th key, keys 1…k−1 are committed and key *k* never replaces the file.

  The failure is `ConfigWriteFailedError(path, key, reason)` → `FAILED`. `REWRITE_CONFIG` stays journaled as started and not completed, with `rewrite_undo` naming the committed keys. `LOAD_DUMP` never starts.
- **`set()` refuses to change the file's owner** (config v0.1.1, when the Run is neither root nor the owner). The error names the ownership cause; the writer never retries by copying. No `wp-config.php` at the target is 7.2's lay-down; the writer never creates one.
- **Every relocation value equals the current one.** `changed` is empty, the file is not rewritten, and the phase completes with `keys_changed=()`.
- **A value PHP cannot carry** (a lone surrogate) gives `ConfigWriteFailedError(reason="unrenderable")` with the file unchanged. Quotes, backslashes and `$` in a password are rendered by `l3io-wordpress-config`, not escaped here.

### Observability requirements

- **`relocation_planned` (INFO),** once, after planning. It carries:
  - `keys`, the `config_rewrite_keys` names only;
  - `db_location`, the relocated `host`, `port` and `name`, none of which is a secret;

  - `credential_source`, the label only;

### Security considerations

- **The new password's lifetime.**
  - The composition root registers the `--new-db-password` value with the Run's `SecretRegistry` before it constructs `Explicit`.
  - The value never appears in `Relocation`, `RestorePlan`, a planned action, the journal, a log record at any level, an exception message, or a `repr`. It is resolved only at the `set_constants` call and inside database's `ensure`/`load`.
  - The `--new-db-password` flag is frozen (AD-22) and visible in `ps`. That is stated in its `--help` text; this story does not create the exposure.
- **The file holding it.** `DB_PASSWORD` lands in a `wp-config.php` whose mode and owner `l3io-wordpress-config` v0.1.1 keeps (AD-18.4).
- **No SQL, grant or identifier quoting here.** AD-28/AD-29 are satisfied inside database's `ensure`. The administrator credentials are E003's `--admin-*` source.
- **Values written into PHP are rendered by the config package's renderer,** never by string formatting here. A test writes a password containing `'`, `\`, `$` and `?>` and reads it back with the config package's `get`.

### Testability approach

**`tests/unit/core/test_relocation.py`** is pure: no filesystem, no database, and named for its module like `tests/unit/domain/test_classifier.py`.

- **No `DB_NAME`, in fixed order.** Every combination of `Relocation`'s optional fields is generated from `dataclasses.fields(Relocation)`, not typed out. For each one, `config_rewrite_keys` never yields `DB_NAME` and follows the fixed order.
- **Validation.** One case per `validate_relocation` rule, including a value that starts with `-`.
- **`relocate`.** It changes only the supplied fields and returns a new frozen instance.
- **Phase order.** `REWRITE_CONFIG` appears iff keys are non-empty, and the plan stays a subsequence of `RestorePhase`.

**`tests/integration/test_relocation_config.py`** (`@pytest.mark.integration`, CI MySQL/MariaDB service, `tests/data/wp-config.php` with WordPress's `define( 'KEY', 'value' );` spacing) restores a fixture Archive into a fresh Site Root:

- **Every relocation option has an observable effect.** The test is parametrised over the restore subparser's `--new-*` actions, **derived from the parser** (global rule 4). A `--new-*` flag with no entry in the test's flag→key table fails the test, so a flag accepted and discarded cannot pass.
- For each subset, each supplied key's value span changed and every other byte is identical. `php -l` passes on the result; `php-cli` is already installed by `ci.yml`.
- `DB_NAME` equals `--new-db-name`, and the new host holds the tables.
- **Read-back failure.** `l3io.wp.config`'s `verify_write` is patched to report a mismatch:
  - `wp-config.php` is byte-identical;
  - the exit is `FAILED`;
  - the journal shows `REWRITE_CONFIG` started and not completed;
  - `load_dump` was never called.
- **A non-empty relocated target** exits `REFUSED`, and nothing changed.

**Recording adapters** (extending E003-S01-001's per-mode phase test) assert that no `set_constants` call containing `DB_NAME` happens before the end of `LOAD_DUMP`.

**`credential_sentinel`** (E002-S02-004) is applied to a relocating restore with the sentinel as `--new-db-password`. The sentinel is absent from structlog and stdlib records, stdout, stderr, the journal file and exception text, and present in `wp-config.php`. This satisfies AD-7 items 1, 3 and 4 for this path.

**Dry Run.** With `dry_run_adapters`, `wp-config.php` and the new host are unchanged, and the planned actions name the keys.
