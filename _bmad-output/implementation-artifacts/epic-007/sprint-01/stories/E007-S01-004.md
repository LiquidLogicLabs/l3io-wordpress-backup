# E007-S01-004: Fail before touching anything when WP-CLI is missing


**Implements:** FR-13


As an operator,
I want to be told WP-CLI is absent before the restore starts,
So that I never end up with files restored and content URLs still pointing at production.

**Acceptance Criteria:**

**Given** a requested relocation
**When** WP-CLI is unavailable
**Then** it is detected before the first destructive step, and the run refuses
**And** the failure names WP-CLI, states why it was needed, and points at installation guidance
**And** a non-relocating restore does not require WP-CLI at all
**And** no partial relocation — config rewritten, content not — can result from its absence

## Business acceptance criteria

### Outcome

A restore that asks for a URL relocation (`--new-site-url` and/or `--new-site-home-url`) checks for WP-CLI in `PREFLIGHT`. The check runs before `VERIFY`, before the Safety Snapshot, and before any command adapter is called. If `wp` is absent, unusable or older than the supported minimum, the Run exits **7 (`NOT_READY`)**, and the Site Root, `wp-config.php` and every database are byte-identical.

stderr names WP-CLI and says why it is needed: the serialization-safe content-URL rewrite for the named flags (FR-12). It also gives installation guidance (`https://wp-cli.org/#installing`), the version found if any, and the minimum. A Dry Run refuses the same way, with the same code.

A restore with no URL relocation never looks for `wp`. That covers a plain restore and a config-only relocation (`--new-db-*` alone). Because a missing WP-CLI is caught before anything is touched, it can never leave config rewritten and content URLs still pointing at the old site.

A reviewer can tell it happened by running a relocating restore with `wp` removed from `PATH`: the exit is 7, the message is as above, and nothing changed. The same restore without the URL flags succeeds.

### Non-goals

- **A preflight adapter.** The binary presence and version probe is Epic 5's `adapters/preflight.py` (E005-S01-002, FR-27), implementing E002-S02-007's `Preflight` port. This story declares the requirement and proves the outcome. It does not implement a second checker.
- **The environment-readiness diagnostic command and the README's required-tools table** (FR-27). Both are Epic 5's. They should read this story's requirement constant rather than restate it.
- **Installing WP-CLI or PHP,** or falling back to any non-WP-CLI rewrite (ADR-0005).
- **`wp` disappearing *between* preflight and `SEARCH_REPLACE`.** That is not "absence" at the start of the Run. It surfaces as 7.3's `WpCliFailedError` with `SEARCH_REPLACE` journaled as incomplete (AD-18.1), and the residual is stated in the docstring.
- **A new exit code.** The refusal maps to the existing `NOT_READY` (E002-S01-005). No `ExitCode` member is added.

## Technical acceptance criteria

### Interface contracts

**Files.**

- Changed: `core/relocation.py` (from 7.1).
- No new module. No `domain/errors.py` change, because E002's `PreflightFailedError(tool, needed_for, found)` → `NOT_READY` already exists.

**Conventions** are as recorded in E007-S01-001.

**Requirement constants (`core/relocation.py`):**

- **`WP_CLI_MINIMUM: Final[tuple[int, ...]]`** equals the WP-CLI release pinned in `.github/workflows/ci.yml`. That is the version the integration suite exercises: 2.12.0 was the latest tag when ADR-0005 verified it on 2026-09-15. The equality is enforced by 7.3's `tests/contracts/test_wp_cli_pin.py`, which reads `ci.yml`, so the minimum can never claim support for a version CI did not run.
- **`WP_CLI_REQUIREMENT: Final = ToolRequirement(name="wp", minimum_version=WP_CLI_MINIMUM, needed_for=...)`.** `needed_for` is `"SEARCH_REPLACE: serialization-safe content URL rewrite for --new-site-url/--new-site-home-url (FR-12); install: https://wp-cli.org/#installing"`. `ToolRequirement` is E002-S02-007's type. It must be placed where `core/` may name it; E003-S01-001's `RestorePlan.required_tools` has the same need.
- **`required_tools(relocation: Relocation) -> tuple[ToolRequirement, ...]`** returns `(WP_CLI_REQUIREMENT,)` iff `requires_search_replace(relocation)` (7.3), and `()` otherwise. That includes a config-only relocation, which needs no `wp`.

**Where preflight runs.**

- **Before anything is read or changed.** The restore composition root runs `Preflight.check(...)` at E003-S01-006's step 3 (`PREFLIGHT`). That is after the Site Lock and the incomplete-journal check, and before `VERIFY` (step 4), the Safety Snapshot and the first command adapter.
- **What it checks.** The check covers the requirements derived from the request: `required_tools(request.relocation)` together with Epic 3's own. They are known before planning because a URL relocation alone decides them. The same tuple is carried into `RestorePlan.required_tools`, so the printed plan lists `preflight: wp >= <min> (needed for SEARCH_REPLACE)`.
- **When it fails.** A `ToolStatus` with `present=False`, a version below the minimum, or `version is None` while a minimum is set (fail closed) raises `PreflightFailedError(tool="wp", needed_for=WP_CLI_REQUIREMENT.needed_for, found=<version or "absent">)` → `NOT_READY`.
- **One `wp` path.** On success, `ToolStatus.path` is the `wp` that 7.3's `WpCliSearchReplace(wp=...)` is constructed with. There is one PATH lookup per Run, so the binary that was checked is the binary that runs.

### Error and edge case handling

Every failure below exits **7 (`NOT_READY`)**:

- **`wp` absent from `PATH`.** stderr reads: `WP-CLI (wp) is required: SEARCH_REPLACE — serialization-safe content URL rewrite for --new-site-url/--new-site-home-url (FR-12). Not found. Install: https://wp-cli.org/#installing. Nothing was changed.`
- **`wp` present but unrunnable** (no PHP, permission denied, a non-zero exit from the probe). The message says `found: unusable (<reason>)`.
- **`wp` older than `WP_CLI_MINIMUM`.** The message says `found: 2.10.0, minimum: <min>`.
- **The version cannot be parsed.** The run fails closed: `found: version unknown`.

In all four cases:

- **Nothing was touched.** No journal `current.json` is written, no Safety Snapshot is taken, no command adapter is called, and the Site Lock is released in its `finally`. Preflight precedes all of them.
- **Dry Run behaves identically.** The Dry Run binds the real `Preflight` (a query, AD-4), so it refuses with the same code and message. It never reports "would restore" where the real Run would refuse.
- **Without a URL relocation, nothing is checked.** `required_tools(...)` is `()`, `wp` is never looked up, and its absence is irrelevant. A config-only relocation is included in this.
- **Two tools missing at once** (`wp` plus another): every failed requirement is reported in one message, not just the first, as long as E005-S01-002's `check` returns all statuses (it returns a `Sequence`).

### Observability requirements

- **A refusal** logs one ERROR record for `PreflightFailedError`, with `tool="wp"`, `needed_for`, `found`, `minimum` and the `run_id`. The human-readable message goes to stderr. `run_finished` then carries `exit_code=7`.
- **A successful check** shows up as the plan's `planned_action` line `preflight: wp >= <min> (needed for SEARCH_REPLACE)`, plus the found version and path in Epic 5's preflight record.
- **Later records.** 7.3's `search_replace_completed` carries the same `wp_cli_version`, so a report can tie the rewrite to the checked binary.

### Security considerations

- **The preflight probe runs before the Archive is verified,** so it must not execute anything from the Site or the Archive. It runs no `--path`, does not bootstrap WordPress and does not read `wp-config.php`, and its `cwd` is the Run workspace, so no `wp-cli.yml` from the Site Root is read. These are required of E005-S01-002's probe (OPEN above).
- **No credential is involved in the check.** The probe's argv and the refusal message are covered by the existing AD-7 assertions in `tests/contracts/test_credential_hygiene.py` through `credential_sentinel` on the refusal path.
- **Refusing to run without WP-CLI is the safety property itself (NFR-1).** No partially relocated site, with config on the new host and content on the old URL, can be produced by this path.

### Testability approach

**`tests/unit/core/test_relocation.py`** gains:

- `required_tools` over every `Relocation` combination, derived from `dataclasses.fields`: `wp` is required iff a URL is supplied;
- `WP_CLI_REQUIREMENT.needed_for` names `SEARCH_REPLACE`, FR-12 and the install URL.

**Recording-adapter test,** following the pattern of E002-S02-007's `tests/unit/cli/test_preflight_order.py` and placed under `tests/unit/core/` beside it, since Epic 7 owns no `cli/` file. With a `Preflight` double reporting `wp` absent, it asserts:

- the recording command log is empty;
- the Archive was never verified;
- the journal received no `begin_run`.

The same holds with `dry_run_adapters`.

**`tests/integration/test_wp_cli_missing.py`** (`@pytest.mark.integration`) runs with `PATH` rebuilt from a temp dir that holds only the tools the test needs:

1. **No `wp`.** A relocating restore exits 7, and stderr contains `WP-CLI`, `SEARCH_REPLACE` and `wp-cli.org`. The Site Root tree hash, the `wp-config.php` bytes and an oracle `CHECKSUM TABLE` of the target database are unchanged. No Safety Snapshot or journal exists.
2. **A fake `wp` script printing `WP-CLI 2.0.0`.** The exit is 7 and the message names the found and minimum versions.
3. **A fake `wp` that exits 127** (no PHP). The exit is 7, `found: unusable`. This case depends on the OPEN above.
4. **The same restore without URL flags.** The exit is 0, and `wp` was never invoked: the fake script writes a marker when run, and the marker is absent.
5. **`--new-db-host` alone.** The exit is 0 without `wp`.
6. **A Dry Run of case 1.** The exit is 7 with the identical message.

- **Detection and version probing** are Epic 5's `adapters/preflight.py` (E005-S01-002) behind E002-S02-007's `Preflight` port. Per E002-S02-007's library note, it uses stdlib `shutil.which` plus executing the binary.
