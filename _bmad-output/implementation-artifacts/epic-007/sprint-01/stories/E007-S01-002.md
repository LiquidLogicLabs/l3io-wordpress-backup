# E007-S01-002: Restore a site whose config lives outside the site root


**Implements:** FR-29


As an operator who keeps `wp-config.php` one level up,
I want that layout to restore correctly,
So that following WordPress's own hardening advice does not break backups.

**Given** an archive whose config is outside the Site Root
**When** it is restored

## Business acceptance criteria

### Outcome

A Site whose `wp-config.php` sits one level above the Site Root can be backed up and restored without that layout breaking anything. This is WordPress's own documented hardening convention, and the same lookup `wp-load.php` performs. Restoring its Archive into a fresh `<dir>/public` Site Root works as follows:

- the Archive's `config`-role member is laid down at `<dir>/wp-config.php`, the location its Manifest records, **before** anything rewrites it;
- relocation keys (7.1) and the `DB_NAME` cutover (E003-S02-005) then land in that file;
- nothing is written at `<dir>/public/wp-config.php`.

If the target already has a config where WordPress would look, that file is used and never extracted over. A v0 Archive has no Manifest and no `config`-role member, so no recorded location is passed on and the default `<Site Root>/wp-config.php` is used *(Gate E004 AG-11, 2026-10-30)*. A Site with no locatable config is refused before any destructive step, and the refusal names the paths searched.

A reviewer can tell it happened in three ways:

- the Archive lists `config/wp-config.php` and no member containing `..`;
- the Manifest records `config_path: "../wp-config.php"`;
- after the restore, `<dir>/wp-config.php` exists with the relocated values and `<dir>/public/wp-config.php` does not.

### Non-goals

- **Locations other than the two WordPress itself reads,** `<Site Root>/wp-config.php` and `<Site Root>/../wp-config.php`. Any other Manifest value is refused, never followed (see Error handling).
- **An operator-stated config path** (FR-29's second consequence). It needs a new restore/backup flag on Epic 2's `cli/parser.py`; it is recorded as OPEN below and not delivered here.
- **The backup side's member writing and Manifest key.** These are Epic 2's `core/backup`, `adapters/tar` and `domain/archive_format` (OPEN below). This story consumes them.
- **Making extraction of an in-root `wp-config.php` atomic.** An in-root config travels in the `site-root` tree. This is a different seam, noted in the OPEN item.
- **Changing the laid-down file's permission bits** beyond what the one extraction function's `filter="data"` does.

**`core/config_location.py`:**

- **`ConfigLocation(StrEnum)`** has two members: `SITE_ROOT = "wp-config.php"` and `PARENT = "../wp-config.php"`. These are the only two locations `wp-load.php` searches. The parent is used only when it holds no `wp-settings.php`, meaning it is not itself a WordPress install. The docstring cites that rule.
- **`ConfigFacts`** (frozen) holds what the target already has, gathered by queries in the restore composition root next to E003-S02-006's step 6 (Plan), which already asks whether the target has a `wp-config.php`: `at_site_root: bool`, `at_parent: bool`, `parent_has_wp_settings: bool`.
- **`ConfigPlacement`** (frozen) carries `location: ConfigLocation`, `action: Literal["use-existing", "lay-down"]` and `source: Literal["target", "manifest", "v0-default"]`.
- **`place_config(manifest_config_path: str | None, facts: ConfigFacts) -> ConfigPlacement`** is pure. It applies these rules in order:
  1. If `at_site_root`, use the existing `SITE_ROOT` file, because WordPress reads it first.
  2. If `at_parent` and not `parent_has_wp_settings`, use the existing `PARENT` file.
  3. If `manifest_config_path is None` (v0, or an Archive with no `config` member), use the `SITE_ROOT` default (`source="v0-default"`) and lay nothing down from a `config` role. A v0 view's `config_path` is a member path (`wp-root/wp-config.php`, E002-S01-003), not a location, and a v0 view has no `config`-role member, so rule 3 applies to it *(Gate E004 AG-11, 2026-10-30)*.

### Error and edge case handling

All of the following are raised before `SNAPSHOT` and change nothing:

- **The Manifest's `config_path` is not a `ConfigLocation` value** (`../../etc/x`, an absolute path, `wp-config.php/../x`). This gives `UnsupportedConfigLocationError(RefusedError)` → `REFUSED`, naming the value as found in the Manifest. The value is never joined to a path.
- **`PARENT` is required but `<Site Root>/..` holds `wp-settings.php`.** That directory is another WordPress install, and WordPress would not read a config there. This gives `ConfigLocationConflictError(RefusedError)` → `REFUSED`, naming the directory.
- **No config can be located or laid down** (FR-29's third consequence). This gives `ConfigFileMissingError(RefusedError)` → `REFUSED`, naming every path searched. It covers two cases:
  - nothing exists at the target and the Archive has no `config` member and no `wp-root/wp-config.php`;
  - the Restore Mode has no `EXTRACT` phase (`database`, `database-clean`) and nothing exists at the target. This prevents E003-S02-005's cutover from failing after the load on a file `set()` will not create.
- **A crafted member that escapes its destination** (`config/../x`, a symlink `config/wp-config.php -> /etc/passwd`) is refused by `extract_archive` under AD-11 with the one extraction function's error. Nothing is written.
- **The config's directory is unwritable** at lay-down. This gives `ConfigLayDownFailedError(BackupError)` → `FAILED`, added here and raised `from` the `OSError` that the extraction surfaces. The journal shows the lay-down started and not completed. The undo text says no prior file existed.
- **A file appears at the target location between planning and lay-down.** The Site Lock covers the Site Root, not its parent, so this is a residual time-of-check/time-of-use (TOCTOU) window. The docstring states it rather than claiming exclusivity.
- **Backlog BL-E003-056 (E003 closure ADV-10, lay-down half; re-homed here 2026-11-06 because this story owns the lay-down).** A lay-down never writes a `wp-config.php` that is outside both the FR-7 guard and the Safety Snapshot. For every Restore Mode (cases derived from `RestoreMode`, never listed), when the lay-down location already holds a file, the restore either refuses before `SNAPSHOT` (`REFUSED`, naming the file; nothing changed) or that file is inside `check_target`'s scope and `snapshot_scope` covers it. A Mode that restores no files (`database`, `database-clean`) never plans a lay-down. Test: one case per Mode with an existing file at each `ConfigLocation`, asserting the refusal or the snapshot's coverage, and that the file is byte-identical after a refusal. Resolve BL-E003-056 with this story's key.

### Security considerations

- **The Manifest is untrusted input (AD-11, NFR-5).** Its `config_path` selects one of two enum members and is never used as a path. The only write outside the Site Root this story can cause is to exactly `<canonical Site Root>/../wp-config.php`.
- **That write is safe by construction.**
  - It never overwrites an existing file (rule 1 and 2 placements use it instead).
  - It is never made into another WordPress install's directory.
  - It goes through the one extraction function, with `filter="data"` (no device, setuid or absolute-link members, and group/other write stripped).
- **`wp-config.php` holds `DB_PASSWORD`.** Its laid-down mode is logged, and the subsequent `set()` calls keep it (config v0.1.1, AD-18.4). The `credential_sentinel` fixture is applied to the integration test below to show the parent-config path leaks no value into records.
