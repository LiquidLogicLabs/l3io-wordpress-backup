# E007-S01-003: Rewrite content URLs without corrupting serialized data


**Implements:** FR-12


As an operator,
I want the restored site's content to point at the new URL,
So that widgets, menus and theme options still work.

**Acceptance Criteria:**

**Given** a relocation to a new URL
**When** the content rewrite runs
**Then** it is delegated to WP-CLI's `search-replace`, never a SQL `REPLACE`
**And** afterwards no row in `wp_options`, postmeta or `wp_posts.post_content` contains the old site URL
**And** serialized values that contained it remain valid and can be unserialized — byte-length prefixes recomputed
**And** the rewrite is reported: replacements made, tables touched
**And** a Dry Run reports the replacements it would make and makes none
**And** it runs after the config rewrite, because `wp` bootstraps from the config just written (AD-17)

## Business acceptance criteria

### Outcome

A restore given `--new-site-url` and/or `--new-site-home-url` ends with the restored database's content pointing at the new URL. Afterwards:

- no row in `wp_options`, `wp_postmeta` or `wp_posts.post_content`, or in any other table carrying the site's table prefix, contains the old stored `siteurl`/`home` value;
- every serialized value that contained it still unserializes, with its byte-length prefixes recomputed;
- widgets, menus and theme options survive.

The rewrite is done by WP-CLI's `wp search-replace` (ADR-0005). It runs as the last phase, `SEARCH_REPLACE`, after `REWRITE_CONFIG` and after `LOAD_DUMP`'s cutover, because `wp` bootstraps from the `wp-config.php` just written (AD-17). The restore report states the replacements made, the tables touched and the pairs applied (old → new). A Dry Run prints the planned replacements and changes nothing.

A reviewer can tell it happened in two ways:

- After a relocating restore of the fixture Archive, an independent PyMySQL count of the old URL in those tables is 0.
- `wp option get` on the fixture's serialized options returns the decoded structure carrying the new URL.

### Non-goals

- Any Python or SQL rewrite of serialized PHP: no SQL `REPLACE`, and no `phpserialize`-style re-serializer (ADR-0005, global rule 1).
- **Encoded or partial variants of the old URL,** none of which contains the stored value verbatim:
  - JSON-escaped `https:\/\/old…`;
  - URL-encoded forms;
  - protocol-relative `//old…`;
  - a bare host;
  - the other scheme.

  The operator can run `wp search-replace` for those directly. This is documented in the operator docs.
- **`guid` columns.** They are skipped (`--skip-columns=guid`), per WordPress's guidance that a GUID must never change.
- Multisite (`--network`, `wp_blogs` domains).
- **Running `wp` as another OS user** (`sudo -u`).
- **Detecting a missing or too-old `wp`.** That is story 7.4, through Epic 5's preflight adapter.
- **The config keys.** Those are story 7.1.

## Technical acceptance criteria

### Interface contracts

**Files.**

- Added: `adapters/wpcli.py`, Epic 7's exclusive file.
- Changed: `core/relocation.py` (from 7.1) and `domain/errors.py` (subclasses only).
- Conventions are as recorded in E007-S01-001. In addition, `adapters/` modules follow E002-S02-009's shape:
  - the adapter class is implementation-prefixed (`WpCli…`) under a capability-named port;
  - its no-op twin lives in `adapters/noop.py`;
  - errors are re-raised with `raise … from`, never as a dependency or `subprocess` type (AD-14).

**`core/relocation.py` additions (pure):**

- **Value types** (frozen): `StoredUrls(siteurl: str, home: str)` and `Replacement(old: str, new: str)`.
- **`replacement_pairs(stored: StoredUrls, relocation: Relocation) -> tuple[Replacement, ...]`:**
  - one pair per supplied URL (`stored.siteurl → site_url`, `stored.home → home_url`);
  - identity pairs are dropped;
  - when `stored.siteurl == stored.home`, a single pair is made, using `home_url` if supplied, else `site_url`, and the report records `merged=True`;
  - pairs are ordered by **descending `len(old)`**, so `https://x.test/wp` is rewritten before `https://x.test`.
- **`requires_search_replace(relocation) -> bool`** is true iff `site_url` or `home_url` is supplied. `build_restore_plan` keeps `SEARCH_REPLACE` iff it is true. The plan's `required_tools` then gains the WP-CLI requirement (story 7.4).
- **`nested(pair) -> bool`** is true when `pair.new` contains `pair.old`. Such a pair skips the zero-remaining check, because the new text legitimately contains the old.

**`adapters/wpcli.py` — `WpCliSearchReplace`, the one place `wp` is invoked.**

- **Construction.** `WpCliSearchReplace(wp: str, *, workspace: Path, run=subprocess.run)`:
  - `wp` is the path that preflight resolved (story 7.4);
  - `workspace` is the Run's private workspace (AD-12);
  - `run` is injectable for tests.
- **Signature.** `relocate_content(site_root: Path, relocation: Relocation) -> SearchReplaceReport`, with frozen `SearchReplaceReport(pairs: tuple[Replacement, ...], replacements: int | None, tables: tuple[str, ...] | None, remaining: int | None, merged: bool)`.
- **Steps, all with `cwd=workspace`.** Running from the workspace means WP-CLI never reads a `wp-cli.yml` from the restored, archive-supplied Site Root.
  1. **Read the stored URLs** with `wp option list --search=siteurl` and `--search=home`, using `--format=json` and stdlib `json`. `option list` reads the options table directly. `wp option get` is not used, because it is filtered by the `WP_SITEURL`/`WP_HOME` constants just written and would return the *new* values. The integration test asserts this behaviour against the pinned WP-CLI version.
  2. **Build the pairs** with `replacement_pairs`.
  3. **Preview each pair** with `--dry-run` and the default table output, which is tab-separated when stdout is not a TTY. It is parsed with stdlib `csv` (`delimiter="\t"`, header `Table, Column, Replacements, Type`). This gives the per-table counts and the `tables` set *before* any change. Unrecognised output raises before the first write.
  4. **Replace each pair** with `--format=count`. The reported total must equal the preview total; a difference is logged at WARNING `search_replace_count_drift` and the actual count is reported.
  5. **Re-count each non-nested pair** with `--dry-run --format=count`, which must be 0.
- **The argument vector** is a list, never a shell string, and is fixed:
  - global flags: `[wp, f"--path={site_root}", "--skip-plugins", "--skip-themes", "--skip-packages", "--no-color"]`;
  - for each pair: `["search-replace", old, new, "--precise", "--all-tables-with-prefix", "--skip-columns=guid", "--report-changed-only"]`, plus the step's `--dry-run`/`--format=count`;
  - `--allow-root` is added only when `os.geteuid() == 0`, with WARNING `wp_cli_running_as_root`. `--skip-plugins --skip-themes` keep the site's plugin and theme code from executing. `wp-config.php` itself still runs, and it is the verified Archive's (AD-11).
  - There are no credential flags, because WP-CLI has none (ADR-0005).
  - The URLs cannot be parsed as options, because 7.1's validation requires an `http(s)://` prefix.
- **Database access.** `wp` reaches the database through `$wpdb`, using the `wp-config.php` written by `REWRITE_CONFIG` and the cutover. The environment is inherited unchanged: nothing is added, and specifically not `MYSQL_PWD`, which AD-7 forbids.

### Error and edge case handling

Errors that can occur after `LOAD_DUMP`'s cutover are journaled. The journal leaves `SEARCH_REPLACE` started and not completed, so the next Run refuses and names the phase (AD-18.1). The undo text is the exact `wp … search-replace` command line still owed, built from the same argv function; URLs are not secrets.

- **A `siteurl` or `home` option is absent or empty** in the loaded database. This gives `StoredUrlMissingError(BackupError)` → `FAILED`, before any write.
- **`wp` exits non-zero** on any step. This gives `WpCliFailedError(step, exit_status, stderr_tail)` → `FAILED`. `stderr_tail` is the last 20 lines after `redact`. A failure in a preview or read step precedes every write. A failure during a replace can leave earlier pairs, or earlier rows within one pair, rewritten; the journal says so. Re-running the owed command is safe for non-nested pairs, because a second pass finds nothing to replace.
- **Preview output that does not parse** (wrong header, non-integer count) gives `WpCliOutputUnrecognisedError(BackupError)` → `FAILED`, raised before the first write. It names the WP-CLI version found by preflight.
- **The zero-remaining check is non-zero** for a non-nested pair. This gives `SearchReplaceIncompleteError(pair, remaining)` → `FAILED`.
- **Nothing to do.** A relocation whose pairs are all identities (the new URL equals the stored one) runs no `wp` command and reports `replacements=0, tables=()`.
- **The `SEARCH_REPLACE` phase is never planned** without a URL relocation (`requires_search_replace`), and never in a Mode without `LOAD_DUMP` (7.1's `RelocationNeedsDatabaseRestoreError`).
- **No timeout is imposed.** A large database legitimately takes long, and an interrupted run is the journaled case above.

- **`wp_cli_invoked` (DEBUG)** per `wp` call, with `argv=redact_argv(argv)` (E002-S01-006), `cwd`, `step` (`read_urls`, `preview`, `replace` or `recount`), `exit_status` and `duration_ms`.

### Security considerations

- **No credential reaches WP-CLI by argument or environment** (AD-7, PRD §5.3's feature NFR). WP-CLI reads `DB_PASSWORD` itself from the `0640`-preserved `wp-config.php`. Every constructed argv is asserted free of registered secrets, and so is the environment delta, which is empty by construction.
- **WP-CLI's stdout and stderr** pass `redact` before they are logged or put into an exception.
- **No archive-supplied WP-CLI config is honoured.**
  - `cwd` is the 0700 Run workspace, so a `wp-cli.yml` planted in the Archive's Site Root, which could `require:` arbitrary PHP, is never read.
  - `--skip-packages` ignores globally installed WP-CLI packages.
  - `--skip-plugins --skip-themes` keep restored plugin and theme code from running.
- **`--allow-root` is passed only when the process is already root,** and is logged at WARNING.
- **URL values were validated by 7.1** (scheme prefix, no quote, whitespace or leading `-`) and are passed as list elements with no shell. A crafted URL is therefore neither an option nor a shell injection.

### Testability approach

**`tests/unit/core/test_relocation.py`** gains cases for:

- `replacement_pairs`: longest-first ordering, identity pairs dropped, equal stored values merged, only one URL supplied;
- `nested`;
- `requires_search_replace` over every `Relocation` combination, derived from `dataclasses.fields`.

**`tests/adapters/test_wpcli.py`** is a unit test using a recording `run` double that returns canned WP-CLI outputs. It asserts:

- the exact argv per step, including `--precise`, `--skip-columns=guid` and `--all-tables-with-prefix`;
- `cwd == workspace`;
- `--allow-root` iff a patched `os.geteuid` returns 0;
- no secret from a planted `SecretRegistry` in any argv or log record;
- the TSV preview is parsed into counts and tables;
- unparseable preview output raises before any `replace` call;
- a non-zero recount raises `SearchReplaceIncompleteError`;
- nested pairs skip the recount.

**`tests/integration/test_search_replace.py`** (`@pytest.mark.integration`; CI MySQL/MariaDB service, `php-cli`, pinned `wp`) restores a fixture Archive whose Dump holds:

- a serialized option `a:2:{s:3:"url";s:22:"http://old.example.com";s:1:"n";i:1;}`;
- a widget option;
- serialized postmeta;
- a `post_content` URL;
- a plugin table `wp_plugin_x` carrying the URL;
- a `guid`.

It then relocates to a URL of a **different length** and asserts:

- **PyMySQL oracle.** An independent count, using PyMySQL as a test dependency (already present via database), of the old URL in `wp_options`, `wp_postmeta`, `wp_posts.post_content` and `wp_plugin_x` is 0.
- **Serialization intact.** `wp option get <opt> --format=json` decodes to the expected structure carrying the new URL, which proves PHP unserialized it and the length prefixes are right.
- **`guid` unchanged.**
- **The reported total** equals the oracle's pre-relocation count.
- **A `wp-cli.yml` planted in the restored Site Root** with `require: marker.php` was not loaded: its marker file is absent.
- **`option list` returns stored rather than constant-filtered values** with `WP_HOME` defined.
- **A Dry Run** leaves the oracle count unchanged and prints the planned pairs.

**Phase order (AD-17).** Recording adapters assert that `SEARCH_REPLACE` follows `REWRITE_CONFIG` and the `LOAD_DUMP` cutover in every Mode that contains it.

**Pinned WP-CLI.**

- **The version.** `.github/workflows/ci.yml`'s "install mysql client and WP-CLI" step today fetches the unpinned latest `wp-cli.phar`. It is changed to fetch a pinned release phar and verify its published checksum.
- **The contract test.** `tests/contracts/test_wp_cli_pin.py` reads that pinned version **from `ci.yml`**, which is the source of truth, and asserts it equals 7.4's `WP_CLI_MINIMUM`, so the minimum and the tested version cannot drift.
- **Ownership.** `ci.yml` is in no epic's exclusive set (Epic 1 is closed), so this story edits that one step only.

### Existing-library check

**WP-CLI `search-replace`** is the serialization-safe implementation (ADR-0005, Option A). It walks serialized values and re-serializes them with corrected lengths. It is used as-is through one adapter. Re-implementing it in Python (Option B) or vendoring Search-Replace-DB (Option C) was rejected in ADR-0005 and is not reopened.

**stdlib** covers the rest: `subprocess` invokes the binary, `json` reads `option list`, and `csv` with a tab delimiter reads the preview table. The adapter's own logic is argv construction and output reading, with no serialization or SQL.

**Tests** use PHP itself (through `wp option get`) as the unserialization oracle and PyMySQL as the independent count. No `phpserialize` dependency is added.
