## Findings

### 1. MEDIUM — correctness / claim: the checked `wp` is not always the `wp` that runs

- **Where:** `src/l3io/wp/backup/adapters/wpcli.py:863-865` (`restore_extension`) and `src/l3io/wp/backup/adapters/preflight.py:247-256` (`_locate`).
- **What:** The two code paths look `wp` up differently.
  - `restore_extension` resolves `wp` with plain `shutil.which("wp")`, which honours relative and empty `PATH` entries, and then makes the result absolute.
  - `BinaryPreflight` resolves `wp` with `_locate`, which drops relative and empty entries on purpose. Its docstring says it does this so the probe never runs "a different file from the one a later lookup finds".
  - So when `PATH` has a relative or empty entry ahead of an absolute one, preflight checks one binary and `SEARCH_REPLACE` runs another, even when nothing changes between the two lookups.
- **Reproduced:** with `PATH="rel:<abs>:/usr/bin:/bin"` and a `wp` in each directory:
  - the extension runs `<tmp>/rel/wp`;
  - preflight checks `<tmp>/abs/wp`.
- **Consequence:** an old or broken relative `wp` passes preflight on the strength of the absolute one. It then fails at `SEARCH_REPLACE`, after the load and the config cutover. That is the partial relocation FR-13 forbids.
  - A trailing `:` in `PATH` is an empty entry, which means the current directory. A `wp` phar downloaded into the working directory is a plausible way to hit this.
- **Why this is the story's claim:** the gate's D4/C3 restatement accepts only "a `PATH` entry changing between the two lookups". This divergence happens with an unchanged `PATH`, and the docstring residual at `wpcli.py:46-49` does not mention it.
- **Why the test missed it:** `test_the_checked_wp_is_the_wp_the_extension_runs` uses a `PATH` with one absolute entry. It proves the rule but not the rule's reach.
- **Fix:**
  1. Promote `adapters/preflight.py::_locate` to a public name, for example `locate_binary`.
  2. Use it in `restore_extension` in place of `shutil.which`. Both modules are `adapters/`, so no layer rule is crossed.
  3. Add a case to `test_wp_cli_preflight_order.py` that attacks the scope: `PATH = "rel" + os.pathsep + str(rig.bin)`, a different fake `wp` in each directory, and an assertion that `ext._wp == status.path`. The case should also cover an empty entry (`":" + str(rig.bin)`).

### 2. MEDIUM — testability (vacuous under Dry Run): the command-log and journal assertions never see the Dry Run adapters

- **Where:** `tests/unit/core/test_wp_cli_preflight_order.py:665-668` (`SELECTIONS`), `:751-753` (`Rig.run`) and `:786-788` (`_refused`).
- **What:** For `selection="dry_run"`, `dry_run_adapters(self.h.adapters())` swaps the harness's recording adapters for no-op ones:
  - `RecordingPort` and `RecordingSiteFiles` become `NoopDatabase` and `NoopSiteFiles`;
  - `RecordingJournal` becomes `NoopRunJournal`.
  - `h.run` is then given `journal=adapters.journal_command`, which is the `NoopRunJournal`. See `src/l3io/wp/backup/cli/adapter_sets.py:196-230`.
- **Effect:** in that branch, `rig.h.log.calls == []` and `rig.h.journal.events == []` check objects the Run never touches. Both pass even if the Dry Run called every command adapter and `begin_run` before `PREFLIGHT`.
  - The `verified`, `snapshots` and config-bytes assertions are still real in the Dry Run branch.
  - The story's "the same holds with `dry_run_adapters`" for "command log empty" and "no `begin_run`" is therefore unproven.
- **Fix:**
  1. Give the `Rig` an `ActionLog` (`l3io.wp.backup.adapters.noop.ActionLog`).
  2. Make the Dry Run selection `functools.partial(dry_run_adapters, log=rig.skipped)`.
  3. In `_refused`, assert `rig.skipped.calls == ()` when the selection is `dry_run`. `NoopRunJournal.begin_run` records into that log (`noop.py:615-617`), so the one assertion covers both the journal and the command adapters.

### 3. MEDIUM — claim / observability: the plan does not show the WP-CLI requirement
