# Code review: E007-S01-002 (restore a site whose config lives outside the site root)

## What was verified

- `uv run pytest tests/unit tests/contracts`: 3415 passed, 5 skipped, 1 xfailed.
- `uv run mypy --strict src` (the CI gate) is clean. `ruff` is clean on the changed files. `lint-imports` keeps 3 contracts, and `tools/check_purity.py` passes over 24 pure modules. `core/config_location.py` uses only `PurePosixPath` and does no I/O (AD-1). No `dry_run`/`what_if` name appears outside `cli/` (AD-4).
- The integration files were read but not run, because `DB_HOST` is unset here. They were checked against `tests/integration/live_cli.py`, `drive_restore` (`cli/restore.py:1195-1400`), `build_restore_plan`/`_config_at_cutover` (`core/restore.py:1394-1454`), `_check_config`/`_extract` (`adapters/restore_runner.py:425-780`) and `complete_cutover` (`adapters/staging.py:778`). I found no wrong fixture, exit code or ordering assumption that would make them fail in CI. The `--resolve-interrupted-run` path finds the laid-down parent file at step 3 (`_locate`), and `complete_cutover` writes `header.wp_config_path`, so the resolve test is consistent.
- Deviations (1)–(6) were checked against the code:
  - (1) `extract_archive` turns `OSError` into `ArchiveWriteError` (`adapters/tar.py:1271-1272`). This matches.
  - (1) The claim that the records "live in the runner" does **not** match (see F-01).
  - (2)–(6) match their justifications.
- **SITE_ROOT behaviour change.** Every v1 Archive carries `config/wp-config.php` (`adapters/tar.py:634`) and also the tree's `wp-root/wp-config.php`, because `PROTECTED_PATHS` stops it being excluded. Restoring such an Archive into a target with no config in a files Mode now plans `lay-down` at `<root>/wp-config.php`. The built runner excludes the tree's copy when the role lay-down lands in the Site Root (`restore_runner.py:762-770`), so the result is one file with the same bytes. What changes is visible: a journaled `config:<path>` step, a `lay down …; then extract …` plan line and Dry Run output, and `config_located action=lay-down`. No existing unit test broke. See F-09.
- **BL-E003-056 rule.** `place_config` refuses only when the Manifest says `PARENT`, `<root>/wp-config.php` exists, and an unshadowed parent file exists. Otherwise an existing file is used and nothing is laid down, so a lay-down is planned only when nothing exists at the placement, as judged by `os.path.exists` (see F-03 for the gap).

## Findings

### F-01 — medium — kind: claim
- **Location:** `src/l3io/wp/backup/adapters/restore_runner.py:745-757` (the lay-down); the developer's deviation (1).
- **Problem:** The story's Observability section requires `config_laid_down` (INFO: `config_path`, octal `mode`, `duration_ms`) and WARNING `config_world_readable`. Its Security section says "Its laid-down mode is logged". Deviation (1) says these records "live in the runner". They do not exist anywhere: `grep -rn "config_laid_down\|config_world_readable" src/ tests/` finds nothing. A `wp-config.php` holding `DB_PASSWORD` can now be written outside the Site Root by `filter="data"`, which strips group/other *write* but keeps other-*read* (0644). No record shows its mode and nothing warns.
- **Suggested fix:** Correct the deviation note. Then either add the two records to `_extract` after the role lay-down, which means an owner decision to overrule the gate's "adds no runner code" (the gate did not address these records), or file a backlog item that names this AC as unmet. Do not close the story as meeting the Observability or Security ACs while the records are missing.

### F-02 — medium — kind: edge
- **Location:** `src/l3io/wp/backup/adapters/wpcli.py:751-765`
- **Problem:** The URL-relocation guard for `--wp-config` accepts a stated file when it exists at *either* search location (`searched`). It does not check that it is the file WordPress actually reads. Two cases slip through:
  - `--wp-config <root>/../wp-config.php` while `<root>/wp-config.php` also exists (WordPress reads the root one);
  - a stated parent file whose directory holds `wp-settings.php`.

  In both, WP-CLI's `search-replace` bootstraps from a different config than the one `REWRITE_CONFIG` and the cutover write. That is the partial or mismatched relocation (FR-13) this guard exists to prevent. The `config_located` record also reports `location="../wp-config.php"` for a file WordPress ignores. No unit test covers either case: `test_a_url_relocation_accepts_a_stated_config_at_a_search_place` plants one file only.
- **Suggested fix:** Compute `existing_location(ConfigFacts(...))` from the same three `file_exists` facts. Accept the stated path only when `_same_file(stated, config_file(site_root, _at(existing)))`; otherwise raise `UsageError`. Add the two cases above to the unit test.

### F-03 — low — kind: edge (security)
- **Location:** `src/l3io/wp/backup/adapters/wpcli.py:778-781`; `src/l3io/wp/backup/adapters/site_files.py:73-75`
- **Problem:** The "is a file already there?" facts use `LocalSiteFiles.file_exists`, which is `os.path.exists`. A dangling symlink at `<root>/../wp-config.php` reads as absent, so a lay-down is planned. The lay-down then goes through `tarfile` into that path:
  - if the link points outside the destination, the patched data filter refuses it (`ExtractionRefusedError`, FAILED) after SNAPSHOT/CLEAN rather than REFUSED before them;
  - if the link points inside `<dir>`, the write follows it.

  A directory named `wp-config.php` reads as *present* (use-existing). `locate_wp_config` uses `is_file()`, so the "agree" table (`test_place_config_and_locate_wp_config_agree`), which plants only regular files, does not catch the difference.
- **Suggested fix:** For the lay-down target, treat `os.path.lexists(...)` true but not a regular file as a `ConfigLocationConflictError` before any effect. Keep PHP `file_exists` semantics for the "WordPress would read it" facts. Add symlink and directory rows to the agreement test.

### F-04 — low — kind: claim
- **Location:** `docs/restore.md:536-537`; `src/l3io/wp/backup/core/config_location.py:19-23`
- **Problem:** The TOCTOU statement says a parent `wp-config.php` created between the checks and the lay-down "is not detected". That understates it. The built `_extract` lays down with `tarfile` (open `wb`), so such a file is **silently overwritten**, and it is outside both FR-7's check and the Safety Snapshot. The arch gate says this explicitly ("would write over a file created in that window"). The Security AC's "It never overwrites an existing file" holds only outside that window, and nothing says so.
- **Suggested fix:** State the consequence in both places, for example "…is not detected and is overwritten by the lay-down; it is not in the Safety Snapshot". Optionally note as a follow-up that the runner's preflight already re-reads `config_existed` for `run.config_file` (`restore_runner.py:420`) and could refuse there, which would narrow the window to preflight→EXTRACT.

### F-05 — low — kind: edge
