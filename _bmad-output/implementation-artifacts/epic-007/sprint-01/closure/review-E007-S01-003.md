## Findings

### H1 — HIGH — Sequential pairs rewrite each other's output and corrupt URLs without detection
- **Where:** `src/l3io/wp/backup/core/relocation.py:297-321` (`replacement_pairs`) and `src/l3io/wp/backup/adapters/wpcli.py:474-516` (`_relocate`).
- **What is wrong:** Pairs run one after another as separate `wp search-replace` passes. Sorting longest-first only stops a shorter *old* from eating a longer *old*. It does not stop a later pair's `old` from matching inside an earlier pair's freshly written `new`. Two cases, both checked against the built `replacement_pairs`:
  - **Host extended.** Stored `https://example.com/wp` and `https://example.com`, moved to `https://example.com.au/wp` and `https://example.com.au`.
    - Pair 1 writes `https://example.com.au/wp`.
    - Pair 2 then rewrites that to `https://example.com.au.au/wp`.
    - Pair 2 is `nested`, so its recount is skipped, and the Run reports success.
  - **Only one half moves to a new host.** Stored `https://a.test/wp` and `https://a.test`, with new site `https://a.test/blog` and new home `https://b.test`.
    - Every siteurl-derived link ends as `https://b.test/blog/...`, but the operator asked for `https://a.test/blog`.
    - Neither pair is nested, and both recounts are 0, so nothing detects it.

  This violates the business outcome that content points at the new URL. It is a realistic shape: a ccTLD move, or a site moved out of a subdirectory.
- **Fix:** After building the pairs and before any `wp` call, compute an interference check: refuse, or handle, when for an earlier-run pair `i` and a later pair `j`, `pairs[j].old in pairs[i].new`.
  - **Smallest in-scope fix:** a pure `core/relocation.py::interfering_pairs(pairs)`, plus a new `RefusedError` subclass raised in `_relocate` before the first preview. That makes the refusal journal-safe, because nothing is written.
  - **Full fix, still all WP-CLI and no hand-rolled serialization:** two-stage replacement through unique placeholder tokens: each `old_i` → `token_i` (a uuid not present in the DB, checked by a `--dry-run --format=count` of 0), then each `token_i` → `new_i`.
  - **Tests:** unit tests on both cases above, in `tests/unit/core/test_relocation.py` and `tests/adapters/test_wpcli.py`, asserting that no `replace` call happens.

### H2 — HIGH — An unparseable replace or recount output says "nothing was replaced" after a write
- **Where:**
  - `src/l3io/wp/backup/adapters/wpcli.py:397-401` (`count` → `unrecognised`) and `:336-340` (docstring "before any replacement");
  - `src/l3io/wp/backup/domain/errors.py:735-748` (`WpCliOutputUnrecognisedError`: docstring "before the first replacement", message "`; nothing was replaced`").
- **What is wrong:** `count()` serves the `replace` step, which runs after the write, and the `recount` step, which runs after every write. Both raise `WpCliOutputUnrecognisedError` on any stdout other than one integer.
  - **What can trigger it:** a restored mu-plugin or drop-in that `echo`es, an xdebug-enabled php that prints notices to stdout, or a future WP-CLI change.
  - **What then goes wrong:** the operator is told that nothing was replaced when the pair *was* written. The story's error AC says that an unrecognised output raises "before the first write", and this path cannot meet that, so the error must not claim it.
- **Fix:** Give the error a `replaced_maybe: bool` (or use a separate `WpCliCountUnrecognisedError`), and pick the trailing text by step: "nothing was replaced" for `read_urls` and `preview`, and "the replacement may have been made; see the journal" for `replace` and `recount`. Correct both docstrings. Add a unit test: canned `replace` stdout `"Notice: x\n3\n"`, asserting step `replace` and that the message does not contain "nothing was replaced".

### H3 — HIGH — The integration test always skips in CI; WP-CLI 2.12's output shapes are verified nowhere
- **Where:** `tests/integration/test_search_replace.py:70-84` (`_wp`, the skip at `:83`) and `.github/workflows/ci.yml:225` (`apt-get install ... mysql-client php-cli`, which has no `php-mysql`).
- **What is wrong:** WordPress cannot reach MySQL without `mysqli`, so in CI every test in this file skips. The assumptions the parser stands on are exercised only against canned strings that the implementer wrote: the tab-separated table off a TTY, the header `Table/Column/Replacements/Type`, `Success: N replacement(s) to be made.` on stdout, and `--format=count` printing one integer. So are the AC claims: zero old URLs by the PyMySQL oracle, serialized values intact, `option list` returning stored values under `WP_HOME`, the planted `wp-cli.yml` files not loaded, and the mu-plugin residual observed. The parser tests are circular, and the suite reports green while none of this has run. This is the false-green failure mode that global rules 1 and 3 warn about.
- **Fix:**
  1. Add `php-mysql` to the `ci.yml` step at `:225`. That is a one-token change to the step this story already depends on, and it needs an orchestrator or owner grant, because the gate says this story does not edit `ci.yml`.
  2. Turn the `mysqli`, `wp` and download skips into `pytest.fail` when `os.environ.get("CI")` is set, so a missing prerequisite in CI cannot read as success.
  3. Once it has run once, capture the real `--dry-run` and `--format=count` stdout from WP-CLI 2.12.0 into fixtures that `tests/adapters/test_wpcli.py` replays, so the unit tests stop testing the implementer's own assumption.
  4. Until the grant exists, record this as an open item on the story rather than passing it.

### M1 — MEDIUM — The ancestor check walks the lexical path; WP-CLI walks the physical one
- **Where:** `src/l3io/wp/backup/adapters/wpcli.py:298-302` (`find_wp_cli_config(self.cwd)`) and `:170-180`.
- **What is wrong:**
  - `cwd` is built from `platformdirs.user_state_path(...)`, which is never resolved (`adapters/journal.py:111`).
  - WP-CLI finds `wp-cli.yml` upward from PHP's `getcwd()`, which is the physical path after `chdir`.
  - If any component of the state path is a symlink, the physical ancestors differ from the lexical ones the check walks. Examples: a symlinked `$HOME` or `~/.local/state`, or NFS automount homes.
  - Scratch check: a `wp-cli.yml` planted in the symlink target's parent is reported as `None` by the lexical walk and found by the resolved walk.
- **Fix:** Check both `self.cwd` and `self.cwd.resolve()`, and refuse if either finds a file. Add a unit test that plants the file above a symlink target and points a patched `journal_directory` through the link.

### M2 — MEDIUM — The env guard proves "explicit", not "minimal", and has unstated alias blind spots
- **Where:** `tests/contracts/test_child_env_explicit.py:124-129` (`_explicit_env`), `:92-106` (`_aliases`) and the docstring's "Blind spots, stated" at `:32`.
- **What is wrong:** Each of the following produces zero violations (checked with `violations()`). None of them is in the stated blind spots, and global rule 3 says prose must not overstate coverage.
  - `subprocess.run(x, env=os.environ)` and `env={**os.environ}` pass the guard. The red-team issue was a child that inherits the environment, so the guard accepts exactly the defect it exists to stop.
  - `from subprocess import *` followed by `run([...])` passes.
  - `import os.path` followed by `os.system(...)` passes. The alias name is `os.path`, which is not in `MODULES`, yet the statement binds `os`.
- **Fix:**
  1. In `_explicit_env`, refuse an `env=` value whose AST contains a reference to `os.environ`, `os.environb` or `os.getenv`, through the resolved `os` aliases. Plant `env=os.environ` and `env={**os.environ}`.
  2. Treat `ImportFrom` with `*` from `subprocess`, `os` or `asyncio` as binding every targeted name, or refuse star imports from those modules outright.
  3. Bind `alias.name.split(".")[0]` for dotted imports.
  4. Add planted cases for 2 and 3.
  5. List what still escapes (an env built from `os.environ` in another function and passed by name) under the stated blind spots.

### M3 — MEDIUM — The leak test never touches the production runner, so it can false-green

Or drive `WpCliSearchReplace(run=run_child)` with a fake `wp` script that dumps its environment.

### M5 — MEDIUM — `kind: claim` — "Re-running the owed commands is safe" is false for nested and interfering pairs
- **Where:**
  - `docs/restore.md:252-254` ("re-running them is safe, since a second pass finds nothing already replaced");
  - the journal text in `src/l3io/wp/backup/adapters/wpcli.py:539-541` ("re-run: …", with no caveat);
  - `docs/restore.md:239-240` ("any old URL left fails the Run").
- **What is wrong:**
  - **Nested pair.** For `old` → `old/blog`, a second pass rewrites `old/blog` to `old/blog/blog`. The operator gets this unqualified advice exactly when a run was interrupted. Only `owed_search_replace`'s docstring states the caveat; the text the operator sees does not.
  - **Interfering pairs (H1).** Re-running both owed commands double-applies those too.
  - **Recount.** Nested pairs skip the recount, so "any old URL left fails the Run" is not true for them.
  - **Merged case.** When the stored `siteurl` and `home` were equal, the owed text still lists two commands.
- **Fix:**
  - **Docs and journal text:** state that a pair whose new URL contains its old URL, or whose new URL contains another pair's old URL, must not be re-run blindly. Tell the operator to check with `wp search-replace <old> <new> --dry-run` first.
  - **Recount wording:** qualify the "any old URL left" sentence for nested pairs, matching the `post_check_skipped` warning.
  - **Owed text:** add `--dry-run` guidance to the owed text.
