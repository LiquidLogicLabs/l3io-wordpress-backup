## Findings

### H1: the integration test's all-flags case builds `expected` in the wrong insertion order, so it fails in CI

- severity: high
- location: `tests/integration/test_relocation_config.py:213-218`, with `_groups()` at `:127-134`
- problem: The test's fixture `wp-config.php` (`live_restore.config_text`) does not define `WP_SITEURL` or `WP_HOME`. `l3io-wordpress-config`'s `set` adds an absent constant directly after `<?php`, so each later insert lands above the earlier ones.
  - At runtime, `REWRITE_CONFIG` calls `set_constants` with `WP_SITEURL` and then `WP_HOME` (`rewrite_values` order; `config_writer.set_constants` writes "in the order given"). The file therefore ends `<?php`, `WP_HOME`, `WP_SITEURL`.
  - The test builds `expected` by iterating `given`, whose order is the group's. For the all-flags group that order is `sorted(_new_flags())`, which puts `--new-site-home-url` before `--new-site-url`. `expected` therefore ends `<?php`, `WP_SITEURL`, `WP_HOME`.
  - Reproduced with the locked library: the two orders give different content. So `assert after == expected.content` fails for the `--new-db-host+…+--new-site-url` case. The single-flag cases are unaffected.
- fix: Build `expected` the way the Run writes it. First apply `relocation.rewrite_values` in order (the `REWRITE_CONFIG` writes), then the cutover keys in `planned_cutover_keys(relocation)` order with `planned_cutover_targets(load, relocation)` plus the password. Better still, see M6: also define `WP_SITEURL`/`WP_HOME` in the fixture, so the check is a value-span comparison and does not depend on where the library inserts.

### M1: `REWRITE_CONFIG`'s prior URL values are kept nowhere in a database-only Mode, yet the journal's undo text says a Safety Snapshot holds them

- severity: medium
- location: `src/l3io/wp/backup/core/relocation.py:214-232` (`relocation_undo`); `src/l3io/wp/backup/adapters/restore_runner.py:816-838` (`_rewrite_config`)
- problem: `--new-site-url`/`--new-site-home-url` are allowed in `database` and `database-clean`. In those Modes `snapshot_scope` captures `BackupScope.DATABASE` only (`core/restore.py:602-628`).
  - `JOURNALED_CONSTANTS` is `{DB_NAME, DB_HOST, DB_USER}` (`domain/journal.py:38`), so the header does not record the prior `WP_SITEURL`/`WP_HOME`.
  - `_rewrite_config` saves a copy only under `--overwrite-wp-config`.
  - So when `REWRITE_CONFIG` commits `WP_SITEURL` and the Run then fails or is killed (for example, `WP_HOME`'s write or `LOAD_DUMP` fails), the prior values exist nowhere. The undo that `undo_for` prints from `phase_undo` says "a Safety Snapshot that covered files holds the prior wp-config.php", and no such snapshot exists.
  - The same applies to any Mode run with the snapshot skipped.
  - The result is a live site whose `wp-config.php` points at the new URL while its database is the old one, with a recovery instruction that leads nowhere (AD-18). The story's design text required the undo to say "where the prior values are".
- fix: In `_rewrite_config`, when `rewrite_values` is non-empty, take the same `config_command.save_copy(config_file, saved)` plus the `STEP_CONFIG_SAVED` step the overwrite path takes. `undo_for`'s existing `config_*` arm then prints "copy <saved> back". This needs the root to set `header.saved_config` for a URL relocation as well. That is a `cli/restore.py` header line, outside the two granted lines, so it needs the grant extended or an owner note. As a minimum within scope, `relocation_undo` should be told the Mode or snapshot scope and must not claim a snapshot holds the file when none covers files.

### M2 (kind: claim): `docs/restore.md` says a read-back mismatch always leaves `wp-config.php` byte-identical

- severity: medium
- location: `docs/restore.md:177-179`
- problem: The added text reads "Every write is read back … a mismatch fails the Run (exit 1) and leaves `wp-config.php` byte-identical." That holds only for the first key.
  - `set_constants` is one atomic write per key. A mismatch on `WP_HOME` leaves `WP_SITEURL` already committed (the story's own edge case: "on the k-th key, keys 1…k−1 are committed").
  - A failed cutover write is `ConfigCutoverError`, with keys already written and keys pending.
  - Operators read this paragraph to decide whether recovery is needed.
- fix: Say that each key's write is verified before it replaces the file. A mismatch fails the Run and leaves the file as it was before that key. Earlier keys of the same phase stay written, and the journal names them.

### M3 (kind: claim): the BL-E003-057 AST guard checks only `os.open`, but its docstring claims every write goes through a port. The planted violation does not attack the guard's scope.

- severity: medium
- location: `tests/unit/adapters/test_restore_runner.py:317-347`
- problem: `_os_open_calls` matches only `os.open(...)` written as an `os.` attribute call. These would all reintroduce the BL-E003-057 workspace write and pass the guard:
  - `Path(...).write_bytes(body)`
  - builtin `open(path, "wb")`
  - `os.fdopen`
  - `from os import open`
  - `shutil.copyfile`
  - `tempfile.NamedTemporaryFile`

  `test_the_executor_opens_no_file_itself`'s docstring says "every write in `adapters/restore_runner.py` goes through a port", which overstates what is checked (global rules 3 and 4). The behavioural tests (`test_a_dry_run_overwrite_writes_no_config_file`, and the workspace-empty assertions) are the real protection. Their scope is the workspace directory only.
- fix: Widen the matcher to every file-writing call form: builtin `open`, `os.open`/`os.fdopen`, any `.open(`, `.write_bytes(`, `.write_text(`, `shutil.*`, `tempfile.*`, plus `ImportFrom` of those names. Plant at least one violation in a form other than `os.open` (for example `Path(p).write_bytes(b)`). Alternatively, restate the docstring as "no `os.open` call" and name what is not covered.

### M4: `core/relocation.py::_cutover_keys` re-implements `core/restore.py::planned_cutover_keys`

- severity: medium
- location: `src/l3io/wp/backup/core/relocation.py:177-191` (used by `relocation_actions`, `:194-211`)
- problem: The Built interface says "Nothing in it duplicates `core/restore.py`." `_cutover_keys` derives the cutover's key set from the flags a second time. `planned_cutover_keys(relocation)` is what the cutover, the journal header and `_check_header` use. The plan's action line ("the cutover sets … ") therefore comes from a separate derivation that can drift. If, for example, E003 changes when `DB_HOST` is written, the plan would name keys the cutover does not write. The two agree today.
- fix: Make `relocation_actions` take the already-built cutover facts, for example `relocation_actions(keys: tuple[str, ...])`. In `WpCliRestoreExtension.resolve`, build the `RestoreRelocation` without `actions`, then call `dataclasses.replace(relocation, actions=relocation_actions(planned_cutover_keys(relocation)))`. Delete `_cutover_keys`.

### M5: no test covers a relocating Dry Run, which the story's Testability section requires

- severity: medium
- location: missing; the natural home is `tests/unit/adapters/test_restore_runner.py` or `tests/unit/adapters/test_wpcli_extension.py`
- problem: The Testability section requires: "Dry Run. With `dry_run_adapters`, `wp-config.php` and the new host are unchanged, and the planned actions name the keys." The only new Dry Run test is the `--overwrite-wp-config` one. No test drives a plan with `rewrite_values` and `cutover_*` through `dry_run_adapters`. Such a test would assert three things:
  - `wp-config.php` is byte-identical;
  - no `ensure`/`load` effect reaches the database command half;
  - the planned actions contain the `rewrite wp-config.php: …` and `relocate: the cutover sets …` lines naming keys only.
- fix: Add one runner-level test using `_harness`/`StagedHarness` with a relocation built by `restore_extension(...).resolve(...)` and `adapters=dry_run_adapters(h.adapters())`. Assert the config bytes, that the recording log has no non-skipped `set_constants`/`ensure`/`load`, and that the planned action texts name the keys.

### M6: the integration test's "every other byte is identical" is checked against the same library's re-render, and the fixture is not WordPress-spaced

- severity: medium
- location: `tests/integration/test_relocation_config.py:213-219` and `:332-335`
- problem: `expected` is built by `l3io.wp.config.WpConfigString.set`, the same renderer that wrote the file. If the library disturbed neighbouring bytes (whitespace, comments, another constant's span), both sides would agree and the test would pass. The AC asks for "each supplied key's value span changed and every other byte is identical".
  - The Testability section also names `tests/data/wp-config.php` with WordPress's `define( 'KEY', 'value' );` spacing. The test uses `live_restore.config_text` instead, which is compact `define('KEY', 'v');` with no `WP_SITEURL`/`WP_HOME`. The spacing case the AC calls out is never exercised end to end, and the URL keys are always inserted rather than rewritten in place.
- fix: Seed the site's config with WordPress spacing and with `WP_SITEURL`/`WP_HOME` already defined. Then derive `expected` from `before` by literal value-span substitution (`"'<old>'" -> "'<new>'"`, as `tests/adapters/test_config_writer.py:399-404` does), not by the library. Keep the `get()` read-back separately. This also removes H1's ordering dependence.

### L1: the reviewed diff's relocation table broke `test_restore_docs`. The table is fixed in the working tree, but the guard still parses the whole file.

- severity: low
- location: `docs/restore.md:166-173`; `tests/contracts/test_restore_docs.py:41-48`
- problem: In `/tmp/e007-s01-001.diff`, the new table's rows begin `` | `--new-…` | `KEY` | ``. `_mode_rows`' regex `^\|\s*`([a-z-]+)`\s*\|\s*`([^`]+)`` matched them, so the Modes contract failed (reproduced). ### L2 (kind: claim): `docs/restore.md` says a non-empty load database is refused "at `LOAD_DUMP` … after the Safety Snapshot", but it is usually refused at `PREFLIGHT`

- severity: low
- location: `docs/restore.md:205-209`; also the docstrings at `tests/integration/test_relocation_config.py:20,229`
- problem: Under `--force`, `check_staged` (in `PREFLIGHT`) calls `check_load(target.load, source=None)` with no `replace=`. The database package reports `DATABASE_NOT_EMPTY` for a database with tables (`l3io/wp/database/transfer.py:854-862`). That code is not in `ENSURE_RESOLVES`, so `_refuse` stops the Run before `SNAPSHOT` (`adapters/staging.py:248-266`). The refusal happens at `LOAD_DUMP` only when the Site's account cannot see the database. The real behaviour is safer than the docs say, but the docs and the test docstring describe a different phase and say the refusal is journaled.
- fix: Say the refusal comes at `PREFLIGHT` from the database checks. Give `LOAD_DUMP` only as the fallback when the account cannot see the database. Make the integration test assert the phase it expects (no `SNAPSHOT`/`LOAD_DUMP` `phase_started` in the journal), so the docs are checked.

### L3 (kind: claim): the URL "must name a host" rule accepts URLs with no host

- severity: low
- location: `src/l3io/wp/backup/core/relocation.py:112-114`; `docs/restore.md:193-196`
- problem: The rule refuses only an empty rest or a rest starting with `/`. `https://?p=1`, `https://#x`, `https://:8443` and `https://@` all pass and are written to `WP_SITEURL`/`WP_HOME`, yet the docs say the value must "name a host".
- fix: Take the authority as the text before the first of `/?#`. Refuse it when it is empty, starts with `:` or `@`, or ends with `@`. Add those four values to `test_each_url_rule`. This stays a string rule, no `urllib`.

### L4: `relocation_planned` is logged before planning and before FR-7, and with only `--new-db-host` its `db_location.name` is not the database loaded

- severity: low
- location: `src/l3io/wp/backup/adapters/wpcli.py:132-150`
- problem: The story places the event "once, after planning". Here it is emitted inside `resolve` (`cli/restore.py:1312`), before the survey, `check_target` and `build_restore_plan`. So a Run refused by `NonEmptyTargetError` still logs that a relocation was planned. Also, with `--new-db-host` alone, `load_location.name` is `site.db_name`, but the Dump goes to the staging name on that host (`staging._target` uses `base.with_name(load_name)`). The event's `db_location.name` therefore names a database the Run does not load. The `name` default follows the story, so it is only the log's wording that misleads.
- fix: Either rename the field to what it is (`location_checked`), or log `db_location` with the actual load name when `load_database is None` (for example, `name=None` plus `load_target="staging"`). Note in the docstring that the event precedes planning, or move it to the root, which needs the grant extended.

### L5: relocation flags are validated late, after the journal check, credential resolution and full Archive verification

- severity: low
- location: `src/l3io/wp/backup/adapters/wpcli.py:104` and `:154-164`
- problem: `validate_relocation` runs only in `resolve`, at step 6 of `drive_restore`. That comes after the incomplete-Run check, the Site Descriptor and credential sources (step 3), and probing and verifying the whole Archive (step 5). A typo such as `--new-site-url staging.example` exits `USAGE` only after the Archive has been fetched, read in full and possibly decrypted. Nothing persistent changes, so the AC holds. The cost is the wasted fetch and verification, plus side reads such as credential providers.
- fix: Run the Mode-independent rules (URL rules and the pair rule) in `restore_extension` itself, which `drive_restore` calls at `:1197` before step 3. Keep the Mode rule in `resolve`. Splitting `validate_relocation` into `validate_relocation_values(request)` and `validate_relocation_mode(request, mode)` keeps both pure.

### L6: the executor now imports a constant from the real config adapter module

## Checks that found nothing

- **Credentials.** `--new-db-password` reaches the root only as `ExplicitCredentialSpec` and is registered twice, which is idempotent. No error message echoes a value (`InvalidRelocationValueError`, `IncompleteRelocationCredentialsError`, `RelocationNeedsDatabaseRestoreError`, and `database_location_from_db_host`'s `UsageError`). Actions, undo text and `relocation_planned` hold keys only. Logged tracebacks go through `format_exc_info` with no locals, so the in-memory Archive config text cannot reach a record.
- **AD-1, AD-4, ADR-0015 amendment.** `core/relocation.py` imports no `os` or `urllib`. `adapters/wpcli.py` imports no `cli` and no `l3io.wp.database`. No `dry_run`/`what_if` identifier was added outside `cli/` and `api/`.
- **Library rule.** The URL rules are documented string rules that `core/` must not delegate to `urllib`. Host and port parsing reuses `database_location_from_db_host`. Rendering and verification are `l3io-wordpress-config`'s. Nothing here is hand-rolled where a library would do.
- **Integration fixtures and teardown.** `LiveSite.teardown` drops every database whose name starts with the site's (covering `_rel`, `_full`, `_cli` and the staging `_l3s_` names) and every user in `extra_users`. Each relocated user is appended before the restore runs. `verify_write` is called by keyword, so the `lambda **_` patch takes effect. `ensure` runs inside `LOAD_DUMP` (`load_staged`), so `site.databases() == databases` is a valid test that nothing was loaded.
