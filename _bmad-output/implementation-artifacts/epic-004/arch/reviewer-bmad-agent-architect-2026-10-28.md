## Findings

BLOCKER: No story decrypts encrypted `site-root` or `config` members on restore, so restoring an encrypted Archive would write `age` ciphertext over the Site's PHP files and `wp-config.php` (FR-4 "restore from one by supplying the same"; NFR-1). This is a spec-gap. E004-S01-003 §Non-goals L46 hands encrypted restore to "Epic 3 story 3.1, which calls this story's decryption adapter". But Epic 3 extracts only through E002-S01-003's `extract_archive(source, destination, view, *, roles, exclude)` (E002-S01-003 L65; E003-S01-001 L71; E002-S02-012's `SiteFilesCommand.extract` delegates to it), and that function takes no cipher. Under AD-11 it is the one extraction function. It is built on `tarfile`'s filter, which cannot transform member content. Only the Dump has a decrypt path (E003-S02-005 L70, "decrypted upstream of the port"). Before E004 or E003 builds, the AD-11 function needs a `cipher` (or a decrypting member source) and a per-member streaming decrypt, decided once. That changes E002-S01-003's gated contract and its consumers in E003. E004-S01-003 should then name the consumer it serves instead of "Epic 3 story 3.1".
MAJOR: E004-S01-002 contradicts the ADR-0017 amendment of 2026-10-28 (spec-conflict, ADR-0017 "Amendment — 2026-10-28: the Concern is resolved — skip and warn"; also E003 gate "Carried items", AG-2). The amendment says `extract_archive` no longer refuses an outward symlink: it skips the link, records it in `ExtractResult.skipped_links` and continues. Four places in the story still assume refusal: §Outcome L33 ("`symlink-escape` is checked at extraction instead"), §Non-goals L46 ("asserts only that extraction refuses one"; the Concern is no longer open), §Interface contracts L57 (`malformed/` = "must not pass verification, or … must not extract") and §Error handling L77 ("`extract_archive` refuses it"). As written, the test fails against a correct E002-S01-003. Rewrite the case so that `symlink-escape` extracts with the link skipped and listed in `skipped_links`, nothing is written outside `tmp_path`, and verification passes as `STRUCTURAL_ONLY`, which the amendment makes assertable. Then move the fixture out of `malformed/`, because the directory defines the failing set by scope. The E003 resolution patched E002-S01-003, E003-S01-001 and E003-S01-006 but not this story.
MAJOR: A missing or wrong key is found only at the first decrypt, which in a restore can come after destructive phases (NFR-1, FR-7; spec-gap). E004-S01-003 §Error handling L111–L112 raises `ArchiveDecryptionError(reason="no_key")` "when the first encrypted member is about to be decrypted", and `wrong_key` only on decrypt. In a restore that point follows SNAPSHOT, and in `*-clean` modes it can follow the Site Root clear or the database drop. Nothing owns raising `no_key` either: with `cipher=None` there is no cipher object to raise it. The planning step should refuse before any destruction when `view` has members marked encrypted and `request.cipher is None`. A key check should also run before the first destructive phase: open one encrypted member's `age` header with the identities or passphrase, which database's `decrypt` does on the first chunk. State the raise site (Epic 3's planner, using E004's error type) and include it in the restore Dry Run.
MAJOR: The key configuration on the restore side is underspecified, and any of three gaps breaks a real restore (spec-gap; E004-S01-003 L68, L73, L76, L99; AD-26). (a) A passphrase-encrypted Archive cannot be restored. E002-S01-006 L58 calls `resolve_passphrase` "only when passphrase encryption is requested or a passphrase-protected identity must be unlocked". Restoring a passphrase Archive is neither, and E002-S02-011 L65 does not say `--encrypt-with-passphrase` is accepted on `restore`. (b) `RestoreRequest.cipher` both decrypts the Archive and encrypts the Safety Snapshot (E003-S02-003 L62, "encrypted iff `request.cipher is not None`"). With only `--identity-file` the cipher has no recipient, and what `AgeMemberCipher.encrypt` does then is undefined. Options: derive the recipients from the identities, refuse, or warn and write plaintext. (c) `build_member_cipher(identity_files=…, passphrase=…)` does not say that the passphrase unlocks the identity (`read_identity(path, passphrase)`) and is then not passed to the cipher. Read literally, `AgeMemberCipher(identities=…, passphrase=…)` breaks database's "exactly one" rule. The mutual-exclusion text names only recipients plus passphrase.
MAJOR: `--encrypt-with-passphrase` with no resolvable passphrase produces a plaintext Archive silently, which contradicts AD-26's "no silent plaintext" and FR-4. E004-S01-003 L76: `build_member_cipher` "returns `None` when given no recipient, recipients file, identity file or passphrase". Under cron (no TTY, no `L3IO_WP_BACKUP_PASSPHRASE`), `resolve_passphrase` returns `None` (E002-S01-006 L58), so the factory returns `None` and the backup writes plaintext. L73's "neither when encryption is requested raises `EncryptionConfigError`" cannot fire, because the factory has no "requested" input. Add `passphrase_requested: bool` (or `encrypt: bool`) to the factory, or require the roots (E008-S01-001, E006-S01-001) to raise `PassphraseUnavailableError` when the flag is set and nothing resolves. Then test it.
MAJOR: E004-S01-003 depends on a parallel epic that the plan does not order before it. §Interface contracts L100 has `AgeMemberCipher.required_tools()` call E005-S01-002's `passphrase_backend_requirements` (`adapters/preflight`, Epic 5). The plan puts E004 and E005 together in phase 2 (`plan-2026-10-27-v2.yaml` phase 2) with no dependency between them, so in E004's dev loop the import target does not exist. Pick one: order E005 before E004 in the plan; move the call to the root (E008-S01-001), with `AgeMemberCipher` exposing only `mode`; or have `required_tools` take the requirement function as an argument.
MAJOR: The CI interop requirement cannot be met as specified. E004-S01-003 L86 says the interop test "covers both backends where the binary is present, and skips neither silently in CI", and L167 installs `age` "via an apt step". The CLI backend needs `age` ≥ 1.3 plus `age-plugin-batchpass` (ADR-0014 amendment). Apt's `age` is older: `ubuntu-latest` (24.04) ships 1.1.x, and even 26.04 "resolute" carries 1.2.1 (checked with `apt-cache policy age` on this host). No apt package provides `age-plugin-batchpass` (`apt-cache search batchpass` returns nothing). As written, CI either fails or skips the CLI-backend case. State the provisioning (a pinned upstream `age` release tarball plus the batchpass plugin, verified by checksum), or limit CI to the binder backend and say so in the story.
MAJOR: Several E004 acceptance tests cannot go green in E004's own dev loop, because they go through surfaces that E006 (phase 3) or E008 (phase 4) build. (1) E004-S01-001 §Testability L120: the end-to-end exclusion test "runs once E008-S01-001 binds the flags; until then they exit `USAGE`", and no xfail or skip mechanism is named, so the story's Outcome is never proven in its own loop. (2) E004-S01-003 L168–L173: the inspector test backs up "with a recipient", but the flags sit in `NOT_YET_IMPLEMENTED` until E008. (3) E004-S01-003 L177: `test_single_passphrase_chain` requires "the CLI and `api/` roots" to resolve through `resolve_passphrase`. `api/` is E006's and the CLI binding is E008's. (4) L165's AST scan of `api/` hits the same problem. Fix: drive (1) and (2) through E002-S01-004's `drive_backup(BackupRequest(..., exclusion=ExclusionSet…, cipher=build_member_cipher(...)))`, which exists after E002. Then either move the root-identity halves of (3) and (4) to E008-S01-001 or E006-S01-001, or make their scope assertion accept an absent `api/` until it exists.
MINOR: Ownership conflict inside `epics.md`. The Epic 4 header (§Epic 4, L513) says "Owns exclusively: … `domain/archive_format` (v0 classifier only)". The Epic List ownership note (L145–L148) says `domain/archive_format` is "Epic 2's alone, including the pure v0 classifier", and that Epic 4 owns only the v0 fixtures and tests. The stories follow the Epic List (E004-S01-002 L41), so the header is stale and should be corrected to match.

E004-S01-003 L30 ("recipient/identity encryption builds on database v0.1.0 … until then a passphrase-only configuration is refused") is overruled by the note at L32, and `epics.md` Story 4.3 carries the same superseded line. AC blocks may not be edited, but `epics.md` and the spine can carry a dated note, as FR-6 and FR-19 do.
MINOR: Spec-conflict with PRD §5.1 FR-4 (L135), whose consequence reads "Encryption parameters sufficient to decrypt (algorithm, KDF parameters, salt …) are recorded in the Manifest". E004-S01-003 L88 and L174 assert the opposite: no algorithm, KDF or salt key may appear. ADR-0014 ("Also changes: PRD FR-4's mechanism") justifies the story, but FR-4 has no amendment backlink, while FR-6 (ADR-0023) and FR-19 (ADR-0019) do. MINOR: E004-S01-003 §Testability L171 ("every non-link member is `encrypted: true` and starts with `age-encryption.org/v1`") contradicts ADR-0017's member table, where `dir` entries are `encrypted: false` with no content. L119 makes the exception only for symlinks. Write the assertion as "every `kind=file` member".
MINOR: `VerifyRequest.cipher` and `--identity-file` on `verify` have no defined effect. E004-S01-003 L99 says "A verify uses `VerifyRequest.cipher`", but §Non-goals L50 (and E002-S01-003 L43) keep verification keyless, and `drive_verify` calls `verify_archive(path)` with no cipher (E002-S01-004 L65). Either drop the cipher and flag from verify, or define what the key does there.
MINOR: Observability placement (AD-10). `encryption_configured` (E004-S01-003 L131) is "per Run", but the only E004 code that knows the mode is `build_member_cipher`, and it runs before `open_run` (L76, decision 4). A record emitted there carries no `run_id`. The `WRITE_ARCHIVE` fields at L132 belong to E002's executor record, which E004 does not own. Say which owner emits each one, after the Run opens.
MINOR: E004-S01-003 does not say who calls `AgeMemberCipher.check()`. L73 and L135 say "the configuration step, before preflight", and the factory bullet (L76) is silent. State that `build_member_cipher` calls `check()` before returning, so all four roots get the same refusal, Dry Run included.

Design coherence summary (not a finding):
- E004's three seams match E002's ports one for one: `ExclusionPolicy` with `ExclusionSet`, the `MemberCipher` port with `AgeMemberCipher`, and `classify` with the v0 fixtures.
- Both the policy and the cipher are per-call arguments, never `AdapterSet` fields (ADR-0016), in E002, E003, E006 and E008 alike.
- AD-23 stays one-way. Nothing in E004 writes v0, the classifier stays in `domain/archive_format`, and E004-S01-002 L107 guards the writer side.
- The defects are concentrated on the decrypt and restore side of FR-4, where E004 provides the adapter and nobody owns the end-to-end wiring.
