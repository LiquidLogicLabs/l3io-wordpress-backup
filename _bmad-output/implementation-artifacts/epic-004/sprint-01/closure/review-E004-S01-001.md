## Findings

### F-1 — medium — Patterns that pathspec compiles to a no-op are accepted silently

- **Location**: `src/l3io/wp/backup/core/exclusions.py:68` (`_compile`)
- **Description**: `GitIgnoreSpec.from_lines` does not raise for gitignore comment
  lines or degenerate patterns; it compiles them to a null pattern
  (`pattern.include is None`) that matches nothing. Probed: `#cache`, `/`, `[` all
  compile with `include=None`; `from_patterns(["#cache"], …).decide("#cache")` →
  not excluded. The set is still `source=custom`, the pattern is recorded in the
  Manifest's `patterns` as if active, and no warning or error is raised. An
  operator who passes `--exclude '#private/'` (a real directory name) or a typo
  such as `[` gets those paths written into the Archive while the Manifest claims
  the rule was applied — for an exclusion used to keep data *out* of an Archive,
  a silent no-op is the unsafe direction. Related, lower-impact: gitignore strips
  unescaped trailing spaces (`"debug.log "` matches `debug.log`, never a file
  named `debug.log `), which the docs do not mention.
- **Suggested fix**: after compiling each pattern, reject it with
  `InvalidExclusionPatternError(pattern, "the pattern matches nothing (a gitignore comment or empty pattern)")`
  when `spec.patterns[0].include is None` (use pathspec's own result — do not
  re-implement comment detection). Add `#x`, `/`, `[` to the invalid-pattern
  parametrisation. Document trailing-space stripping and `\#`/`\ ` escaping in
  `docs/exclusions.md`.

### F-2 — low — kind: claim — Backslash patterns are not "matched literally"

- **Location**: `docs/exclusions.md:58`; test `tests/unit/core/test_exclusions.py:111`
- **Claim (story, Error and edge case handling)**: "a Windows-style
  `wp-content\cache` pattern is matched literally (and matches nothing), not
  translated." The docs repeat "is matched literally and matches nothing".
- **Description**: in gitignore syntax `\` is an escape, so `wp-content\cache`
  compiles to `wp-contentcache`. Probed: it excludes a path named
  `wp-contentcache` and does not match a path literally named `wp-content\cache`.
  The outcome the story cares about (no separator translation, `wp-content/cache`
  not matched) holds, but both statements of *why* are false, and the unit test
  only asserts the non-match, so it cannot catch this.
- **Suggested fix**: correct the docs (and the story text at closure) to "`\` is
  gitignore's escape character, not a separator: `wp-content\cache` means
  `wp-contentcache`". Optionally assert that in the unit test so the documented
  behaviour is pinned.

### F-3 — low — Purity guard's scope stops at names containing "tree"

- **Location**: `tests/contracts/test_exclusions_pure.py:28` (`_tree_walkers`)
- **Description**: the forbidden set is every public name on `pathspec`,
  `pathspec.util`, `PathSpec`, `GitIgnoreSpec` whose name contains `tree`.
  `pathspec.util` re-exports `os`, `pathlib` and `stat`; probed:
  `pathspec.util.os.listdir(".")` and `pathspec.util.pathlib.Path("a").read_text()`
  pass both this test and `tools/check_purity.py` (`_check_imports` and
  `_check_calls` report nothing). An I/O helper added to pathspec under a name
  without "tree" would also pass. The story's claim is limited to "tree-walking
  APIs", so this is not a claim violation, but the guard's reach is narrower than
  its docstring's purpose ("its tree-walking helpers read the filesystem")
  implies (global rule 4).
- **Suggested fix**: invert the guard to an allow-list derived from what the
  module needs: every attribute/name reached through `pathspec` in
  `core/exclusions.py` must be in `{"GitIgnoreSpec", "from_lines", "check_file"}`
  plus the `CheckResult` fields; plant `pathspec.util.os.listdir` as a violation.
  Alternatively add re-exported stdlib modules (`os`, `pathlib`, `stat`, `io`) to
  the forbidden attribute set and plant one.

### F-4 — low — `exclusions_applied` is once per wrapper instance, not once per Run

- **Location**: `src/l3io/wp/backup/adapters/exclusions.py:40`
- **Description**: the story requires "one INFO `exclusions_applied` per Run". The
  once-flag lives in the `LoggedExclusionPolicy` instance. A frozen, hashable
  value object is naturally reused: a library caller (E006 `api/`) that builds
  one `BackupRequest(exclusion=LoggedExclusionPolicy(...))` and runs it twice gets
  the event in the first Run only. Correct today only if every Run builds a new
  wrapper, which nothing enforces.
- **Suggested fix**: key the flag on the Run (e.g. store the bound `run_id` from
  `structlog.contextvars.get_contextvars()` and re-announce when it changes), or
  record in the class docstring and in E008-S01-001's binding that a wrapper is
  per-Run and must not be reused, with a test in E008 that builds one per Run.

### F-5 — low — kind: claim — `path_excluded` count does not equal excluded entries when the target is in the Site Root

- **Location**: `src/l3io/wp/backup/adapters/exclusions.py:52` (interaction with
  `src/l3io/wp/backup/cli/backup.py` `_SkipStaged.decide`)
- **Claim (story, Observability)**: "the excluded count is the number of
  `path_excluded` records".
- **Description**: `drive_backup` wraps the caller's policy (the
  `LoggedExclusionPolicy`) in `_SkipStaged`, which returns its own excluded
  decision for the staged Archive without calling the inner policy. With the
  Archive target inside the Site Root (the CLI default is the current directory),
  the Manifest has one more `excluded` entry than there are `path_excluded`
  events. The integration test places the target outside the Site Root, so it
  does not exercise this.
- **Suggested fix**: in E008-S01-001 (which owns the binding), either log a
  `path_excluded` from `_SkipStaged` or place the logging wrapper outside it; or
  amend the story claim to "excluding the Archive being written". Not fixable in
  this story's files without editing `cli/backup.py`.

### F-6 — low — The public constructor bypasses `from_patterns`'s input checks

- **Location**: `src/l3io/wp/backup/core/exclusions.py:108` (`__post_init__`)
- **Description**: `from_patterns` refuses a bare string, but
  `ExclusionSet("*.log", ExclusionSource.CUSTOM)` is accepted and becomes the
  patterns `("*", ".", "l", "o", "g")` — `*` then excludes everything except
  `wp-config.php`. `source` is also not checked to be an `ExclusionSource`
  (a plain `"bogus"` is accepted here and only rejected later by
  `cli/backup.py::_exclusions` as a `UsageError` mid-Run). The constructor is
  public API by the story's own signature.
- **Suggested fix**: move the `isinstance(patterns, str)` check into
  `__post_init__`, and coerce/validate `source` with `ExclusionSource(self.source)`.

### F-7 — low — kind: claim — The "generated" table is hand-written

- **Location**: `docs/exclusions.md:23`
- **Claim (story, Interface contracts)**: "the documented default set, as a table
  between generated-content markers"; Files in scope: "the generated default-set
  table".
- **Description**: the markers read `BEGIN GENERATED`, but no generator exists; the
  table is hand-maintained and guarded only for the pattern column (the test's
  docstring says so). A reader following the marker will look for a generator to
  re-run. The drift guard itself is sound.
- **Suggested fix**: either rename the markers to e.g. `BEGIN CHECKED:
  default-exclusions` and say "hand-maintained; checked by
  tests/contracts/test_exclusions_documented.py", or add the generator to the
  existing `gen_cli_docs`-style tooling in a follow-up and keep the marker.

### F-8 — low — Docs describe behaviour that is not live until E008-S01-001

- **Location**: `docs/exclusions.md:16` (also lines 62–64)
- **Description**: "Applied when no exclusion is asked for" and "fails the backup
  … with exit code `USAGE`" describe the CLI after E008-S01-001.
  Today `default_exclusion_policy()` returns `INCLUDE_EVERYTHING` and the three
  flags are in `NOT_YET_IMPLEMENTED`, so an operator reading this doc against the
  current build is told caches and logs are left out when they are not.
- **Suggested fix**: add a one-line status note ("takes effect with
  E008-S01-001; until then backups include everything") to be removed by that
  story, or have E008-S01-001 own the operator-facing sentences.

### F-9 — low — Each pattern is compiled twice

- **Location**: `src/l3io/wp/backup/core/exclusions.py:68`
- **Description**: `_compile` builds a one-line `GitIgnoreSpec` per pattern to
  attribute errors, then builds the whole spec again. Story: "Patterns are compiled
  once … at construction". Cost is negligible for a handful of patterns; noted
  only because it contradicts the stated "once" and doubles the work for long
  `--exclude` lists.
- **Suggested fix**: compile each pattern once into its pathspec pattern object
  (keeping the per-pattern error attribution and the F-1 null check), then build
  `GitIgnoreSpec(compiled_patterns)` from those objects.
