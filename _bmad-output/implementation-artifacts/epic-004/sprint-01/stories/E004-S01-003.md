# E004-S01-003: Encrypt an archive at rest


**Implements:** FR-4


As an operator,
I want my archive encrypted,
So that a file containing every user record is not readable by whoever finds it.

**Acceptance Criteria:**

**Given** encryption configured with `age` recipients, or with a passphrase
**When** a backup runs with encryption
**Then** each payload member is `age`, encrypted through `l3io-wp-database`, and the Archive yields no plaintext database or file content to an inspector without the key (ADR-0014)
**And** any encrypted member decrypts with the stock `age -d`, without this package
**And** the Manifest records which members are encrypted and carries no key material
**And** a wrong key or passphrase raises a distinct named error, not a generic corruption error
**And** no key or passphrase appears in process arguments, logs or exceptions
**And** the passphrase resolution chain is shared verbatim by the CLI and the library (AD-26)
**And** recipient/identity encryption builds on database v0.1.0; the passphrase path lands with database **0.2.0** (`passphrase=`), and until then a passphrase-only configuration is refused naming that release

*(Per the E002 gate reconciliation 2026-10-27: the baseline is `l3io-wordpress-database` v0.2.0, rev `48a7da9`, which already carries `passphrase=`. Recipient, identity and passphrase encryption all build on it, and no passphrase-only refusal exists.)*

## Business acceptance criteria

### Outcome

`wpbackup2 backup --wp-dir <Site Root> --recipient age1…` produces an Archive in which `manifest.json` is plaintext and every payload member is encrypted. That covers the Dump and every `site-root/…` and `config` file. Each encrypted member is a standard `age` file, so an operator with the matching identity recovers any member with the stock `age -d -i key.txt`, without this package installed. Someone holding the Archive but no key can still identify, version-gate and checksum-verify it, because the Manifest marks each member `encrypted: true` and its checksum covers the ciphertext. They cannot read any database row or file content from it. Decrypting with the wrong identity raises a named decryption error that is distinct from a corrupt-Archive error and maps to a different exit code. The key never appears in an argument vector, a log record or an exception. Recipient, identity and passphrase encryption all work on `l3io-wordpress-database` v0.2.0, the pinned baseline. A passphrase-encrypted member decrypts with stock `age -d`, which prompts for the passphrase. *(Adopted 2026-10-27 from the E002 gate.)* A reviewer can tell it happened by backing up a Site seeded with sentinel strings, grepping the decompressed Archive for them (none found), and decrypting one member with `age -d`.

### Non-goals

- Restoring from an encrypted Archive onto a Site. That is Epic 3 story 3.1, which calls this story's decryption adapter. The Safety Snapshot's encryption (FR-8, AD-26's "no silent plaintext Snapshot" default) is Epic 3 story 3.3.
- Implementing the AD-26 passphrase resolution chain or the CLI flags. The chain is E002-S01-006's `cli/passphrase.py::resolve_passphrase`. The flags are E002-S02-011's. E008-S01-001 binds this story's cipher into the roots. This story consumes the chain and does not redefine it. *(Adopted 2026-10-27 from the E002 gate.)*
- Hiding member names, sizes or the source Site identity. The plaintext Manifest exposes them by design (ADR-0014, "Kept from ADR-0006"), and an operator who needs them hidden encrypts at the storage layer as well.
- Key management: generating, rotating, escrowing or recovering keys. Losing every identity or the passphrase loses the Archive, and the documentation says so plainly.
- Verifying plaintext integrity with a key (a "deep verify"). Verification stays keyless, over ciphertext (E002-S01-003).
- Having `adapters/database` call `dump(..., recipients=)` so a plaintext Dump never lands in the Run workspace. That optimisation belongs to Epic 2's module. This story encrypts the Dump member like every other member, and the plaintext Dump stays confined to the owner-only workspace AD-12 already removes.
- Any cipher, KDF or `age` implementation in this package.

## Technical acceptance criteria

### Interface contracts

*(Adopted 2026-10-27 from the E002 gate.)* Files this story adds or changes follow E002-S01-001's conventions: a module docstring naming the AD and ADR it carries, `from __future__ import annotations`, an explicit `__all__`, and no new `__init__.py`. `adapters/` may import `domain/`, `ports/` and `core/` (import-linter `layers`). Optional dependencies are imported **inside the function that uses them** (AD-8), as `adapters/database.py` does.

- **`src/l3io/wp/backup/adapters/crypto.py` (new; Epic 4 owns `adapters/crypto`). It is a thin adapter over `l3io-wordpress-database` v0.2.0 (rev `48a7da9`). Signatures were verified with `git show v0.2.0:src/l3io/wp/database/encryption.py`:**
  - `encrypt(reader: IO[bytes], writer: IO[bytes], recipients: Sequence[str] | None = None, *, passphrase: str | None = None) -> None`;
  - `decrypt(reader: IO[bytes], writer: IO[bytes], identities: Sequence[str] | None = None, *, passphrase: str | None = None) -> None`;
  - `check_recipients(recipients: Sequence[str]) -> None`;
  - `check_passphrase(passphrase: str) -> None`;
  - `read_identity(path: str | Path, passphrase: str | None = None) -> str`.
  - Each of `encrypt` and `decrypt` takes exactly one of the sequence or `passphrase=`. `encrypt`, `decrypt`, `check_recipients`, `check_passphrase` and `generate_identity` are imported from the package root: `from l3io.wp.database import encrypt, decrypt, check_passphrase`. `read_identity` is not exported from the root at v0.2.0, so it is imported from the public module `l3io.wp.database.encryption`.
  - Frozen `AgeRecipients(recipients: tuple[str, ...])` and `AgeIdentities(identities: tuple[str, ...])`. Each `__repr__` shows only the count (`AgeIdentities(<2 identities>)`), so an identity can never be `repr`ed into a log (AD-7, AG-14).
  - `class AgeMemberCipher`, implementing E002-S01-001's `ports/crypto.MemberCipher`, with `__init__(self, *, recipients: AgeRecipients | None = None, identities: AgeIdentities | None = None, passphrase: str | None = None)` and three methods:
    - `check(self) -> None` validates before any data moves. With recipients it calls `check_recipients`. With a passphrase it calls `check_passphrase`, which refuses an empty passphrase and a host with no usable passphrase backend.
    - `encrypt(self, reader: IO[bytes], writer: IO[bytes]) -> None`
    - `decrypt(self, reader: IO[bytes], writer: IO[bytes]) -> None`
  - **No method accepts or returns `bytes`** (AD-21, AG-13).
  - Construction with both `recipients` and `passphrase`, or with neither when encryption is requested, raises `EncryptionConfigError`. These are mutually exclusive, matching database's own rule. It is raised from the configuration step, before preflight, dump or any write.
  - **Passphrase mode.** `encrypt(reader, writer, passphrase=...)` and `decrypt(reader, writer, passphrase=...)` emit and consume a sole scrypt recipient that stock `age -d` reads.
  - Every secret this adapter is handed is registered with the Run's `SecretRegistry` (E002-S01-006) at construction: each identity string, and the passphrase. That is the extension point E002-S01-006 reserved for this story ("the redaction set below is extensible so that story adds the passphrase without a second implementation").
- **Errors (AD-14), defined in `adapters/crypto.py` as `BackupError` subclasses** (E002-S01-001's walked hierarchy test covers them). Each wraps database's exception with `raise … from`, and none carries a key, passphrase or identity in its message or attributes:
  - `ArchiveDecryptionError(CredentialsError)`, with fields `member: str` and `reason: Literal["wrong_key", "no_key"]`, is raised from database's `DecryptionError` or when an encrypted member is read with no key. Because it subclasses `CredentialsError`, it maps to `ExitCode.CREDENTIALS` (4) through Epic 2's existing arm.
  - `EncryptedMemberCorruptError(BackupError)`, with field `member: str`, is raised from database's `CorruptDumpError` (truncated, damaged or not `age`). It declares `exit_code = ExitCode.VERIFICATION_FAILED` (8) itself, with an existing member, as E002-S01-005 provides for a later class.
  - `EncryptionConfigError(UsageError)` inherits `USAGE` (2). Database's `InvalidArgumentsError` from `check()` is re-raised as this error.
  - Database's `MissingDependencyError(extra="encryption")` (`pyrage` absent, or no usable passphrase backend) is re-raised as `MissingExtraError(extra="database")`, exit `NOT_READY` (7), with a message naming `l3io-wordpress-database[encryption]`.
  - No new `ExitCode` member is needed.
- **`pyproject.toml` (ADR-0014, amended 2026-10-27).** The `database` extra is `l3io-wordpress-database>=0.2.0,<0.3`, pinned in `[tool.uv.sources]` to rev `48a7da9` (v0.2.0). This story changes it to `l3io-wordpress-database[encryption]>=0.2.0,<0.3`.
  - Database's `encryption` extra requires `pyrage>=1.4,<2` and `l3io-age-passphrase>=0.1,<0.2`. The binder ships as GitHub Release wheels only.
  - uv ignores database's own source for the binder, so without one it would build the Rust binder from source. This story therefore also adds a `[tool.uv.sources]` entry for the binder's release wheels.
  - The `age` ≥ 1.3 CLI fallback (`L3IO_AGE_PASSPHRASE_BACKEND=cli`) is database's. This story's interop test covers both backends where the binary is present, and skips neither silently in CI.
  - This package declares no `pyrage` and no `cryptography` cipher use.
- **Manifest (AD-6, as amended by ADR-0014).** Epic 2's `ManifestMember.encrypted: bool` is set to `True` for every payload member when encryption is on. `size` and `sha256` describe the **stored ciphertext**. The Manifest records no recipient, identity, passphrase, KDF parameter, salt or algorithm field: `age` carries its own header. `manifest.json` itself is never encrypted.
- **Committed fixture (ADR-0014, "including an encrypted one").** `tests/fixtures/archives/v1/encrypted-recipient.tar.gz` is a minimal v1 Archive whose members are encrypted to a **test-only** identity committed beside it as `encrypted-recipient.identity.txt`. That file has a header comment saying it protects nothing and exists for CI. A checked-in generator reproduces the fixture, minus `age`'s random file key, so reproducibility is asserted on the Manifest's structure, not on bytes. E002-S01-003's `test_supported_formats.py` reads its Manifest's `format_version` like any other v1 fixture's.

**Seams in Epic 2's modules, which this story does not edit (decision 6).**

1. **Port.** `ports/crypto.py::MemberCipher` (`check`, `encrypt`, `decrypt`) is a transform listed on E002-S02-007's single-role allowance (E002-S01-001).
2. **The writer.** Encryption happens in E002-S01-010's `write_archive(out, manifest_builder, members, *, cipher)`. Each payload member is streamed through `cipher.encrypt` into its own workspace file and hashed as written. The Manifest and the staged files are then written in order, and each staged file is deleted once copied. Workspace disk use on the encrypted path is therefore bounded by the total ciphertext (about the Archive's size), not by the largest member. Memory stays bounded.
3. **The plan.** `build_backup_plan(..., *, encrypted: bool)` puts `ENCRYPT` in the plan (E002-S01-010). Under ADR-0019 the step runs inside `ArchiveWriterCommand.write` (E002-S02-007), so a Dry Run reports it and encrypts nothing.
4. **Flags.** E002-S02-011 registers repeatable `--recipient` and `--recipients-file PATH` on `backup` and `restore`, repeatable `--identity-file PATH` on `restore` and `verify`, and `--encrypt-with-passphrase`, which takes no value. They sit in `NOT_YET_IMPLEMENTED`, naming this story, until E008-S01-001 binds them and removes the entries.
5. **The AD-26 chain.** E002-S01-006's `resolve_passphrase(*, explicit, environ, prompt, secrets) -> ResolvedPassphrase | None` registers the value with the Run's `SecretRegistry` before it returns.
6. **Exit codes.** These come from the class attribute (E002-S01-005), with no edit in `cli/`.
7. **How the cipher arrives.** It is a per-call argument, never an `AdapterSet` field (ADR-0016). A backup passes `BackupRequest.cipher` to `cli/backup.py::backup(..., cipher=)` (E002-S01-004), and from there to `ArchiveWriterCommand.write(..., cipher=)`. A verify uses `VerifyRequest.cipher` (E002-S01-004), and a restore uses `RestoreRequest.cipher` (E003-S01-006). E008-S01-001 builds the cipher from the flags with this module and binds it at both roots. Epic 6's `api/` builds it the same way.

### Error and edge case handling

- **Wrong identity or passphrase**: raises `ArchiveDecryptionError(member=…, reason="wrong_key")` and exits 4. It is never `EncryptedMemberCorruptError`, never `VerificationFailedError`, and never a bare database exception.
- **Encrypted Archive read with no key**: the same error with `reason="no_key"`, raised when the first encrypted member is about to be decrypted. Keyless verification still passes, because checksums cover the ciphertext.
- **Ciphertext truncated or a byte flipped after write**: keyless verification fails first with `CHECKSUM_MISMATCH` or `TRUNCATED` (E002-S01-003). If `decrypt` is reached with a damaged stream anyway (the adapter driven directly), it raises `EncryptedMemberCorruptError` and exits 8. The two kinds stay distinct (ADR-0014).
- **Member swapped in from another Archive under the same key**: it decrypts cleanly but fails Verification with `CHECKSUM_MISMATCH`, because the Manifest's checksum is over the stored ciphertext (ADR-0014's replacement for key commitment).
- **Invalid recipient string**: `check()` refuses before the dump. Database's `InvalidArgumentsError` message includes only the first 12 characters of a recipient, which is a public key. The re-raised `EncryptionConfigError` names the recipient's index, not its text.
- **Both recipients and passphrase, or encryption requested with neither**: `EncryptionConfigError`, exit 2.
- **`pyrage` or the passphrase backend not installed** (the `database` extra installed without `[encryption]`, e.g. an older lock): `MissingExtraError` naming `l3io-wordpress-database[encryption]`, exit 7, raised by `check()` before any write. *(Adopted 2026-10-27 from the E002 gate.)*
- **Empty member** (a zero-byte file, an empty Dump): encrypts to a valid `age` file, has a checksum over that, and round-trips to zero bytes.
- **Symlink members** carry no content and are stored as links, unencrypted, with `encrypted: false` in the Manifest. A link target is a path and is already visible like a member name. This is asserted, so an inspector test does not flag it.
- **Broken pipe or disk full while writing ciphertext**: database re-raises `BrokenPipeError`/`OSError`. The adapter lets it propagate to Epic 2's `ArchiveWriteError` handling, so the staged file is discarded and no final name exists (AD-20).
- **Passphrase mode**: an empty passphrase is treated as absent by E002-S01-006's chain. If one reaches `check()`, database's `check_passphrase` refuses it with `InvalidArgumentsError`, which is re-raised as `EncryptionConfigError`. A wrong passphrase gives `reason="wrong_key"` exactly as a wrong identity does.

### Observability requirements

- Through the Run-bound logger (`structlog.get_logger(__name__)`, `run_id` via contextvars; nothing here configures logging, AD-10):
  - one INFO `encryption_configured` per Run, with `scheme="age"`, `mode` (`"recipients"` or `"passphrase"`) and `recipient_count`;
  - E002's per-phase `WRITE_ARCHIVE` record gains `encrypted_members` and `bytes` (ciphertext bytes);
  - a decrypt failure logs ERROR `member_decryption_failed` with `member` and `reason`.
- Recipient strings are not logged, only their count. They are public keys, but logging them would turn the log into a key inventory.
- The Dry Run plan lists `ENCRYPT` (AD-4). Under ADR-0019 it encrypts nothing, because `NoopArchiveWriter` stands in for the write. `check()` changes nothing, so it runs when the cipher is configured, before preflight, in a real Run and a Dry Run alike (ADR-0019 point 3). A Dry Run with an invalid recipient therefore refuses exactly as the real Run does. *(Adopted 2026-10-27 from the E002 gate.)*

### Security considerations

- **No secret in process arguments (FR-4, NFR-3).** This package invokes no `age` binary and builds no argument vector for encryption. The secret is passed in-process to database, which passes it to `pyrage` in-process. A passphrase or identity is never accepted as a CLI flag *value*; it arrives from a file path, the environment or a TTY prompt, per AD-26's chain.
- **No secret in logs, `repr` or exceptions (AD-7, AG-14).** Every identity and the passphrase are registered with E002-S01-006's one `SecretRegistry`, so `redact_event` scrubs any accidental occurrence. `AgeIdentities` and `AgeMemberCipher` define `__repr__` without secrets. Re-raised errors build their message from structured fields only.
- **No plaintext content in the Archive.** Every payload member with content is `age`. The only plaintext is the Manifest (names, sizes, checksums, source Site identity) and link targets: the deliberate, documented ADR-0014 trade.
- **Plaintext on disk** is only the Dump, inside the owner-only (`0700`) Run workspace (AD-12). Site Root files are read in place and streamed through the cipher. Every payload member's ciphertext is staged in the workspace (mode `0600`) before the tar is written, and each staged file is deleted once copied into the Archive (E002-S01-010). The workspace is removed in `finally` on both paths. *(Adopted 2026-10-27 from the E002 gate.)*
- **No key material in the Manifest**, asserted by test, including that no recipient string appears in it.
- **The committed test identity** protects only the committed fixture. A contract test asserts it is the only `AGE-SECRET-KEY-` string in the repository outside `tests/fixtures/`, so a real key committed by mistake fails CI.
- This package imports no `pyrage` and no `cryptography` cipher (ADR-0014). A contract test enforces it.

### Testability approach

Layout follows E002-S01-001: `tests/unit/` mirrors the package layers, adapter contract tests go in `tests/adapters/`, architecture guards in `tests/contracts/`, and the live-database tier uses the existing `@pytest.mark.integration` marker. Keys are generated per test with database's `generate_identity()`, except for the committed fixture.

- `tests/adapters/test_crypto.py`:
  - round-trip on an empty stream, a 1-byte stream and a multi-chunk stream;
  - a wrong identity raises `ArchiveDecryptionError(reason="wrong_key")`, with no `CorruptDumpError` reaching the caller;
  - truncation at several offsets, including inside the header, and a flipped payload byte each raise `EncryptedMemberCorruptError`;
  - an invalid recipient raises `EncryptionConfigError` from `check()`;
  - `repr()` of every public type contains no identity substring;
  - every `encrypt`/`decrypt` signature is checked by `typing.get_type_hints` to contain no `bytes` (scope: the module's public callables, found by walking `__all__`).
- *(Adopted 2026-10-27 from the E002 gate.)* **Passphrase path**: `test_passphrase_round_trip` runs on every install. It covers an adapter round trip and stock `age -d` decrypting a passphrase-encrypted member, with the passphrase supplied through `age`'s own TTY prompt, driven via `pty`. A second case asserts that `check()` with a passphrase and no usable backend raises `MissingExtraError` naming `l3io-wordpress-database[encryption]`.
- **Stock `age -d` interoperability** (`tests/adapters/test_age_interop.py`): a member encrypted by the adapter is decrypted by the `age` binary via `subprocess` with `-i <identity file>`, and the bytes must be identical. A member encrypted by `age -r` is decrypted by the adapter. The CI test job installs the `age` package (an apt step added to the test job in `.github/workflows/ci.yml`), and the test **fails** rather than skips when `CI` is set and `age` is absent. Locally it skips with that reason.
- **Inspector** (`tests/integration/test_encrypted_backup.py`, `@pytest.mark.integration`):
  - a Site Root and database are seeded with unique sentinel strings in file bodies, in `wp-config.php` values and in a table row, and backed up with a recipient;
  - the Archive is streamed through `tarfile` and every member body is scanned, as is the raw decompressed stream. No sentinel may appear outside `manifest.json`, and `manifest.json` must contain none of the content sentinels;
  - every non-link member is `encrypted: true` and starts with `age-encryption.org/v1`;
  - `wpbackup2 verify` passes with no key;
  - one member is decrypted with stock `age -d` and must equal the source file.
- **Manifest** (`tests/unit/domain/test_manifest_no_key_material.py`, run against a Manifest built by the encrypted path): no key in the JSON object tree matches `key|kdf|salt|passphrase|identity|recipient|scrypt|nonce`. The recipient string and the identity string do not occur in its text.
- **Secrets in argv, logs and exceptions**: E002-S01-006's `credential_sentinel` fixture already has a passphrase parameter that drives `resolve_passphrase`. This story applies it to an encrypted Run and adds the identity as a sentinel. A full encrypted backup and a failed decrypt are run. Every captured log record, every exception chain taken unredacted (ADR-0018's item 3), and every `/proc/self/cmdline` read during the Run must be clean.
- **AD-21 (AG-13) on the encrypted path**: E002-S01-010's peak-RSS test (Site plus Dump of at least 10× `RSS_BOUND_BYTES`) is parametrised to run with encryption on as well as off. Both must stay under the same bound. The parametrisation is derived from a `(encrypted: bool)` axis, not a second copy of the test.
- **AD-26 single chain** (`tests/contracts/test_single_passphrase_chain.py`): it walks every module under `src/l3io/wp/backup/`, with a scope assertion. The passphrase environment-variable name, `L3IO_WP_BACKUP_PASSPHRASE`, must appear in exactly one module, E002-S01-006's `cli/passphrase.py`. ### Existing-library check

Cryptography is a domain the global rules forbid hand-rolling, and ADR-0014 settles the library. `age` is reached only through `l3io-wordpress-database` v0.2.0's encryption API: `pyrage` for recipients and identities, and the `l3io-age-passphrase` binder (or the `age` CLI fallback) for a passphrase. Their streaming encryptors are what make AD-21 hold on the encrypted path. ADR-0014 records why the alternatives were rejected: ADR-0006's own AES-GCM construction, a direct `pyrage` integration, the `age` CLI, and buffering whole archives for one-shot passphrase calls. No version string is parsed or compared. This story adds no new library. It adds the `encryption` extra of an existing one, and a uv source for that extra's binder wheels. *(Adopted 2026-10-27 from the E002 gate.)*
