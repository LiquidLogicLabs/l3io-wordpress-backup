# E004-S01-003: Encrypt an archive at rest


**Implements:** FR-4


As an operator,
I want my archive encrypted,
So that a file containing every user record is not readable by whoever finds it.

**Acceptance Criteria:**

**Given** encryption configured with `age` recipients, or with a passphrase
**When** a backup runs with encryption
**Then** each payload member is `age`, encrypted through `l3io-wp-database`, and the Archive yields no plaintext database or file content to an inspector without the key (ADR-0014)
**And** any encrypted member decrypts with the stock `age -d`, without this package
**And** the Manifest records which members are encrypted and carries no key material
**And** a wrong key or passphrase raises a distinct named error, not a generic corruption error
**And** no key or passphrase appears in process arguments, logs or exceptions
**And** the passphrase resolution chain is shared verbatim by the CLI and the library (AD-26)
**And** ~~recipient/identity encryption builds on database v0.1.0; the passphrase path lands with database **0.2.0** (`passphrase=`), and until then a passphrase-only configuration is refused naming that release~~ *(struck 2026-11-07: superseded by the note below and ADR-0024)*

## Business acceptance criteria

### Outcome

`wpbackup2 backup --wp-dir <Site Root> --encrypt-with-passphrase`, with the passphrase from AD-26's chain (`L3IO_WP_BACKUP_PASSPHRASE` or a TTY prompt), and the library's `drive_backup(BackupRequest(..., cipher=...))`, produce an Archive whose `manifest.json` is plaintext and whose only other member is `payload.tar.gz.age`. That payload is the Dump, every Site Root file and the config, in one gzip tar encrypted as one `age` stream *(ADR-0024)*. An operator recovers it without this package: `age -d payload.tar.gz.age` prompts for the passphrase and yields a plain gzip tar. Someone holding the Archive but no passphrase can still identify, version-gate and checksum-verify it, because the Manifest records `encrypted: true` and the payload's size and SHA-256 over the stored bytes. They cannot read any database row or file content from it. A restore with the right passphrase decrypts the payload during `VERIFY`, before the Safety Snapshot and before anything destructive. A wrong passphrase, or a damaged or truncated payload, stops the restore there with a named error. The two errors are distinct, `PassphraseRejectedError` and `PayloadDamagedError`, and both exit 8 *(E004/E005 pre-build re-check, 2026-11-06, F-3: replaces "map to different exit codes")*. Encryption requested with no passphrase resolved is refused, never written as plaintext, with `PassphraseUnavailableError`, exit `USAGE` (2) (F-4). An encrypted Archive restored with no passphrase is refused when the plan is built *(Gate E004 AG-6/AG-7/AG-9, 2026-10-30)*. The passphrase never appears in an argument vector, a log record or an exception. A reviewer can tell it happened by backing up a Site seeded with sentinel strings, grepping the Archive for them (none found), decrypting the payload with `age -d`, and restoring with a wrong passphrase to see the named error and an unchanged Site.

### Error and edge case handling

*(E004/E005 pre-build re-check, 2026-11-06, F-3, F-4 and F-18. Read the cases below with the built errors:*
- *every `ArchiveDecryptionError(member=…)`, exit 4, is `PassphraseRejectedError`, exit 8;*
- *every `EncryptedMemberCorruptError`, exit 8, is `PayloadDamagedError`, exit 8;*
- *"Encryption requested and no passphrase resolved" is `require_passphrase`'s `PassphraseUnavailableError`, exit `USAGE` (2), raised before the dump or any write, never `build_payload_cipher`'s `PassphraseRequiredError`;*
- *"`pyrage` or the passphrase backend not installed" gives `MissingExtraError(extra="database")` with its fixed message, exit 7, under `auto`, `binder` or unset. Under `cli` with the binaries absent it gives `EncryptionConfigError`, exit 2.)*

- **Wrong passphrase**: database's `DecryptionError` becomes `ArchiveDecryptionError(member=…)`, exit 4. In a restore it is raised during `VERIFY`'s decrypt, before `SNAPSHOT` and before anything destructive (E003-S01-001). It is never `EncryptedMemberCorruptError`, never `VerificationFailedError`, and never a bare database exception *(Gate E004 AG-7, 2026-10-30)*.
- **Encrypted Archive restored with no passphrase resolved**: `PassphraseRequiredError(operation="restore")`, exit `REFUSED`, raised when the restore plan is built, before `VERIFY` reads the payload (E003-S02-006). Keyless verification of the same Archive still passes *(Gate E004 AG-7, 2026-10-30)*.
- **Encryption requested and no passphrase resolved** (for example under cron, with no `L3IO_WP_BACKUP_PASSPHRASE` and no TTY): `build_payload_cipher` raises `PassphraseRequiredError(operation="backup")`, exit `REFUSED`, before the dump or any write. A plaintext Archive is never written instead (AD-26) *(Gate E004 AG-9, 2026-10-30)*.
- **Payload truncated or a byte flipped after write**: keyless verification fails first, with `CHECKSUM_MISMATCH`, `SIZE_MISMATCH` or `TRUNCATED` (E002-S01-003). If `decrypt` is reached with a damaged stream anyway (the adapter driven directly), it raises `EncryptedMemberCorruptError`, exit 8. The two kinds stay distinct (ADR-0014).
- **Payload swapped in from another Archive under the same passphrase**: it decrypts cleanly but fails keyless verification with `CHECKSUM_MISMATCH`, because the Manifest's payload checksum is over the stored bytes *(ADR-0024)*.
- **Empty passphrase**: E002-S01-006's chain treats it as absent. If one reaches `check()`, database's `check_passphrase` refuses it with `InvalidArgumentsError`, which is re-raised as `EncryptionConfigError`, exit 2.
- **`pyrage` or the passphrase backend not installed** (the `database` extra installed without `[encryption]`, e.g. an older lock): `MissingExtraError` naming `l3io-wordpress-database[encryption]`, exit 7, raised by `check()` inside the factory, before any write. *(Adopted 2026-10-27 from the E002 gate.)*
- **An empty Site Root or an empty Dump** still yields a payload, which encrypts to a valid `age` file and round-trips.
- **Symlink members** travel inside the encrypted payload like every other member. Their targets are visible only through the Manifest's `link_target`, like member names.
- **Broken pipe or disk full while writing the encrypted payload**: database re-raises `BrokenPipeError`/`OSError`. The adapter lets it propagate to Epic 2's `ArchiveWriteError` handling, so the workspace payload and the staged Archive are discarded and no final name exists (AD-20).
- **The Safety Snapshot** is encrypted iff a passphrase resolved at the restore root; otherwise the restore proceeds with AD-26's WARNING (decided 2026-10-20; E003-S02-003, E003-S02-006).

### Existing-library check

Cryptography is a domain the global rules forbid hand-rolling, and ADR-0014 settles the library. `age` is reached only through `l3io-wordpress-database` v0.2.0's `encrypt`/`decrypt(passphrase=)` (0.3.2's, with the same signatures, *E004/E005 pre-build re-check, 2026-11-06, F-5*), backed by the `l3io-age-passphrase` binder or the `age` CLI fallback. Their streaming encryptors are what make AD-21 hold on the encrypted path. The payload is built and read with stdlib `tarfile` and gzip. ADR-0024 records why one payload was chosen over zip (`zipfile` offers only ZipCrypto; `pyzipper` and seeking), 7z (`py7zr` 1.1.4: seeking, extraction advisories) and GnuPG (a new external binary and agent); ADR-0014 records why ADR-0006's own AES-GCM construction and a direct `pyrage` integration were rejected. No version string is parsed or compared. This story adds no new library. It adds the `encryption` extra of an existing one, and the family index as the binder's source. *(Adopted 2026-10-27 from the E002 gate; ADR-0024.)*
