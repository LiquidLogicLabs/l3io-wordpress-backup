# E004-S01-003: Encrypt an archive at rest


**Implements:** FR-4


As an operator,
I want my archive encrypted,
So that a file containing every user record is not readable by whoever finds it.

**Acceptance Criteria:**

**Given** encryption configured with `age` recipients, or with a passphrase
**When** a backup runs with encryption
**Then** each payload member is `age`, encrypted through `l3io-wp-database`, and the Archive yields no plaintext database or file content to an inspector without the key (ADR-0014)
**And** any encrypted member decrypts with the stock `age -d`, without this package
**And** the Manifest records which members are encrypted and carries no key material
**And** a wrong key or passphrase raises a distinct named error, not a generic corruption error
**And** no key or passphrase appears in process arguments, logs or exceptions
**And** the passphrase resolution chain is shared verbatim by the CLI and the library (AD-26)
**And** recipient/identity encryption builds on database v0.1.0; the passphrase path lands with database **0.2.0** (`passphrase=`), and until then a passphrase-only configuration is refused naming that release

*(Per the E002 gate reconciliation 2026-10-27: the baseline is `l3io-wordpress-database` v0.2.0, rev `48a7da9`, which already carries `passphrase=`. Recipient, identity and passphrase encryption all build on it, and no passphrase-only refusal exists.)*

*(ADR-0024, 2026-10-29; Gate E004, 2026-10-30: the AC lines on "each payload member", "any encrypted member", "which members are encrypted", "a wrong key", and the recipient/identity line are superseded. The Archive holds one `age`-encrypted payload, which stock `age -d` decrypts; the Manifest records `encrypted: true` and the payload's checksum; a wrong passphrase raises a distinct named error; the passphrase is the only v1 key (Non-goals). The lines on key material, process arguments, logs, exceptions and the shared AD-26 chain stand.)*

## Business acceptance criteria

### Outcome

`wpbackup2 backup --wp-dir <Site Root> --encrypt-with-passphrase`, with the passphrase from AD-26's chain (`L3IO_WP_BACKUP_PASSPHRASE` or a TTY prompt), and the library's `drive_backup(BackupRequest(..., cipher=...))`, produce an Archive whose `manifest.json` is plaintext and whose only other member is `payload.tar.gz.age`. That payload is the Dump, every Site Root file and the config, in one gzip tar encrypted as one `age` stream *(ADR-0024)*. An operator recovers it without this package: `age -d payload.tar.gz.age` prompts for the passphrase and yields a plain gzip tar. Someone holding the Archive but no passphrase can still identify, version-gate and checksum-verify it, because the Manifest records `encrypted: true` and the payload's size and SHA-256 over the stored bytes. They cannot read any database row or file content from it. A restore with the right passphrase decrypts the payload during `VERIFY`, before the Safety Snapshot and before anything destructive. A wrong passphrase, or a damaged or truncated payload, stops the restore there with a named error, and the two errors are distinct and map to different exit codes. Encryption requested with no passphrase resolved is refused, never written as plaintext; an encrypted Archive restored with no passphrase is refused when the plan is built *(Gate E004 AG-6/AG-7/AG-9, 2026-10-30)*. The passphrase never appears in an argument vector, a log record or an exception. A reviewer can tell it happened by backing up a Site seeded with sentinel strings, grepping the Archive for them (none found), decrypting the payload with `age -d`, and restoring with a wrong passphrase to see the named error and an unchanged Site.

### Non-goals

- The restore-side wiring. The executor's `VERIFY` decrypts through E002-S01-003's `decrypt_payload` with the request's cipher (E003-S01-001). The plan-time refusal and the cipher's construction at the restore root are E003-S02-006's. The Safety Snapshot's encryption is E003-S02-003's. This story supplies the cipher they are handed *(ADR-0024; Gate E004 AG-1, 2026-10-30)*.
- Implementing the AD-26 passphrase resolution chain or the CLI flag. The chain is E002-S01-006's `cli/passphrase.py::resolve_passphrase`. The flag is E002-S02-011's. E008-S01-001 binds this story's cipher into the roots. This story consumes the chain and does not redefine it. *(Adopted 2026-10-27 from the E002 gate.)*
- **Recipient and identity encryption.** The passphrase is the only v1 key. Recipients and identities are deferred to a later additive ADR: adding them changes only `age`'s header stanzas, not the Archive layout, so it is a new flag set, not a format version (ADR-0024). *(Gate E004, 2026-10-30)*
- Hiding member names, sizes or the source Site identity. The plaintext Manifest exposes them by design (ADR-0014, "Kept from ADR-0006"), and an operator who needs them hidden encrypts at the storage layer as well.
- Key management: generating, rotating, escrowing or recovering a passphrase. Losing the passphrase loses the Archive, and the documentation says so plainly.
- Verifying plaintext integrity with a key outside a restore (a "deep verify"). Verification stays keyless (E002-S01-003).
- Encrypting the Dump on its own. The Dump is written plain into the owner-only workspace and travels inside the payload (ADR-0024).
- Any cipher, KDF or `age` implementation in this package.

## Technical acceptance criteria

### Interface contracts

*(Adopted 2026-10-27 from the E002 gate.)* Files this story adds or changes follow E002-S01-001's conventions: a module docstring naming the AD and ADR it carries, `from __future__ import annotations`, an explicit `__all__`, and no new `__init__.py`. `adapters/` may import `domain/`, `ports/` and `core/` (import-linter `layers`). Optional dependencies are imported **inside the function that uses them** (AD-8), as `adapters/database.py` does.

- **`src/l3io/wp/backup/adapters/crypto.py` (new; Epic 4 owns `adapters/crypto`). It is a thin, passphrase-only adapter over `l3io-wordpress-database` v0.2.0 (rev `48a7da9`)** *(ADR-0024)*. Signatures were verified with `git show v0.2.0:src/l3io/wp/database/encryption.py`:
  - `encrypt(reader: IO[bytes], writer: IO[bytes], ..., *, passphrase: str | None = None) -> None` and `decrypt(reader: IO[bytes], writer: IO[bytes], ..., *, passphrase: str | None = None) -> None`. Each also accepts a key sequence, which this package never passes;
  - `check_passphrase(passphrase: str) -> None`.
  - All three are imported from the package root: `from l3io.wp.database import encrypt, decrypt, check_passphrase`.
  - **`class AgePayloadCipher`**, implementing E002-S01-001's `ports/crypto.PayloadCipher`, with `__init__(self, *, passphrase: str)`. It is applied once to the whole payload, never per member:
    - `check(self) -> None` calls `check_passphrase`, which refuses an empty passphrase and a host with no usable passphrase backend. It runs before any data moves.
    - `encrypt(self, reader: IO[bytes], writer: IO[bytes]) -> None` calls `encrypt(reader, writer, passphrase=...)`.
    - `decrypt(self, reader: IO[bytes], writer: IO[bytes]) -> None` calls `decrypt(reader, writer, passphrase=...)`.
    - `required_tools(self) -> tuple[ToolRequirement, ...]` (below).
    - **No method accepts or returns `bytes`** (AD-21, AG-13). `__repr__` shows no passphrase.
  - **The rename follows ADR-0024.** The factory, port and class formerly `build_member_cipher`, `MemberCipher` and `AgeMemberCipher` are `build_payload_cipher`, `PayloadCipher` and `AgePayloadCipher`. The location decided on 2026-10-27, one factory in `adapters/crypto` that every root calls, stands.
  - **The cipher factory, `build_payload_cipher(*, passphrase: str | None, required: bool, secrets: SecretRegistry) -> AgePayloadCipher | None`** *(ADR-0024; Gate E004 AG-6/AG-9, 2026-10-30)*. It is the one way a composition root turns encryption options into a cipher. E008-S01-001's CLI binding (`run_backup`, `run_restore`) and E006-S01-001's `api/` both call it, and neither constructs `AgePayloadCipher` directly. `passphrase` is the value the root resolved through E002-S01-006's `resolve_passphrase` (`adapters/` may not import `cli/`, so it takes the string, not `ResolvedPassphrase`). `secrets` is the registry the root created before the Run (E002-S01-004), so the factory runs before the driver is called. Its rules:
    - With a passphrase, it registers the passphrase with `secrets`, constructs the cipher, and calls `check()` before returning, so every root refuses identically, in a Dry Run too.
    - With no passphrase and `required=True`, it raises E002-S01-001's `PassphraseRequiredError(operation="backup")`. There is no silent plaintext (AD-26).
    - With no passphrase and `required=False`, it returns `None`.
    - A backup root passes `required=True` exactly when encryption was requested (`--encrypt-with-passphrase`, or the library caller's request). A restore root passes `required=False`, because only the Archive's view says whether a passphrase is needed; the refusal of an encrypted Archive with none is E003-S02-006's, at plan time.
  - **`passphrase_backend_requirements(*, environ: Mapping[str, str], needed_for: str) -> tuple[ToolRequirement, ...]`** *(Gate E004 AG-8, 2026-10-30: moved here from E005-S01-002's `adapters/preflight`, so this story imports nothing from Epic 5, which runs in the same phase)*. This is the one statement of the rule; E005-S01-002 cites it. It follows database's documented backend selection (README and ADR-0003 at `47384ba`: `auto` prefers the `l3io-age-passphrase` binder, else `age` plus `age-plugin-batchpass`; `cli` requires them):
    - **No binary requirement:** `()` for `binder`, and for `auto` (or unset) when `importlib.util.find_spec("l3io_age_passphrase")` is not `None`. The binder is detected without being imported.
    - **CLI backend:** `(ToolRequirement("age", (1, 3), needed_for), ToolRequirement("age-plugin-batchpass", None, needed_for))` for `cli`, and for `auto` when the binder is absent. This declares `age` ≥ 1.3 as an external tool with a minimum version (FR-27) *(Gate E004 AG-4, 2026-10-30)*.
    - **Unrecognised value:** `()`. Database's `check_passphrase`, through `check()`, validates it, so it is validated in one place.
    - It reads only the `environ` it is given. Database's backend resolver is private, so this restates the documented rule in about 10 lines; if database later exports a public backend query, a call to it replaces this function.
- **Errors (AD-14), defined in `adapters/crypto.py` as `BackupError` subclasses** (E002-S01-001's walked hierarchy test covers them). Each wraps database's exception with `raise … from`, and none carries a passphrase in its message or attributes:
  - `ArchiveDecryptionError(CredentialsError)`, with field `member: str` (the payload's name), is raised from database's `DecryptionError`: the wrong passphrase. Because it subclasses `CredentialsError`, it maps to `ExitCode.CREDENTIALS` (4) through Epic 2's existing arm.
  - `EncryptedMemberCorruptError(BackupError)`, with field `member: str` (the payload's name), is raised from database's `CorruptDumpError` (truncated, damaged or not `age`). It declares `exit_code = ExitCode.VERIFICATION_FAILED` (8) itself, with an existing member, as E002-S01-005 provides for a later class.
  - `EncryptionConfigError(UsageError)` inherits `USAGE` (2). Database's `InvalidArgumentsError` from `check()` is re-raised as this error.
  - Database's `MissingDependencyError(extra="encryption")` (`pyrage` absent, or no usable passphrase backend) is re-raised as `MissingExtraError(extra="database")`, exit `NOT_READY` (7), with a message naming `l3io-wordpress-database[encryption]`.
  - The refusal for a missing passphrase is E002-S01-001's `PassphraseRequiredError(RefusedError)` in `domain/errors.py`, so Epic 3 names it without importing this module.
  - No new `ExitCode` member is needed.

- **CI provisioning of `age`** *(Gate E004 AG-4, 2026-10-30)*. The test job in `.github/workflows/ci.yml` gains one step that follows the existing "install mysql client and WP-CLI" step's pattern. Its `env` holds `AGE_VERSION: "1.3.2"` and a hard-coded `AGE_SHA256`, the release's published SHA-256 of `age-v1.3.2-linux-amd64.tar.gz`, hard-coded because a checksum fetched beside the file proves nothing about it. The Manifest records no passphrase, KDF parameter, salt or algorithm field: `age` carries its own header. `manifest.json` itself is never encrypted.

**Seams in Epic 2's and Epic 3's modules, which this story does not edit (decision 6).**

1. **Port.** `ports/crypto.py::PayloadCipher` (`check`, `encrypt`, `decrypt`) is a transform on E002-S02-007's single-role allowance (E002-S01-001).
2. **The writer.** E002-S01-010's `write_archive(..., workspace=, cipher=)` builds the payload in the workspace, streams it once through `cipher.encrypt`, then writes `manifest.json` and the payload into the outer tar *(ADR-0024)*.
3. **The plan.** `build_backup_plan(..., *, encrypted: bool)` puts `ENCRYPT` in the plan (E002-S01-010). Under ADR-0019 the step runs inside `ArchiveWriterCommand.write` (E002-S02-007), so a Dry Run reports it and encrypts nothing.
4. **Flag.** E002-S02-011 registers `--encrypt-with-passphrase` on `backup`, which takes no value. It sits in `NOT_YET_IMPLEMENTED`, naming this story, until E008-S01-001 binds it and removes the entry. Restore takes no encryption flag *(ADR-0024)*.
5. **The AD-26 chain.** E002-S01-006's `resolve_passphrase(*, explicit, environ, prompt, secrets) -> ResolvedPassphrase | None` registers the value with the Run's `SecretRegistry` before it returns. The root creates that registry before the Run and `open_run` adopts it (E002-S01-004), so the passphrase and the cipher exist before the driver is called.
6. **Exit codes.** These come from the class attribute (E002-S01-005), with no edit in `cli/`.
7. **How the cipher arrives.** It is a per-call argument, never an `AdapterSet` field (ADR-0016). A backup passes `BackupRequest.cipher` to `cli/backup.py::backup(..., cipher=)` (E002-S01-004), and from there to `ArchiveWriterCommand.write(..., cipher=)`. A restore passes `RestoreRequest.cipher` (E003-S02-006) to the executor's `VERIFY`, which calls `decrypt_payload` (E002-S01-003, E003-S01-001), and to the Safety Snapshot's joined backup (E003-S02-003). A verify takes none, because verification is keyless. E008-S01-001 builds the cipher with `build_payload_cipher` at each CLI root, and Epic 6's `api/` calls the same factory.
8. **The restore read path.** `decrypt_payload`, and the `payload=` argument of `extract_archive` and `read_member`, are E002-S01-003's *(ADR-0024)*.

### Error and edge case handling

- **Wrong passphrase**: database's `DecryptionError` becomes `ArchiveDecryptionError(member=…)`, exit 4. In a restore it is raised during `VERIFY`'s decrypt, before `SNAPSHOT` and before anything destructive (E003-S01-001). It is never `EncryptedMemberCorruptError`, never `VerificationFailedError`, and never a bare database exception *(Gate E004 AG-7, 2026-10-30)*.
- **Encrypted Archive restored with no passphrase resolved**: `PassphraseRequiredError(operation="restore")`, exit `REFUSED`, raised when the restore plan is built, before `VERIFY` reads the payload (E003-S02-006). Keyless verification of the same Archive still passes *(Gate E004 AG-7, 2026-10-30)*.
- **Encryption requested and no passphrase resolved** (for example under cron, with no `L3IO_WP_BACKUP_PASSPHRASE` and no TTY): `build_payload_cipher` raises `PassphraseRequiredError(operation="backup")`, exit `REFUSED`, before the dump or any write. A plaintext Archive is never written instead (AD-26) *(Gate E004 AG-9, 2026-10-30)*.
- **Payload truncated or a byte flipped after write**: keyless verification fails first, with `CHECKSUM_MISMATCH`, `SIZE_MISMATCH` or `TRUNCATED` (E002-S01-003). If `decrypt` is reached with a damaged stream anyway (the adapter driven directly), it raises `EncryptedMemberCorruptError`, exit 8. The two kinds stay distinct (ADR-0014).
- **Payload swapped in from another Archive under the same passphrase**: it decrypts cleanly but fails keyless verification with `CHECKSUM_MISMATCH`, because the Manifest's payload checksum is over the stored bytes *(ADR-0024)*.
- **Empty passphrase**: E002-S01-006's chain treats it as absent. If one reaches `check()`, database's `check_passphrase` refuses it with `InvalidArgumentsError`, which is re-raised as `EncryptionConfigError`, exit 2.
- **`pyrage` or the passphrase backend not installed** (the `database` extra installed without `[encryption]`, e.g. an older lock): `MissingExtraError` naming `l3io-wordpress-database[encryption]`, exit 7, raised by `check()` inside the factory, before any write. *(Adopted 2026-10-27 from the E002 gate.)*
- **An empty Site Root or an empty Dump** still yields a payload, which encrypts to a valid `age` file and round-trips.
- **Symlink members** travel inside the encrypted payload like every other member. Their targets are visible only through the Manifest's `link_target`, like member names.
- **Broken pipe or disk full while writing the encrypted payload**: database re-raises `BrokenPipeError`/`OSError`. The adapter lets it propagate to Epic 2's `ArchiveWriteError` handling, so the workspace payload and the staged Archive are discarded and no final name exists (AD-20).
- **The Safety Snapshot** is encrypted iff a passphrase resolved at the restore root; otherwise the restore proceeds with AD-26's WARNING (decided 2026-10-20; E003-S02-003, E003-S02-006).

### Security considerations

- **No secret in process arguments (FR-4, NFR-3).** This package invokes no `age` binary and builds no argument vector for encryption. The passphrase is passed in-process to database, which hands it to the binder in-process or to the `age` CLI on a file descriptor (ADR-0014 amendment). A passphrase is never accepted as a CLI flag *value*; it arrives from the environment or a TTY prompt, per AD-26's chain.
- **No secret in logs, `repr` or exceptions (AD-7, AG-14).** The passphrase is registered with E002-S01-006's one `SecretRegistry`, so `redact_event` scrubs any accidental occurrence. `AgePayloadCipher` defines `__repr__` without it. Re-raised errors build their message from structured fields only.
- **No plaintext content in the Archive.** Everything except the Manifest is inside the `age` payload. The only plaintext is the Manifest (inner member names, sizes, link targets, the payload's checksum and the source Site identity): the deliberate, documented ADR-0014 trade.
- **Plaintext on disk** exists only inside the owner-only (`0700`) Run workspace, as `0600` files: the Dump and the plain payload at backup, and the decrypted payload at restore. AD-12 removes the workspace in a `finally` on both paths. This is ADR-0024's accepted trade, which NFR-3 allows. *(ADR-0024)*
- **No key material in the Manifest**, asserted by test.
- **The committed test passphrase** protects only the committed fixture. A contract test asserts that no `age` secret key (`AGE-SECRET-KEY-1` followed by 58 characters of `[0-9A-Z]`) appears anywhere in the repository, so a real key committed by mistake fails CI.
- This package imports no `pyrage` and no `cryptography` cipher (ADR-0014). A contract test enforces it.

### Testability approach

Layout follows E002-S01-001: `tests/unit/` mirrors the package layers, adapter contract tests go in `tests/adapters/`, architecture guards in `tests/contracts/`, and the live-database tier uses the existing `@pytest.mark.integration` marker. ### Existing-library check

Cryptography is a domain the global rules forbid hand-rolling, and ADR-0014 settles the library. `age` is reached only through `l3io-wordpress-database` v0.2.0's `encrypt`/`decrypt(passphrase=)`, backed by the `l3io-age-passphrase` binder or the `age` CLI fallback. Their streaming encryptors are what make AD-21 hold on the encrypted path. The payload is built and read with stdlib `tarfile` and gzip. ADR-0024 records why one payload was chosen over zip (`zipfile` offers only ZipCrypto; `pyzipper` and seeking), 7z (`py7zr` 1.1.4: seeking, extraction advisories) and GnuPG (a new external binary and agent); ADR-0014 records why ADR-0006's own AES-GCM construction and a direct `pyrage` integration were rejected. No version string is parsed or compared. This story adds no new library. It adds the `encryption` extra of an existing one, and the family index as the binder's source. *(Adopted 2026-10-27 from the E002 gate; ADR-0024.)*
