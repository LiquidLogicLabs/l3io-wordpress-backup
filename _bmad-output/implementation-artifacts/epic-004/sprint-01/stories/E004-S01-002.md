# E004-S01-002: Read an archive written before the rewrite


**Implements:** FR-10


As an operator,
I want my existing `.tar.gz` backups to still restore,
So that the upgrade does not strand everything I already hold.

**Acceptance Criteria:**

**Given** a manifest-less archive containing `database.sql` and `wp-root/`
**When** it is read
**Then** it is detected as v0 and handled by default, with no opt-in flag (AD-23)
**And** its verification reports `STRUCTURAL_ONLY` rather than claiming integrity it cannot compute
**And** format detection happens in one place, by inspection, never inferred from the filename
**And** nothing in the product writes the v0 format

*(E004/E005 pre-build re-check, 2026-11-06: the criteria stand. Two limits are now stated rather than implied. "Handled by default" does not mean every v0 Archive passes: a v0 Archive holding a hard link fails verification with `UNSUPPORTED_MEMBER_TYPE` and cannot be restored (F-16). "Nothing in the product writes the v0 format" is proved by extending the built `tests/contracts/test_archive_format_owner.py`, not by a new grep (F-10).)*

## Business acceptance criteria

### Outcome

An operator holding Archives written by wpbackup2 0.2.21 or earlier — a gzipped tar with members `database.sql` and `wp-root/…` and no Manifest — runs `wpbackup2 verify --archive <file>` on one and gets a pass reported as `integrity: STRUCTURAL_ONLY`, with output saying integrity was not checked because a pre-rewrite Archive carries no checksums. No flag, environment variable or configuration is needed, and renaming the file to anything (`backup.bak`, no extension) changes nothing. That behaviour is pinned by committed fixture Archives in `tests/fixtures/archives/v0/` that CI reads on every run. One of them was produced by the released 0.2.21 tool itself, and v0 acceptance is checked against those fixtures, not taken on trust (ADR-0017's fixture-checked `SUPPORTED_FORMAT_VERSIONS` covers v1; v0 is detected by shape). The same fixtures are what Epic 3's restore tests use to prove a v0 Archive restores. A reviewer can tell it happened by running `verify` against each committed v0 fixture and seeing `STRUCTURAL_ONLY` passes, and against each malformed one and seeing a named failure. `symlink-escape` passes verification, and its outward link is skipped at extraction and reported, per the ADR-0017 amendment of 2026-10-28 *(Gate E004 AG-2, 2026-10-30)*. *(Adopted 2026-10-27 from the E002 gate.)* "Existing backups still restore" has one stated exception. The 0.2.21 writer's `stream.add` emits a hard-link (`LNKTYPE`) member for any file with more than one link (`baseline-pre-rewrite:wpbackup2/classes/wp_internal_backup.py` L97). The built verifier refuses every hard link (`UNSUPPORTED_MEMBER_TYPE`, ADR-0017 amendment of 2026-11-03), so such an Archive neither verifies nor restores. The `malformed/hardlink.tar.gz` fixture pins this, and `docs/restore.md` tells the operator (BL-E004-022) *(E004/E005 pre-build re-check, 2026-11-06, F-16)*.

### Non-goals

- Writing the v0 classifier, `ArchiveView`, `Integrity`, `ArchiveProbe` or the verifier. All of these are Epic 2's (`domain/archive_format`, `ports/archive`, `adapters/tar`, `core/verify`; E002-S01-003). This story commits the fixtures and the tests that prove that code reads them. A defect those tests find is fixed in Epic 2's module, as a dependency, not by this story editing it.
- Restoring a v0 Archive onto a Site. That is Epic 3's, and it is built: `tests/integration/test_restore_cli.py` restores a files-only v0 Archive with `--mode db` (refused) and applies `--overwrite-wp-config` from a v0 config, through `tests/restore_harness.py::write_v0`. E003 is closed, so this story adds no fixture to E003's phase-order test *(E004/E005 pre-build re-check, 2026-11-06, F-11: replaces "whose AD-17 phase-order test carries a v0 fixture from this story")*.
- Upgrading or converting v0 Archives to v1. Nothing writes v0, and nothing rewrites one.
- Encrypted v0 Archives. None exist: 0.2.21 had no encryption.
- `config_path` for v0. E002-S01-003's classifier sets it to `"wp-root/wp-config.php"` when that member is present and `None` otherwise; this story's fixtures assert it *(Gate E004 AG-11, 2026-10-30)*.
- Deciding what happens to a symlink whose target is absolute or leaves the Site Root. ADR-0017's 2026-10-28 amendment decided it: verification passes, and `extract_archive` skips the link, records it in `ExtractResult.skipped_links` and continues (E002-S01-003). This story asserts that behaviour on a v0 fixture *(Gate E004 AG-2, 2026-10-30)*.

## Technical acceptance criteria

### Interface contracts

*(Adopted 2026-10-27 from the E002 gate.)* This story adds test data and tests only; it adds no module under `src/l3io/wp/backup/`. Conventions are inherited from E002-S01-003, which created `tests/fixtures/archives/` and its `v1/` member, and from E002-S01-001's test layout (`tests/unit/` mirrors package layers, `tests/contracts/`, `tests/adapters/`, the `integration` marker).

- **`tests/fixtures/archives/v0/` (new; Epic 4 owns the v0 fixture Archives and their tests, Epic List ownership note).** Committed binary fixtures:
  - `released-0.2.21-all.tar.gz`: produced once by the **released** `wpbackup2==0.2.21` from PyPI, run as `wpbackup2 backup --wp-dir <site> --mode all --archive <file>` against the CI database service and `tests/data/wp-config.php` plus a few-kilobyte Site Root. If 0.2.21 no longer installs from PyPI (its `wpconfigr` and `mysql-connector` dependencies), it is run from the tag `baseline-pre-rewrite` checkout instead, and the provenance file says so. It is committed as-is and never regenerated. Beside it, `released-0.2.21-all.provenance.json` records the command, the tool version, the Python version, the date and the SHA-256 of the file. This is the fidelity anchor: a fixture written by the code that actually wrote the operators' Archives.
  - `synthetic-*.tar.gz`: generated by `tests/fixtures/archives/v0/make_v0_fixtures.py`, which is checked in beside them. The generator mirrors the legacy writer at tag `baseline-pre-rewrite` (`wpbackup2/classes/wp_internal_backup.py` L80–97). It reproduces that writer's member layout: `stream.add(dump, arcname="database.sql")`, then `stream.add(site_root, arcname="wp-root")`, which yields a `wp-root` directory member followed by `wp-root/<path>` members. It is deterministic, so it writes through `tarfile.open(fileobj=gzip.GzipFile(..., mode="wb", mtime=0), mode="w", format=...)` rather than the legacy `"w:gz"` (which stamps the current time into the gzip header), with a `filter` that fixes member mtimes, uid/gid and names. The set covers: `synthetic-all-pax.tar.gz` (PAX, the default on Python 3.8 and later); `synthetic-all-gnu.tar.gz` (`format=tarfile.GNU_FORMAT`, which is what a 0.2.x run on Python 3.7 or earlier wrote); `synthetic-all-symlink.tar.gz` (a symlink inside the Site Root, stored as a link because legacy `add` does not dereference); `synthetic-all-longname.tar.gz` (a member path over 100 bytes); `synthetic-files-only.tar.gz` (the shape 0.2.21's `--mode files` wrote: `wp_internal_backup.py` L155–159 calls `__backup_files(..., include_database_dump=False)`, so a `wp-root` directory member and `wp-root/<path>` members, with no `database.sql`); and `synthetic-renamed.bak` (identical bytes to `synthetic-all-pax.tar.gz` under a non-`.tar.gz` name).
  - `symlink-escape.tar.gz`, directly in `v0/` (the passing set): the v0 files-only shape plus `wp-root/link -> ../../outside`. It passes verification as `STRUCTURAL_ONLY`, and extraction skips the link *(Gate E004 AG-2, 2026-10-30: moved out of `malformed/`, which defines the failing set by directory)*.
  - `malformed/`: synthetic Archives that must **not** pass verification. `missing-wp-root.tar.gz` (`database.sql` alone, a shape 0.2.21 never wrote); `stray-manifest-late.tar.gz` (the v0 shape plus a later `manifest.json`); `escape-dotdot.tar.gz` (`wp-root/../escape`); `escape-absolute.tar.gz` (`wp-root//etc/x`: the absolute path is spelled inside the v0 prefix, because a bare `/etc/x` is outside every v0 role, so `classify` raises `UnrecognisedArchiveError` and no view exists to extract with *(E004/E005 pre-build re-check, 2026-11-06, F-9)*); `hardlink.tar.gz` (the v0 shape plus a `LNKTYPE` member `wp-root/x` linking to `wp-root/index.php`, as 0.2.21 writes for a multiply-linked file *(F-16)*); and `truncated.tar.gz` (`synthetic-all-pax` cut mid-member). The generator writes these too. Fixtures in `malformed/` are excluded from the passing set by directory, not by a list.
  - **Which files are Archives** *(E004/E005 pre-build re-check, 2026-11-06, F-8)*. The built `test_supported_formats.py::_archives()` treats every regular file whose suffix is not `.py` as an Archive, so `released-0.2.21-all.provenance.json` would be classified (and fail "classifies as v0"), and E004-S01-003's `encrypted-passphrase.passphrase.txt` would be opened as a tar. This story adds one helper, `tests/archive_fixtures.py::archive_files(directory: Path) -> list[Path]`: regular files directly in `directory`, minus `*.py` and minus any name ending in one of `SIDECAR_SUFFIXES: Final = (".provenance.json", ".passphrase.txt")`. `test_supported_formats.py` and `test_v0_fixtures.py` both select through it, and neither keeps its own rule. A test plants a sidecar of each suffix and a `.py` in `tmp_path` and asserts none is selected, and a planted `x.tar.gz` is. E004-S01-003 consumes the helper and adds no second rule, so it builds after this story.
- **The supported set is checked against fixtures (AD-6, AG-6, ADR-0017).** `domain/archive_format.SUPPORTED_FORMAT_VERSIONS` is `frozenset({1})` (E002-S01-003). v0 has no `format_version`, is detected by shape and is not a member of that constant, so these fixtures add nothing to it. E002-S01-003's `tests/contracts/test_supported_formats.py` asserts the constant equals the `format_version` set read from the Manifests of the fixtures under `tests/fixtures/archives/v*/`, and that every fixture under `v0/` classifies as v0. It reports v0 as *accepted-without-fixture* until Epic 4 commits fixtures. This story makes two changes to that file. It removes the allowance, so a classifier that accepts v0 with no committed v0 fixture fails CI again. It also excludes `v0/malformed/` from the "classifies as v0" walk, by directory (already implicit, because `malformed/` is not a regular file). A third change replaces `_archives()` with `tests/archive_fixtures.py::archive_files` (F-8, above) *(E004/E005 pre-build re-check, 2026-11-06)*. That test is a v0 fixture test, which the ownership note gives to Epic 4. If the orchestrator rules the file Epic 2's, both lines are a dependency on E002-S01-003.
- **Consumed interfaces (Epic 2's, unchanged; all E002-S01-003):** `TarArchiveProbe.member_index(source) -> MemberIndex` / `member_digests(source)`, `domain.archive_format.classify(index) -> ArchiveView`, `Integrity.STRUCTURAL_ONLY`, `UnrecognisedArchiveError`, `core.verify.verify(view, digests, index) -> VerificationResult`, `adapters.tar.verify_archive(path: Path) -> VerificationResult`, `adapters.tar.extract_archive(source: StorageTarget, destination, view, *, roles, exclude=frozenset()) -> ExtractResult`, `cli verify --archive`, and `VerificationReason`. `classify` recognises exactly three shapes (AD-23 as amended 2026-10-20): v1; v0 with `database.sql` and `wp-root/…` (`dump_present=True`); and v0 files-only, `wp-root/…` with no `database.sql` (`dump_present=False`, no `dump`-role member). A database Mode restoring a files-only v0 Archive refuses with `ArchiveHasNoDumpError` (Epic 3). `database.sql` without `wp-root/` is unrecognised. `--mode db` in 0.2.21 wrote no Archive, so no fixture exists for it.

### Error and edge case handling

Each case is a committed fixture with an asserted result. The reasons are E002-S01-003's `VerificationReason` members, and no new reason is added.

*(Adopted 2026-10-27 from the E002 gate.)*

- Every Archive fixture directly in `v0/`: `passed=True`, `integrity=STRUCTURAL_ONLY`, `format_version=None`, synthesized role `site-root` for every `wp-root/…` member and, where `database.sql` is present, `dump` for it with `dump_present=True`. `synthetic-files-only` has `dump_present=False` and no `dump`-role member. No member carries a checksum, so nothing claims one was compared (ADR-0024). Every member's `link_target` is `None`, symlinks included, because v0 has no Manifest *(Gate E004 AG-2, 2026-10-30)*. `config_path` is `"wp-root/wp-config.php"` for every fixture that carries that member and `None` for any that does not *(Gate E004 AG-11, 2026-10-30)*.
- The `wp-root` directory member appears in the index as `wp-root` (tarfile strips the trailing slash). The classifier must recognise the v0 shape from that real spelling, and the PAX, GNU and released fixtures prove it does.
- `synthetic-renamed.bak`: classified exactly as its `.tar.gz` twin. This proves detection is by inspection, never by filename (AD-23).
- `missing-wp-root` (`database.sql` alone): `UNRECOGNISED_FORMAT` naming the members found, never `STRUCTURAL_ONLY`. The operator sees "not a recognised Archive shape", not "your backup is corrupt".
- `stray-manifest-late`: `UNRECOGNISED_FORMAT`, not silently v0.
- `escape-dotdot` and `escape-absolute`: `UNSAFE_MEMBER_PATH` during verification, before any extraction (AD-11). When `extract_archive` is driven directly against them, it also refuses, with nothing written outside `tmp_path`. *(E004/E005 pre-build re-check, 2026-11-06, F-9: with `escape-absolute` spelled `wp-root//etc/x`, both halves were confirmed against the built code: verification reports `UNSAFE_MEMBER_PATH` naming that member, and `extract_archive` raises `ExtractionRefusedError` ("escapes its role prefix"). A bare `/etc/x` would instead give `UNRECOGNISED_FORMAT` naming the first member, and could not be extracted at all.)*
- `hardlink` *(E004/E005 pre-build re-check, 2026-11-06, F-16)*: `UNSUPPORTED_MEMBER_TYPE` naming `wp-root/x`, exit 8 at the CLI. It is a shape the released 0.2.21 writer produces, so its failure is the documented limit in the Outcome, not a crafted attack.
- `symlink-escape`: verification passes as `STRUCTURAL_ONLY`. `extract_archive` skips the link: it is absent from the destination, `link` is in `ExtractResult.skipped_links` with reason `outside_destination` (`SkippedLink.path` is relative to its role prefix, so it is `link`, not `wp-root/link`; confirmed against the built code *(E004/E005 pre-build re-check, 2026-11-06, F-15)*), exactly one `symlink_skipped` WARNING is logged, every other member is extracted, and nothing is written outside `tmp_path` (E002-S01-003; ADR-0017 amendment) *(Gate E004 AG-2, 2026-10-30)*.
- `truncated`: `TRUNCATED`. No `EOFError` or `tarfile.ReadError` reaches the caller.
- A v0 Archive is never reported as `VERIFIED` in any output, log record or result value.
- CLI: `wpbackup2 verify --archive <v0 fixture>` exits `ExitCode.OK` (0), and its human output names `STRUCTURAL_ONLY` and the reason. Each malformed fixture exits `ExitCode.VERIFICATION_FAILED` (8) through Epic 2's `exit_code_for`, and no new code is added.

### Security considerations

- A v0 Archive is untrusted input (AD-11, NFR-5) and has no checksums, so containment is its only protection. The `escape-*` fixtures are therefore committed permanently, and they run on every Python in the CI matrix inside the existing `AD-11 extraction containment` step. That step runs only `tests/contracts/test_extraction.py` (`.github/workflows/ci.yml`), so the `escape-*` and `symlink-escape` extraction cases live in that file, parametrised over the committed fixtures, and not in `tests/adapters/test_v0_fixtures.py`, which keeps their verification cases *(E004/E005 pre-build re-check, 2026-11-06, F-17)*.
- The fixtures contain no real data. The released fixture's Dump comes from the CI database seeded with the test schema, and its Site Root is synthetic. The `tests/data/wp-config.php` credentials it embeds are the existing public test values. A test asserts the released fixture's `database.sql` contains no string from the operator-secret patterns E002-S01-006's sentinel uses.
- The generator script writes the committed fixtures only when a developer invokes it, and then only under `tests/fixtures/archives/v0/`. Its builder function is importable, and the test suite calls it to build into `tmp_path` (the reproducibility guard, the AD-21 case and, optionally, `restore_harness.write_v0` and `test_tar_probe._v0`). The package never imports it *(E004/E005 pre-build re-check, 2026-11-06, F-11: replaces "never imported by the test suite")*.

### Existing-library check

Stdlib `tarfile` builds the fixtures. Its `GNU_FORMAT`/`PAX_FORMAT` selection reproduces both legacy header formats, and `gzip.GzipFile(mtime=0)` makes the output deterministic. `hashlib` produces the provenance digest, and `pytest` parametrisation runs the table. The released fixture uses the real legacy tool from PyPI rather than a re-implementation of it. No tar, gzip or JSON parsing is hand-written (AD-23), and no dependency is added.
