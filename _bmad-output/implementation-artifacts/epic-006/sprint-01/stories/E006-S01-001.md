# E006-S01-001: Drive backup and restore from Python


**Implements:** FR-22


As a DevOps engineer,
I want to import this and call it,
So that I can embed it in a provisioning pipeline without shelling out.

**Acceptance Criteria:**

**Given** the installed distribution
**When** a caller imports it
**Then** backup, restore and verification are all available without invoking a subprocess or parsing output *(pruning removed 2026-10-27: it is FR-17, out of scope until v1.1 per the FR Coverage Map)*
**And** the public API is fully annotated and passes `mypy --strict`
**And** every operation available on the CLI is available through the API
**And** constructing a Site Descriptor with invalid or incomplete values fails at construction with a named error, not at use
**And** `py.typed` ships

## Business acceptance criteria

### Outcome

A DevOps engineer writes `from l3io.wp.backup.api import backup, restore, verify` and runs a backup, a verification or a restore from inside a provisioning script. No subprocess is started and no output is parsed. Each call returns a frozen domain value or raises a package exception. The library and the CLI share one composition sequence. That sequence opens or joins a Run Context through Epic 2's `join_or_open`, and it takes the Site Lock the way the CLI does. Encryption secrets resolve through the same AD-26 chain. A restore goes through E003-S01-006's `drive_restore`, the function `wpbackup2 restore` also calls. The library never configures logging and never installs a signal handler. A reviewer can check the outcome in three ways. First, call each entry point against a fixture Site in a test process. Second, read the captured records: one `run_id` per call, `run_started`/`run_finished` present, and the same `phase_completed` sequence the matching CLI invocation emits. Third, confirm that `structlog.is_configured()`, the root logger's handlers and `signal.getsignal(SIGTERM)` are the same after the call as before it.

### Non-goals

- Pruning and a Retention Policy. Pruning is FR-17, out of scope for v1 and deferred to v1.1 (`epics.md` FR Coverage Map). The CLI has no prune operation, so the API has none either. See the resolved pruning note under Interface contracts.
- The exception contract: one base, the translation at the public boundary and the raise-site check. Those are E006-S01-002. This story's entry points raise whatever the functions they call raise.
- Declaring and documenting the public surface, and the AD-27 checks for `api/`. Those are E006-S01-003.
- Spans. Those are E006-S01-004.
- An async API, and a public way to open one Run Context that spans several API calls. The `context=` parameter joins a context the caller was given; this story adds no public opener.
- A new Restore Mode decision path. A library caller passes a `RestoreMode` and an `OverrideSet` directly. The AD-25 flag table is the CLI's translation, and the FR-7 target guard is enforced by Epic 3's plan whichever root called it.
- Any change to modules owned by Epic 2 (`cli/*`, `domain/*`, `ports/*`, `adapters/{tar,database,store,lock,redaction,noop,config_writer}`) or Epic 3 (`cli/restore.py`, `core/restore`). Where this story needed one, it is recorded as a dependency on the owning story (the resolved notes under Interface contracts).
- A caller-built `SiteDescriptor` as a backup input. *(Decided 2026-10-27.)* Like the CLI, the API takes a Site Root path, an optional `wp_config` and a `CredentialSpec`; the descriptor is built once, at the composition root, from `wp-config.php` (AD-3). A Site with no readable `wp-config.php` cannot be backed up through the API. This is a stated API difference from 0.2.21 for any caller that passed a descriptor: the Python API is not a preserved contract (AD-22). `SiteDescriptor` stays re-exported and still validates at construction (the AC).

## Technical acceptance criteria

### Interface contracts

*(Adopted 2026-10-27 from the E002 gate.)* Files added or changed, all under `src/l3io/wp/backup/api/`:

- `api/__init__.py`, which already exists. Its `__all__: list[str] = []` is filled.
- `api/operations.py`, a new file holding the entry points.

These follow the conventions the existing siblings set (`api/__init__.py`, `adapters/__init__.py`, `domain/flag_map.py`, `cli/parser.py`):

- every module opens with a docstring naming the AD it implements, then `from __future__ import annotations`, then an explicit `__all__`;
- no `__init__.py` is added above `l3io/wp/backup/` (AD-27);
- the layer is the directory, never a filename suffix (Consistency Conventions);
- `api/` may import `cli/`, `adapters/`, `ports/`, `core/` and `domain/`. `pyproject.toml`'s layers contract puts `cli : api` in one non-independent layer. In import-linter 2.x, `:` means the siblings may import each other, which was verified against the installed `importlinter/contracts/layers.py`.

**Entry points.** Each is a plain synchronous function. Every parameter after the first is keyword-only, and every parameter and return value is fully annotated. Each returns a frozen value and never an exit code.

```python
def backup(
    site: str | os.PathLike[str],
    *,
    scope: BackupScope,
    target: StorageTarget | str | os.PathLike[str] | None = None,
    wp_config: str | os.PathLike[str] | None = None,
    credentials: CredentialSpec | None = None,
    exclusion: ExclusionPolicy | None = None,
    recipients: Sequence[str] = (),
    recipients_file: str | os.PathLike[str] | None = None,
    passphrase: str | None = None,
    prompt: Callable[[str], str] | None = None,
    dry_run: bool = False,
    context: RunContext | None = None,
) -> BackupResult

def verify(
    archive: StorageTarget | str | os.PathLike[str],
    *,
    identity_files: Sequence[str | os.PathLike[str]] = (),
    passphrase: str | None = None,
    prompt: Callable[[str], str] | None = None,
    context: RunContext | None = None,
) -> VerificationResult

def restore(
    site_root: str | os.PathLike[str],
    *,
    archive: StorageTarget | str | os.PathLike[str],
    mode: RestoreMode,
    overrides: OverrideSet,
    snapshot: SnapshotPolicy,
    snapshot_dir: str | os.PathLike[str] | None = None,
    admin: CredentialSpec | None = None,
    recipients: Sequence[str] = (),
    recipients_file: str | os.PathLike[str] | None = None,
    identity_files: Sequence[str | os.PathLike[str]] = (),
    passphrase: str | None = None,
    prompt: Callable[[str], str] | None = None,
    resolve_run_id: str | None = None,
    dry_run: bool = False,
    context: RunContext | None = None,
) -> RestoreOutcome
```

Rules for the parameters:

- `scope`, `mode`, `overrides` and `snapshot` have no defaults. The CLI's defaults are argparse's to give; the library makes the caller state them (AD-5).
- A string target or archive is parsed by `domain/storage_target.py::parse_storage_target`, after a relative path is resolved against the caller's working directory. A `StorageTarget` passes through unchanged. A `target` of `None` takes the same legacy default name the CLI uses (E002-S01-001).
- `site` is the Site Root path, and `wp_config`, when given, is the stated `wp-config.php` (the library's equivalent of `--wp-config`). Both go into the request unread. `drive_backup` canonicalises the root, takes the Site Lock, locates the config with `locate_wp_config(site_root, stated=wp_config)` and reads the descriptor and the WordPress source with `site_descriptor_from_wp_config` (E002-S01-001, E002-S01-004, E002-S02-008). `api/` opens no `wp-config.php` itself (AD-3, AG-8).
- `credentials` and `admin` are backup-owned specs from E002-S01-006's `domain/credentials.py`: `CredentialSpec = ExplicitCredentialSpec(username, password) | AwsSecretCredentialSpec(secret_id, region)`. They are never `l3io.wp.database` types (ADR-0015 amendment). `credentials` becomes `BackupRequest.credentials`. The driver turns it into a source through `cli/credentials.wordpress_source`, which delegates to `adapters/database.py`. An explicit spec is chained ahead of the `wp-config.php` source in `WORDPRESS_CREDENTIAL_PRECEDENCE` order. It no longer replaces that source, because Epic 2's builder decides this. `admin` becomes `RestoreRequest.admin` (E003-S01-006) and goes through `cli/credentials.admin_source`. An `AwsSecretCredentialSpec` raises `UsageError` naming Epic 5 until E008-S01-001 binds Epic 5's provider.
- **`api/` constructs no database credential class.** It never calls `Explicit`, `Environment`, `AwsSecretsManager`, `WpConfigFile` or `CredentialChain`, and no `api/` parameter is annotated with an `l3io.wp.database` type. E002-S01-006's `test_credential_sources_built_once.py` walks the whole package, `api/` included. This story's parity test checks the signatures (Testability).

**Run Context and Site Lock (AD-16, AD-19, AG-9, AG-11).**

- Every entry point gets its context only through its driver, which calls `cli/context.py::join_or_open(ctx, ...)` and gets back a `RunHandle(ctx, opened)` (E002-S01-004). With `context=None`, the driver opens a Run: a new UUIDv4 `run_id`, a workspace, `run_started`/`run_finished`, and the Site Lock for the canonical Site Root (restore and backup; verify takes none; E002-S02-008).
- Given a context, it joins: it creates no Run ID, workspace or log binding, and binds no adapters (`opened=False`, ADR-0016). It also takes no lock for a Site Root the context's `site_lock` already covers (E002-S02-008).
- Calling an entry point with `context=None` while a Run is active in the current `contextvars` context raises Epic 2's `RunContextActiveError` and never starts a second Run.
- `RunContext`, `BackupResult`, `VerificationResult`, `RestoreOutcome`, `SiteDescriptor`, `BackupScope`, `StorageTarget`, `RestoreMode`, `OverrideSet`, `SnapshotPolicy`, `CredentialSpec`, `ExplicitCredentialSpec` and `AwsSecretCredentialSpec` are re-exported from `api/__init__.py`. - A caller who binds `correlation_id` through `structlog.contextvars` sees it on every record (E002-S01-004).

**Optional extras (AD-8).**

### Error and edge case handling

- **Invalid Site Descriptor.** A `SiteDescriptor(...)` with a relative `site_root`, an empty `db_host` or `db_name`, or a port outside 1–65535 raises `InvalidSiteDescriptorError` from `__post_init__`, at construction, through the re-exported class (FR-22, E002-S01-001). A `site` path that does not exist fails at the driver's canonicalisation (`Path.resolve(strict=True)`), before any lock. A Site Root with no locatable `wp-config.php` raises `InvalidSiteDescriptorError` from `locate_wp_config`, and an unreadable config raises `CredentialsError`. Both happen after the Site Lock is taken (E002-S01-001, E002-S02-008), and the lock is released in `finally`. *(Adopted 2026-10-27 from the E002 gate.)*
- **Another Run holds the Site Lock.** The call raises `SiteLockedError`, naming the holder's `run_id`, PID and start time (AG-16). Nothing changes.
- **Same process, two threads, same Site.** Each thread opens its own Run, because `contextvars` are per thread. The second one is refused by the lock registry (E002-S02-008), never deadlocked.
- **Called inside an active Run without `context=`.** The call raises `RunContextActiveError`, naming the active `run_id`.
- **Rejected restore combination.** A combination the FR-7 guard rejects (for example a clean Mode against a non-empty target without `overrides` waiving it) is refused by Epic 3's `build_restore_plan` with the same `RefusedError` subclass the CLI produces, before step 7. The API skips the AD-25 flag table, but the guard still runs.
- **Incomplete journal from an interrupted Run.** The call raises `IncompleteRunError`. `resolve_run_id` resolves the journal and returns a `RestoreOutcome` with no phases run. Resolving and restoring are never one call (E003-S01-006).
- **Encryption.** A missing identity for an encrypted Archive, or a prompt that raises `EOFError`, raises the same error the CLI path raises (`PassphraseUnavailableError` and Epic 4's errors), before any destructive phase.
- **An `AwsSecretCredentialSpec`** before E008-S01-001 binds Epic 5's provider raises `UsageError` naming Epic 5, from `cli/credentials` (E002-S01-006).
- **A database operation without the `database` extra.** The call raises `MissingExtraError(extra="database")` before the lock.
- **Workspace cleanup.** On every failure path the workspace is removed and the lock released by `open_run`'s `finally`. This does not apply when the call joined a context: the outer Run owns both.
- **`KeyboardInterrupt` or `SystemExit` from the host.** These propagate unchanged after the `finally` runs. A host that is killed is covered by the kernel releasing `flock` (E002-S02-008).

### Observability requirements

- An API-opened Run emits the same records as the CLI-opened Run of the same operation: `run_started`, `run_finished`, `phase_completed` with `phase`, `duration_ms`, `bytes`, `exit_code` and `outcome`, and for restore `restore_mode_resolved` and `planned_action`. All of them come from Epic 2's and Epic 3's code, through the host's logging configuration. This root adds no second record of its own for the same event.
- `run_finished.exit_code` carries the `ExitCode` the CLI would have exited with: `type(exc).exit_code` for a `BackupError`, 0 on success. So a log consumer reads one schema whichever root ran.
- The records reach the host's handlers because the library configures nothing. With an unconfigured host they go to structlog's defaults, which is the host's choice. A caller-bound `correlation_id` appears on every record.

### Security considerations

- **Passphrase.** A passphrase given as an argument is registered with the Run's `SecretRegistry` by `resolve_passphrase` before it is used. The entry point does not keep it in a local that outlives the call, and no result value carries it.
- **Credential reprs.** `repr()` of every argument-holding value this story builds (`RestoreRequest` and the backup and verify requests) shows no credential or passphrase. E002-S01-006's walked `__repr__` contract test covers them by annotation, with no list.
- **Environment reads.** The library reads `os.environ` at one point only: it hands the mapping to `resolve_passphrase`, which is the AD-26 chain's environment step (`L3IO_WP_BACKUP_PASSPHRASE`). Nothing deeper reads the environment.
- **No subprocess.** No entry point starts a subprocess, so FR-22's "without invoking a subprocess" holds. All database work goes through `l3io-wp-database` in process (ADR-0015), and `tests/contracts/test_no_mysql_client.py` stays green.
- **No database credential type in `api/`** (ADR-0015 amendment). Credential values cross `api/` only as `CredentialSpec`. `ExplicitCredentialSpec.__repr__` hides the password (E002-S01-006). *(Adopted 2026-10-27 from the E002 gate.)*
- **Input validation.** Paths are canonicalised (`resolve(strict=True)`) by the driver before locking (AD-19, E002-S01-004). A `str` archive with a non-`file` scheme raises `UnsupportedStorageSchemeError` (Storage Target grammar).

### Testability approach

New tests go beside E002's: unit cases under `tests/unit/api/`, contract checks under `tests/contracts/`, and integration cases under `tests/integration/`, marked `@pytest.mark.integration`. They use the adapter doubles and recording adapters Epics 2 and 3 already define; no new double is written. CI syncs `--all-extras`, so nothing here uses `importorskip`: a skip would be a false green.

- **`tests/unit/api/test_operations.py`**
  - Each entry point against a fixture Site, using doubles, gives exactly one `run_started` and one `run_id`.
  - `context=ctx` gives no `run_started`, no new workspace and no second lock acquisition, by a spy on `SiteLock.acquire`.
  - A nested call without `context=` raises `RunContextActiveError`.
  - `dry_run=True` reaches the driver as `request.dry_run`, and the bound set's command halves are the no-ops (`ctx.adapters.archive_writer` is a `NoopArchiveWriter`, E002-S02-007).
  - `backup` and `verify` call `drive_backup`/`drive_verify` exactly once each, with a `BackupRequest`/`VerifyRequest` equal to the expected value, checked by a spy.
  - `restore` calls `drive_restore` exactly once with a `RestoreRequest` equal to the expected value, by a spy.
  - `backup` without `exclusion` passes a request whose `exclusion` equals the one `run_backup` builds with no exclusion flag; `ExclusionSet.none()` passed explicitly reaches the request unchanged.
  - With `context=None` each driver receives a `secrets` registry that already holds the passphrase (spy on `register`, called before the driver); with a `context`, it is `context.secrets` (identity).
  - The passphrase path calls `cli.passphrase.resolve_passphrase` by identity. The test patches that name and asserts it is called, which fails if a copy exists.
- **`tests/unit/api/test_process_state.py`**
  - After every entry point returns or raises, `structlog.is_configured()`, `logging.getLogger().handlers` and `signal.getsignal(signal.SIGTERM)` equal their values before the call.
  - A phase double reads `signal.getsignal` during the Run, so a handler installed and then restored is also caught.
- **`tests/contracts/test_api_parity.py`** derives its scope from the source of truth.
  - It walks the subparsers of `cli/parser.py::build_parser()` (`backup`, `restore`, `verify` today) and asserts each name is a callable in `l3io.wp.backup.api.__all__`. A subcommand added later without an API function fails CI.
  - It asserts the walk found at least the two AD-22 subcommands, so an empty walk cannot pass.
  - It asserts no `api` callable has a parameter named `args` or `argv`, or annotated `argparse.Namespace` (FR-22's "does not require CLI argument lists").
  - It asserts, through `typing.get_type_hints`, that no `api` callable has a parameter or return annotated with a type from `l3io.wp.database` (ADR-0015 amendment). The scope comes from `api.__all__`. *(Adopted 2026-10-27 from the E002 gate.)*
- **`tests/contracts/test_api_one_sequence.py`**
  - An AST check that `api/operations.py` names no `RestorePhase` member and calls no `core.restore` function, `open_run`, `join_or_open`, `bind_adapters`, `real_adapters`/`dry_run_adapters` or `SiteLock.acquire`. The drivers do all of these.
  - Planted-violation case: the same check run over a temporary copy with one such call added must fail.
- **`tests/contracts/test_api_base_install.py`**
  - Runs in a subprocess with `sys.modules["l3io.wp.database"] = None` and `sys.modules["opentelemetry.sdk"] = None` set before import.
  - `import l3io.wp.backup.api` succeeds, and every name in `__all__` resolves.
  - `backup(..., scope=BackupScope.DATABASE)` raises `MissingExtraError` with `extra == "database"`.
  - This is AD-8's "a base install imports every public module".
- **`tests/unit/api/test_descriptor_construction.py`**
  - Parametrised over invalid values (relative root, empty host, empty name, ports 0 and 65536), each raising `InvalidSiteDescriptorError` from `l3io.wp.backup.api.SiteDescriptor(...)`.
- **Typing.** CI's existing `mypy --strict` covers `api/`. Also, `tests/typing/api_consumer.py`, a consumer script that imports and calls each entry point, is type-checked by the same mypy step: it is included in mypy's `files`, or run as `mypy --strict tests/typing`.
- **`tests/integration/test_api_roundtrip.py`**
  - Against the fixture Site and database used by E002's integration tier: `backup` of each `BackupScope`, `verify` of the result, then `restore` into an empty target.
  - Asserts one `run_id` per call and a phase sequence equal to the CLI run of the same operation, both captured as JSON records.
