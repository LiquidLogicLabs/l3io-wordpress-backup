# E006-S01-001: Drive backup and restore from Python


**Implements:** FR-22


As a DevOps engineer,
I want to import this and call it,
So that I can embed it in a provisioning pipeline without shelling out.

**Acceptance Criteria:**

**Given** the installed distribution
**When** a caller imports it
**Then** backup, restore and verification are all available without invoking a subprocess or parsing output *(pruning removed 2026-10-27: it is FR-17, out of scope until v1.1 per the FR Coverage Map)*
**And** the public API is fully annotated and passes `mypy --strict`
**And** every operation available on the CLI is available through the API
**And** constructing a Site Descriptor with invalid or incomplete values fails at construction with a named error, not at use
**And** `py.typed` ships

*(E006 arch gate, 2026-11-06, against the built code at `e0902df`; see `epic-006/arch/reviewer-l3io-arch-review-2026-11-06.md`. These corrections apply to the criteria above.)*
- *"every operation available on the CLI is available through the API"* (A1, A2, A9, A10). The operations are the parser's subcommands that are bound today: `backup`, `restore`, `verify` (`cli/parser.py:136-197`). `doctor` is registered but `NOT_YET_IMPLEMENTED` (`cli/parser.py:109`) until E008-S01-001 binds it; who adds its API entry then is an owner decision (gate O-4). Each bound subcommand's bound flags reach the API: `restore --overwrite-wp-config`, `--archive-database`, `--admin-tls`/`--admin-tls-ca`, `--reset-existing-db-user` (A1), `verify --authenticate` (A2), and `backup --list-default-excludes` as the re-exported `enumerate_defaults` (A9).
- *"available without ... parsing output"* (A3). A failure the CLI turns into a non-zero exit after its driver returns reaches a library caller as an exception too: a failed verification raises `VerificationFailedError`, and a real restore whose database report does not say restored raises `DatabaseNotRestoredError`. Both are the CLI's own rules, imported (PRD FR-23: "Failures reach a library caller as typed exceptions").

## Business acceptance criteria

### Outcome

A DevOps engineer writes `from l3io.wp.backup.api import backup, restore, verify` and runs a backup, a verification or a restore from inside a provisioning script. No subprocess is started and no output is parsed. Each call returns a frozen domain value or raises a package exception. The library and the CLI share one composition sequence. That sequence opens or joins a Run Context through Epic 2's `join_or_open`, and it takes the Site Lock the way the CLI does. Encryption secrets resolve through the same AD-26 chain. A restore goes through E003-S02-006's `drive_restore`, the function `wpbackup2 restore` also calls. The library never configures logging and never installs a signal handler. A reviewer can check the outcome in three ways. First, call each entry point against a fixture Site in a test process. Second, read the captured records: one `run_id` per call, `run_started`/`run_finished` present, and the same `phase_completed` sequence the matching CLI invocation emits. Third, confirm that `structlog.is_configured()`, the root logger's handlers and `signal.getsignal(SIGTERM)` are the same after the call as before it.

## Technical acceptance criteria

### Interface contracts

*(Adopted 2026-10-27 from the E002 gate.)* Files added or changed, all under `src/l3io/wp/backup/api/`:

- `api/__init__.py`, which already exists. Its `__all__: list[str] = []` is filled.

These follow the conventions the existing siblings set (`api/__init__.py`, `adapters/__init__.py`, `domain/flag_map.py`, `cli/parser.py`):

- every module opens with a docstring naming the AD it implements, then `from __future__ import annotations`, then an explicit `__all__`;

### Error and edge case handling

- **Invalid Site Descriptor.** A `SiteDescriptor(...)` with a relative `site_root`, an empty `db_host` or `db_name`, or a port outside 1–65535 raises `InvalidSiteDescriptorError` from `__post_init__`, at construction, through the re-exported class (FR-22, E002-S01-001). A `site` path that does not exist fails at the driver's canonicalisation (`Path.resolve(strict=True)`), before any lock. A Site Root with no locatable `wp-config.php` raises `InvalidSiteDescriptorError` from `locate_wp_config`, and an unreadable config raises `CredentialsError`. Both happen after the Site Lock is taken (E002-S01-001, E002-S02-008), and the lock is released in `finally`. *(Adopted 2026-10-27 from the E002 gate.)*
- **Another Run holds the Site Lock.** The call raises `SiteLockedError`, naming the holder's `run_id`, PID and start time (AG-16). Nothing changes.
- **Same process, two threads, same Site.** Each thread opens its own Run, because `contextvars` are per thread. The second one is refused by the lock registry (E002-S02-008), never deadlocked.
- **Called inside an active Run without `context=`.** The call raises `RunContextActiveError`, naming the active `run_id`.
- **Rejected restore combination.** A combination the FR-7 guard rejects (for example a clean Mode against a non-empty target without `overrides` waiving it) is refused by Epic 3's `build_restore_plan` with the same `RefusedError` subclass the CLI produces, before step 7. The API skips the AD-25 flag table, but the guard still runs.
- **Incomplete journal from an interrupted Run.** The call raises `IncompleteRunError`. `resolve_run_id` resolves the journal and returns a `RestoreOutcome` with no phases run. Resolving and restoring are never one call (E003-S02-006).
- **Encryption.** No passphrase resolved for an encrypted Archive, or for `backup(encrypt=True)` (a prompt that raises `EOFError` resolves none), raises the same `PassphraseRequiredError` the CLI path raises; a wrong passphrase raises Epic 4's `ArchiveDecryptionError` during `VERIFY`. Both come before any destructive phase *(ADR-0024; Gate E004 AG-7/AG-9, 2026-10-30)*.
- **An `AwsSecretCredentialSpec`** before E008-S01-001 binds Epic 5's provider raises `UsageError` naming Epic 5, from `cli/credentials` (E002-S01-006).
- **A database operation without the `database` extra.** The call raises `MissingExtraError(extra="database")` before the lock.
- *(E006 arch gate, 2026-11-06; these bullets correct the four above where they differ from the built code.)*
  - **Rejected restore combination (A12).** The FR-7 guard runs at step 6, the plan. `drive_restore` re-raises its `NonEmptyTargetError` as `cli/restore.py::NonEmptyTargetRefusal` (`:483-525`, raised at `:1343`).   - **Encryption (A4).**

    - A prompt that raises `EOFError` or `KeyboardInterrupt` raises `PassphraseUnavailableError` too (`cli/passphrase.py:65-71`). It does not resolve to nothing.
    - An encrypted Archive with no resolved passphrase is refused at plan time with `PassphraseRequiredError("restore")` (`cli/restore.py:942-946`). `verify(authenticate=True)` with none raises `PassphraseRequiredError("verify")` (`cli/verify.py:110-112`), and `ArchiveNotEncryptedError` for a plain Archive (`:105-106`).
    - A wrong passphrase raises `PassphraseRejectedError`, and a damaged or tampered payload raises `PayloadDamagedError`, both `VERIFICATION_FAILED` (8) (`adapters/crypto.py:85-88`; `domain/errors.py:466-494`). E004-S01-003 does not add `ArchiveDecryptionError`.

  - **A failed verification or an unrestored database (A3).** These raise `VerificationFailedError` or `DatabaseNotRestoredError` after the driver returns, as on the CLI. `run_finished` has already been written by then.
  - **A Dry Run joining a real Run (A18).** This raises `UsageError` from `join_or_open`.
- **Workspace cleanup.** On every failure path the workspace is removed and the lock released by `open_run`'s `finally`. This does not apply when the call joined a context: the outer Run owns both.
- **`KeyboardInterrupt` or `SystemExit` from the host.** These propagate unchanged after the `finally` runs. A host that is killed is covered by the kernel releasing `flock` (E002-S02-008).

### Security considerations

- **Passphrase.** A passphrase given as an argument is registered with the Run's `SecretRegistry` by `resolve_passphrase` before it is used. The entry point does not keep it in a local that outlives the call, and no result value carries it.
- **Credential reprs.** `repr()` of every argument-holding value this story builds (`RestoreRequest` and the backup and verify requests) shows no credential or passphrase. E002-S01-006's walked `__repr__` contract test covers them by annotation, with no list.
- **Environment reads.** The library reads `os.environ` at one point only: it hands the mapping to `resolve_passphrase`, which is the AD-26 chain's environment step (`L3IO_WP_BACKUP_PASSPHRASE`). Nothing deeper reads the environment. *(E006 arch gate, 2026-11-06, A8: this is not what the built code does, and the claim is withdrawn. - **No subprocess.** No entry point starts a subprocess, so FR-22's "without invoking a subprocess" holds. All database work goes through `l3io-wp-database` in process (ADR-0015), and `tests/contracts/test_no_mysql_client.py` stays green.
