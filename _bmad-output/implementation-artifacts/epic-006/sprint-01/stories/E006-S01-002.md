# E006-S01-002: Catch typed failures


**Implements:** FR-23


As a DevOps engineer,
I want failures to arrive as exceptions I can catch by type,
So that I can branch on what went wrong.

**Acceptance Criteria:**

**Given** any documented failure mode
**When** it occurs
**Then** it raises a documented exception type exported from this package, descending from one base
**And** no exception from a dependency or the stdlib crosses the public boundary — each is caught and re-raised with `raise ... from`
**And** exceptions carry structured fields, not only a formatted message
**And** no exception message contains a credential

## Business acceptance criteria

### Outcome

A library caller writes `except l3io.wp.backup.api.BackupError` and catches every failure the package can raise. They can also catch a specific type, such as `SiteLockedError`, `CredentialsError`, `VerificationFailedError` or `RefusedError`, and read its structured fields: `exc.holder_run_id`, `exc.result.integrity`, `exc.findings`. `exc.exit_code` gives the same `ExitCode` the CLI would have exited with.

No exception from `l3io.wp.database`, `l3io.wp.config`, `tarfile`, `OSError` or any other dependency or stdlib type escapes an API call. Each arrives wrapped, with the original on `__cause__`. No message, repr or traceback contains a credential or passphrase.

The hierarchy is Epic 2's `domain/errors.py`. This story re-exports it, documents it, and enforces it at the API boundary. It defines no parallel hierarchy.

A reviewer can check this in two ways. Force each documented failure through the API with doubles and catch it by its exported type. Then search every formatted traceback for a planted credential sentinel and confirm there are zero hits.

### Non-goals

- A second base class, or a parallel `api`-side copy of any Epic 2 exception. There is one base, `BackupError`, in `domain/errors.py`.
- New `ExitCode` members, and any edit to `cli/exit.py`. The exit code is the class attribute `exit_code: ClassVar[ExitCode]` that Epic 2 decided on.
- Adding structured fields to, or fixing raise sites of, exception classes owned by Epics 2, 3, 4, 5 or 7. Where this story's checks find such a gap, it is reported against the owning story, not edited here (see Error and edge case handling).
- Making the CLI's error output match the library's. The CLI maps exceptions to codes in `cli/exit.py`. That is Epic 2's (E002-S01-005).
- Wrapping `BaseException` subclasses that are not `Exception`: `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` belong to the host.

**Re-exports, scope from the hierarchy.**

- `api/errors.py` imports `BackupError` from `domain/errors.py`, and every subclass of it defined anywhere in the package, from the module that defines it. Under Epic 2's rule, a class whose only raise site is a later epic's module is defined in that module.
- It lists them all in its `__all__`. `api/__init__.py` re-exports that list (`from .errors import *` with an explicit `__all__` concatenation, so mypy sees the names).
- The set is not hand-kept. A contract test imports every module under `src/l3io/wp/backup/` (walked), collects `BackupError` and its subclasses recursively through `__subclasses__()`, and asserts that set equals the exception names in `l3io.wp.backup.api.__all__`, in both directions. So:
  - a subclass added in any epic without being exported fails CI;
  - an exported name that is not a `BackupError` subclass fails CI.

  Every re-exported class is the defining class by identity (`api.SiteLockedError is domain.errors.SiteLockedError`, or the defining module's class).

**The one class this story defines.**

```python
class UnexpectedError(BackupError):
    """A non-package exception reached the API boundary. It is a defect."""
    cause_type: str  # fully qualified name of the original type, e.g. "tarfile.ReadError"
```

- It inherits `exit_code = ExitCode.FAILED` from `BackupError`, which matches `cli/exit.py`'s treatment of a non-`BackupError` exception as `FAILED`.
- It is a subclass, not a second base, and it is defined in `api/errors.py` because its only raise site is `api/`, per Epic 2's rule.

**The boundary.**

```python
def public_boundary(fn: Callable[P, R]) -> Callable[P, R]
```

- It lives in `api/errors.py`. It is the only translation, and every entry point in `api/__all__` is decorated with it. E006-S01-001's `backup`, `restore` and `verify` are wrapped in this story.
- It passes through any `BackupError` unchanged, with its traceback intact.
- It re-raises any other `Exception` as `UnexpectedError(cause_type=f"{type(e).__module__}.{type(e).__qualname__}") from e`. This covers `l3io.wp.database.DatabaseError` and `l3io.wp.config` errors that an adapter failed to wrap, and stdlib errors such as `OSError`, `tarfile.TarError` and `json.JSONDecodeError`.
- Its message is a fixed sentence naming `cause_type` and the API function. The original exception's text is never interpolated, so a dependency message that happens to carry a value cannot reach `str(exc)`.
- It lets every `BaseException` that is not an `Exception` propagate untouched.
- It logs the wrap once at ERROR as `unexpected_exception`, with `cause_type` and `exc_info`, through the bound logger. The record passes through `redact_event` when the host's chain is E002-S01-004's `configure_logging`. A host that configures logging itself has no `redact_event`, and ADR-0018 records that limit. *(Adopted 2026-10-27 from the E002 gate.)*
- *(E006 arch gate, 2026-11-06, B3.)* **Where the boundary sits relative to the Run.** `public_boundary` wraps the entry point, and the entry point calls a driver that opens the Run itself (`join_or_open`, `cli/context.py:307-356`). An exception therefore leaves the Run before the boundary sees it. By then `open_run`'s `finally` has written `run_finished` and called `run_span.set_outcome` (`cli/context.py:270-290`), and the Run's `run_id` is no longer bound in the context variables. The built code puts the id on the exception instead: `_stamp_run_id` sets `RUN_ID_ATTR` (`cli/exit.py:113`; `cli/context.py:293-304`). The `unexpected_exception` record is emitted after `run_finished` and carries `run_id=getattr(exc, RUN_ID_ATTR, None)`, read from the original exception, as the CLI's `command_failed` does. A call that failed before any Run opened carries no `run_id`.

**Documented fields.** `BackupError`'s docstring and each re-exported class's docstring name its structured attributes. E006-S01-003's documentation check reads those docstrings, and the doc page lists them. These are the fields Epic 2's stories define, for example:

### Error and edge case handling

- **Database exceptions.** `l3io.wp.database` exceptions never cross the public boundary (AD-14). The adapters (Epic 2) wrap them first, for example `AuthenticationFailedError` → `CredentialsError` and `RefusedError` → `DatabaseRefusedError`. The boundary is the backstop, not the mechanism. The test therefore asserts both layers: an adapter-raised database error arrives as its mapped type, and a database error injected past the adapter arrives as `UnexpectedError` with `__cause__` set.
- **Each re-raise uses `raise ... from`.** `__cause__` is the original exception and `__suppress_context__` is `True`, so a host's traceback shows the chain explicitly rather than "During handling of …".
- **A `BackupError` subclass raised inside a joined context** (the Safety Snapshot's backup) propagates unchanged through both the inner and outer roots. Wrapping is idempotent: the boundary never wraps a `BackupError` in `UnexpectedError`.
- **An `ExceptionGroup`** (none is raised today; guarded for a future concurrency change) is an `Exception`. It is wrapped as `UnexpectedError`, and its members stay reachable through `__cause__`.
- **A gap found in another epic's class.** If the field check below finds a concrete exported class with no structured field, or the raise-site check finds an exported class nothing raises, the test fails, naming the class and its defining module. The fix belongs to the owning epic's story: add the field, wire the raise, or remove the class (FR-23). It is recorded there, and this story does not edit that module. *Assumption:* Epic 2's classes as specified all carry fields, so the gate is expected green at landing. A red result is the gate working, not this story failing. *(E006 arch gate, 2026-11-06, B2: the assumption is false for the built classes. They were walked at `e0902df`, and the message-only classes are listed under the acceptance criteria above. The owning epics are closed, so a red gate here would have no story to fix it, and this story could not close its own loop. The scope is set by the owner's decision (gate O-1).)*
- **`UnexpectedError` is reachable** through the boundary's single raise. That counts as its raise site for the check below.

### Observability requirements

- An `UnexpectedError` wrap emits exactly one ERROR record, `unexpected_exception`, with `cause_type`, `api_function` and `exc_info`, carrying the Run's `run_id`. It is emitted before `run_finished` when the wrap happens inside a Run, and the wrap is visible in the log stream as a defect marker.
- Wrapping a `BackupError` emits nothing extra. Epic 2's `run_finished` already carries `exit_code` from `type(exc).exit_code`, so the log and the exception agree on the code.
- A wrapped failure seen in a span (E006-S01-004) carries `error.type` set to the exported class's qualified name, not the dependency's.
- *(E006 arch gate, 2026-11-06, B3, B4: the two bullets above are corrected.)*
  - **Ordering.** `unexpected_exception` comes **after** `run_finished`, not before, and carries the `run_id` stamped on the exception (see The boundary).
  - **What the Run reported.** `run_finished.error` and the root span's `error.type` are written inside the Run by `open_run`, from the exception as it left the driver: `type(error).__name__` (`cli/context.py:275-290`). For a defect, that is the dependency's class name, for example `OSError`, because the boundary wraps later. That is a type name and never a value, the same information as `UnexpectedError.cause_type`. Making the Run report `UnexpectedError` would mean translating inside `open_run`, an Epic 2 module this story does not edit. So the log and the span name the original type, and only the exception the caller catches is `UnexpectedError`.

### Security considerations

- *(Adopted 2026-10-27 from the E002 gate.)* **Messages.** No exception message contains a credential (FR-23, AD-7 item 4, AG-14). `BackupError.__str__` does no redaction (ADR-0018). Every message is built from structured fields and never interpolates a credential or a dependency exception's text. That is the primary control, and a library caller who formats an exception gets the text exactly as built. `UnexpectedError`'s message never contains the wrapped exception's text, and its `cause_type` is a type name, not a value.
- **The whole surface is tested.** The test asserts on the full surface a host might log: `str(exc)`, `repr(exc)`, every structured attribute's `repr`, and `"".join(traceback.format_exception(exc))`, which includes the `__cause__` chain. The sentinel is planted as the database password, the admin password and the passphrase.
- **Wrapped exceptions are not scrubbed.** The boundary does not redact the wrapped dependency's own text in `__cause__`. Database's contract keeps its messages credential-free, and the traceback assertion above is what proves it. If it ever fails, the defect is raised against `l3io-wordpress-database`, not hidden here.
- **No redaction at this boundary, and no second redaction path.** Under ADR-0018 redaction runs where text leaves the program: `cli/exit.py::render_failure`, `redact_event`, and E006-S01-004's span attributes. An exception raised to a library caller is not one of those places, so `public_boundary` redacts nothing. It also defines no function whose name contains `redact`, and E002-S01-006's contract test enforces that.
