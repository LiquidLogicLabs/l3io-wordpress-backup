# E006-S01-004: See spans in a pipeline that already has tracing


**Implements:** FR-30


As a DevOps engineer whose application already runs an OpenTelemetry SDK,
I want this library's work to appear as spans,
So that I see it in the trace I already collect.

**Acceptance Criteria:**

**Given** a host application with a configured SDK
**When** a run executes
**Then** spans appear — one root per Run, one child per phase, never one per file
**And** with no SDK configured the instrumentation is a no-op: no output, no error, no measurable cost
**And** a base install depends on `opentelemetry-api` only; the SDK and exporter are an optional extra
**And** `process.command_args` is recorded only after the same redaction the logs use — one implementation, not two
**And** log records carry flat `trace_id` and `span_id` fields when, and only when, a span is recording
**And** phase fields are emitted as logs whether or not tracing is configured — tracing is never the only way to see what a run did

*(E006 arch gate, 2026-11-06, against the built code at `e0902df`; see `epic-006/arch/reviewer-l3io-arch-review-2026-11-06.md`.)*
- *"one child per phase"* (D6). Phases nest in the built code. `ENCRYPT` runs inside `WRITE_ARCHIVE` (`adapters/tar.py:448-455`, called from inside `:565-569`), and a Safety Snapshot's backup phases run inside the restore's `SNAPSHOT` phase. So there is one span per `phase_completed` record, each the child of the phase span or root span that encloses it. There is never a span per file.
- *"`process.command_args` is recorded only after the same redaction"* (D7). No v1 root passes `command_args`: `api/` passes `None`, and the CLI binds the no-op tracer. The criterion is therefore proved on the adapter directly, by calling `run_span(command_args=...)`, not through a root.

## Business acceptance criteria

### Outcome

A host application that already runs an OpenTelemetry SDK calls `l3io.wp.backup.api.backup(...)` or `restore(...)` inside one of its own spans, and sees the Run in its existing trace:

- one `l3io.wp.backup.run` span, a child of the host's current span;
- under it, one child span per phase the plan executes: the AD-17 `RestorePhase` members for a restore, and the backup plan's steps for a backup;
- under those, the spans `l3io-wordpress-database` already emits for `dump`, `load`, `ensure` and similar calls, nested by context propagation rather than duplicated;
- no span per file.

The host configures nothing in this package. A process with no SDK sees no output, no error and no cost, and every phase still logs `phase`, `duration_ms`, `exit_code` and `bytes`. When a span is recording, every log record of the Run carries flat `trace_id` and `span_id`. Any command line placed on a span has been through `adapters/redaction.py`, the same single implementation the logs use.

A reviewer can check this by running the API under an in-memory SDK exporter and reading the span tree, then running it again with no SDK and finding no span and an unchanged log stream except for the absent ids.

### Non-goals

- **Configuring an SDK, a tracer provider, a sampler or an exporter**, from the library or from the CLI. The `otel` extra makes them installable for a host. Nothing in this package imports `opentelemetry.sdk`.
- **The OpenTelemetry logs signal.** It is excluded by AD-10. Logs stay structlog, and the only coupling is the `trace_id`/`span_id` processor.
- **`TRACEPARENT` propagation into subprocesses.** It is deliberately skipped (AD-24), and this package starts no MySQL subprocess anyway (ADR-0015).
- **Spans for `l3io-wp-config`.** AD-24 as amended binds backup and database only. The config write is seen as the time inside the `REWRITE_CONFIG` (or `LOAD_DUMP` cutover) phase span; no span is opened around a config call by itself.
- **Metrics.**
- **Re-instrumenting database operations.** `l3io.wp.database` emits its own `l3io.wp.database.<operation>` spans. This package opens no span around a single database call.
- **The per-phase log fields themselves.** `adapters/phase.py::phase()` emits them, and it is Epic 2's (E002-S01-004). This story asserts they are present with and without tracing; it does not produce them.

### Error and edge case handling

- **No SDK installed or configured.** The global provider is `ProxyTracerProvider`, spans are `NonRecordingSpan`, `add_trace_ids` adds nothing, and no attribute is computed. There is no warning and no output.
- **An SDK whose sampler drops the Run.** The span is non-recording, so behaviour is the same as with no SDK: no ids in the logs. The rule is `is_recording()`, not "a valid span context exists".
- **The host installs a provider after this package was imported.** It is honoured, because the tracer is resolved at call time.
- **A failure inside a phase.** That phase's span and the root span both end with `ERROR`, `error.type` and `process.exit.code` equal to `type(exc).exit_code`. *(E006 arch gate, 2026-11-06, D1/B4: the root span's `error.type` and code come from `set_outcome` (`cli/context.py:290`). The phase span's code comes from `PhaseSpan.set_outcome` (`adapters/phase.py:123`), whose port carries no error type. So the phase span's `error.type` and status are set by the adapter's context manager from the exception it sees on exit, as `type(exc).__name__`. That is the same spelling as the root's, and the description is passed through `secrets.redact`.)* Every span opened is ended, in `finally`, including on `KeyboardInterrupt`, `SystemExit` and the CLI's `RunTerminated` on SIGTERM.
- **An exception from the tracing API itself** (a misbehaving host SDK) is not allowed to fail the Run. Span start and attribute calls inside `adapters/tracing.py` are wrapped so that an `Exception` from OpenTelemetry is logged once at WARNING as `tracing_error`, with the exception's type name only, and the Run proceeds. The OpenTelemetry API already guarantees the no-SDK path cannot raise. This covers third-party SDKs. *(E006 arch gate, 2026-11-06, D3: superseded. The built `GuardedTracer` does this for every tracer `open_run` binds, and logs `tracer_failed` (`adapters/noop.py:27-31, :174-197`). A second wrapper here would give one failure two records under two names.)*
- **A Safety Snapshot or other joined entry point.** It opens no second root. Its phases are children of the outer Run's current phase span.
- **Concurrent Runs in threads or asyncio tasks.** Each has its own current span through `contextvars`, which is OpenTelemetry's context mechanism. Records from one Run never carry another's ids.
- **A Run with many files.** The span count is independent of file count. There is no per-file or per-member span.

### Security considerations

- **A span attribute is as public as a log line (AD-24).** ADR-0018 names this adapter as one of the three places redaction runs, with CLI rendering and `redact_event`. `process.command_args` is set only from `redact_argv`, and every free-text attribute, the status description included, goes through the Run's `SecretRegistry.redact`. *(Adopted 2026-10-27 from the E002 gate.)* Both are the one implementation in `adapters/redaction.py` (FR-30, AG-14). No exception event or stack trace is recorded on a span (`record_exception=False`), so chained dependency text cannot leak into a trace backend that lacks the log pipeline's `redact_event`.
- **Test with a planted secret.** With the `credential_sentinel` fixture planted as the database password, the admin password and the passphrase, and the host process's argv (the API path's `command_args`) carrying the sentinel after `--admin-password`, the sentinel appears in no exported span: not in its name, its attributes, its events or its status description.
- **No secret in the context headers.** The library sets no baggage and propagates no context outward, so no secret can travel in `baggage`/`traceparent` headers.

### Testability approach

Adapter tests follow E002's `tests/adapters/test_<module>.py` naming, and contract checks go under `tests/contracts/`. The SDK is available in tests through the `dev` group (`opentelemetry-sdk`, already present). Tests use the SDK's own `InMemorySpanExporter` with a `SimpleSpanProcessor`, not a hand-written recorder.

A session fixture installs one `TracerProvider` globally, because OpenTelemetry allows the global provider to be set only once per process, and clears the exporter between tests. The no-SDK cases run in a subprocess with a fresh interpreter, so the global provider there is genuinely the proxy.

- **`tests/adapters/test_tracing.py`**
  - A backup and a restore with Epic 2 and 3 doubles under the in-memory exporter, parametrised over every `RestoreMode`, with scope from the enum.
  - Exactly one span named `l3io.wp.backup.run`, whose parent is the test's host span.
  - Its children's `wpbackup2.phase` values equal `plan.phases` (or the backup plan's steps) in order, one each. The scope comes from the plan the run built, not from a list.
  - The count of `l3io.wp.backup.*` spans is the same for a Site Root of 1 file and of 500 files.
  - A Safety Snapshot run produces no second root.
  - A failing phase yields `ERROR`, `error.type` and `process.exit.code` equal to the exception's `exit_code`, and no exception events.
- **`tests/adapters/test_tracing_database_nesting.py`.** With database's real `_observe` (the `database` extra is installed in CI) and a database double below it, `l3io.wp.database.dump` is a child of the `DUMP` phase span. No `l3io.wp.backup.*` span wraps a single database call.
- **`tests/adapters/test_trace_ids_processor.py`**
  - Inside a recording span, records carry `trace_id` (32 lowercase hex) and `span_id` (16) that equal the current span's.
  - Inside a non-recording span, from an `ALWAYS_OFF` sampler, and outside any span, the keys are absent, which is asserted as `"trace_id" not in event`.
  - Values are flat strings, not a nested dict.
- **`tests/contracts/test_tracing_no_sdk.py`** (subprocess, no provider set)
  - A full API backup with doubles.
  - `trace.get_tracer_provider()` is a `ProxyTracerProvider`.
  - Nothing is written to stdout or stderr beyond the configured log records.
  - No record carries `trace_id`.
  - A spy on the Run registry's `redact_argv` records zero calls from `adapters/tracing.py`, so no attribute work is done on a non-recording span. That is the deterministic form of "no measurable cost"; no timing assertion is used.
  - The `phase_completed` records equal those from the SDK run except for the id fields.
- **`tests/contracts/test_tracing_redaction.py`.** The sentinel check over every exported span, run under `@pytest.mark.integration` on the API path with `sys.argv` monkeypatched to carry the sentinel, and asserting that no exported span has a `process.command_args` attribute and that the sentinel appears in no span attribute or event (corrected 2026-10-28). On the CLI path it asserts that no `l3io.wp.backup.*` span is exported at all (the no-op tracer).
- **`tests/contracts/test_otel_dependencies.py`**
  - Reads `pyproject.toml` with `tomllib` and asserts three things:
    - `opentelemetry-api` is in `dependencies`;
    - no entry in `dependencies` starts with `opentelemetry-sdk` or `opentelemetry-exporter`;
    - no requirement anywhere in `dependencies` or `optional-dependencies` names `opentelemetry-exporter-otlp` exactly, or `grpcio`.
  - The requirements are parsed with `packaging.requirements.Requirement`, already in the `test` group. Prefix string matching is not used, because the allowed `opentelemetry-exporter-otlp-json-file` shares the forbidden prefix.
  - An AST scan of `src/l3io/wp/backup/` finds no import of `opentelemetry.sdk` or `opentelemetry.exporter`.
  - Planted cases for both: a temp `pyproject.toml` with the umbrella exporter, and a temp module importing the SDK, must each fail.
- **The existing `make verify-install`** already asserts that the built wheel's base install finds no `opentelemetry.sdk`. It stays as is and is cited as the installed-tree half of the base-install check.
- *(E006 arch gate, 2026-11-06: corrections to the tests above.)*
  - **D6, `test_tracing.py`.** "Its children's `wpbackup2.phase` values equal `plan.phases` … one each" is red on arrival for an encrypted backup, because `ENCRYPT` is a child of `WRITE_ARCHIVE`. The assertion instead compares the phase spans with the Run's own `phase_completed` records, captured in the same test, which come from the same `phase()` call (`adapters/phase.py:102-123`):
    - the multiset of the `l3io.wp.backup.<phase>` spans' `wpbackup2.phase` equals the multiset of those records' `phase`;
    - every phase span descends from the one root;
    - the root's direct children, in start order, equal the restore plan's `phases`.
    - A planted case that drops one span from the comparison must fail.
  - **D3, guarded failure.** An SDK double whose `start_as_current_span` raises leaves the Run's outcome unchanged. It gives exactly one `tracer_failed` record, from `GuardedTracer`, and no `tracing_error`.
  - **D7, no cost.** On the API path `command_args` is `None` (E006-S01-001), so the zero-call spy above checks nothing, and a test over it passes vacuously. Two adapter-level tests replace it:
    - under a non-recording span (no provider, and `ALWAYS_OFF`), `run_span(..., command_args=["--admin-password", sentinel])` followed by `set_attributes(db_name=...)` calls neither `secrets.redact` nor `secrets.redact_argv`, by a spy;
    - under a recording span, the same calls set `process.command_args` equal to `secrets.redact_argv(command_args)`, so the sentinel is absent from it, and set `process.executable.name` to `"wpbackup2"`. This is the acceptance criterion's evidence. A planted adapter that sets the raw argv must fail.
  - **D1, the AD-4 gate.** The existing `tests/contracts/test_no_dry_run_outside_roots.py` already walks `adapters/tracing.py` once it exists. No new test is needed, and the module must pass it.

### Existing-library check

- **`opentelemetry-api`** (1.44.0 in the lock; `>=1.40,<2` declared). It provides everything used: `trace.get_tracer`, `start_as_current_span`, `get_current_span`, `Span.is_recording`, `format_trace_id`/`format_span_id`, `Status`/`StatusCode`, and the no-op `ProxyTracer`/`NonRecordingSpan` path. No shim is written (ADR-0011's reason for making it a hard dependency).
- **Semantic-convention attribute names** are string literals. `opentelemetry-semantic-conventions` would be a second runtime dependency for constants, and AD-24 limits the base install to the API.
- **The trace-id processor** is the one piece written here. structlog 26.1 ships no OpenTelemetry processor (its `add_open_telemetry_spans` is a documentation example that nests the ids). AD-24 records the reason for a flat-field variant: about ten lines, owned by this story.
- **Tests** use `opentelemetry-sdk`'s `InMemorySpanExporter`, `SimpleSpanProcessor` and `ALWAYS_OFF` sampler, all in the `dev` group.
- **Redaction** reuses `adapters/redaction.py` (E002-S01-006).
