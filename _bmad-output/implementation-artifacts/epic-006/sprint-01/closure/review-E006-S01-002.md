The fields check enforces this on its own: a future direct `RefusedError(msg)` would bring `RefusedError` into scope and fail it. The one message change is minor (see F-08).
2. **`UsageError(message, *, arguments: tuple[str, ...])`, required.** Accepted. Because the keyword is required, `mypy --strict` proves every raise site passes it. The content of the field is uneven (see F-05).

4. **`PassphraseRejectedError(scheme=...)`; `DumpFailedError`/`LoadFailedError` gain `database` and `exit_status`; `MalformedManifestError` gains `field`.** `database`, `exit_status` and `field` are accepted. `scheme` is a constant that tells the caller nothing (see F-06).
5. **`test_api_one_sequence` allows `BackupError` imports from `core.restore`; `test_api_parity` allows `UnexpectedError`.** Accepted. The relaxation resolves the imported name and allows it only when it is a `BackupError` subclass. The planted case still reports `build_restore_plan`. The parity exemption is one identity-checked class.

## Findings

### F-01 — medium — kind: claim
**Location:** `src/l3io/wp/backup/adapters/database.py:440`, `:1132`, `:1174`; `src/l3io/wp/backup/core/restore.py:212`; `src/l3io/wp/backup/adapters/tar.py:266`, `:594`; `src/l3io/wp/backup/core/exclusions.py:88`

**Problem:** The story's Security considerations say: *"Every message is built from structured fields and never interpolates a credential or a dependency exception's text. That is the primary control."* The built code breaks this at seven sites, all reachable through the API:
- `InvalidSiteDescriptorError(str(exc))` forwards `wpdb.InvalidArgumentsError` and `wpdb.InvalidIdentifierError` text at three sites. The same module's `_tls_settings` comments the opposite rule for the same dependency class: "ADV-S02-11: a fixed text; database's message is never forwarded".
- `SnapshotFailedError` builds its reason as `f"{type(cause).__name__}: {cause}"`.
- `ArchiveWriteError` interpolates `{exc}` from a host-supplied `ExclusionPolicy.decide`, and `str(exc)` of `tarfile.TarError`.
- `InvalidExclusionPatternError` forwards the pathspec error text.

None of these is a known credential leak today. The point is that the story states the primary control as absolute, and nothing enforces it. `test_no_credential_in_errors.py` drives none of these paths, so global rule 3 applies: the prose overstates its coverage.

**Fix:** Either correct the claim in the story to name these sites as known exceptions, with their owning stories, or replace the interpolation with the type name or a fixed text, as `_tls_settings` and `DumpFailedError` already do. Also add a mechanical check: an `ast` walk under `src/` that flags `str(<except-bound name>)`, or an f-string interpolating it, inside an `except` clause whose body raises a `BackupError`. Give that check a planted violation.

### F-02 — medium — kind: claim (false green in guard scope)
**Location:** `tests/exception_scope.py:67` (`is_private`), `tests/contracts/test_api_exception_exports.py:51`, `:129`; `src/l3io/wp/backup/api/errors.py:248`

**Problem:** The AC says a failure *"raises a documented exception type exported from this package"*. The export check drops every private class (a leading `_` or `<locals>`) from scope. The replacement guard only proves that the class's *name* is not written in another module. A private `BackupError` subclass raised inside a module-level function and not caught there still leaves through the public functions of that same module. `public_boundary` then passes it through untouched, because it is a `BackupError`. The caller receives a type that is not exported or documented, and every guard is green.

Today `_ProbeFailedError` is caught at `preflight.py:312`, so there is no defect now. The guard, however, does not prove the rule's reach (global rule 4).

**Fix:** Make private failure classes not `BackupError`: `class _ProbeFailedError(Exception)`. Then, if one ever escapes, the boundary wraps it as `UnexpectedError` and logs it, which is the safe default. Add a contract that no private class subclasses `BackupError`, derived from the same walk, with a planted case. Once no private `BackupError` subclass can exist, the name-only leak guard can go.

### F-03 — medium — kind: testability
**Location:** `tests/unit/api/test_no_credential_in_errors.py:178-201`

**Problem:** This test is the only place the administrator-password sentinel is planted. It replaces `operations.drive_restore` with a double that raises `OSError`, so no code that handles `admin=` ever runs. What it proves is narrower: `public_boundary` does not interpolate call arguments into `UnexpectedError`. That is already structurally obvious, because the message contains only `cause_type` and `api_function`. The story requires *"The sentinel is planted as the database password, the admin password and the passphrase"* for each failure mode reachable through the API. The admin password is never put through a real failure. Examples would be provisioning with `admin=` rejected (`CredentialsError` from the admin path), `ExistingDatabaseUserError`, or `ProvisioningFailedError`.

**Fix:** Drive at least one admin-credential failure with the real `WpDatabase` adapter and the `wpdb` double raising, as the `MODES` table does for `check_dump`. For example, monkeypatch the provisioning call to raise `wpdb.AuthenticationFailedError`, with `admin=ExplicitCredentialSpec(password=sentinel.admin_password)`. Then assert the mapped type and zero leaks on the four surfaces.

### F-04 — low — kind: testability
**Location:** `tests/unit/api/test_no_credential_in_errors.py:161`

**Problem:** The "verification failed" mode accepts `VerificationFailedError | api.ArchiveReadError`. Flipping a byte in the middle of a gzip stream will usually fail decompression first and raise `ArchiveReadError`, so the `VerificationFailedError` surfaces may never be exercised. Those surfaces carry `result.failures[].member`, which is the field most likely to carry Site data. I did not run a probe to confirm which type arrives, because the review was read-only.

**Fix:** Build the damaged case so that it deterministically yields `VerificationFailedError`, for example by corrupting a member's content after the gzip layer or by using an existing helper that alters a member's checksum. Assert that exact type.

### F-05 — low — kind: interface contract
**Location:** `src/l3io/wp/backup/domain/errors.py:129` (docstring), `src/l3io/wp/backup/core/exclusions.py:66`, `src/l3io/wp/backup/adapters/database.py:238-258`, `src/l3io/wp/backup/cli/backup.py:373, :403, :407, :468`

**Problem:** `UsageError.arguments` is documented as *"names the flags or parameters at fault, spelled as the message spells them"*. In practice, what it holds depends on the layer that raised the error, not on the surface the caller used:
- `InvalidExclusionPatternError` reports `("--exclude",)`. Its message does not name that flag, and a library caller passed `exclusion=`.
- The `_tls_settings` refusals report `--admin-tls` to an API caller who passed `admin_tls=AdminTls(...)`.
- The internal plan-invariant checks report `("plan",)`, `("plan", "cipher")` and `("plan", "database")`. These name no argument any caller supplied, and they are defects, not usage errors.

A host that branches on `exc.arguments` cannot rely on one vocabulary.

**Fix:** Do one of two things:
- Make the docstring state the actual contract: CLI spelling where a flag exists, the Python parameter name otherwise, and `()` for an internal invariant.
- Pass `arguments=()` at the four plan-invariant sites, as `FlagCombinationRejectedError` does, and use the docstring's own rule ("empty only where no single argument is at fault") consistently.

### F-06 — low — kind: interface contract
**Location:** `src/l3io/wp/backup/adapters/crypto.py:55`, `:202`; `src/l3io/wp/backup/domain/errors.py` (`PassphraseRejectedError.__init__`)

**Problem:** O-1 asks for fields *"carrying what its message states"*. The message is "the passphrase cannot decrypt this archive". The new field `scheme` is the module constant `"age"` at the only raise site, so it carries nothing a caller can branch on. It exists to satisfy the fields guard, which checks that a field exists, not whether it means anything. The message names "this archive", so the archive is the field the message actually states.

**Fix:** Prefer the identity of the archive (or payload) that failed authentication, if the raise site can obtain it. The restore runner and verify both hold it, so they could re-raise with it attached. Otherwise, record in the docstring that `scheme` is the only field available at the cipher layer and why.

### F-07 — low — kind: testability (guard reach)
**Location:** `tests/contracts/test_api_exception_exports.py:47-63`

**Problem:** `_difference` matches defined classes to exports by `__name__`. If two package modules defined a public `BackupError` subclass with the same name and only one were exported, `missing` would not report the other, because the name is present. `not_identical` would not report it either, because the exported object is in `public`. No duplicate exists today; I verified this by walking the package.

**Fix:** Compare by identity: `missing = public - set(exported.values())`. Also add a planted same-named class in a second module.

### F-09 — low — kind: testability (guard reach)
**Location:** `tests/unit/api/test_boundary.py` (`test_every_entry_point_in_all_is_wrapped`)

**Problem:** The test treats "is wrapped" as `hasattr(fn, "__wrapped__")`, as the story specified. Any `functools.wraps` decorator would satisfy it, for example a future tracing decorator, with no `public_boundary` present. Only `backup`, `verify` and `restore` are proven behaviourally, by the parametrised run-id test. An entry point added later would be covered only by the attribute check.

**Fix:** Have `public_boundary` mark its wrapper, for example `wrapper.__l3io_public_boundary__ = True` or a module-level `WeakSet`. Assert that marker over the derived entry-point set, and keep the planted unwrapped case.
