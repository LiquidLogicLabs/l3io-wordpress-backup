## Findings

### M1 — MEDIUM — kind: claim — An implicit namespace directory between two regular packages passes the "regular package" walk

`tests/contracts/test_namespace_layout.py:51` (`implicit_namespace_directories`); planted case at `:144`.

**What is wrong.** The walk only examines directories that directly hold a `.py` file. A directory that holds only subpackages and has no `__init__.py` is an implicit namespace package, and the walk never visits it. Probe on the real file list plus `api/ns/inner/__init__.py` and `api/ns/inner/m.py`: `implicit_namespace_directories(...) == []`. The check passes, and `api/ns` is a PEP 420 namespace portion inside the distribution. `test_every_module_is_classified` classifies `l3io.wp.backup.api.ns.inner.m` as `api-implementation`, so nothing else catches it either.

**Why it matters.** The story's business AC says "every directory below `l3io/wp/backup/` is a regular package". The technical AC gives the reason: "There is no implicit namespace package below the distribution root, so `mypy --strict`'s module resolution and the wheel's file list agree." The guard proves its rule against directories that hold `.py` files, but its scope misses exactly the shape that defeats the invariant (global rule 4). The planted case only attacks the rule (a leaf directory without a marker), not the scope.

**Fix.** Add every ancestor of each `.py` file, up to and excluding `root`, to `directories`:

```python
directories = {p for n in under for p in n.parents if p.is_relative_to(root)}
```

Then require `d / "__init__.py"` for each. Add the planted case above (`api/ns/inner/{__init__,m}.py` must report `.../api/ns`) for both the source list and a wheel-name list.

### M2 — MEDIUM — kind: claim — The environment table leaves out variables the library reads from the host

`docs/api.md:57-69`.

**What is wrong.** The page says "A library call may read these variables from the host's environment". It then lists only `L3IO_WP_BACKUP_*` names, plus prose for `AWS_*`, the siblings and OTel. The package itself also reads:

- **`PATH`**: tool lookup in `adapters/preflight.py:242,256`, and it is passed to every `wp`/probe child at `adapters/wpcli.py:197` and `adapters/preflight.py:175`. Every restore that runs WP-CLI and every preflight depends on it.
- **`HOME`**: passed to the `wp` child and the probes (`adapters/wpcli.py:198`, `adapters/preflight.py:176`). WP-CLI uses it for its cache and package directory.
- **`TMPDIR`/`TEMP`/`TMP`**: `tempfile.mkdtemp(dir=None)` in `adapters/workspace.py:50` decides where the Run workspace goes, and the Dump lives there.

`test_every_environment_variable_the_source_names_is_listed` covers only the `L3IO_WP_BACKUP_*` regex (its docstring says so accurately). The page's sentence, however, claims completeness.

**Why it matters.** The story (arch gate, A8) assigns this list to the page: "It lists the variables a library call may read from the host's environment." A host that runs the library in a scrubbed environment, such as a systemd unit or a container with `env -i`, gets a different `wp` binary, a different WP-CLI home, or a workspace on a different filesystem. The page does not tell it so. `TMPDIR` also decides where an unencrypted Dump sits on disk.

**Fix.** Add a row for `PATH` (locating `wp`, `mysql`, `mysqldump`/`mariadb-dump`; only absolute entries are used), `HOME` (passed to WP-CLI) and `TMPDIR`/`TEMP`/`TMP` (the Run workspace, holding the Dump, when no parent is given). Alternatively, reword the sentence to "the package's own variables are…" and state that the standard process variables apply. Whichever wording is kept, the test docstring already states the mechanical scope correctly.

### M3 — MEDIUM — The Logging preface omits the case most library callers hit: logging left unconfigured

`docs/api.md:42-50`.

**What is wrong.** The preface covers two hosts: one that calls `configure_logging`, and one that "configures logging itself". It says nothing about a host that does neither. In that case structlog's built-in defaults apply. Checked in `.venv`: `logger_factory` is `PrintLoggerFactory`, which writes to **stdout**, the last processor is `ConsoleRenderer`, and there is no level filter. Every package record, including DEBUG records such as `credential_chain_built` and `workspace_created`, is printed to the host's stdout, with no `redact_event`.

**Why it matters.** This is the default path for anyone who runs `from l3io.wp.backup.api import backup; backup(...)`. A host that uses stdout as a data channel (JSON output, a pipe) has it corrupted. The redaction guarantee the page discusses is also absent there, which the page does not say. The story assigns the ADR-0018 logging statement to this preface. As written, it reads as if the only no-redaction case is a host-configured chain.

**Fix.** Add one sentence: "A host that configures nothing gets structlog's defaults: every record, at every level, printed to stdout without redaction. Call `configure_logging` or configure structlog before the first call."

### M4 — MEDIUM — kind: existing-library — The `cli` → `api` ban is a hand-rolled import resolver where import-linter already does this

`tests/contracts/test_public_surface.py:137-166` (`_imports_of`, `cli_imports_of_api`).

**What is wrong.** The check re-implements module resolution: absolute imports, `from X import Y` submodule expansion, and relative-level arithmetic. That is the job of import-linter/grimp, which the project already runs in CI (`lint-imports`) and already configures with two `forbidden` contracts (`pyproject.toml:354-386`). A contract does the same job, with grimp's maintained resolution, at no new dependency:

```toml
[[tool.importlinter.contracts]]
name = "FR-24 — cli never imports api"
type = "forbidden"
source_modules = ["l3io.wp.backup.cli"]
forbidden_modules = ["l3io.wp.backup.api"]
```

The story mandated "an AST check", and `pyproject.toml` was "consumed, not edited", so the developer followed the spec. The story's existing-library section, however, lists `ast` as the tool and never weighs import-linter, so the decision was never recorded (global rule 1).

**Why it matters.** It is about 30 lines of untested-by-library resolution logic that must track Python's import semantics. Its planted cases are good, but it is a second, divergent source of truth beside the import graph the contracts already build. Neither approach catches `importlib.import_module("l3io.wp.backup.api")`. Today the AST check also catches imports under `if TYPE_CHECKING:`, which grimp does too.

**Fix.** Preferred: amend the story's scope to allow the `pyproject.toml` edit, add the `forbidden` contract, and replace the AST check with a test that reads the contract with `tomllib` (as `layers_from` does) and asserts that it exists with that source and target. Keep one planted case, `lint-imports` over a tmp copy, or drop it with the reason that import-linter is the library's tested behaviour. If the AST check stays, record the decision in the story's existing-library section with the reason import-linter was rejected.

### L1 — LOW — `own_docstring` finds the class by bare name; a qualname-keyed helper already exists

`tests/contracts/test_public_surface.py:121-133` (lookup at `:130`).

**What is wrong.** `ast.walk` returns the first `ClassDef` whose `name == obj.__name__`. A module holding a nested or `TYPE_CHECKING` class of the same name, or a class built under one name and re-bound, can make the check read another class's docstring. The result is a false green for an undocumented public class. No public class is affected today (probed on 3.11 and 3.14). `tests/contracts/test_repr_clean.py:99-114` (`_module_classes`) already keys every `ClassDef` by `__qualname__`, and this module already imports from that file.

**Fix.** `node = _module_classes(obj.__module__).get(obj.__qualname__)`, and fail if it is `None`. Alternatively, export a small public helper from `test_repr_clean.py` rather than importing the underscore name.

### L2 — LOW — kind: claim — "What the Run reports" is unconditional, but holds only when the failure happens inside an opened Run

`docs/api.md:71-75`.

**What is wrong.** The page says that when a non-package exception escapes, "the Run's `run_finished.error` record and its span's `error.type` still name the original exception's type". Two cases break that:

- **Before the Run opens, there is no `run_finished` at all.** Examples: a host `prompt` callable raising inside `require_passphrase` (`api/operations.py:155`), `Path(site)` with a wrong type, or `_target()` (`:168`). All of them run before the driver opens the Run.
- **With `context=`, the joined call writes no `run_finished` of its own.** The exception reaches the outer Run's `open_run` only after `public_boundary` has turned it into `UnexpectedError`, so the outer record names `UnexpectedError`.

**Fix.** Qualify the claim: "When the exception escapes an opened Run, …; a failure before the Run opens writes no `run_finished` (only `unexpected_exception`), and a joined call's outer Run records `UnexpectedError`."

### L3 — LOW — The coexistence extension has no planted case of its own

`tests/contracts/test_namespace_coexistence.py:118-128`. The existing teeth test is at `:131`.

### L4 — LOW — kind: claim — Docstrings say more than the checks cover

- **The "each has a docstring" claim.** `src/l3io/wp/backup/api/__init__.py:25` says "each has a docstring and a heading". The story's business outcome says the same. That cannot be true of `__version__` (a `str`) or `CredentialSpec` (a union alias). `test_every_public_class_and_callable_has_a_docstring` (`test_public_surface.py:288-294`) skips non-callables silently. The skip is reasonable, but the prose overstates it.
- **The "Not checked" list.** `tests/contracts/test_api_docs.py:17-18` lists what is not checked, but it omits that the `Returns:`/`Raises:` lines the story requires for callables are not checked either. Only parameter, member and protocol-method mentions are.

**Fix.**
- In `api/__init__.py`: "each class and callable has a docstring; each name has a heading in `docs/api.md`".
- In `test_api_docs.py`'s "Not checked" sentence, add: "nor that a callable's section states its return and the exceptions raised".

### L5 — LOW — Public signatures depend on names that are not public

`docs/api.md:274-285` (`ExclusionSet`), `:229-248`, `:344-391`, `:431-444`.

**What is wrong.** The documented constructors and fields reference types that are not in `__all__`: `ExclusionSource`, `Integrity`, `BackupPlan`, `VerificationFailure`, `RestorePhase`, `DatabaseRestoreReport`; for `RunContext`, also `SecretRegistry`, `Tracer`, `RunSpan`, `Clock` and `LockHandle`. By the page's own rule, a caller can only reach them through internal modules.

The practical ways to build an `ExclusionSet` (`ExclusionSet.default()`, `.none()`, `.from_patterns(...)`) and `OverrideSet.none()` are not mentioned. `RunContext`'s constructor is documented as if callable, while the preface says v0 offers no public way to open a Run.

StrEnum coercion means strings work for `ExclusionSource` and `Integrity`, so callers are not blocked. The surface is still under-specified at exactly the point the story makes enumerable.

**Fix.**
- Document the classmethod factories under `ExclusionSet` and `OverrideSet`.
- Note under `RunContext` that it is obtained only from an enclosing Run and is not to be constructed.
- State that the field types of returned values are not part of the import contract (string values of the StrEnums are), or export the ones a caller compares against (`Integrity`). Record the choice; deciding it may be out of scope for this story.
