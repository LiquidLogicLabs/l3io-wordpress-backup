## Findings

### R-001: low, kind: test-coverage

- **Location:** `tests/adapters/test_tracing.py:565-569`
  (`test_a_provider_installed_after_import_is_honoured`)
- **Description:** The test is named for the edge case "a provider the host
  installs after import is honoured", but it installs no provider. It only
  asserts that no module attribute is a `trace.Tracer` instance. A
  regression that cached the tracer another way would pass, for example
  `functools.cache` on `_tracer`, or a cached `TracerProvider`.
  The behaviour itself is exercised implicitly, because `adapters/tracing` is
  imported at collection, before `otel_spans` calls `install()`. Nothing
  states that dependency, though. In the subprocess case, `CHILD` sets the
  provider *before* importing the package.
- **Suggested fix:** In the subprocess `CHILD` (`tests/contracts/test_tracing_no_sdk.py`),
  for the `sdk` mode, import `l3io.wp.backup.api` and `adapters.tracing`
  first, then call `trace.set_tracer_provider(...)`, and assert that
  `redact_argv` was called (it already is). Alternatively, rename the
  in-process test so it claims only "no module-level tracer object".

### R-002: low, kind: test-coverage

- **Location:** `tests/contracts/test_tracing_no_sdk.py:181-195` (`test_the_phase_records_differ_only_by_the_ids`)
- **Description:** The story says the `phase_completed` records "equal those
  from the SDK run except for the id fields". The test compares the key sets,
  but compares values only for `phase`, `outcome` and `exit_code`. Values of
  `bytes` and of any extra per-phase fields are never compared, so a
  tracing-dependent change to a logged byte count or extra field would pass.
  `duration_ms` is legitimately volatile.
- **Suggested fix:** Compare every key except `trace_id`, `span_id`,
  `duration_ms` and any other demonstrably volatile key (named, with the
  reason), e.g.
  `[{k: v for k, v in r.items() if k not in VOLATILE} for r in plain] == [... traced]`.

### R-003: low, kind: test-coverage

- **Location:** `tests/adapters/test_trace_ids_processor.py` / `tests/adapters/test_tracing.py` (absent case)
- **Description:** The story's edge-case list says "Concurrent Runs in
  threads or asyncio tasks … Records from one Run never carry another's
  ids". No test drives two Runs or two spans concurrently, so this rests
  on OTel's `contextvars` mechanism without evidence in this suite. The
  Testability section does not list the case explicitly, which is why this
  is low.
- **Suggested fix:** Add one test that opens two host spans in two threads
  (or two `asyncio` tasks) and calls `add_trace_ids` in each. Assert that each
  record's ids equal its own span's.

### R-004: low, kind: claim

- **Location:** `src/l3io/wp/backup/api/operations.py:30-34` (module docstring, "Tracing (AD-24)")
- **Description:** The docstring says the tracer gives "one root span per Run
  with one child per phase". The E006 arch gate correction D6 states that
  phases nest: `ENCRYPT` sits inside `WRITE_ARCHIVE`, and a Safety
  Snapshot's backup steps sit inside `SNAPSHOT`. The correct statement is
  one span per `phase_completed` record, each the child of the span that
  encloses it. `adapters/tracing.py`'s own docstring states this correctly.
- **Suggested fix:** Reword to "one root span per Run and one span per
  phase record, nested in the span that encloses it".
