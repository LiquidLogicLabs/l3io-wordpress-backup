## Findings

### F-1 — MEDIUM — kind: claim (Observability) / reused-before-written
- **Location:** `src/l3io/wp/backup/api/operations.py:132-140`
- **Trigger:** `L3IO_WP_BACKUP_PASSPHRASE` is set in the host environment, and the caller runs `api.backup(site, scope=...)` without `encrypt=True`.
- **Claim contradicted:** "An API-opened Run emits the same records as the CLI-opened Run of the same operation". Deviation 3 also gives the rationale "an Archive is never written plain by omission".
- **What happens:** The CLI root's `cli/backup.py::_cipher` calls `cli/passphrase.py::note_unused_passphrase(environ)` (`cli/backup.py:661-671`). That call emits the `passphrase_ignored` WARNING ("encryption was not requested, so the Archive is unencrypted"). The API root never calls it. So in the case that most needs the warning, the library writes a plaintext Archive with no record at all. An explicit `passphrase=` is refused, but the same intent expressed through the environment variable is silently dropped. The A9 record-equality test cannot catch this because the autouse fixture `tests/unit/api/conftest.py::_no_passphrase` deletes the variable.
- **Suggested fix:** In the `encrypt=False` branch, call the imported `note_unused_passphrase(os.environ)`; do not copy it. Add a unit test that sets the variable and asserts one `passphrase_ignored` record from both `run_backup` and `api.backup`. Another option is to extend `test_an_api_backup_logs_what_the_cli_backup_logs` with the variable set.

### F-2 — MEDIUM — kind: testability (partial check reported as whole)
- **Location:** `tests/unit/api/test_process_state.py:47-58` (fixture `during`), used at `:101-104`
- **Claim:** "A phase double reads `signal.getsignal` during the Run, so a handler installed and then restored is also caught". The module docstring says this holds for every entry point.
- **What happens:** The fixture patches only `cli.backup.phase`. `cli/verify.py:53` and `adapters/restore_runner.py:56` each import their own `phase` binding, so no state is ever sampled during a `verify` or `restore` Run. `assert all(state == before for state in during)` therefore checks backup's phases only. A `drive_verify` or `drive_restore` that swaps `SIGTERM` and restores it before returning would pass. The planted case (`:107-125`) also exercises backup only.
- **Suggested fix:** Patch the `phase` name in every module that imports it from `adapters.phase`. Derive that set by scanning `sys.modules` for modules whose `phase` attribute `is adapters.phase.phase`; do not list them by hand. Record which entry point each sample came from, assert that each entry point produced at least one sample, and add a planted swap through `drive_restore`.

### F-3 — MEDIUM — kind: claim (Testability, integration)
- **Location:** `tests/integration/test_api_roundtrip.py:72-90`
- **Claim:** The integration tier "Asserts one `run_id` per call and a phase sequence equal to the CLI run of the same operation". The operations are backup, verify and restore.
- **What happens:** `api.verify(made_at)` is checked for one Run, but its `phase_completed` sequence is never compared with a `wpbackup2 verify` run. Only backup and restore are compared with the CLI. No other test compares verify's records with the CLI's either: the unit A9 comparison is backup only.
- **Suggested fix:** Run `run_cli(["--log-format","json","verify","--archive", str(made_at)], capsys)` and assert `_phases(checked) == _phases(cli.records)`. The same can be done in the unit tier through `verify_cli.run_verify` and `capture_logs`, which runs without the CI database.

### F-4 — MEDIUM — kind: testability (guard reach, global rule 4)
- **Location:** `tests/contracts/test_api_one_sequence.py:31-60`; `tests/unit/api/test_process_state.py:136-165`
- **Trigger:** Ordinary import spellings that each guard misses:
  - `from l3io.wp.backup.core import restore as r` followed by `r.build_restore_plan(...)`. `ImportFrom.module` is `l3io.wp.backup.core`, so it does not match `FORBIDDEN_MODULES`.
  - A relative import.
  - `restore_mod.RestorePhase.X`, an `ast.Attribute` rather than an `ast.Name`.
  - `from signal import signal; signal(SIGTERM, h)`, which gives key `(None, "signal")`, not in `_FORBIDDEN`.
  - `import signal as s; s.signal(...)`.
  - `from structlog import configure; configure()`, and `from logging import basicConfig`.
- **Why it matters:** Each guard reports green over code that does exactly what it forbids. The planted cases attack the file scope (nested directories), which is good. They do not attack the call-form scope, so these blind spots are untested. No current code violates the rule. This is a latent false green.
- **Suggested fix:** Resolve names through the module's imports. Build a map from local name to fully-qualified origin from `Import` and `ImportFrom` nodes, including `asname` and relative `level`. Match the qualified target (`signal.signal`, `structlog.configure`, `logging.basicConfig`, `l3io.wp.backup.core.restore.*`, `...RestorePhase`), and also flag `ImportFrom(module="l3io.wp.backup.core", names=[restore])`. Add planted cases for each aliased and from-import form.

### F-5 — LOW — kind: reused-before-written / Security
- **Location:** `src/l3io/wp/backup/api/operations.py:236-237`
- **What happens:** The rule that registers `relocation.new_db_password` is copied from `run_restore` (`cli/restore.py:1647-1648`), including `source="--new-db-password"`. A library Run therefore labels the registered secret with a CLI flag the caller never used. If a third root appears, or the field set grows (for example a second relocation secret), the copies will drift.
- **Suggested fix:** Move the registration to one shared place both roots call: a `RelocationFlags.register_secrets(registry, source=...)` helper, or registration inside `drive_restore` from `request.relocation`. Name the API source `relocation.new_db_password`.

### F-6 — LOW — kind: claim (Testability)
- **Location:** `tests/integration/test_api_roundtrip.py:22-23`
- **Claim:** "CI syncs `--all-extras`, so nothing here uses `importorskip`: a skip would be a false green."
- **What happens:** The file calls `pytest.importorskip("l3io.wp.database")` and `pytest.importorskip("pymysql")`. The pattern has precedent (21 of 28 integration files use it), and the `DB_HOST` skip is the tier's real gate. Even so, it contradicts the story text, and a broken extra would turn this file into a skip instead of a failure.
- **Suggested fix:** Use plain imports. The `DB_HOST` `skipif` alone gates the tier. Alternatively, record in the story that the tier convention overrides this line.

### F-7 — LOW — kind: Security (test-secret hygiene)
- **Location:** `tests/typing/api_consumer.py:39` (`password="pw"`); `tests/contracts/test_api_base_install.py:62` (`DB_PASSWORD 'not-a-real-secret'`)
- **What happens:** Neither is a unique sentinel. The consumer script is only type-checked, never run, so its literal is harmless. The base-install probe does run with the literal password in `wp-config.php`, but nothing checks the child's stdout and stderr for it. A regression that printed it would not be caught.
- **Suggested fix:** Generate the base-install password per test (`f"base-pw-{uuid4().hex}"`) and assert it is absent from `ran.stdout + ran.stderr`, or route it through the existing `credential_sentinel` fixture. Use an obviously-placeholder name in the consumer.

### F-8 — LOW — kind: claim (deviation 3 consistency)
- **Location:** `src/l3io/wp/backup/api/operations.py:188-196`
- **What happens:** `verify(archive, passphrase="x")` without `authenticate=True` silently ignores the passphrase, and the value is never registered. Deviation 3 rejects exactly this pattern for `backup` ("refused rather than ignored"). A caller who believes a passphrase-bearing verify authenticated gets a keyless consistency pass.
- **Suggested fix:** Raise `UsageError` when `passphrase is not None and not authenticate`, as `backup` does, and test it. Alternatively, record why verify differs.

### F-9 — LOW — kind: simplification
- **Location:** `src/l3io/wp/backup/api/operations.py:82, 144-167`
- **What happens:** `_NO_ENVIRONMENT` duplicates `cli/verify.py`'s private constant, which is also `drive_verify`'s default for `environ`. `BackupRequest` is built in two near-identical branches that differ only in `exclusion=`.
- **Suggested fix:** Pass `environ=os.environ` only when `authenticate` (build the keyword arguments conditionally) and rely on the driver's default otherwise. Build the backup request's keyword arguments once and add `exclusion` only when given.

## Resolution (fix iteration 1, 2026-11-06)

- **F-1 fixed.** `api.backup` calls the imported `note_unused_passphrase(os.environ)` when `encrypt=False` and no explicit passphrase was given. `test_an_unused_passphrase_variable_is_logged_as_the_cli_logs_it` sets the variable and asserts one `passphrase_ignored` record and record-shape equality with `run_backup`; it fails with the call removed.
- **F-2 fixed.** The `during` fixture patches `phase` in every `l3io.wp.backup.*` module in `sys.modules` whose `phase` is `adapters.phase.phase` (asserted at least two), and samples inside the restore rig's executor. Samples are tagged by entry point; the test asserts backup, verify, verify-fails and restore each produced samples. The planted SIGTERM swap is parametrised over all three drivers.
- **F-3 fixed.** The integration test runs `wpbackup2 verify` on the API's Archive and compares phase sequences. A unit-tier comparison (`test_an_api_verify_logs_what_the_cli_verify_logs`, through `run_verify`) runs without the CI database.
- **F-4 fixed.** Both guards resolve callees and references through the module's imports (`tests/qualified_names.py`: aliases, from-imports, relative imports against the scanned file's package). Planted cases cover every spelling listed above.
- **F-5 to F-9 (LOW) deferred:** BL-E006-001 to BL-E006-005.
