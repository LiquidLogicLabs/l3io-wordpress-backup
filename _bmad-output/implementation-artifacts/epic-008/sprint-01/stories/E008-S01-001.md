So that `backup`, `restore` and `doctor` behave as documented without any root assembling them differently.

**Given** Epics 4 and 5 have landed
**When** `wpbackup2 backup`, `restore`, `verify` or `doctor` runs
**Then** credentials come from Epic 5's chains in the order `domain/credentials.py` declares, for the WordPress account and the administrator alike
**And** every external binary the plan needs is checked by Epic 5's `BinaryPreflight` before the first command adapter
**And** `wpbackup2 doctor` prints the FR-27 diagnosis and exits `OK` or `NOT_READY`
**And** no flag that now works is still refused as not implemented

## Technical acceptance criteria

### Interface contracts

- **`cli/credentials.py` bodies (E002-S01-006's seam).** `wordpress_source(...)` delegates to `adapters/credential_providers.wordpress_credentials(explicit=..., wp_config=..., aws_secret_id=..., aws_region=...)` and `admin_source(...)` to `admin_credentials(...)`, both taking their step order from `domain/credentials.py`'s tuples; the signatures of the two `cli/credentials` functions do not change. Requires E005-S01-001's `wordpress_credentials` to accept the AWS pair (E005 follow-up in the round-2 gap map). *(E004/E005 pre-build re-check, 2026-11-06, E005 F5: superseded. The grant to E005-S01-001 is an orchestrator decision, 2026-11-06, under the owner's standing scoping rule: the story that adds credential sources registers them for redaction where they are created; the owner may overrule. E004/E005 re-check 2, 2026-11-06, M-1, which replaces "decision 9".)*
  - **Nothing to change here.** `cli/credentials.py`'s bodies stay as built: they delegate to `adapters/database.py::wordpress_source`/`admin_source`. E005-S01-001's edit makes those functions call its builders and wrap every result in `_registering`, so every resolved password stays registered.
  - **Why not delegate straight to the builders.** Delegating from `cli/credentials.py` to `credential_providers` would bypass that registration.
  - *(E004/E005 re-check 2, 2026-11-06, E005 M-3.)* **The stale docstring.** `cli/credentials.py`'s module docstring says "Epic 8 (E008-S01-001) changes only the delegation here, to Epic 5's providers". That is no longer true. This story already edits the file (the `ADMIN_PASSWORD_VAR` import, below), and rewrites that sentence in the same change: the bodies keep delegating to `adapters/database.py`, which calls Epic 5's builders.
  - **What this story binds** for credentials is the CLI flags. It removes the AWS flags from `NOT_YET_IMPLEMENTED` and passes them through the built `admin_spec(aws_secret_id=, aws_region=)` / `wordpress_spec(aws_secret_id=, aws_region=)`.
- **`AdminCredentialsRequiredError`'s message** names `--admin-username`/`--admin-password`, `--admin-credentials-aws-secret-id`, and `L3IO_WP_BACKUP_ADMIN_USER`/`L3IO_WP_BACKUP_ADMIN_PASSWORD`, reading the variable names from Epic 5's constants (no second literal). *(E004/E005 pre-build re-check, 2026-11-06, E005 F4: this story also retires `cli/parser.py::ADMIN_PASSWORD_VARIABLE` (L71) in favour of `adapters/credential_providers.ADMIN_PASSWORD_VAR`, and repoints `cli/credentials.py`'s import and the help text at it (BL-E002-084).)*
- **`RootPreflight` (`cli/context.py`)** wraps E005-S01-002's `BinaryPreflight(environ=os.environ)` and is what `real_adapters`/`dry_run_adapters` bind as `AdapterSet.preflight` (replacing the `check_dump`-only binding of E002-S02-007): its `check(requirements)` first raises `PreflightFailedError(tool="platform", ...)` when `unsupported_platform()` returns a reason, then delegates — it checks exactly the plan's `required_tools`. *(E004/E005 pre-build re-check, 2026-11-06, E005 G1: "delegates" means routing. Orchestrator decision, 2026-11-06, under the owner's standing rule that built code wins over story text: the built `DumpReadinessPreflight` owns `database-dump`. E004/E005 re-check 2, 2026-11-06, M-1, which replaces "decision 10".)*
  - **The routing.** Every built plan that dumps carries `core/backup.py::DUMP_REQUIREMENT` (`name="database-dump"`). `RootPreflight` sends a requirement named `DUMP_REQUIREMENT.name` (imported, never a literal) to the built `cli/preflight.py::DumpReadinessPreflight`, and every other requirement to `BinaryPreflight(cwd=<the Run workspace>)`. It returns the statuses in requirement order.
  - **Why it matters.** `BinaryPreflight` raises `ValueError` for `database-dump`, so binding it alone would crash every `database`/`all` backup and every restore that dumps a snapshot.
  - **Where it binds.** The built `AdapterSet` has no `preflight` field. The built roots pass `preflight=DumpReadinessPreflight(...)` explicitly (`cli/backup.py` L649, `cli/restore.py` L1019), and `RootPreflight` replaces those two constructions. *(Decided 2026-10-28.)* The passphrase backend reaches it through the plan: each root passes `extra_tools=cipher.required_tools()` (E004-S01-003) into `BackupRequest`/`RestoreRequest`, which the plan builders append (E002-S02-007, E003-S01-001); `RootPreflight` never infers the cipher's mode. Every root — `cli/backup.py`, `cli/verify.py`, Epic 3's `cli/restore.py`, Epic 6's `api/` — gets it through `real_adapters` and adds nothing.
  - *(E004/E005 re-check 2, 2026-11-06, N-5.)* **Who passes `extra_tools`.**
    - **Restore.** E004-S01-003 adds `extra_tools=() if cipher is None else cipher.required_tools()` to `run_restore`'s `RestoreRequest`, in the same change as its factory call. The built `run_restore` passes none. This story cites that line and does not add it. When this story builds, it is present, and `test_root_preflight.py`'s restore case relies on it.
    - **Backup.** This story passes `extra_tools` in `run_backup` (below).
    - **Verify.** `cli/verify.py` has no plan, no `PREFLIGHT` and no `extra_tools`, so it passes none. Its cipher's `check()` runs in the factory.
    - **Until this story lands.** The built restore root's `DumpReadinessPreflight` reads no tool version. So under `L3IO_AGE_PASSPHRASE_BACKEND=cli`, an encrypted CLI restore refuses at `PREFLIGHT` with `found="unusable (version unknown)"`, exit 7 (E004-S01-003). Binding `RootPreflight` here, which routes `age` to `BinaryPreflight`, ends that.
- **`cli/doctor.py::run_doctor(args) -> int`** builds `diagnose(preflight=RootPreflight(...), environ=os.environ, target=<--archive parsed>, database=<DatabaseQuery.check_dump when --wp-dir is given>)` and renders `Diagnosis` as text on a TTY, `to_dict()` as JSON otherwise or with `--json`; returns `OK` when `ready`, else `NOT_READY`. It opens a Run without a Site Lock (it changes nothing).
- **Epic 4 bindings.** *(Decided 2026-10-27.)* The cipher and the exclusion set are per-call arguments — `BackupRequest.cipher`/`.exclusion` and `RestoreRequest.cipher`, reaching `backup(...)` — never `AdapterSet` fields and never `real_adapters` arguments. This story binds them in `cli/`, using the registry each root created before the Run (E002-S01-004) and Epic 4's `adapters/crypto.build_payload_cipher` (E004-S01-003) *(ADR-0024; Gate E004 AG-6/AG-9, 2026-10-30)*: `run_backup` resolves the passphrase only with `--encrypt-with-passphrase` and calls `build_payload_cipher(passphrase=..., required=args.encrypt_with_passphrase, secrets=registry)`, so the flag with no passphrase resolved exits `REFUSED` (`PassphraseRequiredError`) rather than writing plaintext; `run_restore` resolves it on every restore and passes `required=False`; `run_verify` builds no cipher, because verification is keyless. *(E004/E005 pre-build re-check, 2026-11-06, E004 F-2, F-4, F-6 and F-19; supersedes the cipher clauses of this bullet.)*
  - **The factory.** `build_payload_cipher(*, passphrase, secrets)` takes no `required` flag and raises no refusal.
  - **`run_backup`.** With `--encrypt-with-passphrase` it resolves through the built `cli/passphrase.py::require_passphrase`, which refuses a missing passphrase with `PassphraseUnavailableError`, exit `USAGE` (2), before anything is read. It then calls `build_payload_cipher(passphrase=resolved.value, secrets=registry)`.
  - **The cipher's tools.** It passes `extra_tools=cipher.required_tools()`, read from the factory's concrete `PassphraseCipher` type.
  - **Restore and verify are already done.** E004-S01-003 already routes `run_restore` and `verify --authenticate` (in `cli/verify.py`) through the factory. Keyless `verify` builds no cipher, and `verify --authenticate` authenticates. So this story adds no cipher code to `cli/restore.py` or `cli/verify.py`. *(E004/E005 re-check 2, 2026-11-06, N-5: that includes the restore root's `extra_tools=cipher.required_tools()`, which E004-S01-003 adds. This story does not add it again, and does not assume it is absent.)* `run_backup` builds the exclusion set from `--exclude`/`--no-default-excludes` with `ExclusionSet.from_patterns(...)`, wrapped in `LoggedExclusionPolicy` (E004-S01-001, Gate E004 AG-12). With no exclusion flag it passes none, and this story changes `cli/backup.py::default_exclusion_policy()` (E002-S01-004) from `INCLUDE_EVERYTHING` to `LoggedExclusionPolicy(ExclusionSet.default())`, so the library and the CLI get the same default from one place.

### Error and edge case handling

- Conflicting credential sources: Epic 5's `CredentialSourceConflictError` → `USAGE`, before the lock. *(E004/E005 pre-build re-check, 2026-11-06, E005 F4: no such class. The built `cli/credentials.py::admin_spec`/`wordpress_spec` raise `UsageError` → `USAGE`, before the lock.)*
- `--admin-credentials-aws-*`/`--db-credentials-aws-*` without the `aws` extra: `MissingExtraError(extra="aws")` → `NOT_READY`, raised when the chain is built, not at import (AD-8).
- Windows: `PreflightFailedError(tool="platform")` → `NOT_READY` before any other check, files-only Runs included.
- `doctor` with an unreachable database: the diagnosis records database's finding codes and `ready: false`; exit `NOT_READY`, never `UNREACHABLE` (doctor reports, it does not fail on what it reports).
