# Code review — E008-S01-001

Two run_bounded findings (R-01, R-02) were reproduced with a small script against the
working tree (`~/.cache/e008pt/review/sig.py`, `gc.py`). Everything else comes from reading
the code at the cited lines.

## Findings

### R-01 — HIGH — kind: deletion (confidence: high) — `src/l3io/wp/backup/adapters/preflight.py:327-336` (`run_bounded`)

**What is wrong.** The old `adapters/wpcli.py::run_child` and `_version_output` called
`subprocess.run`, which wraps the wait in `except: process.kill(); raise`. Because of that, any
exception during the wait killed the child: `RunTerminated` from the SIGTERM handler
(`cli/__init__.py:63`) or a `KeyboardInterrupt`. `run_bounded` handles only
`subprocess.TimeoutExpired`. Any other exception leaves the `with Popen(...)` block, and then:
- `Popen.__exit__` closes the pipes. A reader thread holds the buffer lock in `read()`, so the
  close blocks until the child exits.
- For a non-`KeyboardInterrupt` exception, `__exit__` then waits with no timeout.

The child runs with `start_new_session=True`, so the terminal's SIGINT does not reach it either.
Reproduced: with an alarm handler raising after 1 s, a `sh -c 'sleep 4'` child, and
`timeout=60`, the exception reached the caller after **4.0 s**, which is when the child finished.
It was not killed.

**Consequence.** A SIGTERM or Ctrl-C during `wp search-replace` no longer stops WP-CLI. The Run
blocks until `wp` finishes, up to `CHILD_TIMEOUT_S` or longer, while holding the Site Lock, and
the database keeps changing after termination was asked for.

**Fix.** Wrap the body after `Popen` in `try: ... except BaseException: _kill_group(process.pid);
process.wait(); raise`. That restores `subprocess.run`'s kill-on-any-exception, now for the whole
group. Add a test that raises from a signal handler during a sleeping child and asserts the group
is gone within a second.

### R-02 — MEDIUM — kind: defect — `src/l3io/wp/backup/adapters/preflight.py:327-336` (`run_bounded`)

**What is wrong.** `timeout` bounds only `process.wait()`. The `reader.join()` calls have no
deadline, on both the normal path and the timeout path. A descendant that left the process group
(`setsid`, `daemon()`) keeps the pipe write ends open, so the joins block until it exits, and
`_kill_group` cannot reach it.

Reproduced: `sh -c 'setsid sleep 5 & sleep 0.3; echo hi'` with `timeout=1` returned after
**5.0 s**. The docstring says "a stray grandchild cannot hold the pipes open", which is true only
inside the group.

The old `subprocess.run(timeout=...)` bounded the reads too: `communicate(timeout)`. So this is
also a regression of the guarantee `CHILD_TIMEOUT_S` documents: "restored code that never returns
cannot hold the Site Lock for ever". `wp` runs the restored `wp-config.php`, which can fork such
a daemon.

**Fix.**
- Track one deadline across `wait` and the joins: `join(timeout=remaining)`.
- If a reader is still alive at the deadline, close the parent's pipe ends and raise
  `TimeoutExpired`. Mark the call failed even when the leader exited 0.
- Correct the docstring.
- Add the `setsid` case above as a test.

### R-03 — MEDIUM — kind: defect — `src/l3io/wp/backup/cli/doctor.py:85` with `adapters/preflight.py:487`

**What is wrong.**
- `BinaryPreflight._status("wp")` now raises `WpCliConfigFoundError` when a `wp-cli.yml` sits
  in the Run workspace or above it.
- `diagnose()` probes every `KNOWN_TOOLS` entry, `wp` included, and catches nothing.
- `drive_doctor` does not catch it either.

So `doctor`, and `api.doctor`, which promises "it raises nothing for what it reports", exit 3 and
print no diagnosis in the exact situation an operator would run `doctor` to find. The story says
doctor "reports, it does not fail on what it reports" (Error and edge case handling, last bullet).

**Fix.** In `BinaryPreflight`, when `optional=True` (doctor), turn `WpCliConfigFoundError` into
`ToolStatus(name="wp", present=True, version=None, path=..., error="wp-cli.yml found at <path>")`
so the diagnosis is not ready. Keep the raise for the roots. Add a doctor test with a planted
`wp-cli.yml` above the workspace that expects exit 7 and a printed diagnosis.

### R-04 — MEDIUM — kind: defect — `src/l3io/wp/backup/adapters/preflight.py:487` with `adapters/workspace.py:50`

**What is wrong.**
- The `wp-cli.yml` ancestor check runs from the Run workspace.
- That workspace is `mkdtemp(dir=None)`, which on a default host is under the world-writable
  `/tmp`.
- `find_wp_cli_config` walks `/tmp/wpbackup-…`, then `/tmp`, then `/`.

So any local user can create `/tmp/wp-cli.yml` and make every URL-relocating restore refuse with
exit 3, and with R-03, make `doctor` fail too. This includes a restore run as root. Before this
change the probe read that file, which was worse. The refusal is right, but the probe's cwd now
lets other users deny service.

**Fix.** Run the `wp` probe from a directory whose ancestors no other user can write: the
per-user state directory that `_check_wp_cli_directory` already prepares, or `/`. Otherwise,
refuse only on a hit in a directory that is not owned by the effective uid or root, or that is
writable by others. Add a test with the file planted in a world-writable ancestor. Update the
`docs/restore.md` sentence ("starts from the Run workspace under `$TMPDIR`").

### R-05 — MEDIUM — kind: claim — `src/l3io/wp/backup/adapters/tar.py:687`

**The claim.** AC (Error and edge case handling, first bullet): "The backup refuses **before
writing anything** … **the plan computes** the serialized Manifest size from the collected member
list", and "a member list just over the cap is refused **at plan time** with nothing written".

**What the code does.**
- The check runs inside `TarArchiveWriter.write`, at `WRITE_ARCHIVE`, after `DUMP`, so the full
  database dump has already been taken into the workspace.
- The Dry Run's `NoopArchiveWriter` (`adapters/noop.py:404`) never collects, so it never checks.
  A `--whatIf` of a backup that will be refused reports success.

The size computation itself is sound: same builder, same serialiser, and the payload's two
unknown fields set to their longest forms.

**Fix.** Choose one:
- (a) Move the measurement to the plan or `COLLECT_SITE_ROOT`, before `DUMP`, and run the
  collection in the Dry Run as well.
- (b) Amend the AC to "refused at `WRITE_ARCHIVE`, before the Archive is written; not checked by
  a Dry Run", with the owner's consent.

The test file also does not run the AC's "an Archive whose Manifest is just under 256 MiB
verifies". It extrapolates from a measured ratio (`MEMORY_FACTOR = 25`), which states about
6.4 GiB at the cap. Record that as a stated deviation, or run it as a marked slow test.

### R-06 — MEDIUM — kind: claim — `docs/adr/0024-one-encrypted-payload-passphrase-only.md:245`

**The claim.** AC (Testability, E004 closure (2)): "`MIN_ENCRYPTION_PASSPHRASE_LENGTH = 12`,
enforced for encryption only (backup, the library `backup`, **the Safety Snapshot**) … 11
characters refused and 12 accepted on **each encrypting path**".

**What the code does.** The Safety Snapshot is encrypted with any restore passphrase of 4 or more
characters, and `note_short_restore_passphrase` only logs a WARNING. The ADR amendment records
this as a "deviation" decided in the implementation, not by the owner.

Its justification, "no weaker than the Archive it copies", is wrong. The Safety Snapshot copies
the **current Site**, not the Archive. With an unencrypted Archive plus `--allow-unencrypted`, or
an Archive encrypted under a different scheme, the current Site's data ends up behind a 4-character
passphrase.

**Fix.** At minimum, enforce the floor for the snapshot when the Archive is unencrypted: nothing
is being decrypted, so the "decryption is unaffected" rule does not apply. Then either get the
owner's sign-off on the remaining deviation and record it in the story, or refuse to take an
encrypted snapshot under a short passphrase (`PassphraseTooShortError`, with `--no-snapshot` as
the way out). Correct the ADR's reasoning either way.

### R-07 — LOW — kind: deletion (confidence: high) — `src/l3io/wp/backup/cli/credentials.py:175`

**What is wrong.** `value = explicit or None` makes an empty `--new-db-password ""` count as "not
given". Before, `validate_relocation_values` refused it with `InvalidRelocationValueError("must
not be empty")`, exit 2. Now it falls through to the file or to `L3IO_WP_BACKUP_NEW_DB_PASSWORD`.
With `--new-db-user` and the variable set, an explicit empty flag is silently overridden by the
environment. An empty `--new-db-password-file` is likewise treated as absent rather than refused
under the ADR-0018 floor. The story requires that "Every source … the ADR-0018 floor applies".

**Fix.** Treat a given-but-empty explicit value or file as given: `explicit is not None`,
`file is not None`. Let the `MIN_SECRET_LENGTH` check refuse it with `CredentialTooShortError`.
Add tests for the empty flag and the empty file.

### R-08 — LOW — kind: defect — `src/l3io/wp/backup/cli/credentials.py:144`

**What is wrong.** `_read_password_file` calls `handle.readline()` with no size limit.
`--new-db-password-file /dev/zero`, a FIFO, or a large one-line file reads without bound before
any check.

**Fix.** Use `handle.readline(4096)` and refuse a line that fills the limit without a newline. Or
`stat` first and refuse anything that is not a regular file.

### R-09 — LOW — kind: deletion (confidence: medium) — `src/l3io/wp/backup/adapters/preflight.py:373`

**What is wrong.** The probe now parses the version from the **first line of stdout** only.
Before, it searched stdout and stderr combined. PHP prints deprecation and startup notices to
stdout before WP-CLI's `WP-CLI 2.12.0` line when `display_errors` is on, which is common with
PHP 8.x and older WP-CLI phars. Then `version=None`, and `wp >= 2.12.0` fails as "unusable
(version unknown)", exit 7, on a host where WP-CLI works. The stricter parse does protect
against picking up a stray token, which is a fair reason for it.

**Fix.** Take the first stdout line that matches `^WP-CLI \d` for `wp`, or more generally the
first line containing a version token. Alternatively, add `-d display_errors=stderr` through
`WP_CLI_PHP_ARGS` in `probe_env`. Add a test where a notice line precedes the version.

### R-10 — LOW — kind: claim — `src/l3io/wp/backup/adapters/lock.py:29` (reach of `cli/preflight.py::RootPreflight`)

**The claim.** AC (Error and edge case handling): "Windows: `PreflightFailedError(tool=
"platform")` → `NOT_READY` before any other check", and `doctor` "reports `platform_supported:
false` rather than refusing".

**What the code does.**
- `adapters/lock.py` does `import fcntl` at module level.
- `cli/adapter_sets.py:29` imports it, and every root and `doctor` import `cli/adapter_sets.py`.
- On a real Windows interpreter, the command therefore fails at import with `ModuleNotFoundError`
  before `RootPreflight.check` or `diagnose` runs.
- In `drive_backup`, the Site Lock, the `wp-config.php` read and `ArchiveExistsError`
  (`cli/backup.py:552`) all come before `require_tools`.

The tests patch `sys.platform` on Linux, so they cannot see this.

**Fix.** Either import `fcntl` inside `FcntlSiteLock`'s methods (AD-8 style) and call
`refuse_unsupported_platform()` first in each `run_*` root and in `run_doctor`'s caller, or amend
the AC to "on a POSIX host reporting an unsupported `sys.platform`".

### R-11 — LOW — kind: claim — `src/l3io/wp/backup/cli/restore.py:1496`

**The claim.** AC (E006 closure decision 2): `RunWarning.code` is "the WARNING event name". The
`RunWarning` docstring says the same, and "The structured WARNING log records stay in both
cases".

**What the code does.** No WARNING record named `safety_snapshot_encrypted` exists. That notice
was a bare `print` before this change, and still has no log record. A library caller that
correlates `code` with the log cannot do so for this notice.

**Fix.** Add `_log.warning("safety_snapshot_encrypted", path=str(result.path))` beside the
`emit_warning` call, mirroring the unencrypted branch. Have the sink test check that each
`RunWarning.code` has a matching WARNING record.

## Checked and found sound

- **`run_bounded` overflow path.** The group is killed, the reader drains to EOF, and
  `ChildOutputLimitError` is mapped by both callers. No fd leak: the `Popen` context manager
  closes the pipes.
- **The `wp-cli.yml` check.** It runs on the path as given and on the resolved path, before the
  probe. The BL-E007-008 check runs in `resolve` before any effect.
- **Error text.** Control characters are stripped and the text is truncated.
- **`RootPreflight`.** It refuses the platform first, routes by `DUMP_REQUIREMENT.name`, and
  returns statuses in order. It is built only by `root_preflight`, at the three sites.
  `require_tools` no longer returns early, and `preflight_passed` is logged only when there are
  requirements. `verify` refuses the platform before its Run.
- **`CredentialTooShortError`.**
  - It is raised after registration in `_explicit_step`, `_RegisteringSource.resolve` and
    `new_db_password`, before any connection.
  - The AWS flags are bound for backup and restore. `RestoreRequest.credentials` reaches
    `wordpress_source(..., environ={})`.
  - `--new-db-password` precedence is flag, then file, then environment, and the environment is
    read only with `--new-db-user`.
- **Encryption floor.** It is enforced in `require_passphrase`, which the CLI and library backups
  both call. The prompt asks twice and compares in constant time. Restore and verify stay
  permissive.
- **Passphrase on an unencrypted Archive.** `ArchiveNotEncryptedError(passphrase_supplied=True)`
  is raised before any effect, in the shared driver, so a Dry Run and the library path refuse
  too.
- **Exclusions.** The Safety Snapshot passes `exclusion=INCLUDE_EVERYTHING` explicitly
  (`cli/restore.py:1461`). Every other `BackupRequest` without `exclusion` takes the new default
  by design: the CLI and `api.backup`. `--list-default-excludes` returns before any Run.
- **`doctor`.**
  - It opens a Run without a Site Lock.
  - A `BackupError` from the Site path becomes a blocker, and the exit is `NOT_READY`, never
    `UNREACHABLE`.
  - The output is redacted through the Run's registry. The passphrase backend is reported by
    name only.
- **`public_boundary`'s `signature.bind`.** It is safe for every wrapped function (`backup`,
  `verify`, `restore`, `doctor`, all keyword-only). It checks only the arguments' shape (arity
  and keywords), so an argument mistake raises a plain `TypeError` before anything runs.
- **`Secret`.**
  - `repr` and `str` are opaque, and `__hash__` is `None`.
  - Comparing with a `str` falls back to `False`, and two `Secret`s compare with
    `hmac.compare_digest`.
  - `__reduce__` refuses pickling, which also blocks `copy` and `deepcopy`. No `asdict` or
    `deepcopy` is applied to any object holding one.
  - `.reveal()` is called only in `domain/secret.py`, `adapters/redaction.py`,
    `adapters/credential_providers.py` and `adapters/crypto.py`.
  - The cutover password reaches `wp-config.php` through the database source, as plain text.
- **`context=`.** Removed from all three public signatures. `target` is required on
  `api.backup`.
- **Existing-library use.** The providers wrap `l3io-wordpress-database`, the probe uses
  `shutil.which` and `packaging`, and rendering uses stdlib `json`. `Secret` is hand-written by
  owner decision ("no pydantic"). `run_bounded` has no maintained stdlib equivalent, because
  `subprocess.run` cannot bound output. Its defects (R-01, R-02) are where it departs from
  `subprocess.run`'s structure, so the fix is to restore that structure rather than to add a
  dependency.
