## Findings

### F-1: high, kind: claim / correctness. Restore can provision an account that the restored `wp-config.php` does not name

- **Location:**
  - `src/l3io/wp/backup/cli/restore.py:1221-1223` (unchanged; now reaches `credential_providers.wordpress_credentials` through `adapters/database.py:609-615`);
  - `src/l3io/wp/backup/adapters/database.py:946-951` (`ensure` with `self._credentials`);
  - `src/l3io/wp/backup/cli/restore.py:976-979` and `:1316` (`db_user` is read from `wp-config.php`).
- **What is wrong:**
  - With deviation 6, a restore that is not relocated builds its WordPress source as environment, then `wp-config.php`. When `L3IO_WP_BACKUP_DB_USER`/`_PASSWORD` are set (for example, left in the operator's shell for the cron backup), that account wins.
  - The restore then uses it in the places that matter: `check_ensure`/`ensure` (`database.py:885`, `:949`) create the account or reset its password with `GRANT ALL` on the target database, and `check_load`/`load` run as it. `cli/adapter_sets.py:149-151` makes `restore_database` the same instance when nothing is relocated.
  - Meanwhile the survey (`wordpress_user=relocation.cutover_user or db_user`), the reset-consent check (`user=db_user`) and the restored or kept `wp-config.php` all name `wp-config.php`'s `DB_USER`. The account restore provisions and the account the site will use are different.
  - On a fresh server, the site's `DB_USER` is never created. On a shared one, an unrelated account is given its password and full rights on this database. The restore reports success either way.
  - This contradicts the story's AC "no provider silently substitutes one credential for another" and AD-9/FR-15. It also goes beyond the story's own statement of what the chain is for ("A restore … takes [administrator credentials] from …"; the WordPress-account chain is described for `backup`). The README table backs this up: it lists only `BackupRequest.credentials` as the WordPress account's explicit source.
- **Suggested fix:** Keep the non-relocated restore on `wp-config.php` alone, which is the pre-story behaviour.
  - One way: give `wordpress_source` an `environ`-free path for restore, by passing `environ={}` from `cli/restore.py:1222`. That needs `cli/restore.py` added to the grant, or the orchestrator's decision.
  - The other way: make it the builders' rule, with a documented `include_environment` flag on `wordpress_credentials` that restore sets to `False`.
  - Either way, add a unit test showing that a restore-built WordPress source with both `L3IO_WP_BACKUP_DB_*` set still resolves `wp-config.php`'s account. If the owner does want restore to honour the variables, then `db_user` must come from the resolved source and not from `wp-config.php`, and that decision needs an ADR. A recorded deviation is not enough.

### F-2: medium, kind: deletion (confidence: high). `exc.extra` puts database's extra names into backup's install hint

- **Location:** `src/l3io/wp/backup/adapters/database.py:420` (`_parse`), `:496`, `:579`, `:759`, `:810`, `:1095`.
- **What is wrong:**
  - The deleted fixed `_EXTRA` ("database") was not only a constant. It translated a `MissingDependencyError` from database's extra names (`aws`, `encryption`, `wpconfig`; see the 0.3.2 METADATA) into this package's extra names (`database`, `aws`, `otel`).
  - Only `aws` exists in both. Reproduced: with `l3io.wp.config` hidden, `site_descriptor_from_wp_config` now raises `MissingExtraError(extra='wpconfig')` with the message "pip install 'l3io-wordpress-backup[wpconfig]'". No such extra exists. pip warns and installs nothing, and the operator is stuck at exit 7. Before this change the message correctly named `[database]`, which lists `l3io-wordpress-config`.
  - `encryption` (`_passphrase.py`, `encryption.py`) has the same problem.
  - The story's text ("every other `except wpdb.MissingDependencyError` site, `MissingExtraError(extra=exc.extra)`") prescribed this. So it is a defect in the story as well as in the code. Only the boto3 case was reasoned about.
- **Suggested fix:** Use a single private mapping function, for example `_backup_extra(exc) -> str`, that returns `"aws"` for `exc.extra == "aws"` and `"database"` otherwise. Derive the accepted set from `importlib.metadata.metadata("l3io-wordpress-backup").get_all("Provides-Extra")` rather than a hand-typed list. Use the function at all six sites. Add a test that hides `l3io.wp.config` and asserts `extra == "database"`, and a contract test asserting that every value the function can return is a `Provides-Extra` of this distribution.

### F-3: low, kind: claim / observability. `credential_source_selected` is logged on every `resolve()`, not once

- **Location:** `src/l3io/wp/backup/adapters/database.py:594`.
- **What is wrong:**
  - The story says "one INFO `credential_source_selected`". A backup resolves the same source in `require_wp_config_credentials`, `check_dump` and `dump`, so the record appears three or more times per Run. A restore adds more, from survey, `check_ensure`, `ensure`, `check_load`, `load` and the cutover.
  - When a source has been re-wrapped for a different registry (`_registering`, `:617-618`), each resolve logs twice.
  - The integration test compares a `set`, so it cannot see the count.
- **Suggested fix:** Either log once per wrapper, using a `_logged` flag in the slots, or amend the story to "per resolution" and assert the count in `tests/integration/test_credential_sources.py`.

### F-4: low, kind: error-handling. The region message tells a library caller to pass a flag that does not exist yet

- **Location:** `src/l3io/wp/backup/adapters/database.py:581-583`.
- **What is wrong:**
  - In this release, AWS can be selected only from the library (README and story F8). Both region flags are still in `cli/parser.py::NOT_YET_IMPLEMENTED`.
  - The reason "pass --db-credentials-aws-region or set AWS_DEFAULT_REGION" therefore tells the only possible caller to use an unbound CLI flag.
  - The story does mandate naming the flag, so this is a wording gap, not a contradiction.
- **Suggested fix:** Also name the library field, for example "pass {flag} (`AwsSecretCredentialSpec.region`) or set AWS_DEFAULT_REGION". E008-S01-001 can drop the parenthesis when it binds the flags.

### F-5: low, kind: claim. An adapter reads `os.environ` to word an error

- **Location:** `src/l3io/wp/backup/adapters/database.py:507`.
- **What is wrong:**
  - The story says `environ` is passed in "so only the composition root reads the process environment to decide which steps exist". Deviation 4 reads `os.environ` inside `adapters/`, separately from and later than the read made by database's `Environment.resolve()`.
  - If a library caller's `environ` differs from `os.environ`, the half-set error can name the wrong variable, or none.
  - The information is already on the exception: `Environment.resolve` raises with the unset variable's name. `CredentialsUnobtainableError` carries no `.key`, though, so parsing its message would be brittle.
- **Suggested fix:** Pass the `environ` mapping to `require_wp_config_credentials`; `cli/backup.py:630` already has `os.environ`. That call site is outside the grant, so the alternative is to leave the code as it is and record it as an accepted exception in the story's re-check notes.

### F-6: low, kind: claim. "Neither source has an answer" no longer lists the environment step

- **Location:** `src/l3io/wp/backup/adapters/credential_providers.py:151-159` (deviation 1).
- **What is wrong:**
  - The story says: "WordPress variables unset, and `wp-config.php` defines neither … the chain raises `CredentialsAbsentError` with `sources` listing every step tried … re-raised as `CredentialsError` naming each source label."
  - Because the environment step is now omitted when neither variable is set, the error names only `wp-config:<path>`. An operator who hits it is not told that `L3IO_WP_BACKUP_DB_*` would also work.
  - The deviation is otherwise sound, so this is a small loss of discoverability.
- **Suggested fix:** Either name both variables in `require_wp_config_credentials`'s "defines neither" reason (`database.py`, the `CredentialsAbsentError` branch), or amend the AC to describe the steps actually built.

### F-7: low, kind: testability. A common word is used as the leak sentinel

- **Location:** `tests/unit/adapters/test_credential_providers.py:216`, `:226` (and `:250`).
- **What is wrong:** `assert "half" not in str(caught.value)` checks that no value leaks by searching for the English word "half". That breaks the project rule that tests use unique sentinels. If the error wording ever contains "half" (for example "half-set"), the test fails for no real reason. And the assertion does not prove a distinctive value is absent.
- **Suggested fix:** Set `f"half-{uuid.uuid4().hex}"` and assert that exact value is absent.

### F-8: low, kind: testability. One AWS test does not skip when `boto3` is missing

- **Location:** `tests/unit/adapters/test_credential_providers.py:316` (`test_the_builders_resolve_nothing`).
- **What is wrong:** `monkeypatch.setattr("boto3.client", …)` imports `boto3`. Without the `aws` extra the test errors, whereas every other AWS test uses `pytest.importorskip("boto3")`. CI installs `--all-extras`, so CI is green, but a developer running `uv sync --extra database` gets a red that is not real.
- **Suggested fix:** Add `pytest.importorskip("boto3")` at the top of the test.
