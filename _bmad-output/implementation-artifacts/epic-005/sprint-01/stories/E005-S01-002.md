# E005-S01-002: Fail before starting when a required tool is missing


**Implements:** FR-27


As an operator,
I want to be told up front that `wp` or `mysqldump` is absent,
So that I do not discover it halfway through a restore.

**Acceptance Criteria:**

**Given** a plan that requires external binaries
**When** the run begins
**Then** every required tool is checked before the first effect, not at the point of use
**And** a missing tool aborts with nothing changed, names the tool, and states why it was needed
**And** required tools and their minimum versions are documented, and a diagnostic command reports what is present
**And** an absent optional Python dependency raises a package-owned error naming the extra, rather than being folded into binary preflight

## Business acceptance criteria

### Outcome

Before a Run makes its first effect, every external binary its plan needs has been checked for presence and, where a floor is declared, for version. "First effect" means taking the Site Lock's protected actions, writing to the workspace, the Storage Target or the Site, or touching the database. This holds for a real Run and a Dry Run alike.

What the operator sees when a check fails:
- **A tool is missing or too old.** The Run stops with exit `NOT_READY` (7) and changes nothing. The message names the tool, the plan step that needed it, what was found (absent, or the version), and where to get it.
- **An optional Python extra is missing.** It is still reported at the point of use as E002's `MissingExtraError` naming the extra. Binary preflight never reports it.

The binaries this package checks itself are:
- `age` (at least 1.3) and `age-plugin-batchpass`, when a passphrase-encrypted Run would use database's CLI passphrase backend (`L3IO_AGE_PASSPHRASE_BACKEND`);
- `wp`, when Epic 7's relocation plan declares it (story 7.4).

`mysqldump` and `mysql` are **not** checked here: since ADR-0015 database's `check_dump`/`check_load` own their presence, version and skew (`CLIENT_TOOL_MISSING`, `CLIENT_SERVER_SKEW`).

Separately, a diagnostic reports:
- the Python version and the platform;
- each known tool, with presence, version and path;
- each extra, installed or not;
- optionally, a Storage Target's writability and the database findings for a Site.

A reviewer can check it worked:
- with `PATH` stripped of `age`, an encrypted Run using the CLI backend exits 7 with an empty Storage Target directory and no workspace left behind;
- the diagnostic lists `age` as absent;
- the README's external-tools table matches what the plans can require.

*(E004/E005 pre-build re-check, 2026-11-06, G4, and the orchestrator decision under the criteria above, E004/E005 re-check 2, M-1, which replaces "decision 14".)*
- **In this story.** A Run handed an `age` requirement with `age` absent from `PATH`, or with a fake `age` printing `age v1.2.0`, raises `PreflightFailedError` (exit 7) through the built `backup(..., preflight=BinaryPreflight(...))` before any command adapter is called. The Storage Target is empty and no workspace remains. `diagnose(...)` lists `age` as absent.
- **In E008-S01-001.** The real encrypted CLI Run and `wpbackup2 doctor`.

Preflight's exit 7 is what an `age` below 1.3 produces, because `check()` only looks for the binary.

This adapter never runs, locates or names those binaries, and `tests/contracts/test_no_mysql_client.py` keeps that mechanical.
- WP-CLI semantics: its minimum version, when relocation needs it, the refusal wording that points to installation guidance, and how `wp` is invoked. Those are Epic 7's (story 7.4, `adapters/wpcli`). This adapter checks whatever `ToolRequirement` 7.4 declares, under the tool name `wp`, with no WP-CLI-specific logic. *(E004/E005 pre-build re-check, 2026-11-06, G2: "no WP-CLI-specific logic" means no WP-CLI code path. - Defining the `Preflight` port, `ToolRequirement`, `ToolStatus`, `PreflightFailedError` or the order "preflight before the first command adapter". All are Epic 2's (E002-S02-007, E002-S01-005).
- Optional Python dependencies at run time. `MissingExtraError` is raised at the import site (AD-8, E002-S01-001). The diagnostic only lists extras.
- Remote Storage Target reachability. v1.0 accepts `file:` only (AG-27).

**`BinaryPreflight` implements `ports/preflight.Preflight` (E002-S02-007).** `check(requirements: Sequence[ToolRequirement]) -> Sequence[ToolStatus]` is a pure query. It returns one `ToolStatus` per requirement, in the requirement order. It **never short-circuits**: every requirement is probed, so all unmet tools are visible together.

Constructor: `BinaryPreflight(*, which: Callable[[str], str | None] = shutil.which, probe: Callable[[str], str | None] = _version_output, environ: Mapping[str, str])`. The defaults are real; tests inject doubles. *(E004/E005 pre-build re-check, 2026-11-06, G2: superseded by the constructor above, which takes `cwd` and an argv-taking `probe`.)*

For each requirement:
1. **Locate.** `which(name)` locates the binary. `None` gives `ToolStatus(present=False, version=None, path=None)`.
2. **Probe the version, only when a minimum is set.** *(E004/E005 pre-build re-check, 2026-11-06, G2 and G3: every present tool is probed, with `[path, *ToolInfo.version_argv, *root_argv-if-root]` in `cwd`; see above.)* `probe(path)` runs `[path, "--version"]` with `subprocess.run`:
   - `capture_output=True`, `text=True`, `timeout=10`, `check=False`;
   - `env` minimal: `PATH`, `HOME` and `LC_ALL=C` only. It never forwards `AGE_PASSPHRASE_FD`, `L3IO_WP_BACKUP_*`, `MYSQL_*` or any other inherited variable.
3. **Parse.** The first `\d+(?:\.\d+)+` token in the combined output is parsed with `packaging.version.Version(...).release`. The tool-specific output parsing is that one generic regex.

**The allow-list.** `KNOWN_TOOLS: Final[Mapping[str, ToolInfo]]`, where `ToolInfo(frozen)` has `purpose: str` and `install_hint: str` *(E004/E005 pre-build re-check, 2026-11-06, G2: and `version_argv`, `root_argv`; see above)*. ### Error and edge case handling

- **Tool absent.** `present=False`. The root raises `PreflightFailedError(tool, needed_for, found="absent")` → 7. That happens before the first command adapter, so the Storage Target, the Site and the database are untouched, and the workspace is removed by its `finally` (AD-12).
- **Several tools unmet.** Every unmet requirement is logged at ERROR, so the operator sees all of them in one Run. The raised error names the first in plan order, because E002's error carries one tool. *(E004/E005 pre-build re-check, 2026-11-06, G7: the raise is the built `cli/preflight.py::require_tools`'s, not this adapter's. The ERROR records are `BinaryPreflight`'s `preflight_checked`, below.)*
- **Version below the minimum.** `found="<version>"`, and the message states the minimum. For example, `age 1.2.1 found; 1.3 or later is needed for ENCRYPT (passphrase, CLI backend)`.
- **Version output with no parseable token, a non-zero exit, a timeout, or `PermissionError`/`OSError` on execution.** `version=None`. Unmet only if a minimum is declared, with `found="version unknown"` plus the first output line, truncated to 200 characters and passed through E002-S01-006's `redact`. *(E004/E005 pre-build re-check, 2026-11-06, G7 and G8: `found` follows the built `preflight_failure`. A non-zero exit, a timeout or an `OSError` sets `ToolStatus.error` (the reason plus the truncated first output line), which gives `"unusable (<error>)"` and fails the requirement whatever its minimum. Output with no parseable token gives `version=None` and no `error`, which fails only a declared minimum (`UNKNOWN_VERSION`). No `redact` call is made here, because the logging pipeline and the root's failure rendering already redact.)* A hung `--version` is bounded by the 10-second timeout and never blocks the Run.
- **A requirement name not in `KNOWN_TOOLS`.** `ValueError` naming it, before any `which` or probe. That includes any MySQL client name and anything an epic adds without registering.
- **An empty requirements sequence.** Returns `()`. A files-only backup without encryption needs no binary.
- **Dry Run.** Preflight is a query, so the dry-run adapter set binds the same `BinaryPreflight` instance (E002-S02-007), and a Dry Run fails exactly where the real Run would.
- **`L3IO_AGE_PASSPHRASE_BACKEND=binder` with the binder absent.** No binary requirement is emitted. Database's `check_passphrase` raises `MissingDependencyError(extra="encryption")`, and E004 maps it to `MissingExtraError` → 7. This is the extra-versus-binary separation the fourth AC requires.
- **Unsupported platform.** Refused before any other check with `tool="platform"`, `found=sys.platform` → 7.
- **Diagnostic edge cases.** A `Storage Target` whose parent directory is missing or not writable is reported, not raised. With `database=None`, the MySQL pseudo-row says the Site was not given. An extra whose metadata cannot be read (an editable install without metadata) is reported `installed=False` with `missing=("<metadata unavailable>",)`.

### Security considerations

- **What the probe runs.** It executes only allow-listed names, as resolved by `shutil.which` against the operator's `PATH`. That is the same resolution the operation itself would use, so the probe adds no new trust. The resolved absolute `path` is logged so an operator can see which binary was trusted.
- **No `shell=True`.** The argument vector is fixed (`[path, "--version"]`) and holds no credential (FR-15). *(E004/E005 pre-build re-check, 2026-11-06, G2: `[path, *version_argv]`, plus `--allow-root` for `wp` as root, all fixed data from `KNOWN_TOOLS`.)*
- **Minimal probe environment.** No passphrase file descriptor, no `L3IO_WP_BACKUP_*` variable, and no `MYSQL_*` variable reaches a probed child. A unit test spies on `subprocess.run` and asserts the `env` keys are exactly `{"PATH", "HOME", "LC_ALL"}`.
- **Probe output** is untrusted. It is truncated, redacted, and never interpreted beyond the version regex.
- **The diagnostic** prints no environment values. For `L3IO_AGE_PASSPHRASE_BACKEND` it prints the backend chosen, and for credential variables at most whether they are set, never their contents. It is covered by a `credential_sentinel` variant (E002-S01-006) that sets every credential and passphrase variable and asserts the rendered `Diagnosis`, in text and in JSON, is sentinel-free. *(E004/E005 re-check 2, 2026-11-06, M-5: "variant" means the test plants the values, not a new fixture parameter.
