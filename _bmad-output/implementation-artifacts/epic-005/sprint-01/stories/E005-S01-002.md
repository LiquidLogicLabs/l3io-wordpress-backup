# E005-S01-002: Fail before starting when a required tool is missing


**Implements:** FR-27


As an operator,
I want to be told up front that `wp` or `mysqldump` is absent,
So that I do not discover it halfway through a restore.

**Acceptance Criteria:**

**Given** a plan that requires external binaries
**When** the run begins
**Then** every required tool is checked before the first effect, not at the point of use
**And** a missing tool aborts with nothing changed, names the tool, and states why it was needed
**And** required tools and their minimum versions are documented, and a diagnostic command reports what is present
**And** an absent optional Python dependency raises a package-owned error naming the extra, rather than being folded into binary preflight

## Business acceptance criteria

### Outcome

Before a Run makes its first effect, every external binary its plan needs has been checked for presence and, where a floor is declared, for version. "First effect" means taking the Site Lock's protected actions, writing to the workspace, the Storage Target or the Site, or touching the database. This holds for a real Run and a Dry Run alike.

What the operator sees when a check fails:
- **A tool is missing or too old.** The Run stops with exit `NOT_READY` (7) and changes nothing. The message names the tool, the plan step that needed it, what was found (absent, or the version), and where to get it.
- **An optional Python extra is missing.** It is still reported at the point of use as E002's `MissingExtraError` naming the extra. Binary preflight never reports it.

The binaries this package checks itself are:
- `age` (at least 1.3) and `age-plugin-batchpass`, when a passphrase-encrypted Run would use database's CLI passphrase backend (`L3IO_AGE_PASSPHRASE_BACKEND`);
- `wp`, when Epic 7's relocation plan declares it (story 7.4).

`mysqldump` and `mysql` are **not** checked here: since ADR-0015 database's `check_dump`/`check_load` own their presence, version and skew (`CLIENT_TOOL_MISSING`, `CLIENT_SERVER_SKEW`).

Separately, a diagnostic reports:
- the Python version and the platform;
- each known tool, with presence, version and path;
- each extra, installed or not;
- optionally, a Storage Target's writability and the database findings for a Site.

A reviewer can check it worked:
- with `PATH` stripped of `age`, an encrypted Run using the CLI backend exits 7 with an empty Storage Target directory and no workspace left behind;
- the diagnostic lists `age` as absent;
- the README's external-tools table matches what the plans can require.

### Non-goals

- Checking MySQL/MariaDB client tools. Database's `check_dump`/`check_load` verify presence, version, client–server skew and `MISSING_DEPENDENCY`. They are bound as `DatabaseQuery` queries by Epic 2 (E002-S02-007) and Epic 3 (E003-S02-006 step 3). This adapter never runs, locates or names those binaries, and `tests/contracts/test_no_mysql_client.py` keeps that mechanical.
- WP-CLI semantics: its minimum version, when relocation needs it, the refusal wording that points to installation guidance, and how `wp` is invoked. Those are Epic 7's (story 7.4, `adapters/wpcli`). This adapter checks whatever `ToolRequirement` 7.4 declares, under the tool name `wp`, with no WP-CLI-specific logic.
- Selecting or validating the passphrase backend. Database's `check_passphrase`, called by Epic 4's cipher `check()` (E004-S01-003), refuses an invalid `L3IO_AGE_PASSPHRASE_BACKEND` value and a missing binder. This story only adds the `age` version floor that database does not check.
- Defining the `Preflight` port, `ToolRequirement`, `ToolStatus`, `PreflightFailedError` or the order "preflight before the first command adapter". All are Epic 2's (E002-S02-007, E002-S01-005).
- Optional Python dependencies at run time. `MissingExtraError` is raised at the import site (AD-8, E002-S01-001). The diagnostic only lists extras.
- Remote Storage Target reachability. v1.0 accepts `file:` only (AG-27).

## Technical acceptance criteria

### Interface contracts

**Files added or changed.**
- `src/l3io/wp/backup/adapters/preflight.py` (new).
- `tools/gen_tool_docs.py` (new). It follows E002-S01-005's `tools/gen_cli_docs.py`: a `--check` mode, and output written between marker comments.
- `README.md`: a new `<!-- tools:begin -->`/`<!-- tools:end -->` block, separate from E002's CLI block.
- `pyproject.toml`: `packaging` becomes a runtime dependency (Existing-library check).
- Tests, listed under Testability.

Sibling conventions:
- An adapter satisfies a port Protocol and is named for its implementation (`LocalArchiveStore`, Consistency Conventions).
- `adapters/__init__.py`'s `__all__` stays `[]`.
- No optional extra is imported at module scope (AD-8). This module imports only the stdlib and `packaging`.

**`BinaryPreflight` implements `ports/preflight.Preflight` (E002-S02-007).** `check(requirements: Sequence[ToolRequirement]) -> Sequence[ToolStatus]` is a pure query. It returns one `ToolStatus` per requirement, in the requirement order. It **never short-circuits**: every requirement is probed, so all unmet tools are visible together.

Constructor: `BinaryPreflight(*, which: Callable[[str], str | None] = shutil.which, probe: Callable[[str], str | None] = _version_output, environ: Mapping[str, str])`. The defaults are real; tests inject doubles.

For each requirement:
1. **Locate.** `which(name)` locates the binary. `None` gives `ToolStatus(present=False, version=None, path=None)`.
2. **Probe the version, only when a minimum is set.** `probe(path)` runs `[path, "--version"]` with `subprocess.run`:
   - `capture_output=True`, `text=True`, `timeout=10`, `check=False`;
   - `env` minimal: `PATH`, `HOME` and `LC_ALL=C` only. It never forwards `AGE_PASSPHRASE_FD`, `L3IO_WP_BACKUP_*`, `MYSQL_*` or any other inherited variable.
3. **Parse.** The first `\d+(?:\.\d+)+` token in the combined output is parsed with `packaging.version.Version(...).release`. The tool-specific output parsing is that one generic regex.

**The allow-list.** `KNOWN_TOOLS: Final[Mapping[str, ToolInfo]]`, where `ToolInfo(frozen)` has `purpose: str` and `install_hint: str`. Its entries are exactly `age`, `age-plugin-batchpass` and `wp`; `wp` is the name Epic 7's story 7.4 must use.
- A requirement whose name is not in `KNOWN_TOOLS` raises `ValueError`. That is a programming error, raised before anything is executed.
- So this adapter can never be handed a MySQL client name and run it. It also never writes one as a literal, which keeps `tests/contracts/test_no_mysql_client.py` green.
- The minimum version is **not** in `KNOWN_TOOLS`. The requirement emitted by the plan is the only floor, so a declaring epic never edits this module to change one.

**`passphrase_backend_requirements(*, environ: Mapping[str, str], needed_for: str) -> tuple[ToolRequirement, ...]`.** It follows database's documented backend selection (README and ADR-0003 at `47384ba`: `auto` prefers the `l3io-age-passphrase` binder, else `age` plus `age-plugin-batchpass`; `cli` requires them).
- **No binary requirement:** returns `()` for `binder`, and for `auto` (or unset) when `importlib.util.find_spec("l3io_age_passphrase")` is not `None`. The binder is detected without being imported.
- **CLI backend:** returns `(ToolRequirement("age", (1, 3), needed_for), ToolRequirement("age-plugin-batchpass", None, needed_for))` for `cli`, and for `auto` when the binder is absent.
- **Unrecognised value:** returns `()` and leaves validation to database's `check_passphrase` (through E004's cipher `check()`), so the value is validated in one place.

Who calls it: the composition root, only when the cipher is in passphrase mode, appending the result to the plan's `required_tools` before calling `check`. It reads only the `environ` it is given.

**`unsupported_platform(platform: str = sys.platform) -> str | None`.** Returns a reason for `win32`/`cygwin`, else `None`. The Stack row says "Windows is unsupported in v1.x and refused at preflight". The root raises `PreflightFailedError` with `tool="platform"` when it is not `None`, before any other check. Database's `PLATFORM_UNSUPPORTED` covers only database-touching Runs; this covers files-only Runs too.

**`diagnose(...) -> Diagnosis`, the FR-27 diagnostic command's data.** Signature: `diagnose(*, preflight: Preflight, environ: Mapping[str, str], target: StorageTarget | None = None, database: Readiness | None = None) -> Diagnosis`.

`Diagnosis` is frozen, with a `to_dict()` that is JSON-serialisable. Its fields:
- `python: str` (`platform.python_version()`);
- `platform: str`, `platform_supported: bool`;
- `tools: tuple[ToolStatus, ...]`, covering every `KNOWN_TOOLS` entry, plus a pseudo-row for MySQL clients that states "checked per Site by l3io-wordpress-database (`check_dump`/`check_load`)", carries `database`'s finding codes when given, and never runs anything;
- `passphrase_backend: str`, the backend `passphrase_backend_requirements` implies;
- `extras: tuple[ExtraStatus(name, installed, missing: tuple[str, ...]), ...]`;
- `storage_target: TargetStatus(path, exists, writable) | None`;
- `ready: bool`.

How `extras` is derived: from the installed distribution's own metadata, never a hand-kept list. The source is `importlib.metadata.metadata("l3io-wordpress-backup").get_all("Provides-Extra")`, with each `requires()` entry parsed by `packaging.requirements.Requirement`, filtered by `marker.evaluate({"extra": name})`, and checked with `importlib.metadata.version` against `specifier.contains`.

How `database` arrives: as E002-S02-007's `Readiness`, computed by the caller's `DatabaseQuery.check_dump`. This module calls no database function.

**Documented minimums (FR-27's first consequence).** `tools/gen_tool_docs.py` renders the README table from:
- the requirements the plan builders can emit, enumerated over `BackupScope` from the enum, and once present over `RestoreMode` and relocation;
- `passphrase_backend_requirements(...)` for each of `binder`, `cli` and `auto`-without-binder;
- each tool's `purpose` and `install_hint` from `KNOWN_TOOLS`;
- one fixed row pointing MySQL/MariaDB clients at database's documented floor (client 8.4+, MariaDB 11.4; Stack).

CI runs `tools/gen_tool_docs.py --check` beside `gen_cli_docs.py --check` and fails on drift.

**Errors.** No new error class and no new `ExitCode`:
- A missing or too-old tool is E002's `PreflightFailedError(tool, needed_for, found)` → `NOT_READY`.
- A probe failure is data, not an exception: `present=True, version=None`. A requirement with a minimum then counts as unmet, with `found="version unknown"`.

### Error and edge case handling

- **Tool absent.** `present=False`. The root raises `PreflightFailedError(tool, needed_for, found="absent")` → 7. That happens before the first command adapter, so the Storage Target, the Site and the database are untouched, and the workspace is removed by its `finally` (AD-12).
- **Several tools unmet.** Every unmet requirement is logged at ERROR, so the operator sees all of them in one Run. The raised error names the first in plan order, because E002's error carries one tool.
- **Version below the minimum.** `found="<version>"`, and the message states the minimum. For example, `age 1.2.1 found; 1.3 or later is needed for ENCRYPT (passphrase, CLI backend)`.
- **Version output with no parseable token, a non-zero exit, a timeout, or `PermissionError`/`OSError` on execution.** `version=None`. Unmet only if a minimum is declared, with `found="version unknown"` plus the first output line, truncated to 200 characters and passed through E002-S01-006's `redact`. A hung `--version` is bounded by the 10-second timeout and never blocks the Run.
- **A requirement name not in `KNOWN_TOOLS`.** `ValueError` naming it, before any `which` or probe. That includes any MySQL client name and anything an epic adds without registering.
- **An empty requirements sequence.** Returns `()`. A files-only backup without encryption needs no binary.
- **Dry Run.** Preflight is a query, so the dry-run adapter set binds the same `BinaryPreflight` instance (E002-S02-007), and a Dry Run fails exactly where the real Run would.
- **`L3IO_AGE_PASSPHRASE_BACKEND=binder` with the binder absent.** No binary requirement is emitted. Database's `check_passphrase` raises `MissingDependencyError(extra="encryption")`, and E004 maps it to `MissingExtraError` → 7. This is the extra-versus-binary separation the fourth AC requires.
- **Unsupported platform.** Refused before any other check with `tool="platform"`, `found=sys.platform` → 7.
- **Diagnostic edge cases.** A `Storage Target` whose parent directory is missing or not writable is reported, not raised. With `database=None`, the MySQL pseudo-row says the Site was not given. An extra whose metadata cannot be read (an editable install without metadata) is reported `installed=False` with `missing=("<metadata unavailable>",)`.

### Observability requirements

- One record per requirement, `preflight_checked`, with:
  - `tool`, `present`, `version` (dotted string or `null`), `path`, `minimum`, `needed_for`;
  - `outcome`: one of `ok`, `missing`, `too_old` or `version_unknown`.
- Level is DEBUG for `ok` and ERROR otherwise.
- One `preflight_completed` record per Run carries `checked` (count), `unmet` (list of tool names) and `duration_ms`.
- Records carry the Run ID through `merge_contextvars`, and UTC ISO-8601 timestamps (E002-S01-004). Nothing in this module configures logging.
- Probe output is logged only on failure, truncated and redacted (above).
- Spans for the `PREFLIGHT` phase are Epic 6's (`adapters/tracing`). This adapter emits none.
- The diagnostic emits no log records of its own beyond the `preflight_checked` records of its `check` call. Its output is the rendered `Diagnosis`.

### Security considerations

- **What the probe runs.** It executes only allow-listed names, as resolved by `shutil.which` against the operator's `PATH`. That is the same resolution the operation itself would use, so the probe adds no new trust. The resolved absolute `path` is logged so an operator can see which binary was trusted.
- **No `shell=True`.** The argument vector is fixed (`[path, "--version"]`) and holds no credential (FR-15).
- **Minimal probe environment.** No passphrase file descriptor, no `L3IO_WP_BACKUP_*` variable, and no `MYSQL_*` variable reaches a probed child. A unit test spies on `subprocess.run` and asserts the `env` keys are exactly `{"PATH", "HOME", "LC_ALL"}`.
- **Probe output** is untrusted. It is truncated, redacted, and never interpreted beyond the version regex.
- **The diagnostic** prints no environment values. For `L3IO_AGE_PASSPHRASE_BACKEND` it prints the backend chosen, and for credential variables at most whether they are set, never their contents. It is covered by a `credential_sentinel` variant (E002-S01-006) that sets every credential and passphrase variable and asserts the rendered `Diagnosis`, in text and in JSON, is sentinel-free.

### Testability approach

`tests/unit/adapters/test_preflight.py` follows E002's `tests/unit/<layer>/test_<module>.py` naming. It uses injected `which`/`probe` doubles and needs no real binaries. It covers:
- present at the minimum, present above it, absent, too old, unparseable output, non-zero exit, and timeout (a `probe` double raising `subprocess.TimeoutExpired`);
- the order of `ToolStatus` and that nothing short-circuits (a recording `which` sees every name);
- an unknown name raising `ValueError` before any `which` call;
- the env-key spy described under Security;
- a test that runs the real default probe against a temporary executable script printing `v1.3.1`, so the default `_version_output` is exercised without real `age`.

`passphrase_backend_requirements` is tested for each of `binder`, `cli`, `auto` and unset, with and without the binder. Binder absence is simulated via `monkeypatch` of `importlib.util.find_spec`. An invalid value returns `()`.

`unsupported_platform` is parametrised over `linux`, `darwin`, `win32` and `cygwin`.

`diagnose` is tested against the installed distribution's real metadata. A scope assertion checks that `extras` is non-empty and equals `Provides-Extra`.

`tests/contracts/test_tool_requirements_documented.py` derives its scope from the source of truth:
- it builds every plan the package can build, `BackupScope` from the enum crossed with plain or passphrase-encrypted;
- it collects `required_tools` together with `passphrase_backend_requirements` for every backend value;
- it asserts that every name is in `KNOWN_TOOLS` and in the generated README table, with the same minimum.

It is a tripwire like E002-S01-006's: it fails once `core/restore` exists (Epic 3) or relocation emits requirements (Epic 7) without their enumeration being added. A planted-violation case adds a requirement named `zz-fake` to a temporary plan and asserts the check fails.

`tests/contracts/test_cli_docs.py`'s sibling, `tests/contracts/test_tool_docs.py`, runs `tools/gen_tool_docs.py --check`.

`tests/integration/test_preflight_refusal.py` is marked `@pytest.mark.integration`. It runs a real passphrase-encrypted backup with `L3IO_AGE_PASSPHRASE_BACKEND=cli` and a `PATH` containing a fake `age` that prints `age v1.2.0`. It asserts:
- exit 7;
- the message names `age`, `1.3` and the step;
- the Storage Target directory is unchanged, and no `l3io-wp-backup-*` workspace remains;
- the recording command adapters were never called.

The "before the first command adapter" order itself is E002-S02-007's `tests/unit/cli/test_preflight_order.py`. This story reuses that test with `BinaryPreflight` bound, once the composition-root OPEN is resolved.

### Existing-library check

- **Locating binaries:** stdlib `shutil.which`, as E002-S02-007 anticipates.
- **Running the probe:** stdlib `subprocess.run` with `timeout`.
- **Version parsing and comparison:** `packaging` (`packaging.version.Version`). The global rule forbids hand-rolled version comparison. `packaging` 26.3 was verified as the current PyPI release on 2026-10-27 (licence Apache-2.0 OR BSD-2-Clause). It is already in `uv.lock` as a dev dependency (`packaging>=25.0`) and becomes a runtime dependency as `packaging>=25,<27`, with no new transitive dependencies.
- **Extras inspection:** stdlib `importlib.metadata`, with `packaging.requirements.Requirement` and markers for parsing `Requires-Dist`. No regex parser of requirement strings is written.
- **Binder detection:** stdlib `importlib.util.find_spec`.

Database (rev `47384ba`) already covers MySQL client presence, version and skew (`check_dump`/`check_load`, `Code.CLIENT_TOOL_MISSING`/`CLIENT_SERVER_SKEW`/`MISSING_DEPENDENCY`) and passphrase backend selection (`check_passphrase`). Both are used, not duplicated. Database's backend resolver (`_passphrase.resolve_backend`) and tool finder (`_client.find_tool`) are private, so `passphrase_backend_requirements` restates the documented `auto`/`binder`/`cli` rule in about 10 lines. If database later exports a public backend query, this function is replaced by a call to it.

Custom code is limited to the allow-list, the generic version-token regex, and the `Diagnosis` assembly.
