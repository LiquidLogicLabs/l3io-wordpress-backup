# E005-S01-001: Source credentials from somewhere other than the command line


**Implements:** FR-14


As an operator,
I want credentials to come from my environment or the site's own config,
So that I do not have to put them in a cron line.

**Acceptance Criteria:**

**Given** the declared resolution order — explicit argument, environment, `wp-config.php`
**When** credentials are needed
**Then** resolution is deterministic and documented, and each source is selectable from both the CLI and the library
**And** resolution is an explicit call returning a frozen value, never a property getter performing I/O (AD-9)
**And** no provider silently substitutes one credential for another — absent admin credentials is an error naming what is missing
**And** a library caller can supply their own provider without subclassing an internal type
**And** the chain is composed from `l3io-wp-database`'s `CredentialChain` (first present wins; a failing provider stops the chain), not a second implementation here

## Business acceptance criteria

### Outcome

An operator can run `wpbackup2 backup --wp-dir <Site Root>` from cron with no credential on the command line. The WordPress database credentials come from `L3IO_WP_BACKUP_DB_USER`/`L3IO_WP_BACKUP_DB_PASSWORD` when both are set, and otherwise from the Site's `wp-config.php`. A restore that needs administrator rights takes them from the frozen `--admin-username`/`--admin-password` flags, from AWS Secrets Manager (`--admin-credentials-aws-secret-id`, optional `--admin-credentials-aws-region`), or from `L3IO_WP_BACKUP_ADMIN_USER`/`L3IO_WP_BACKUP_ADMIN_PASSWORD`. It never takes them from `wp-config.php` and never falls back to the WordPress account. A library caller can pass any object that satisfies `l3io-wp-database`'s `CredentialSource` Protocol (`source` label plus `resolve()`), including a class of their own that subclasses nothing. *(E004/E005 pre-build re-check, 2026-11-06, F1, F2 and F8: the last sentence is superseded. A library caller passes a backup-owned `CredentialSpec`, either `ExplicitCredentialSpec(username, password)` or `AwsSecretCredentialSpec(secret_id, region)`, as `BackupRequest.credentials` or `RestoreRequest.admin`, or sets the environment variables. Custom providers wait for v1.1 (PRD §13.2). Until E008-S01-001 binds the AWS flags, the AWS administrator source is selectable through the library only; the cron line above already needs none of them.)*

Precedence is fixed and written down: explicit argument, then environment, then `wp-config.php`. Administrator credentials have no `wp-config.php` step. Every chain is a `l3io.wp.database.CredentialChain`, so the rule is database's: the first source with an answer wins, and a source that *failed* stops the chain. This package writes no chain of its own.

A reviewer can check it worked:
- each source wins when the sources before it are absent;
- a half-set environment pair fails rather than falling through to `wp-config.php`;
- a restore with no administrator source is refused, naming the flags and the variables it accepts;
- the winning source's label, never its value, appears in the Run's log.

- **`wordpress_credentials(spec: CredentialSpec | None, *, wp_config: CredentialSource, environ: Mapping[str, str], secrets: SecretRegistry) -> CredentialSource`.**
  - It returns `CredentialChain(*steps)`, in `domain/credentials.py::WORDPRESS_CREDENTIAL_PRECEDENCE` order.
  - The explicit step comes from the spec. `ExplicitCredentialSpec` becomes `Explicit(username, password)`, with the password registered into `secrets` at construction, the rule the built `adapters/database.py::_explicit` follows. `AwsSecretCredentialSpec` becomes `AwsSecretsManager(secret_id, region)`. `None` means no explicit step.
  - Then `Environment(WORDPRESS_USER_VAR, WORDPRESS_PASSWORD_VAR)`.

**`adapters/credential_providers.py`.**

*Environment variable names*, each `Final[str]`, namespaced like E002-S01-006's `L3IO_WP_BACKUP_PASSPHRASE`:
- `WORDPRESS_USER_VAR = "L3IO_WP_BACKUP_DB_USER"`
- `WORDPRESS_PASSWORD_VAR = "L3IO_WP_BACKUP_DB_PASSWORD"`
- `ADMIN_USER_VAR = "L3IO_WP_BACKUP_ADMIN_USER"`
- `ADMIN_PASSWORD_VAR = "L3IO_WP_BACKUP_ADMIN_PASSWORD"`

Database's default `DB_USER`/`DB_PASSWORD` are deliberately not used. Those names are generic enough that an unrelated tool on the host may already have set them, which would silently win over `wp-config.php`.

*`wordpress_credentials(*, explicit: CredentialSource | None, wp_config: CredentialSource) -> CredentialSource`* *(superseded: the built seam above, F1)* returns `CredentialChain(*sources)`, built from:
- `explicit`, when given. This is the library's `credentials=` argument.
- `Environment(WORDPRESS_USER_VAR, WORDPRESS_PASSWORD_VAR)`.
- `wp_config`, the `WpConfigFile` from E002-S01-001.

The function does no I/O and calls no `resolve()`. It returns a chain even when only `wp_config` is present, so the label format is the same on every path.

*`admin_credentials(*, explicit: CredentialSource | None = None, username: str | None = None, password: str | None = None, aws_secret_id: str | None = None, aws_region: str | None = None, environ: Mapping[str, str]) -> CredentialSource | None`* *(superseded: the built seam above; flag validation is `cli/credentials.py::admin_spec`'s, F1 and F4)*:
- **Explicit step.** Take exactly one of `explicit` (the library's `admin=`), the `username` pair (`--admin-username`, `--admin-password`), or `AwsSecretsManager(aws_secret_id, aws_region)`. More than one raises `CredentialSourceConflictError`, which names the arguments that were given.
- **Username without a password.** `username` given without `password` takes the password from `environ[ADMIN_PASSWORD_VAR]`. The operator named the account, so this is a choice, not a substitution, and it matches database's own `--admin-user` plus `--admin-password-env`. If the variable is unset, `CredentialsError` names `--admin-password` and `ADMIN_PASSWORD_VAR`.
- **Password without a username.** `password` without `username` raises `CredentialSourceConflictError`.
- **`aws_region` without `aws_secret_id`.** Also `CredentialSourceConflictError`.
- **Environment step.** `Environment(ADMIN_USER_VAR, ADMIN_PASSWORD_VAR)`.
- **No `wp-config.php` step, ever.**
- **Return value.** `None` when no explicit argument is given and neither admin variable is set in `environ`. The caller then has no administrator source, and the AD-9 refusal is raised where one is needed (below). Otherwise it returns `CredentialChain(...)` over the steps present.

`environ` is passed in; the CLI passes `os.environ`. This mirrors `resolve_passphrase` (E002-S01-006), so only the composition root reads the process environment to decide which steps exist. Database's `Environment.resolve()` still reads `os.environ` when the chain resolves. That is database's documented behaviour and is not reimplemented. The library root passes the same `os.environ`, so both roots see the same process state.

*`CREDENTIAL_PRECEDENCE: Final = ("explicit", "environment", "wp-config")`* is the documented order *(superseded: not declared; imported as `domain/credentials.py::WORDPRESS_CREDENTIAL_PRECEDENCE`, F3)*. `ADMIN_CREDENTIAL_PRECEDENCE: Final = ("explicit", "environment")`. Both builders take their step order from these tuples, so the documentation and the code read one value.

*Custom providers (FR-14).* *(Deferred to v1.1, PRD §13.2; this paragraph is not built, F2.)* A library caller's object needs only `source: str` and `resolve() -> ResolvedCredentials`. It is checked with `isinstance(obj, CredentialSource)`; database's Protocol is `@runtime_checkable`. A non-conforming object raises `TypeError` at build time, never at resolve time. To signal "nothing here, try the next source", a custom provider raises `l3io.wp.database.CredentialsAbsentError`. Any other exception stops the chain. Epic 6 (E006-S01-001, E006-S01-003) decides whether `api/` re-exports `CredentialSource`, `ResolvedCredentials`, `Explicit`, `Environment`, `AwsSecretsManager` and `CredentialsAbsentError`. This story names them as the types a custom provider touches.

*Error classes.* *(Superseded: no `CredentialSourceConflictError`; the built `admin_spec` raises `UsageError`, F4.)* `CredentialSourceConflictError(UsageError)` maps to `USAGE` and carries `given: tuple[str, ...]`. It is declared here, subclassing E002-S01-005's `UsageError` and inheriting its `exit_code`. It adds no `ExitCode` and no edit to `cli/exit.py`. `CredentialsError` is E002-S01-001's.

**`pyproject.toml`.** Add the `aws` extra: `aws = ["l3io-wordpress-database[aws]>=0.1.0,<0.2"]`, matching how the `database` extra is pinned *(superseded: `>=0.3.2,<0.4`, F7)*. `boto3` stays out of the base install, transitively too (FR-14's second consequence). ### Error and edge case handling

How resolution failures map:
- **Both WordPress variables set:** the environment wins over `wp-config.php`, even when the two disagree. `wp-config.php` is never opened for credentials; it is still read for host and database name, by E002-S01-001.
- **Only one WordPress variable set:** database's `Environment` raises `CredentialsUnobtainableError`, a failure and not an absence, so the chain stops. It does **not** fall through to `wp-config.php`. The Epic 2 adapter re-raises it as `CredentialsError` (`CREDENTIALS`, 4), naming the unset variable. A unit test asserts that `wp-config.php`'s `resolve()` was never called.
- **WordPress variables unset, and `wp-config.php` defines neither `DB_USER` nor `DB_PASSWORD`:** the chain raises `CredentialsAbsentError` with `sources` listing every step tried. This is re-raised as `CredentialsError` naming each source label.
- **No administrator source anywhere:** `admin_credentials` returns `None`. A plan that needs administrator rights is refused with `AdminCredentialsRequiredError` → `CREDENTIALS` before any phase after `VERIFY` (E003-S02-006). The WordPress credentials are never tried in its place. A plan that does not need them, such as a backup or a files-only restore, proceeds.
- **Only one administrator variable set:** this is a failure (`CredentialsUnobtainableError` → `CredentialsError`), not "no administrator source". The operator meant to supply one.
- **AWS:** *(E004/E005 pre-build re-check, 2026-11-06, F6: reachable only through this story's edit to `adapters/database.py`'s handlers, which read `exc.extra` and catch `RegionNotKnownError` first. The built handlers map every `MissingDependencyError` to `extra="database"` and every `CredentialsUnobtainableError` to a bare `CredentialsError(source)`.)* If `boto3` is absent, database raises `MissingDependencyError(extra="aws")`, re-raised as E002's `MissingExtraError(extra="aws")` → `NOT_READY` (7). If AWS has no region, database raises `RegionNotKnownError`, re-raised as `CredentialsError` naming `--admin-credentials-aws-region` (or `--db-credentials-aws-region` for the WordPress account). If the secret is unreadable or malformed, database raises `CredentialsUnobtainableError`, re-raised as `CredentialsError` naming the secret id, never its content. In every AWS case the chain stops; there is no fall-through to the environment.

Argument and input problems:
- **Conflicting explicit arguments** (flags plus an AWS secret id, `--admin-password` without `--admin-username`, `--admin-credentials-aws-region` alone, or library `admin=` plus flags): `CredentialSourceConflictError` → `USAGE` (2), raised while the request is being built, before the Site Lock or any read of the Site. *(E004/E005 pre-build re-check, 2026-11-06, F4: the built `cli/credentials.py::admin_spec`/`wordpress_spec` raise `UsageError` (2) for these combinations while the request is built. That includes a username with no password from either the flag or `L3IO_WP_BACKUP_ADMIN_PASSWORD`, which is `UsageError` (2), not `CredentialsError` (4). A library caller builds one spec, so it cannot pass two. This story adds no error class.)*
- **Empty string values:** an empty value in a variable is passed to database as is. Database's `Environment` treats `""` as set, and the account then fails authentication with `CREDENTIALS`. This story does not reinterpret it. The behaviour is stated in the docstring so it is not mistaken for absence. *(E004/E005 pre-build re-check, 2026-11-06, F4: this holds for the `Environment` steps. One built exception: `admin_spec`'s `--admin-password` fallback reads an empty `L3IO_WP_BACKUP_ADMIN_PASSWORD` as unset (`cli/credentials.py` L70). The docstring states both.)*
- **Custom provider that is not a `CredentialSource`:** `TypeError` from the builder (a programming error), before any I/O. *(E004/E005 pre-build re-check, 2026-11-06, F2: deferred to v1.1 with custom providers. This bullet and the next are not built.)*
- **Custom provider that raises an arbitrary exception:** the chain stops, and Epic 2's adapter re-raises it as `CredentialsError` with `raise … from`. The message carries the source label and exception class, never the exception's text (AD-14; E002-S01-006).
- **Dry Run:** the same chains are built and resolved for real (E002-S02-007: "credential resolution … execute[s] for real"). A Dry Run fails exactly where the real Run would.

### Security considerations

Exposure of each source:
- **Environment variables.** `/proc/<pid>/environ` is readable by the same user and by root. The README section on credentials says so, as database's CLI documents its own variables, and recommends `wp-config.php` or AWS for shared hosts.
- **The frozen `--admin-password` flag.** Its value is visible in `ps` to every user on the machine. That is the v0.2.21 behaviour, kept by AD-22. The flag's `--help` text says so and points to `L3IO_WP_BACKUP_ADMIN_PASSWORD`; that help text is Epic 2's (part of the composition-root OPEN). This story's purpose is that no cron line needs the flag.

No substitution and no fallback (AD-9, AD-29, FR-15):
- `admin_credentials` has no `wp-config.php` step and never receives the WordPress chain. A unit test asserts that no `WpConfigFile` or WordPress-role `Environment` appears among its sources for any combination of inputs.
- The chain stops on failure (database's rule), so a mistyped secret id cannot quietly become the environment's account.

Handling of values:
- Nothing here reads, logs or holds a password value, except building `Explicit(username, password)` from arguments or `environ`. That object's `repr` is redacted by database. Registration with the `SecretRegistry` happens in the adapter that calls `resolve()` (E002-S01-006). A `credential_sentinel` variant plants the sentinel in `L3IO_WP_BACKUP_DB_PASSWORD` and in `L3IO_WP_BACKUP_ADMIN_PASSWORD`, and asserts it is absent from every captured output. *(E004/E005 re-check 2, 2026-11-06, M-5: "variant" means the test plants it, not a new fixture parameter. The built fixture takes only `{"passphrase": True}`, and `tests/conftest.py` is outside this story's grant; E004-S01-003 edits it in the same phase. The test calls `credential_sentinel.monkeypatch.setenv(WORDPRESS_PASSWORD_VAR, credential_sentinel.password)`, and likewise for `ADMIN_PASSWORD_VAR`, with the user variables set beside them.)*
- The new walked `__repr__` contract (E002-S01-006) covers anything in this module annotated with `CredentialSource` or `password`. This module defines no such class, and the test confirms that rather than assuming it.
