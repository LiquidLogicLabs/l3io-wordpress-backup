# E005-S01-001: Source credentials from somewhere other than the command line


**Implements:** FR-14


As an operator,
I want credentials to come from my environment or the site's own config,
So that I do not have to put them in a cron line.

**Acceptance Criteria:**

**Given** the declared resolution order — explicit argument, environment, `wp-config.php`
**When** credentials are needed
**Then** resolution is deterministic and documented, and each source is selectable from both the CLI and the library
**And** resolution is an explicit call returning a frozen value, never a property getter performing I/O (AD-9)
**And** no provider silently substitutes one credential for another — absent admin credentials is an error naming what is missing
**And** a library caller can supply their own provider without subclassing an internal type
**And** the chain is composed from `l3io-wp-database`'s `CredentialChain` (first present wins; a failing provider stops the chain), not a second implementation here

## Business acceptance criteria

### Outcome

An operator can run `wpbackup2 backup --wp-dir <Site Root>` from cron with no credential on the command line. The WordPress database credentials come from `L3IO_WP_BACKUP_DB_USER`/`L3IO_WP_BACKUP_DB_PASSWORD` when both are set, and otherwise from the Site's `wp-config.php`. A restore that needs administrator rights takes them from the frozen `--admin-username`/`--admin-password` flags, from AWS Secrets Manager (`--admin-credentials-aws-secret-id`, optional `--admin-credentials-aws-region`), or from `L3IO_WP_BACKUP_ADMIN_USER`/`L3IO_WP_BACKUP_ADMIN_PASSWORD`. It never takes them from `wp-config.php` and never falls back to the WordPress account. A library caller can pass any object that satisfies `l3io-wp-database`'s `CredentialSource` Protocol (`source` label plus `resolve()`), including a class of their own that subclasses nothing.

Precedence is fixed and written down: explicit argument, then environment, then `wp-config.php`. Administrator credentials have no `wp-config.php` step. Every chain is a `l3io.wp.database.CredentialChain`, so the rule is database's: the first source with an answer wins, and a source that *failed* stops the chain. This package writes no chain of its own.

A reviewer can check it worked:
- each source wins when the sources before it are absent;
- a half-set environment pair fails rather than falling through to `wp-config.php`;
- a restore with no administrator source is refused, naming the flags and the variables it accepts;
- the winning source's label, never its value, appears in the Run's log.

### Non-goals

- A second chain or a backup-owned provider type. `Explicit`, `Environment`, `AwsSecretsManager`, `WpConfigFile` and `CredentialChain` are database's (rev `47384ba`) and are used as they are. This story adds no class that implements `resolve()`.
- Credential transport to client tools, redaction, and the `credential_sentinel` fixture: E002-S02-004. This story registers nothing itself; the adapter that calls `resolve()` does.
- Reading `wp-config.php` and building the Site Descriptor: E002-S01-001's `site_descriptor_from_wp_config`. This story receives the `WpConfigFile` source that function returns.
- Calling `resolve()`, binding sources into `adapters/database`, and the `AdminCredentialsRequiredError` raise site: Epic 2 (E002-S01-001, E002-S02-007, E002-S02-009) and Epic 3 (E003-S02-004).
- A TTY password prompt for administrator credentials. Database's own CLI has one; this package's CLI does not add one in this story.
- New CLI flags. The frozen surface (AD-22) is not changed here (see OPEN under Interface contracts).
- Relocation's target credentials (`--new-db-user`/`--new-db-password`): Epic 7.
- Other secret stores (Vault, GCP, Azure): a library caller supplies them as a custom `CredentialSource`.

## Technical acceptance criteria

### Interface contracts

**Files added or changed.**
- `src/l3io/wp/backup/adapters/credential_providers.py` (new).
- `pyproject.toml`: a new `aws` extra.
- `tests/unit/adapters/test_credential_providers.py` (new).
- `tests/contracts/test_single_credential_chain.py` (new).

Sibling conventions:
- `adapters/__init__.py` says "an adapter *holds* a core object and satisfies a Protocol; it never subclasses". `__all__` stays `[]` there; the public surface is Epic 6's `api/`.
- `l3io.wp.database` is the optional `database` extra. E002-S01-001 sets the rule that it is imported **inside the functions that use it**, never at module scope (AD-8). Type names used in signatures come from an `if TYPE_CHECKING:` import.
- The module docstring states the AD-1 layer (`adapters`) and what it may import.

**`adapters/credential_providers.py`.**

*Environment variable names*, each `Final[str]`, namespaced like E002-S02-004's `L3IO_WP_BACKUP_PASSPHRASE`:
- `WORDPRESS_USER_VAR = "L3IO_WP_BACKUP_DB_USER"`
- `WORDPRESS_PASSWORD_VAR = "L3IO_WP_BACKUP_DB_PASSWORD"`
- `ADMIN_USER_VAR = "L3IO_WP_BACKUP_ADMIN_USER"`
- `ADMIN_PASSWORD_VAR = "L3IO_WP_BACKUP_ADMIN_PASSWORD"`

Database's default `DB_USER`/`DB_PASSWORD` are deliberately not used. Those names are generic enough that an unrelated tool on the host may already have set them, which would silently win over `wp-config.php`.

*`wordpress_credentials(*, explicit: CredentialSource | None, wp_config: CredentialSource) -> CredentialSource`* returns `CredentialChain(*sources)`, built from:
- `explicit`, when given. This is the library's `credentials=` argument.
- `Environment(WORDPRESS_USER_VAR, WORDPRESS_PASSWORD_VAR)`.
- `wp_config`, the `WpConfigFile` from E002-S01-001.

The function does no I/O and calls no `resolve()`. It returns a chain even when only `wp_config` is present, so the label format is the same on every path.

*`admin_credentials(*, explicit: CredentialSource | None = None, username: str | None = None, password: str | None = None, aws_secret_id: str | None = None, aws_region: str | None = None, environ: Mapping[str, str]) -> CredentialSource | None`*:
- **Explicit step.** Take exactly one of `explicit` (the library's `admin=`), the `username` pair (`--admin-username`, `--admin-password`), or `AwsSecretsManager(aws_secret_id, aws_region)`. More than one raises `CredentialSourceConflictError`, which names the arguments that were given.
- **Username without a password.** `username` given without `password` takes the password from `environ[ADMIN_PASSWORD_VAR]`. The operator named the account, so this is a choice, not a substitution, and it matches database's own `--admin-user` plus `--admin-password-env`. If the variable is unset, `CredentialsError` names `--admin-password` and `ADMIN_PASSWORD_VAR`.
- **Password without a username.** `password` without `username` raises `CredentialSourceConflictError`.
- **`aws_region` without `aws_secret_id`.** Also `CredentialSourceConflictError`.
- **Environment step.** `Environment(ADMIN_USER_VAR, ADMIN_PASSWORD_VAR)`.
- **No `wp-config.php` step, ever.**
- **Return value.** `None` when no explicit argument is given and neither admin variable is set in `environ`. The caller then has no administrator source, and the AD-9 refusal is raised where one is needed (below). Otherwise it returns `CredentialChain(...)` over the steps present.

`environ` is passed in; the CLI passes `os.environ`. This mirrors `resolve_passphrase` (E002-S02-004), so only the composition root reads the process environment to decide which steps exist. Database's `Environment.resolve()` still reads `os.environ` when the chain resolves. That is database's documented behaviour and is not reimplemented. The library root passes the same `os.environ`, so both roots see the same process state.

*`CREDENTIAL_PRECEDENCE: Final = ("explicit", "environment", "wp-config")`* is the documented order. `ADMIN_CREDENTIAL_PRECEDENCE: Final = ("explicit", "environment")`. Both builders take their step order from these tuples, so the documentation and the code read one value.

*Custom providers (FR-14).* A library caller's object needs only `source: str` and `resolve() -> ResolvedCredentials`. It is checked with `isinstance(obj, CredentialSource)`; database's Protocol is `@runtime_checkable`. A non-conforming object raises `TypeError` at build time, never at resolve time. To signal "nothing here, try the next source", a custom provider raises `l3io.wp.database.CredentialsAbsentError`. Any other exception stops the chain. Epic 6 (E006-S01-001, E006-S01-003) decides whether `api/` re-exports `CredentialSource`, `ResolvedCredentials`, `Explicit`, `Environment`, `AwsSecretsManager` and `CredentialsAbsentError`. This story names them as the types a custom provider touches.

*Error classes.* `CredentialSourceConflictError(UsageError)` maps to `USAGE` and carries `given: tuple[str, ...]`. It is declared here, subclassing E002-S02-006's `UsageError` and inheriting its `exit_code`. It adds no `ExitCode` and no edit to `cli/exit.py`. `CredentialsError` is E002-S01-001's.

**`pyproject.toml`.** Add the `aws` extra: `aws = ["l3io-wordpress-database[aws]>=0.1.0,<0.2"]`, matching how the `database` extra is pinned. `boto3` stays out of the base install, transitively too (FR-14's second consequence). The existing comment block on why family packages are extras applies unchanged.

**OPENs.**

- OPEN: **the resolution order is to be "declared in `domain/`"** (AD-9; Consistency Conventions "Config"). `domain/` is Epic 2's, and no E002 story declares a credential precedence. This story declares `CREDENTIAL_PRECEDENCE` in `adapters/credential_providers.py`. Recommended resolution: Epic 2 adds `domain/credentials.py` with `CredentialOrigin(StrEnum)` (`EXPLICIT`, `ENVIRONMENT`, `WP_CONFIG`) and the two precedence tuples. This module would then import them, and the test below would assert against the domain value.
- OPEN: **composition-root wiring is in modules this epic does not own.**
  - `cli/backup.py` and `cli/context.py::real_adapters` (Epic 2) must pass `wordpress_credentials(...)`'s chain to `adapters/database` in place of the bare `WpConfigFile`. They must also build the administrator source with `admin_credentials(...)`, using `--admin-credentials-aws-secret-id`/`--admin-credentials-aws-region`. Those flags are registered by E002-S02-006 as accepted-but-not-implemented.
  - `cli/restore.py::run_restore` (Epic 3, E003-S01-006) builds `RestoreRequest.admin` as a bare `Explicit` today. It must call `admin_credentials(...)` instead; E003-S01-006 lists AWS administrator credentials as Epic 5's.
  - `AdminCredentialsRequiredError` (E002-S02-007 / E003-S02-004) must name `ADMIN_USER_VAR`/`ADMIN_PASSWORD_VAR` and `--admin-credentials-aws-secret-id` beside the two flags.
  - No E002 or E003 story provides any of this. It is a dependency on both, not an edit here.
- OPEN: **FR-14's "each built-in provider is selectable from the CLI", for the WordPress account.** The environment and `wp-config.php` steps are selectable on the CLI without a flag: set the variables, or don't. Explicit WordPress credentials and AWS Secrets Manager for the WordPress account have no flag in the frozen v0.2.21 surface (AD-22), and `cli/parser.py` is Epic 2's. Recommended resolution: Epic 2 registers `--db-credentials-aws-secret-id`/`--db-credentials-aws-region`, which is additive and therefore a minor change under §10. It adds no flag that takes a password value, matching database's CLI rule that "no option takes a password value". Alternatively, decide that FR-14's CLI selectability is met for the WordPress account by the environment and `wp-config.php` steps alone.

### Error and edge case handling

How resolution failures map:
- **Both WordPress variables set:** the environment wins over `wp-config.php`, even when the two disagree. `wp-config.php` is never opened for credentials; it is still read for host and database name, by E002-S01-001.
- **Only one WordPress variable set:** database's `Environment` raises `CredentialsUnobtainableError`, a failure and not an absence, so the chain stops. It does **not** fall through to `wp-config.php`. The Epic 2 adapter re-raises it as `CredentialsError` (`CREDENTIALS`, 4), naming the unset variable. A unit test asserts that `wp-config.php`'s `resolve()` was never called.
- **WordPress variables unset, and `wp-config.php` defines neither `DB_USER` nor `DB_PASSWORD`:** the chain raises `CredentialsAbsentError` with `sources` listing every step tried. This is re-raised as `CredentialsError` naming each source label.
- **No administrator source anywhere:** `admin_credentials` returns `None`. A plan that needs administrator rights is refused with `AdminCredentialsRequiredError` → `CREDENTIALS` before any phase after `VERIFY` (E003-S01-006). The WordPress credentials are never tried in its place. A plan that does not need them, such as a backup or a files-only restore, proceeds.
- **Only one administrator variable set:** this is a failure (`CredentialsUnobtainableError` → `CredentialsError`), not "no administrator source". The operator meant to supply one.
- **AWS:** if `boto3` is absent, database raises `MissingDependencyError(extra="aws")`, re-raised as E002's `MissingExtraError(extra="aws")` → `NOT_READY` (7). If AWS has no region, database raises `RegionNotKnownError`, re-raised as `CredentialsError` naming `--admin-credentials-aws-region`. If the secret is unreadable or malformed, database raises `CredentialsUnobtainableError`, re-raised as `CredentialsError` naming the secret id, never its content. In every AWS case the chain stops; there is no fall-through to the environment.

Argument and input problems:
- **Conflicting explicit arguments** (flags plus an AWS secret id, `--admin-password` without `--admin-username`, `--admin-credentials-aws-region` alone, or library `admin=` plus flags): `CredentialSourceConflictError` → `USAGE` (2), raised while the request is being built, before the Site Lock or any read of the Site.
- **Empty string values:** an empty value in a variable is passed to database as is. Database's `Environment` treats `""` as set, and the account then fails authentication with `CREDENTIALS`. This story does not reinterpret it. The behaviour is stated in the docstring so it is not mistaken for absence.
- **Custom provider that is not a `CredentialSource`:** `TypeError` from the builder (a programming error), before any I/O.
- **Custom provider that raises an arbitrary exception:** the chain stops, and Epic 2's adapter re-raises it as `CredentialsError` with `raise … from`. The message carries the source label and exception class, never the exception's text (AD-14; E002-S02-004).
- **Dry Run:** the same chains are built and resolved for real (E002-S02-007: "credential resolution … execute[s] for real"). A Dry Run fails exactly where the real Run would.

### Observability requirements

- Each builder emits one DEBUG record, `credential_chain_built`, with:
  - `role` (`wordpress` or `administrator`);
  - `sources`: the ordered tuple of step labels, using database's `.source` strings such as `environment:L3IO_WP_BACKUP_DB_USER,L3IO_WP_BACKUP_DB_PASSWORD` and `wp-config:/srv/site/wp-config.php`;
  - `none_configured: true`, when `admin_credentials` returns `None`.
- Labels name variables and paths, never values.
- The winning source is logged as `credential_source` by the Epic 2 adapter that calls `resolve()`, read from `ResolvedCredentials.source`. That field already exists (E002-S02-004). This story's integration test asserts that it shows the environment label when the environment wins.
- `CredentialSourceConflictError` is logged once at ERROR by the root's failure handler, with `given` and without values.
- Records carry the Run ID through `merge_contextvars` (E002-S02-005). This module binds nothing itself.

### Security considerations

Exposure of each source:
- **Environment variables.** `/proc/<pid>/environ` is readable by the same user and by root. The README section on credentials says so, as database's CLI documents its own variables, and recommends `wp-config.php` or AWS for shared hosts.
- **The frozen `--admin-password` flag.** Its value is visible in `ps` to every user on the machine. That is the v0.2.21 behaviour, kept by AD-22. The flag's `--help` text says so and points to `L3IO_WP_BACKUP_ADMIN_PASSWORD`; that help text is Epic 2's (part of the composition-root OPEN). This story's purpose is that no cron line needs the flag.

No substitution and no fallback (AD-9, AD-29, FR-15):
- `admin_credentials` has no `wp-config.php` step and never receives the WordPress chain. A unit test asserts that no `WpConfigFile` or WordPress-role `Environment` appears among its sources for any combination of inputs.
- The chain stops on failure (database's rule), so a mistyped secret id cannot quietly become the environment's account.

Handling of values:
- Nothing here reads, logs or holds a password value, except building `Explicit(username, password)` from arguments or `environ`. That object's `repr` is redacted by database. Registration with the `SecretRegistry` happens in the adapter that calls `resolve()` (E002-S02-004). A `credential_sentinel` variant plants the sentinel in `L3IO_WP_BACKUP_DB_PASSWORD` and in `L3IO_WP_BACKUP_ADMIN_PASSWORD`, and asserts it is absent from every captured output.
- The new walked `__repr__` contract (E002-S02-004) covers anything in this module annotated with `CredentialSource` or `password`. This module defines no such class, and the test confirms that rather than assuming it.

### Testability approach

`tests/unit/adapters/test_credential_providers.py` follows E002's `tests/unit/<layer>/test_<module>.py` naming. It uses `monkeypatch.setenv`/`delenv` and database's real source classes with a temporary `wp-config.php` (the `tests/data/wp-config.php` shape). The `database` extra is in the dev group, so the tests need no database server. It covers:
- **Precedence**, parametrised from `CREDENTIAL_PRECEDENCE`, not from a list typed in the test. For each step, every earlier step is absent and that step wins, shown by `ResolvedCredentials.source`.
- **Half-set environment pair:** the chain stops, and a recording `wp_config` stand-in shows `resolve()` was never called.
- **Administrator builder:** every combination of `explicit`, `username`, `password`, `aws_secret_id`, `aws_region` and the two variables. Each combination asserts either the conflict error and its `given` field, `None`, or the ordered source labels. `wp-config` never appears.
- **AD-9:** both builders call no `resolve()` (recording sources). Reading `.source` on the returned chain does no I/O: a source whose `resolve` raises is still labelled without raising.
- **Custom provider:** a plain class with `source` and `resolve` (no base class) wins as `explicit`. A non-conforming object raises `TypeError`. A custom provider raising `CredentialsAbsentError` falls through to the next step.
- **AWS** (needs `boto3`, in the dev group): `botocore.stub.Stubber` drives a found secret, a malformed secret, and an access error. With `boto3` hidden via `monkeypatch.setitem(sys.modules, "boto3", None)`, `MissingExtraError(extra="aws")` results.

`tests/contracts/test_single_credential_chain.py` is AST-based, like `tests/contracts/test_no_mysql_client.py`. Its scope is every `*.py` under `src/l3io/wp/backup/`, walked, with a non-empty scope assertion. It fails if:
- any `except` handler naming `CredentialsAbsentError` sits inside a `for`/`while` loop, which is the defining shape of a second chain;
- any class defines a method named `resolve` returning `ResolvedCredentials`, which would be a second provider.

A planted-violation case writes such a module into a temporary tree and asserts the check fires, so the guard is shown to reach its scope.

AD-8:
- The CI base-install import check, which needs no extras, imports `l3io.wp.backup.adapters.credential_providers` successfully.
- An AST assertion in the unit module shows `l3io.wp.database` is imported only inside functions or under `TYPE_CHECKING`.

`tests/integration/test_credential_sources.py` is marked `@pytest.mark.integration` and runs against the CI database:
- a backup with only the environment variables set, while `wp-config.php` holds wrong credentials, succeeds and logs the environment label;
- the reverse also succeeds;
- a half-set pair exits `CREDENTIALS`.

### Existing-library check

Database (rev `47384ba`, `credentials.py`, `wpconfig.py`) already provides every part this story needs:
- the chain, as `CredentialChain`;
- every built-in source: `Explicit`, `Environment` (variable names configurable), `AwsSecretsManager` (behind its `aws` extra, imported inside `resolve()`), and `WpConfigFile`;
- the frozen value, `ResolvedCredentials` (frozen and slotted, with a redacted `repr`);
- the structural Protocol, `CredentialSource`, which is `@runtime_checkable`.

Each was verified with `git -C ../l3io-wordpress-database show 47384ba:src/l3io/wp/database/credentials.py`. None is reimplemented, and no backup-side provider is written, because database has every source FR-14 names.

The AWS client is `boto3`, through database's `aws` extra (`boto3>=1.34,<2` at `47384ba`), never imported here. Test stubbing uses `botocore.stub.Stubber`, which ships with `boto3`.

The custom code is two builder functions of a few dozen lines that put database's objects in order.
